## 핵심 요약

**배포했으면 끝인가요? 아니에요. 피드백 받아야 진짜 시작이에요. URL이 생겼어요. 이제 가설에 맞는 고객에게 보여주고, 내 제품에 맞는 고객이 누구인지 배워야 해요.**

## 1. 왜 피드백인가요?

혼자 만들면 "이게 좋을 거야"라고 착각해요. 실제로 보여주면 "이거 왜 이래?"가 나와요.

피드백은 칭찬을 받으려고 하는 게 아니에요. **고객을 더 이해하고, 내 제품에 맞는 고객을 탐색하기 위해서** 하는 거예요. 아이디어 단계에서는 말로 1차 반응을 봤고, 이제는 실제 제품을 만졌을 때의 행동을 보는 거예요. 6개월 만들고 아무도 안 쓰는 것보다, 1주 만에 틀린 가설을 아는 게 낫잖아요.

## 2. 기대치가 달라졌어요

2020년에 "AI 채팅 서비스"을 보여주면 "오 이것도 돼요? 너가 만들었어요? 대단하다"였어요. 지금은 ChatGPT, Claude를 매일 써요. Character.ai도 써본 사람 있을거고, 관련 쟁쟁한 서비스들도 많아요. 사용자의 기준이 **이미 높아져 있어요.**

| 옛날 | 지금 |
| --- | --- |
| "돌아가네? 신기하다" | "이거 왜 이렇게 느려?" |
| "AI가 답변을 하네" | "답변이 왜 이렇게 딱딱해?" |
| "무료라 감사" | "무료여도 불편하면 안 써" |

바이브코딩으로 만든 앱은 쏟아져요. 비슷한 거 10개 중에 사람들이 쓰는 건 1~2개예요. 그 1~2개는 기능이 많아서가 아니에요. **써보니까 좋아서예요.**

## 3. 가설에 맞는 5명이면 돼요

```text
❌ Google Analytics 설치 → 대시보드 분석
✅ 가설에 맞는 5명에게 보여주고 → 직접 물어보기
```

분석 도구보다 먼저 사람을 봐요. 단, 아무 5명이 아니라 **가설에 맞는 5명**이어야 해요. 직장인 영어 학습 앱이면 출근길에 공부하려는 직장인에게 보여줘야 하고, 팀 TODO 앱이면 실제 쓸 것 같은 사람들에게 보여줘야 해요.

5명 전부 지인이면 안 돼요. 최소 2명은 모르는 사람이어야 해요. 지인은 칭찬 편향이 있고, 모르는 사람의 반응이 진짜 시장 반응에 더 가까워요. 모르는 사람을 어디서 데려오는지는 [모객](/go-to-market/distribution)에서 다뤄요.

## 4. 어떻게 물어보나요?

### Step 1. URL을 보내

```text
"나 이런 가설로 작은 서비스를 만들었어. 1분만 써보고 솔직하게 말해줘."
https://my-app.vercel.app
```

**"솔직하게"를 꼭 넣어.** 안 넣으면 "좋아~"만 나와요. 친구들은 기분 안 상하게 하려고 칭찬만 해요. "솔직하게"가 있어야 진짜가 나와요.

### Step 2. "돌아가?"보다 "내 문제에 맞나요?"를 물어봐요

기능 검증(돌아가?)은 기본이에요. MLP는 여기서 한 발 더 나가요.

```text
[기능 검증 — 돌아가?]
"써보니까 어땠어? 불편한 거 없었어?"
"중간에 그만두고 싶었던 적 있어?"

[고객 검증 — 내 문제에 맞아?]
"이거 네 상황에서 다시 쓸 것 같아?"
"비슷한 거 있으면 이거 쓸 것 같아, 그거 쓸 것 같아?"
"첫인상이 어땠어? 솔직하게."
"어떤 사람에게는 맞고, 어떤 사람에게는 안 맞을 것 같아?"
"돈 내고 쓸 것 같아?"
```

**"다시 쓸 것 같아요? 누구에게 맞을 것 같아?"가 핵심 질문이야.** 이 답을 들으면 고객을 더 이해하게 돼요. 그냥 "어때?"라고 물으면 진짜 피드백이 안 나와요.

### Step 3. 기록하기

```text
- 지현: "첫 화면에서 뭘 해야 할지 바로 알겠어. 근데 입력이 좀 귀찮았어"
- 민수: "나는 안 쓸 것 같은데, 매일 루틴 만드는 사람은 좋아할 듯"
- 수진: "끝까지 했어. 내일 다시 들어오라는 알림이 있으면 좋겠어"
```

Claude한테 정리시켜도 돼요.

```text
이 피드백들 정리해줘.
공통된 불만이 뭔지, 다음에 뭘 고쳐야 하는지 포함해서.
코드는 짜지 마.
```

## 5. 가설이 맞았나요? 고객을 더 이해했나요?

아이디어 단계에서 세운 핵심 가정을 확인해요. 근데 두 가지를 봐야 해요.

**1. 방향 검증 — 가설이 맞나요?**

```text
✅ 맞았다 → 2번으로
❌ 틀렸다 → 고객·문제·해결책 중 하나를 바꿔보기
🔶 애매하다 → 설명이 부족한지, 제품 경험이 부족한지, 고객군이 다른지 나눠보기
```

**2. 고객 검증 — 누구에게 맞나요?**

```text
✅ "내가 다시 쓸 것 같아" → 그 고객군을 더 깊게 탐색
🔶 "괜찮은데..." → 완성도를 올려 (디자인, 속도, 문구)
❌ "비슷한 다른 거 쓸래" → 문제 정의나 고객군을 다시 잡아
```

방향이 맞아도 경험이 별로면 안 퍼져요. 또 경험이 좋아도 고객군이 틀리면 안 돌아와요. **기능 추가보다 고객과 기존 경험을 다시 보는 게 먼저예요.**

## 6. 틀려도 괜찮아요

방향 전환(피벗)은 실패가 아니에요. 아이디어가 바뀌는 건 자연스러운 일이에요.

```text
6개월 만들고 틀린 거 알면? → 6개월 날림
1주 만들고 틀린 거 알면? → 1주만 날리고 방향 수정
```

바이브코딩으로 만들었으니까 잃는 건 시간뿐이에요. 그 시간에 배운 건 남아요. 시장을 더 이해해서 바뀔 수도 있고, 만들면서 내가 진짜 원하던 게 명확해져서 바뀔 수도 있어요.

## 7. 보너스 — 사용 로그를 같이 봐요

사람한테 묻는 게 1순위지만, **DB에 쌓인 사용 로그**도 같은 답을 해줘요. 예를 들면 이런 것들이에요.

- 어느 기능을 가장 많이 눌렀어요?
- 한 사람이 평균 몇 번 입력했어요?
- 첫 결과를 본 뒤 다음 행동까지 몇 초 걸렸어요? (체류)
- 며칠 뒤에 다시 들어왔어요? (리텐션)

복잡한 분석 도구 깔지 마세요. **간단한 관리 페이지(`/admin`)에 숫자 5 개만 띄우는** 것으로 시작해요.

```text
나: "/admin 페이지 만들어줘.
    Supabase의 logs / feedback 테이블에서 다음 5가지를 카드로 보여줘.
    1. 누적 사용 수
    2. 어제 새로 시작된 세션 수
    3. 가장 많이 눌린 기능
    4. 사용자당 평균 입력 수
    5. 7일 리텐션 (지난주 사용자가 오늘 다시 왔나)

    인증된 운영자만 접근하게 해줘."
```

5 명이 말한 정성 피드백 + 5 개 숫자의 정량 흐름. 둘이 같이 보면 다음에 뭘 다듬을지가 한결 분명해져요.

## 8. 고치고 다시 돌려

피드백 반영해서 고치고, 다시 배포하고, 다시 물어봐요.

```text
가설 → 만들기 → 배포 → 피드백 → 의견 반영 → 다시 배포 → 다시 피드백
```

이 사이클을 빨리 돌릴수록 고객을 더 빨리 이해하게 돼요.

근데 "고치기"에서 많이 실수해요. 피드백 받으면 기능을 추가하고 싶어져요.

```text
❌ "결제 기능도 넣어야 하나..."
❌ "다크모드도 있으면 좋겠는데..."
✅ "대화 응답이 느리다고 했으니 속도부터 잡자"
✅ "첫 화면이 허전하다고 했으니 디자인 다듬자"
```

**기능 추가는 참고, 기존 경험부터 다듬어.** 하나를 제대로 좋게 만드는 게 열 개를 대충 만드는 것보다 낫거든요.

## 자주 헷갈리는 포인트

### 5명한테 보여주기 부끄러워요

부끄러워서 6개월 더 만들고 보여주면 더 부끄러운 게 나와요. 일찍 보여줘서 일찍 고쳐요.

### 가족한테 보여줘도 되나요?

좋아요. 다만 "솔직하게"를 강하게 강조해요. 가족은 칭찬만 하기 쉬워요.

### 피드백이 다 다르면?

공통된 게 있어요. 5명 중 3명 이상이 같은 말 하면 그게 진짜예요. 1명만 한 말은 흘려도 돼요.

피드백 사이클이 돌기 시작했으면 [PMF 찾기](/go-to-market/pmf)로 가요. 보여줄 사람 자체가 부족하면 [모객](/go-to-market/distribution)으로 이어가요.
