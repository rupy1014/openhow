## 핵심 요약

이 문서의 핵심은 세 줄이에요.

- **AI에게 나한테 질문하라고 시켜라.** 끌려다니지 않는 가장 쉬운 방법이에요.
- **검증은 반드시 다른 세션에서 해라.** 만든 세션에서 검증하면 오염된 눈으로 검사하는 꼴이에요.
- **큰 일은 계획부터 보고 시작해라.** 코드가 나온 뒤에 고치는 것보다 훨씬 싸요.

```text
질문을 시켜서 빈칸을 찾는다.
계획을 먼저 보고 방향을 잡는다.
검증은 만든 곳이 아닌 다른 곳에서 한다.
```

## 1. AI에게 되물어보게 시켜라

AI를 오래 쓰다 보면 이런 순간이 와요.

```text
AI가 내놓는 결과에 내가 끌려가고 있다.
얘가 만든 걸 내가 다 이해하지도 못하고 있다.
```

이럴 때 제일 효과 좋은 방법이 있어요.

**나한테 질문을 던지라고 시키는 거예요.**

```text
이 내용 보고 나한테 질문을 해줘.
```

이렇게 하면 AI가 내 생각에서 빈 곳을 찾아서 물어봐요.

그 빈칸을 채우는 과정에서 내가 생각을 훨씬 많이 하게 돼요.

특히 뭘 시켜야 할지 막막할 때 유용해요.

```text
블로그 글 써줘
→ 아무 글이나 그럴듯하게 씀

블로그 글을 쓰고 싶은데, 뭘 알아야 잘 써줄 수 있는지 나한테 질문해줘
→ 주제, 대상 독자, 길이, 말투를 되물어봄
```

두 번째가 훨씬 나은 결과로 이어져요.

내가 줘야 할 정보를 AI가 대신 뽑아내주는 거니까요.

## 2. 소크라테스 질문법

되물어보게 시키는 걸 조금 더 밀어붙인 방식이에요.

본질적인 질문을 던지게 해서, **내가 인지하지 못하고 있던 빈칸**을 찾아내는 거죠.

기획서나 요구사항 문서를 써놓고 이렇게 시켜봐요.

```text
이 문서 읽어보고, 소크라테스식 질문으로 나한테 물어봐줘.
```

그러면 "이 부분은 왜 이렇게 정했어?", "이 경우엔 어떻게 되는 건가요?" 같은 질문이 돌아와요.

답하다 보면 내가 대충 넘어갔던 지점이 드러나요.

여기서 중요한 게 있어요.

**질문에 대한 답을 AI가 채우게 두지 말고, 사람이 직접 생각해봐요.**

앞 문서에서 말했듯이 AI는 평균적인 답을 내놓는 경향이 있어요.

우리가 만들려는 건 대개 평균에서 벗어난 거고.

```text
내가 원하는 게 구체적일수록
AI의 평균적인 맥락과는 멀어진다.
```

그래서 빈칸을 사람이 채우는 게 중요해요.

## 3. 크게 뭉친 건 잘게 쪼개라

요구사항이나 기획서를 쓰다 보면 불필요한 게 섞여 들어가요.

이럴 때 쓰는 사고법이 제1원리 사고예요.

큰 덩어리를 아주 작은 단위로 계속 쪼개고, 필요 없는 건 버리고 필요한 것만 취하는 방식이에요.

```text
이 요구사항을 제1원리로 쪼개서 분석해줘.
꼭 필요한 것과 없어도 되는 걸 구분해줘.
```

이렇게 물어보면 내가 당연하다고 생각했던 것 중에 빼도 되는 게 꽤 나와요.

## 4. 큰 일은 계획부터 보고 시작해라

복잡한 작업이면 바로 시키지 말고 계획부터 받아봐요.

```text
바로 만들지 말고 계획부터 세워줘.
```

Claude Code에는 아예 플랜 모드가 있어요.

`shift + tab`을 누르면 모드가 바뀌어요.

| 모드 | 동작 |
| --- | --- |
| 기본 | 실행할 때마다 허락을 받고 진행 |
| 자동 | 허락 없이 알아서 진행 |
| 플랜 | 코드를 만들지 않고 계획만 세움 |

큰 그림을 그릴 때는 플랜 모드가 정말 좋아요.

이유는 간단해요.

**코드가 나오기 전에 청사진을 보면, 틀린 게 눈에 보이거든요.**

```text
계획을 보고 고친다 → 문장 몇 줄 고치면 끝
코드가 나온 뒤 고친다 → 다시 만들어야 함
```

토큰으로 봐도 계획 단계에서 잡는 게 훨씬 싸요.

기획 작업이면 이런 식으로 쓰면 좋아요.

```text
이런 내용으로 기획서를 쓰려고 해.
내가 봤을 때는 이런 것들이 들어가야 할 것 같은데,
여기서 더 발전시킬 방법이 뭐가 있을지 계획을 세워보자.
```

계획을 보고 "이건 빼도 되겠다", "이건 더 넣자"를 정한 다음에 실제 작업을 시키는 거예요.

## 5. 아니다 싶으면 바로 ESC

일을 시키면 Claude Code는 이런 순서로 움직여요.

```text
분석 → 계획 수립 → 실행 → 검토
```

그 과정이 화면에 쭉 보여요.

보다가 "어요? 저건 내가 요청한 게 아닌데" 싶으면 **바로 ESC를 눌러요.**

그냥 두면 두 가지를 잃어요.

```text
1. 엉뚱한 작업이 끝날 때까지 토큰이 계속 나간다
2. 다시 제대로 요청하는 것도 또 비용이다
```

계속 지켜보고 있을 순 없지만, 중요한 결정이 걸린 작업이라면 앞부분은 한 번씩 봐주는 게 좋아요.

## 6. 검증은 반드시 다른 세션에서

이건 이 문서에서 제일 중요한 얘기예요.

로그인 기능을 만들었다고 해봐요.

만든 그 세션에서 이렇게 물어보면 어떻게 될까요?

```text
로그인 기능이 잘 동작하는지 검증해줘
```

AI는 매번 대화 맨 위부터 다시 읽는다고 했죠?

그러니까 **자기가 방금 만든 과정을 전부 읽은 상태에서 검사하는 거예요.**

```text
만든 사람이 자기 답안지를 보면서 채점하는 것과 같다.
```

이미 오염된 상태에서 검증하는 악순환이 생겨요.

그래서 검증은 이렇게 해야 해요.

| 방법 | 어떻게 |
| --- | --- |
| 다른 세션 | 새 창을 열고 결과물만 보여준 뒤 검증 요청 |
| 다른 도구 | Codex 같은 다른 에이전트에게 검증 요청 |
| 전용 스킬 | 시큐어 코딩 검사 같은 별도 스킬 활용 |

새 세션에서는 이런 식으로 물어보면 돼요.

```text
다른 세션에서 로그인 기능을 만들었어.
코딩 컨벤션이 잘 지켜졌는지, 빠뜨린 게 없는지 검증해줘.
```

### 검증은 얼마나 자주 해야 하나요?

기능 하나 붙일 때마다 하는 게 기본이에요.

```text
기초 화면을 만들었다 → 검증
로그인 기능을 붙였다 → 검증
관리자 페이지를 만들었다 → 검증
```

작업 규모가 크면 더 잘게 나눠서 검증해야 하고, 간단한 화면 하나 만든 정도면 건너뛰어도 돼요.

정해진 정답은 없어요. 하다 보면 "이때는 필요하겠다" 감이 붙어요.

### 뭘 검증해달라고 해야 할지 모르겠어요

이때도 되물어보게 시키면 돼요.

```text
내가 개발을 잘 몰라서 뭘 검증해야 할지 모르겠어.
이 기능에서 뭘 확인해야 하는지 나한테 질문해줘.
```

눈으로 보이는 화면은 직접 확인할 수 있지만, 백엔드나 데이터베이스처럼 안 보이는 건 이렇게 물어보는 게 나아요.

투두 리스트가 있으면 그걸 던져주고 이렇게 시켜도 좋아요.

```text
이 목록에서 빠진 게 있는지 검증해줘.
```

### 그냥 두면 알아서 검증 안 하나요?

안 해요.

**"검증해줘"라고 명시적으로 말하지 않으면 대부분 그냥 넘어가요.**

계속 검증시키는 패턴이 쌓이면 알아서 하는 경우도 생기지만, 기본적으로는 시켜야 해요.

## 7. 구조화해서 주면 더 잘 알아듣는다

AI는 구조가 있는 글을 훨씬 잘 받아들여요.

구조화된 형식이 몇 가지 있는데, 우리가 실제로 쓸 건 사실상 하나예요.

| 형식 | 언제 보나 | 알아야 할 정도 |
| --- | --- | --- |
| 마크다운 | 기획서, PRD, `CLAUDE.md` 등 우리가 쓰는 문서 전부 | 직접 쓸 줄 알면 좋음 |
| JSON | 데이터나 API를 다룰 때 | 눈에 보이면 알아보는 정도 |
| XML | 시스템 프롬프트나 에이전트 구조를 짤 때 | 이런 게 있다는 정도 |

마크다운을 제일 많이 보게 될 거예요.

가장 단순하고, 사람이 보기도 쉽고, 동시에 구조가 있어서 AI가 보기도 쉽거든요.

```text
# 제목
## 소제목
**굵게**
- 목록
```

이 정도만 알아도 충분해요.

JSON은 열어보면 키와 값이 짝지어 나열된 형태예요. 데이터를 다룰 때 만나게 돼요.

일일이 이해할 필요 없어요. 이렇게 시키면 돼요.

```text
이 JSON 내용 분석해서 어떤 패턴인지 알려줘.
```

XML은 Claude가 특히 잘 이해한다는 얘기가 있어요. 다만 입문 단계에서 직접 쓸 일은 거의 없어요.

```text
이런 형식들이 있다는 것만 알면 되고,
직접 열어서 코드를 읽을 필요는 없다.
```

## 자주 헷갈리는 포인트

### 되물어보라고 하면 질문이 너무 많이 와요

"제일 중요한 것 3개만 물어봐"처럼 개수를 정해주면 돼요.

### 플랜 모드는 항상 써야 하나요?

아니요. 작은 수정에는 오히려 번거로워요. 여러 파일을 건드리거나 방향이 애매한 작업일 때 써요.

### 검증용 세션에는 뭘 줘야 하나요?

만든 결과물과 원래 하려던 것(투두 리스트나 요구사항)을 주면 돼요. 만드는 과정의 대화까지 옮길 필요는 없어요. 그걸 옮기면 다시 오염돼요.

### ESC 누르면 지금까지 한 게 날아가나요?

지금 진행 중인 동작만 멈춰요. 이미 저장된 파일은 그대로 남아 있어요.

### 마크다운을 꼭 배워야 하나요?

`#`으로 제목, `-`로 목록. 이 둘만 알아도 시작할 수 있어요. 나머지는 쓰면서 자연스럽게 붙어요.

### AI가 만든 걸 내가 이해 못 하는데 괜찮은가요?

전부 이해할 필요는 없어요. 다만 "이 파일 뭔가요?", "이거 왜 이렇게 했어?"를 계속 물어보는 습관은 들여두는 게 좋아요. 끌려다니는 걸 막아주거든요.
