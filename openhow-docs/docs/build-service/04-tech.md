## 핵심 요약

**기술 선택과 아키텍처는 따로 떨어진 문제가 아니에요. 둘 다 “이번 MVP에서 고객 반응을 보려면 어디까지 만들어야 하지?”라는 질문에 답하는 일이에요.**

처음부터 개발자처럼 이렇게 말할 필요는 없어요.

```text
Next.js로 만들고,
API Route를 두고,
Supabase DB를 붙이고,
프론트와 백엔드를 분리해줘.
```

오히려 먼저 이렇게 물어봐야 해요.

```text
화면만 보여줘도 배울 수 있나?
진짜 AI API를 호출해야 하나?
숨겨야 하는 API 키가 있나?
나중에 다시 볼 데이터가 있나?
사용자마다 다르게 보여줘야 하나?
고객 5명에게 URL로 보내려면 무엇이 꼭 필요하지?
```

이 질문에 답하다 보면 기술 선택과 구조가 같이 정해져요.

## 기술 선택은 도구 이름 맞히기가 아니에요

기술 선택이라고 하면 이런 이름부터 떠올라요.

```text
React
Next.js
Supabase
Firebase
PostgreSQL
API Route
Serverless
```

하지만 초보자에게 더 중요한 건 도구 이름이 아니라 **단순하게 시작하는 순서**예요.

```text
1. 일단 화면으로 보여준다
2. 진짜 기능이 필요하면 서버/API를 붙인다
3. 다시 볼 데이터가 필요하면 DB를 붙인다
4. 사람마다 달라져야 하면 로그인을 붙인다
5. 사용자가 늘면 비용과 운영을 본다
```

처음부터 오른쪽 끝까지 갈 필요 없어요. 린 스타트업 MVP에서는 **지금 배울 수 있는 최소 구조**가 좋은 구조예요.

## 1. 먼저 어디에서 돌아갈지 정해요

가장 먼저 정할 건 “웹이냐, 앱이냐, 자동화냐”예요.

| 종류 | 쉽게 말하면 | 처음 만들 때 |
| --- | --- | --- |
| 웹 | 링크로 접속하는 서비스 | 제일 추천. URL 보내기 쉬워 |
| 앱 | 스마트폰에 설치하는 서비스 | 앱스토어, 심사, 기기 대응이 필요해 |
| 자동화/봇 | 화면 없이 대신 처리하는 도구 | 업무 자동화에는 좋지만 고객 검증이 어려울 수 있어 |

입문자 MVP라면 웹부터가 좋아요.

```text
이 링크 한번 눌러보고 써봐.
어디서 막히는지 알려줘.
```

고객에게 이렇게 보낼 수 있어야 피드백을 받기 쉽거든요.

## 2. 프론트엔드만으로 시작해도 돼요

프론트엔드는 사용자가 직접 보는 화면이에요.

```text
버튼
입력창
카드
이미지
결과 화면
완료 메시지
```

처음에는 화면에 필요한 내용을 코드 안에 직접 넣고 시작해도 돼요.

예를 들어 영어 문장 MVP라면.

```text
오늘의 문장 1개
한국어 뜻
짧은 해설
완료 버튼
```

이걸 전부 화면에 넣어도 고객에게 물어볼 수 있어요.

```text
이 화면 이해돼?
출근길에 이 정도면 볼 것 같아?
완료 버튼을 누르고 싶어?
내일 다시 들어올 것 같아?
```

이걸 확인하는 게 목적이면 DB도, 로그인도, 서버도 없어도 돼요. 이건 나쁜 구조가 아니라 **처음 가설을 빨리 확인하기 위한 구조**예요.

## 3. 보여주기식 MVP도 실험이에요

처음 MVP가 꼭 진짜 기능을 다 갖춰야 하는 건 아니에요.

상품 설명 생성기를 만든다고 해봐요.

```text
상품명을 입력한다
미리 준비한 예시 결과를 보여준다
고객이 “이 정도 결과면 써보고 싶다”고 말하는지 본다
```

처음부터 AI API를 붙이지 않아도 배울 수 있어요.

고객이 “별로 필요 없는데요?”라고 하면 API를 붙일 필요도 없을 수 있어요. 반대로 반응이 있으면 그때 진짜 기능을 붙이면 돼요.

```text
가짜 결과로 반응 확인
→ 반응 있으면 진짜 API 연결
→ 저장이 필요하면 DB 추가
→ 반복 사용자가 생기면 로그인 검토
```

처음부터 다 만드는 게 성실한 게 아니에요. **배울 수 있는 최소한만 만드는 게 더 좋은 선택**일 수 있어요.

## 4. 서버가 필요한 경우를 구분해요

백엔드는 사용자가 직접 보지는 않지만 뒤에서 처리하는 곳이에요. 쉽게 말하면 식당의 주방이에요.

백엔드는 이런 일을 해요.

```text
AI API 호출하기
API 키 숨기기
입력값 검사하기
DB에 저장하기
결제 처리하기
관리자만 볼 정보 보호하기
```

특히 비밀 값이 있으면 서버가 필요해요.

```text
OpenAI API 키
OpenRouter API 키
결제 API 키
관리자 비밀번호
```

브라우저에 들어간 코드는 사용자가 볼 수 있어요. 그래서 숨겨야 하는 값은 프론트엔드에 넣으면 안 돼요.

기준은 이렇게 잡으면 돼요.

```text
보여줘도 되는 것 → 프론트엔드
숨겨야 하는 것 → 백엔드
화면이 서버에게 부탁하는 창구 → API
나중에 다시 볼 데이터 → DB
사람마다 나눠야 하는 데이터 → 로그인
```

## 5. API는 화면과 서버가 말하는 창구예요

API는 프로그램끼리 데이터를 주고받는 통로예요. 어렵게 들리지만 그냥 **주문 창구**라고 생각하면 돼요.

```text
사용자: 버튼을 누름
프론트엔드: 서버에게 요청 보냄
API: 요청을 받는 주소
백엔드: 요청을 처리함
프론트엔드: 결과를 화면에 보여줌
```

예를 들어 사용자가 “오늘 문장 추천” 버튼을 누르면 이런 흐름이 돼요.

```text
1. 사용자가 버튼을 누른다
2. 프론트엔드가 /api/today 로 요청을 보낸다
3. 백엔드가 오늘 문장을 준비한다
4. 필요하면 AI API를 호출한다
5. 결과를 프론트엔드로 돌려준다
6. 화면에 오늘 문장이 보인다
```

API 주소는 보통 이런 식으로 생겨요.

```text
/api/today
/api/generate
/api/save
/api/feedback
```

AI가 `/api/generate` 같은 파일을 만들었다면 이렇게 물어보면 좋아요.

```text
이 API는 누가 호출해?
어떤 데이터를 받아서 어떤 결과를 돌려줘?
프론트에서 직접 하면 안 되는 이유가 있어?
```

## 6. DB는 “나중에 다시 볼 데이터”가 있을 때 붙여

DB는 데이터를 저장하는 곳이에요.

처음부터 무조건 붙일 필요 없어요.

DB 없이 시작해도 되는 경우는 이런 거예요.

```text
새로고침하면 사라져도 괜찮아
한 번 보여주고 반응만 보면 돼
사용자별 기록이 필요 없어
피드백은 구글폼으로 받을 거야
```

반대로 이런 경우에는 DB가 필요해요.

```text
사용자가 만든 결과를 다시 보여줘야 해
사용 기록을 보고 싶어
피드백을 서비스 안에 저장하고 싶어
여러 사람이 같은 데이터를 봐야 해
```

“저장”에도 단계가 있어요.

| 저장 위치 | 쉽게 말하면 | 언제 써? |
| --- | --- | --- |
| 메모리 | 지금 화면에서만 기억 | 새로고침하면 사라져도 되는 선택값 |
| localStorage | 내 브라우저에 저장 | 내 설정, 임시 저장 |
| DB | 서버 쪽 저장소 | 여러 기기·사용자·분석에 필요한 데이터 |

처음부터 저장 방식을 맞히려고 하지 말고, 데이터의 성격을 말해줘요.

```text
오늘 선택한 문장은 새로고침하면 사라져도 돼.
하지만 고객 피드백은 나중에 볼 수 있게 저장하고 싶어.
```

그러면 AI가 저장 위치를 추천할 수 있어요.

## 7. BaaS는 백엔드와 DB를 빌려 쓰는 방법이에요

백엔드와 DB를 전부 직접 만들 필요는 없어요.

Supabase나 Firebase처럼 이미 만들어진 서비스를 빌려 쓸 수 있어요. 이런 걸 BaaS라고 해요. Backend as a Service, 즉 “백엔드 빌려쓰기”예요.

```text
직접 만들면:
프론트엔드 + 백엔드 + DB + 로그인 모두 직접 관리

BaaS를 쓰면:
프론트엔드 + Supabase/Firebase가 제공하는 DB·로그인 기능 사용
```

입문 단계에서는 이런 도구를 쓰는 게 자연스러울 수 있어요. 다만 BaaS도 마법은 아니에요.

```text
어떤 데이터를 저장할지
누가 볼 수 있는지
로그인이 필요한지
비용이 얼마나 나올지
```

이런 판단은 여전히 필요해요.

AI가 Supabase나 Firebase를 추천했다면 이렇게 물어봐요.

```text
왜 이 프로젝트에 Supabase를 추천했어?
더 단순한 방법은 없어?
처음 MVP에서는 안 써도 되는지 판단해줘.
나중에 붙인다면 어떤 기능부터 붙이면 돼?
```

## 8. 폴더 구조는 역할을 찾는 지도예요

AI가 코드를 만들어주면 파일이 여러 개 생겨요.

처음엔 폴더 이름만 봐도 헷갈려요.

Next.js 같은 웹 프로젝트에서는 보통 이런 느낌이에요.

```text
app/          화면과 페이지
app/api/      서버 API
components/   버튼, 카드, 입력창 같은 조각
lib/          API 호출, DB 연결 같은 도구
public/       이미지, 아이콘
```

깊게 외울 필요는 없어요. 다만 이런 감각은 있으면 좋아요.

```text
화면을 바꾸고 싶다 → app 또는 components
버튼 모양을 바꾸고 싶다 → components
AI API 호출을 바꾸고 싶다 → app/api 또는 lib
DB 연결을 바꾸고 싶다 → lib
이미지를 넣고 싶다 → public
```

이걸 알면 AI에게 더 안전하게 시킬 수 있어요.

```text
버튼 디자인만 바꿔줘.
API 호출 로직은 건드리지 마.
어떤 파일을 수정했는지도 설명해줘.
```

## 9. 상황별 선택은 이렇게 해요

| 상황 | 선택 | 이유 |
| --- | --- | --- |
| 랜딩페이지, 포트폴리오 | 프론트만 | 보여주기만 하면 됨 |
| 화면 흐름 확인 | 프론트 중심 MVP | 저장 없이 반응 확인 가능 |
| 가짜 결과로 반응 보기 | 프론트 + 샘플 데이터 | API 붙이기 전 검증 가능 |
| 진짜 AI 호출 | 서버/API 필요 | API 키를 숨겨야 함 |
| 결과 저장 | DB 필요 | 나중에 다시 볼 데이터가 있음 |
| 사용자별 기록 | 로그인/인증 필요 | 사람마다 데이터를 나눠야 함 |
| 사용자가 늘어남 | 비용 검토 | API, DB, 배포 비용이 생김 |

처음에는 제일 단순한 선택부터 봐요.

```text
프론트로 충분해? → 프론트로 시작
API 키를 숨겨야 해? → 서버 추가
저장해야 해? → DB 추가
사람마다 달라야 해? → 로그인 추가
비용이 커져? → 사용량과 요금 확인
```

## 10. AI에게는 이렇게 물어봐요

AI에게 이렇게 물으면 어려운 답이 나올 수 있어요.

```text
이 서비스에 가장 적합한 기술 스택 추천해줘.
```

대신 이렇게 물어봐요.

```text
나는 [서비스 이름/아이디어]를 만들고 싶어.
사용자는 [누가]이고,
사용자는 [어떤 상황]에서 [무엇]을 하고 싶어 해.

첫 버전은 고객 5명에게 보여줄 MVP로 만들고 싶어.
나는 개발 구조를 잘 몰라.

다음을 쉬운 말로 판단해줘.

아직 코드는 짜지 마.
```

추천을 받았으면 바로 크게 만들지 말고 이렇게 이어가요.

```text
추천하는 대로 해줘.
단, 한 번에 너무 크게 만들지 말고
10분 안에 확인할 수 있는 작은 단위로 진행해줘.

각 단계가 끝날 때마다
내가 확인해야 할 화면,
눌러봐야 할 버튼,
아직 안 만든 기능을 정리해줘.
```

그리고 모르는 말이 나오면 바로 물어봐요.

```text
방금 말한 API가 정확히 뭐야?
이 프로젝트에서 백엔드는 어떤 역할을 해?

지금은 안 해도 되는 건 뭐야?
```

## 좋은 기술 선택과 구조의 기준

좋은 선택은 화려한 스택이 아니에요.

다음 질문에 답하면 돼요.

```text
가장 빨리 고객에게 보여줄 수 있어?
지금은 가짜 결과로도 배울 수 있어?
비밀 키가 노출되지 않아?
지금 꼭 저장이 필요해?
로그인이 지금 꼭 필요해?
사용자가 늘면 비용을 어디서 보게 될까?
AI가 만든 파일에서 화면, API, 저장 역할을 구분할 수 있어?
```

이 질문에 답할 수 있으면 지금 단계에 맞는 구조를 고를 수 있어요.

## 자주 헷갈리는 포인트

### 프론트에 다 넣으면 나쁜 구조 아닌가요?

오래 운영할 실제 서비스라면 한계가 있어요. 하지만 첫 MVP에서 고객 반응만 보는 용도라면 괜찮아요. 목적이 분명하면 좋은 선택이에요.

### 가짜 결과를 보여줘도 되나요?

돼요. 단, 고객을 속이면 안 돼요. “이런 결과가 나오면 쓸 것 같은지 보고 싶다”는 식으로 확인하는 용도라면 충분히 의미 있어요.

### API 키가 있으면 무조건 서버가 필요한가요?

숨겨야 하는 키라면 서버가 필요해요. 브라우저 코드에 넣으면 노출될 수 있어요.

### 처음부터 DB를 붙이면 더 안전한 거 아닌가요?

항상 그렇진 않아요. 저장할 데이터가 없는데 DB부터 붙이면 설정과 에러만 늘어요. 저장이 필요해질 때 붙이면 돼요.

### AI가 추천한 구조를 그대로 믿어도 되나요?

그대로 믿기보다 “왜 지금 필요한지”, “더 단순한 방법은 없는지”, “이번 MVP에서 안 해도 되는 건 무엇인지”를 다시 물어봐요. AI 시대의 핵심은 추천을 받는 능력보다 **추천을 줄이고 정리하는 능력**이에요.
