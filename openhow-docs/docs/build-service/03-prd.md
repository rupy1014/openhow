## 핵심 요약

**PRD는 처음부터 빈 문서에 힘줘서 쓰는 게 아니에요. 먼저 “이런 거 만들고 싶어”라고 AI와 이야기하면서 뭘 만들고 싶은지 정리해요. 방향이 어느 정도 보이면 그때 “이 대화를 기반으로 prd.md 만들어줘”라고 하면 돼요.**

기획이 처음인 사람은 PRD 양식을 먼저 보면 막혀요.

```text
대상 고객은?
핵심 가설은?
검증 기준은?
시장 진입 전략은?
```

이런 말을 들으면 오히려 더 어렵거든요.

처음엔 대부분 이렇게 시작해요.

```text
나 이런 거 만들고 싶어.
근데 어디서부터 해야 할지 모르겠어.
누가 쓸지도 애매하고,
어떤 기능부터 만들어야 할지도 모르겠어.
```

이게 정상이고, 여기서부터 시작하면 돼요.

PRD는 정답을 쓰는 문서가 아니에요. **대화하면서 정리된 생각을 한 장으로 묶는 문서**예요.

## 먼저 뭘 만들고 싶은지 이야기해요

처음부터 이렇게 말하면 PRD가 나오긴 해요.

```text
영어 공부 앱 PRD 작성해줘.
```

근데 이렇게 하면 AI가 빈칸을 알아서 채워요.

- 고객도 AI가 상상하고
- 문제도 AI가 상상하고
- 기능도 AI가 상상하고
- 시장 진입 방법도 AI가 상상하고
- 기술도 AI가 상상해요

그러면 문서는 그럴듯한데, 내 생각이 별로 안 들어가요.

중요한 건 처음부터 PRD 형식을 맞추는 게 아니에요. **내가 뭘 만들고 싶은지 먼저 말해보는 것**이에요.

그 대화에서 이런 걸 계속 정리해야 해요.

```text
나는 왜 이걸 만들고 싶은지
누가 쓸 것 같은지
그 사람이 지금 뭘 불편해하는지
비슷한 서비스는 뭐가 있는지
나는 그중 어디를 다르게 할 건지
첫 버전은 어디까지 만들지
누구에게 먼저 보여줄지
```

이런 얘기를 먼저 해보고 PRD를 만들면 훨씬 좋아져요.

먼저 뭘 만들고 싶은지 이야기하고, 질문하고, 비교하고, 줄여본 다음에 PRD로 묶는 거예요.

## 1. 처음엔 그냥 막연하게 말해도 돼요

처음부터 멋진 기획 문장으로 말할 필요 없어요.

그냥 이렇게 시작해도 돼요.

```text
나 출근길에 영어 공부하는 사람들을 위한 서비스를 만들고 싶어.
근데 정확히 뭘 만들지는 모르겠어.
아이디어를 같이 구체화해보자.
질문을 해주면서 고객, 문제, 첫 버전 범위를 잡아줘.
아직 코드는 짜지 마.
```

또는 이렇게 말해도 돼요.

```text
나는 쇼핑몰 상품 설명 쓰는 게 너무 귀찮아서
이걸 AI로 줄여주는 서비스를 만들고 싶어.
근데 누가 진짜 쓸지, 어떤 기능부터 만들어야 할지 모르겠어.
나한테 질문하면서 아이디어를 좁혀줘.
```

처음엔 이 정도면 충분해요.

AI에게 바로 답을 달라고 하지 말고, **질문을 받으면서 같이 정리하는 게 좋아요.**

## 2. AI가 질문하게 해요

좋은 대화는 AI가 질문을 하면서 시작돼요.

예를 들면 이런 질문들이 나와야 해요.

```text
이 문제를 가장 자주 겪는 사람은 누구야?
그 사람은 지금 이 문제를 어떻게 해결하고 있어?
돈을 내고라도 해결하고 싶은 문제야?
하루 중 어느 순간에 이 서비스가 필요해?
비슷한 서비스를 써본 적 있어?
첫 버전에서 꼭 있어야 하는 기능은 뭐야?
반대로 없어도 되는 기능은 뭐야?
누구에게 먼저 보여줄 수 있어?
```

이 질문에 답하다 보면 내 생각이 정리돼요.

처음에는 “영어 공부 앱”이었는데, 대화하다 보면 이렇게 바뀔 수 있어요.

```text
출근길 10분 안에
오늘의 영어 문장 하나만 보고
완료 체크를 하고
다음 날 다시 들어오는지 확인하는 서비스
```

이 정도로 바뀌면 훨씬 만들기 쉬워져요.

## 3. 레퍼런스를 같이 보면서 비교해요

내 아이디어만 보고 있으면 잘 안 좁혀져요.

비슷한 서비스가 어떤 식으로 문제를 풀고 있는지 보면 감이 와요. 이때는 AI에게 “찾아줘”라고만 하기보다, 내가 아는 링크나 이미지도 같이 주면 좋아요.

예를 들면 이런 것들이 레퍼런스예요.

| 레퍼런스 | 언제 좋아? | 예시 |
| --- | --- | --- |
| 비슷한 서비스 링크 | 전체 흐름을 비교할 때 | “이 서비스는 고객을 어떻게 설득하지?” |
| 경쟁사 랜딩페이지 | 첫 화면 문구를 볼 때 | 제목, CTA, 가격표, 기능 소개 |
| 앱스토어 스크린샷 | 모바일 화면 흐름을 볼 때 | 온보딩, 핵심 화면, 결제 전 화면 |
| 내가 좋아하는 화면 캡처 | UI 느낌을 전달할 때 | 카드형 목록, 입력창, 결과 화면 |
| 커뮤니티 불만 글 | 고객 문제를 찾을 때 | “이 기능이 불편하다”는 실제 말 |
| 손그림/와이어프레임 | 내가 원하는 배치를 보여줄 때 | 종이에 그린 화면도 충분해 |

스크린샷은 특히 강해요. 말로 “헤더가 있고, 가운데 카드가 있고, 하단에 버튼이 있고...”라고 길게 설명하는 것보다, 캡처 한 장을 주는 게 훨씬 빠를 때가 많아요.

그리고 이렇게 물어보면 돼요.

```text
이 링크와 이미지를 참고해서 내 아이디어와 비교해줘.
각 서비스가 누구를 대상으로 하는지,
어떤 문제를 어떻게 풀고 있는지,
내가 배울 점과 피해야 할 점을 정리해줘.

단, 그대로 따라 하자는 게 아니라
내 첫 MVP에서 무엇을 다르게 잡을지 찾고 싶어.
```

PRD에 레퍼런스를 넣을 때는 길게 넣을 필요 없어요. 이렇게만 적어도 돼요.

```text
참고할 것:
- A 서비스의 첫 화면 구조
- B 서비스의 짧은 결과 카드 UI
- C 앱스토어 리뷰에서 나온 “너무 복잡하다”는 불만

따라 하지 않을 것:
- 로그인부터 요구하는 흐름
- 기능을 10개 이상 보여주는 첫 화면
- 긴 설명과 복잡한 메뉴

내 MVP에 반영할 것:
- 첫 화면에서 바로 핵심 결과를 보여준다
- 버튼은 하나만 둔다
- 1분 안에 끝나는 흐름으로 만든다
```

중요한 건 “비슷한 게 있으니 접자”가 아니에요.

비슷한 게 있으면 오히려 배울 수 있어요.

```text
저 서비스는 너무 기능이 많네.
나는 더 작게 가야겠다.
저 서비스는 학습 기록을 강조하네.
나는 출근길 1분 경험만 강조해야겠다.
저 서비스는 영어 고급자를 보네.
나는 왕초보 직장인만 봐야겠다.
```

레퍼런스는 베끼려고 보는 게 아니에요. **내가 어디를 다르게 잡을지 찾는 재료**예요.

나중에 같은 규칙을 계속 반복해서 말하게 되면 그때 `CLAUDE.md` 같은 규칙 파일에 적어두면 돼요. 하지만 처음 PRD 단계에서는 너무 어렵게 생각하지 말고, 링크·이미지·경쟁사 예시를 보면서 “나는 무엇을 다르게 할지”만 정리해도 충분해요.

## 4. “나는 어떻게 할지”를 계속 골라야 해요

AI가 여러 방향을 제안하면 그중 하나를 골라야 해요.

여기서 기획자의 역할이 생겨요.

AI가 이렇게 말할 수 있어요.

```text
방향 A: 매일 문장 추천 앱
방향 B: 발음 연습 중심 앱
방향 C: 짧은 퀴즈 앱
방향 D: 출근길 알림 서비스
```

그럼 골라야 해요.

```text
나는 A로 갈게.
발음 연습은 나중에 하고,
첫 버전은 문장 1개와 해설만 검증하고 싶어.
출근길 직장인에게 먼저 보여줄 거야.
```

이 선택이 중요해요.

PRD는 AI가 대신 써줄 수 있지만, **무엇을 선택할지는 내가 정해야 해요.**

## 5. MVP 범위를 줄여

대화하다 보면 기능이 계속 늘어나요.

```text
로그인도 있으면 좋겠다.
학습 기록도 있으면 좋겠다.
알림도 있으면 좋겠다.
레벨 시스템도 있으면 좋겠다.
공유 기능도 있으면 좋겠다.
```

다 좋아 보여요.

근데 다 넣으면 출시를 못 해요.

AI에게 이렇게 물어봐요.

```text
이 아이디어를 3일 안에 만들 수 있는 MVP로 줄여줘.
가설 검증에 꼭 필요한 기능과,
이번 버전에서 빼도 되는 기능을 나눠줘.
```

그러면 이런 식으로 정리할 수 있어요.

```text
이번에 만들 것:
- 오늘의 문장 1개 보기
- 짧은 해설 보기
- 완료 버튼 누르기

이번에 안 만들 것:
- 로그인
- 학습 통계
- 레벨 시스템
- 결제
- 커뮤니티
```

이 정도가 돼야 만들 수 있어요.

## 6. 시장 진입도 같이 이야기해요

처음 만드는 사람은 보통 “만들면 사람들이 알아서 오겠지”라고 생각해요.

근데 안 와요.

그래서 PRD를 만들기 전에 이것도 이야기해야 해요.

```text
이 서비스를 처음 누구에게 보여줄 수 있을까?
그 사람들은 어디에 모여 있을까?
어떤 말로 설명하면 반응할까?
첫 5명은 어떻게 찾을까?
첫 1,000명이 있다면 어떤 사람들일까?
```

시장 진입이라고 하면 거창해 보이지만, 처음에는 그냥 이거예요.

**처음 누구에게 보여줄지 정하는 것.**

예를 들어요.

```text
출근길 영어 공부 서비스라면
- 회사 동료 5명
- 영어 공부 오픈채팅방
- 직장인 커뮤니티
- 링크드인/스레드에 짧은 사용기
```

이 정도만 정해도 배포 후 할 일이 생겨요.

만들기 전에 “누구에게 보낼지”가 없으면, 배포하고 나서 멈춰요.

## 7. 충분히 구체화되면 prd.md로 묶어요

방향이 어느 정도 정리되면 그때 이렇게 말하면 돼요.

```text
지금까지 대화를 기반으로 prd.md를 만들어줘.

다음 내용을 포함해줘:
- 서비스 한 줄 설명
- 대상 고객
- 고객 문제
- 핵심 가설
- MVP 범위
- 이번에 만들 기능
- 이번에 안 만들 기능
- 사용자 흐름
- 첫 시장 진입 방법
- 검증 기준

코드는 아직 짜지 마.
```

이때 나오는 PRD는 처음에 바로 만든 PRD보다 훨씬 좋아요.

왜냐하면 이미 대화에서 선택을 했기 때문이에요.

```text
누구를 볼지 선택했고
무엇을 뺄지 선택했고
어떤 링크나 이미지, 경쟁사 예시를 참고할지 선택했고
누구에게 먼저 보여줄지 선택했어
```

PRD는 그 선택을 정리한 문서예요.

## 8. PRD를 받으면 그대로 믿지 말고 다시 봐요

AI가 만든 PRD가 항상 맞는 건 아니에요.

받고 나서 이걸 확인해요.

```text
고객이 너무 넓지 않아?
문제가 진짜 구체적이야?
MVP 범위가 너무 크지 않아?
안 만들 것이 충분히 적혀 있어?
첫 사용 흐름이 5단계 안에 들어와?
시장 진입 방법이 실제로 내가 할 수 있는 일이야?
검증 기준이 감상이 아니라 행동으로 되어 있어?
```

여기서 이상하면 바로 고쳐달라고 해요.

```text
고객이 아직 넓어. 출근길 직장인으로 좁혀줘.
MVP 범위가 너무 커. 로그인과 통계는 빼줘.
시장 진입 방법을 내가 이번 주에 실제로 할 수 있는 방식으로 바꿔줘.
검증 기준을 “좋은 반응”이 아니라 실제 행동으로 바꿔줘.
```

이렇게 몇 번 고치면 충분히 시작할 수 있는 PRD가 돼요.

## 좋은 PRD의 기준

좋은 PRD는 길지 않아도 돼요.

다음 질문에 답하면 돼요.

```text
누가 쓰는가?
어떤 문제를 줄이는가?
첫 버전에서 무엇을 만들고 무엇을 뺄 것인가?
사용자는 어떤 순서로 쓰는가?
처음 누구에게 보여줄 것인가?
무엇을 보면 가설이 맞거나 틀렸다고 볼 것인가?
```

이 질문에 답할 수 있으면 PRD 역할은 충분히 해요.

## 자주 헷갈리는 포인트

### PRD를 AI가 써줘도 괜찮은가요?

괜찮아요. 오히려 그렇게 하는 게 자연스러워요. 다만 바로 “PRD 써줘”보다, 먼저 뭘 만들고 싶은지 이야기한 다음 정리하게 하는 게 좋아요.

### 내가 기획을 잘 몰라도 되나요?

돼요. 그래서 질문을 받으면서 정리하면 돼요. “나한테 질문하면서 구체화해줘”라고 하면 돼요.

### 레퍼런스를 보면 베끼는 거 아닌가요?

아니에요. 베끼려고 보는 게 아니라, 고객과 기능과 차별점을 이해하려고 보는 거예요. 링크, 이미지, 경쟁사 화면을 보면서 “나는 무엇을 다르게 할지”를 정하는 게 목적이에요.

### 시장 진입까지 PRD에 넣어야 하나요?

처음에는 넣는 게 좋아요. 거창한 마케팅 전략이 아니라, “처음 누구에게 보여줄지” 정도면 충분해요.

### PRD가 나오면 바로 개발해도 되나요?

바로 가도 되지만, 먼저 너무 큰 기능이 없는지 확인해요. 특히 로그인, 결제, 관리자, 통계 같은 기능이 들어갔다면 첫 MVP에 꼭 필요한지 다시 봐요.
