## 핵심 요약

**서비스는 크게 “고객이 보는 부분”과 “뒤에서 처리하는 부분”으로 나뉘어요. 프론트엔드는 고객이 보고 누르고 입력하는 화면이고, 백엔드는 버튼을 누른 뒤 입력을 검사하고, 비밀 키를 숨기고, 외부 API를 호출하고, 필요하면 DB에 저장하는 곳이에요.**

코드를 하나도 몰라도 괜찮아요. 이 글의 목표는 프론트엔드와 백엔드 코드를 외우는 게 아니에요.

```text
이 파일은 화면을 그리는구나.
이 값은 화면이 기억하는 값이구나.
이 버튼을 누르면 백엔드로 요청이 가는구나.
이 기능은 API 키 때문에 화면만으로는 안 되는구나.
이 데이터는 나중에 다시 봐야 해서 DB가 필요하구나.
```

이 정도 감각을 잡는 게 목표예요.

## 서비스는 이렇게 움직여

사용자는 화면만 보지만, 서비스 안에서는 이런 흐름이 생겨요.

예를 들면 이런 식이에요.

```text
문의 폼
→ 이름과 문의 내용을 입력한다
→ 제출 버튼을 누른다
→ 로딩 표시가 뜬다
→ 백엔드가 내용을 저장하거나 이메일을 보낸다
→ 접수 완료 메시지가 보인다
```

```text
상품 설명 생성기
→ 상품명을 입력한다
→ 생성 버튼을 누른다
→ 백엔드가 AI API를 호출한다
→ 결과 카드가 화면에 보인다
→ 필요하면 생성 기록을 저장한다
```

처음에는 이 흐름만 잡아도 충분해요.

## 1. 프론트엔드는 “고객이 만지는 곳”이에요

프론트엔드는 사용자가 직접 보는 부분이에요.

쉽게 말하면 **화면**이에요.

```text
버튼
입력창
카드
표
목록
이미지
결과 화면
에러 메시지
완료 메시지
```

고객은 서비스를 쓸 때 코드를 보지 않아요. 고객은 이런 걸 봐요.

```text
어디에 입력해야 하지?
어떤 버튼을 눌러야 하지?
결과가 어디에 나오지?
지금 로딩 중이야?
실패했으면 왜 실패했지?
다음에 뭘 하면 되지?
```

그래서 프론트엔드는 단순히 예쁘게 꾸미는 영역이 아니에요. 고객이 서비스를 이해하고, 행동하고, 결과를 확인하는 곳이에요.

처음에는 이 한 줄만 기억해도 돼요.

```text
프론트엔드 = 사용자가 보고 누르고 입력하는 부분
```

## 2. 화면은 보통 조각과 상태로 나뉘어요

AI가 화면을 만들면 파일이 여러 개 생길 수 있어요.

처음엔 복잡해 보이지만 대부분 이런 조각이에요.

| 화면 조각 | 쉽게 말하면 | 예시 |
| --- | --- | --- |
| 페이지/스크린 | 한 화면 전체 | 홈, 결과, 설정 화면 |
| 컴포넌트 | 반복해서 쓰는 화면 조각 | 버튼, 카드, 입력창, 리스트 한 줄 |
| 상태 | 화면이 기억하는 값 | 입력값, 로딩 여부, 결과, 에러 메시지 |
| 스타일 | 모양과 배치 | 색, 간격, 폰트, 반응형 |
| 이벤트 | 사용자의 행동 | 클릭, 입력, 제출, 탭 |

예를 들어 문의 폼 화면이라면 이렇게 볼 수 있어요.

```text
화면 전체 → 문의하기 화면
화면 조각 → 이름 입력, 이메일 입력, 문의 내용 입력, 제출 버튼
상태 → 지금 입력한 이름/이메일/문의 내용, 제출 중 여부
이벤트 → 제출 버튼 클릭
스타일 → 입력창 간격, 버튼 색상, 에러 메시지 위치
```

상태는 어렵게 생각하지 마세요.

```text
상태 = 지금 화면이 기억하고 있어야 하는 값
```

입력창의 글자, 선택한 날짜, 생성 중인지 여부, 결과값, 에러 메시지 같은 게 상태예요.

## 3. 백엔드는 “뒤에서 처리하는 곳”이에요

백엔드는 사용자가 직접 보지는 않지만 뒤에서 처리하는 곳이에요.

식당으로 비유하면 쉬워요.

```text
프론트엔드 = 손님이 보는 홀
백엔드 = 주문을 처리하고 음식을 만드는 주방
```

손님은 메뉴판을 보고 주문해요. 하지만 음식은 주방에서 만들어져요.

서비스도 비슷해요.

```text
사용자는 화면에서 입력한다
버튼을 누른다
결과를 본다
```

그 사이에 백엔드가 이런 일을 할 수 있어요.

```text
입력값 받기
입력값이 이상하지 않은지 확인하기
외부 서비스에 요청하기
비밀 키 숨기기
DB에 저장하기
저장된 데이터 다시 불러오기
결과를 화면에 돌려주기
```

처음에는 이 한 줄만 기억해도 돼요.

```text
사용자가 보는 건 프론트엔드,
사용자 몰래 뒤에서 처리하는 건 백엔드.
```

## 4. 화면만으로 되는 일과 백엔드가 필요한 일

모든 기능에 백엔드가 필요한 건 아니에요.

처음 MVP에서는 화면만으로도 충분한 일이 많아요.

| 기능 | 프론트엔드만으로 가능? | 백엔드가 필요한 순간 |
| --- | --- | --- |
| 소개 페이지 보여주기 | 가능 | 관리자에서 내용을 바꿔야 할 때 |
| 버튼 누르면 샘플 결과 보여주기 | 가능 | 진짜 결과를 외부 API로 만들어야 할 때 |
| 계산기 | 대부분 가능 | 계산 기록을 저장하거나 공유해야 할 때 |
| 피드백 폼 | 화면은 가능 | 제출 내용을 저장해야 할 때 |
| 로그인 | 어려움 | 사용자별 데이터가 필요할 때 |
| 결제 | 백엔드 필요 | 결제 검증과 보안 처리가 필요할 때 |

처음에는 이렇게 나눠서 생각하면 돼요.

```text
보여주기만 한다 → 프론트엔드
비밀 키가 필요하다 → 백엔드
저장해야 한다 → DB
사람마다 다르게 보여줘야 한다 → 백엔드 + DB
돈이 오간다 → 백엔드 필수
```

## 5. API는 화면과 백엔드가 말하는 창구예요

API는 화면이 백엔드에게 부탁하는 창구예요.

```text
화면: 이 문의 내용을 저장해줘
백엔드: 알겠어. 저장하고 결과를 알려줄게
```

웹 프로젝트에서는 보통 이런 주소처럼 보일 수 있어요.

```text
/api/contact
/api/generate
/api/save-feedback
/api/reservations
```

이 주소를 외울 필요는 없어요.

그냥 이렇게 이해하면 돼요.

```text
/api/... = 화면이 백엔드에게 부탁하는 문
```

AI가 API 코드를 만들었다면 이렇게 물어봐요.

```text
이번에 만든 API 목록을 정리해줘.
각 API마다
1. 화면에서 언제 호출되는지
2. 어떤 데이터를 받는지
3. 어떤 일을 하는지
4. 화면에 무엇을 돌려주는지
표로 설명해줘.
```

## 6. 비밀값과 외부 API는 백엔드에서 다뤄

서비스를 만들다 보면 API 키라는 말이 나와요.

API 키는 비밀번호 같은 거예요.

```text
외부 AI 서비스 키
결제 API 키
이메일 발송 서비스 키
지도 API 키
관리자용 비밀 키
```

이런 값은 화면 코드에 넣으면 안 돼요.

브라우저에서 돌아가는 코드는 사용자가 볼 수 있기 때문이에요.

```text
고객에게 보여줘도 되는 것 → 프론트엔드
고객에게 보여주면 안 되는 것 → 백엔드
```

외부 API도 보통 백엔드가 대신 호출해요.

```text
화면 → 내 백엔드 → 외부 API → 내 백엔드 → 화면
```

AI에게는 이렇게 검사시켜요.

```text
이 프로젝트에 비밀 키가 들어가는 부분이 있는지 확인해줘.
브라우저에 노출되면 안 되는 값은 무엇인지 알려줘.
그 값들이 서버에서만 사용되는지 검사해줘.
```

## 7. DB는 “나중에 다시 볼 데이터”가 있을 때 붙여

DB는 데이터를 저장하는 곳이에요.

하지만 처음부터 무조건 붙일 필요는 없어요.

이 기준으로 보면 돼요.

```text
새로고침하면 사라져도 괜찮다 → DB 없어도 됨
나중에 다시 봐야 한다 → DB 필요
여러 사람이 각자 자기 기록을 봐야 한다 → DB 필요
운영자가 고객 반응을 분석해야 한다 → DB 필요
```

예를 들어요.

| 서비스 | 저장할 수 있는 데이터 |
| --- | --- |
| 문의 폼 | 이름, 이메일, 문의 내용, 접수 시간 |
| 피드백 수집 | 평점, 의견, 불편한 점 |
| 예약 서비스 | 예약자, 날짜, 시간, 상태 |
| 생성 도구 | 입력값, 생성 결과, 생성 시간 |
| 학습 서비스 | 완료한 콘텐츠, 점수, 진행률 |

DB가 필요해 보이면 AI에게 먼저 정리시켜요.

```text
이 PRD에서 저장해야 하는 데이터를 찾아줘.
MVP에 꼭 필요한 데이터와 나중에 저장해도 되는 데이터를 나눠줘.
DB가 지금 꼭 필요한지도 판단해줘.
```

여기서 중요한 건 DB 기술 이름이 아니에요. **무엇을 저장해야 하는지**가 먼저예요.

## 8. 만들어진 소스를 보는 순서

AI가 프론트엔드와 백엔드 코드를 만들었다면 바로 다음 기능으로 넘어가지 마세요.

먼저 소스를 설명받아요.

```text
방금 만든 소스를 초보자 기준으로 설명해줘.

순서는 이렇게 해줘.
1. 사용자가 처음 보는 화면 파일
2. 입력창, 버튼, 카드 같은 컴포넌트 파일
3. 화면이 기억하는 상태
4. 버튼을 눌렀을 때 실행되는 동작
5. 화면에서 백엔드를 호출하는 부분
6. 백엔드가 요청을 받는 파일
7. 외부 API나 DB를 쓰는 부분이 있다면 그 부분
8. 화면에 결과나 에러를 돌려주는 부분

각 파일마다 “이 파일은 한 줄로 뭐 하는 파일인지” 먼저 설명해줘.
```

목표는 코드를 다 외우는 게 아니에요.

역할을 잡는 거예요.

```text
아, 이 파일은 화면 전체구나.
아, 이 파일은 버튼 조각이구나.
아, 이 값은 입력창에 적은 글자를 기억하는구나.
아, 이 파일은 백엔드가 요청을 받는구나.
아, 이 부분은 외부 API를 부르는구나.
아, 이 부분은 DB에 저장하는구나.
```

이 정도면 충분해요.

## 9. 검증은 화면과 데이터로 확인해요

코드는 AI가 만들어줘도 확인은 내가 해야 해요.

:::steps
1. 처음 화면을 열어봐요. 무엇을 해야 하는지 바로 보이나요?
2. 입력창에 값을 넣어봐요. 글자가 잘 들어가나요?
3. 버튼을 눌러봐요. 로딩, 결과, 에러 중 필요한 반응이 보이나요?
4. 빈 값으로 제출해봐요. 사용자에게 안내 메시지가 나오나요?
5. 백엔드 요청이 있다면 결과가 화면으로 돌아오나요?
6. 저장 기능이 있다면 새로고침 후에도 남아 있나요?
7. 비밀 키가 화면 코드에 노출되지 않았는지 AI에게 검사시켜봐요.
:::

문제가 생기면 이렇게 말하면 돼요.

```text
버튼을 눌렀는데 결과가 안 나와.
화면 문제인지, 버튼 동작 문제인지, 백엔드 문제인지, 외부 API 문제인지
초보자 기준으로 확인 순서를 알려줘.
내가 확인해야 할 파일과 로그도 알려줘.
```

저장 문제라면 이렇게 말해요.

```text
저장은 되는 것 같은데 화면에 다시 안 보여.
DB 저장 문제인지, 불러오기 문제인지 구분해줘.
초보자 기준으로 확인 순서를 알려줘.
```

## 10. 한 입 끝나면 저장하고 정리해요

기능 하나가 끝나면 이 리듬을 지켜요.

```text
기능 끝 → 확인 → 저장 → 정리 → 다음 기능
```

- **확인**: 브라우저나 기기에서 직접 눌러봐요.
- **저장**: “지금까지 만든 거 git으로 저장해줘.” 다음 기능 만들다 망가지면 이 시점으로 되돌릴 수 있어요.
- **정리**: “뭘 만들었고 어떤 파일이 뭘 하는지 정리해줘.” 대화가 길어져도 다음 작업 맥락을 잡기 쉬워요.
- **배운 것 기록**: “예상과 달랐던 점 정리해줘.” 기능마다 적어두면 PRD 방향도 업데이트할 수 있어요.

백엔드 기능은 특히 한 번 망가지면 어디서 깨졌는지 찾기 어려울 수 있어요. 그래서 작은 기능 하나가 끝날 때마다 저장해두는 게 좋아요.

## AI에게 요청할 때는 이렇게 시작해요

처음부터 개발자처럼 말하지 않아도 돼요.

```text
나는 코드를 잘 몰라.
이 PRD를 기준으로 첫 MVP 기능을 만들어줘.

먼저 화면에서 사용자가 하는 행동과
뒤에서 처리해야 하는 일을 나눠서 설명해줘.

그다음 MVP에 꼭 필요한 것부터 하나씩 만들어줘.
한 번에 다 만들지 말고,
첫 번째 기능이 브라우저에서 확인될 때마다 멈춰서 설명해줘.
```

소스 설명은 이렇게 요청해요.

```text
방금 만든 파일들을 표로 정리해줘.
각 파일이 화면, 상태, 버튼 동작, API, 저장 중 어디에 해당하는지 알려줘.
내가 디자인만 바꾸면 되는 파일과
기능 로직이라 조심해야 하는 파일도 나눠줘.
```

## 자주 헷갈리는 포인트

### 프론트엔드는 디자인만 말하는 건가요?

아니에요. 디자인도 포함하지만, 사용자가 입력하고 클릭하거나 탭하고 결과를 확인하는 전체 경험이 프론트엔드예요.

### 백엔드는 꼭 있어야 하나요?

아니에요. 보여주기식 MVP나 계산기처럼 저장과 비밀 키가 없는 기능은 프론트엔드만으로도 시작할 수 있어요.

### API랑 백엔드는 같은 건가요?

완전히 같지는 않아요. API는 화면이 백엔드에게 부탁하는 창구예요. 백엔드는 그 요청을 받아 처리하는 곳이고.

### 백엔드랑 DB는 같은 건가요?

아니에요. 백엔드는 뒤에서 처리하는 코드고, DB는 데이터를 저장하는 곳이에요. 백엔드가 DB에 저장하거나 DB에서 꺼내오는 일을 해요.

### LLM API가 백엔드인가요?

아니에요. LLM API는 외부 API 중 하나예요. 백엔드는 LLM API, 결제 API, 이메일 API 같은 외부 서비스를 대신 호출할 수 있어요.

### 새로고침하면 입력한 값이 사라져요

정상일 수 있어요. 화면 안에서만 기억하는 값은 사라질 수 있어요. 나중에 다시 봐야 하는 데이터라면 백엔드나 DB가 필요해요.

### AI가 만든 화면이나 구조가 너무 복잡해요

“초보자 기준으로 파일을 줄이고, 지금 MVP에 필요 없는 구조는 덜어내줘”라고 말해요. 처음부터 완벽한 구조보다 이해 가능한 구조가 더 중요해요.
