> "코드가 꼬여도 괜찮습니다. 우리에겐 언제든 어제로 돌아갈 수 있는 타임머신이 있거든요."

## 05.1 git과 GitHub — 무한 세이브 슬롯과 온라인 보관함

자, 이제 여러분은 나만의 캐릭터와 대화하는 멋진 서비스를 하나 가지게 되었습니다. 뿌듯하시죠? 그런데 즐거움도 잠시, 갑자기 이런 걱정이 들기 시작합니다. 

"여기서 기능을 더 넣다가 코드가 다 망가지면 어떡하지?"
"어제는 잘 됐는데, 오늘 뭘 건드렸는지 기억이 안 나네..."
"내 컴퓨터가 갑자기 고장 나면 이 소중한 코드들은 다 사라지는 건가?"

걱정 마세요. 개발자들은 이미 수십 년 전부터 이런 공포 속에서 살아왔고, 그 해결책을 완벽하게 만들어 두었습니다. 바로 **Git(깃)**과 **GitHub(깃허브)**입니다. 

이름이 비슷해서 헷갈리시죠? 아주 쉽게 비유해 드릴게요. **Git은 내 컴퓨터에 있는 '무한 세이브 슬롯'**이고, **GitHub은 그 세이브 파일을 올려두는 '온라인 금고'**입니다. 이 두 가지만 있으면 여러분은 코딩의 세계에서 무적의 생존자가 될 수 있습니다.

---

### git = 언제든 되돌리는 무한 세이브 슬롯

여러분, 혹시 어려운 게임을 해본 적 있으신가요? 강력한 보스를 만나기 직전, 우리는 습관적으로 '저장(Save)' 버튼을 누릅니다. 만약 싸우다 죽더라도 저장한 시점으로 다시 돌아가서 도전하면 되니까요.

코딩도 똑같습니다. 새로운 기능을 넣기 직전에 '세이브'를 해두면, 나중에 코드가 엉망이 되어도 "에잇, 어제로 돌아갈래!"라고 외치며 단 1초 만에 깔끔했던 상태로 되돌릴 수 있습니다. 이 **타임머신 장치가 바로 Git**입니다.

**"코드가 꼬이는 걸 두려워하지 마세요. Git이 여러분의 뒤를 든든하게 지켜주고 있습니다."**

실제로 제가 스터디를 운영할 때, 한 수강생분이 코드를 실수로 다 지워버리고 울먹이며 연락하신 적이 있습니다. 하지만 다행히 10분 전에 세이브(커밋)를 해두셨더라고요. 명령어 한 줄로 0.1초 만에 코드를 복구해 드렸더니 "이게 마법이냐"며 놀라시던 모습이 기억납니다.

---

### GitHub = 내 코드를 지켜주는 온라인 보관함

Git이 내 컴퓨터 안에서의 세이브 슬롯이라면, GitHub은 그 세이브 파일들을 인터넷 세상 어딘가에 안전하게 보관해 주는 서비스입니다. 구글 드라이브나 드롭박스 같은 '코드 전용 클라우드'라고 생각하시면 편합니다.

GitHub을 써야 하는 이유는 명확합니다.

1.  **안전성**: 내 노트북을 카페에 두고 오거나 커피를 쏟아도, 코드는 GitHub에 안전하게 살아있습니다.
2.  **협업**: 나중에 친구나 AI 조수와 함께 코드를 짤 때, GitHub이 있으면 서로의 코드를 합치기가 정말 쉽습니다.
3.  **배포의 시작**: 우리가 다음 섹션에서 배울 '전 세계에 내 서비스 공개하기(배포)'를 하려면, 반드시 GitHub에 코드가 올라가 있어야 합니다.

**"GitHub은 여러분의 포트폴리오이자, 서비스가 세상으로 나가는 출입구입니다."**

---

### [실습] 첫 번째 세이브 포인트 찍기

이론은 여기까지 하고, 이제 실제로 여러분의 캐릭터 챗 코드를 GitHub이라는 금고에 넣어보겠습니다. 터미널 명령어라고 해서 겁먹을 필요 없습니다. 딱 4개의 단어만 기억하면 됩니다. 

#### 01 현재 상태 확인하기 (`git status`)
먼저 내 폴더에 어떤 변화가 있는지 확인해 봅시다. 터미널에 아래 명령어를 입력해 보세요.

```bash
git status

> **확인**: 빨간색 글씨로 파일 이름들이 보인다면, 아직 '세이브 박스'에 담기지 않은 변화들이 있다는 뜻입니다.

```
#### 02 세이브 박스에 담기 (`git add .`)
변경사항들을 한데 모아 박스에 담습니다. 여기서 마침표(`.`)는 "이 폴더의 모든 변화를 다 담겠다"는 뜻입니다.

```bash
git add .

```
#### 03 박스 밀봉하고 메모 남기 (`git commit`)
이제 박스를 테이프로 붙이고, 겉면에 이 세이브가 어떤 내용인지 메모를 적습니다. 이걸 **'커밋(Commit)'**이라고 부릅니다.

```bash
git commit -m "캐릭터 챗 첫 완성"

```
#### 04 온라인 금고로 보내기 (`git push`)
마지막으로 내 컴퓨터에 저장된 이 박스를 GitHub이라는 온라인 금고로 휙 던집니다.

```bash
git push

```
**"이 4단계(status → add → commit → push)가 여러분이 앞으로 매일 하게 될 루틴입니다."**

처음에는 어색하겠지만, 몇 번 해보면 마치 양치질하는 것처럼 익숙해질 거예요. "아, 이제 하나 끝냈으니 세이브해야지!" 하는 마음으로 가볍게 쳐주시면 됩니다.

### GitHub 계정 연결은 코덱스에게 시키세요

"잠깐만요, 저는 GitHub 계정도 없고 연결하는 법도 모르는데요?"

맞습니다. 처음 GitHub을 시작할 때 가장 어려운 게 계정을 만들고, 내 컴퓨터와 연결(인증)하는 과정입니다. 예전에는 이걸 배우는 데만 한 시간이 걸렸지만, 이제 우리에겐 코덱스가 있죠. 

여러분은 그냥 코덱스에게 당당하게 요청하시면 됩니다.

01 VS Code 터미널에서 `codex`를 실행합니다.
02 다음과 같이 말해보세요. 
> "나 지금 만든 프로젝트를 내 GitHub 계정에 올리고 싶어. GitHub 계정 만드는 법부터, 이 프로젝트를 push 하는 것까지 하나하나 단계별로 알려주고 같이 진행해줘."

그러면 코덱스가 여러분의 운영체제(윈도우인지 맥인지)에 맞춰서 아주 친절하게 가이드를 줄 겁니다. 

> **🙋 질문이요! 아이디랑 비밀번호를 매번 쳐야 하나요?**
>
> 아뇨! 코덱스가 'GitHub Desktop' 같은 도구를 설치하라고 하거나, 한 번만 인증하면 다음부터는 자동으로 로그인되도록 도와줄 겁니다. 복잡한 설정은 코덱스에게 맡기고, 여러분은 '세이브'라는 본질에만 집중하세요.

## 여기서 막혔나요?

**Q. `git push`를 했는데 "Permission denied" 에러가 떠요.**

**A.** 여러분의 컴퓨터가 아직 GitHub 금고의 열쇠(인증 정보)를 가지고 있지 않아서 생기는 문제입니다. 당황하지 마세요. 코덱스에게 그 에러 메시지를 그대로 복사해서 붙여넣으세요. "로그인 정보가 없어서 push가 안 된대. 어떻게 해결할까?"라고 물어보면 해결책을 바로 알려줄 겁니다.

**Q. 잘못된 코드를 커밋(세이브)해 버렸어요! 어떡하죠?**

**A.** 괜찮습니다. 세이브 슬롯은 무한하니까요. "방금 한 커밋 취소하고 5분 전으로 되돌려줘"라고 코덱스에게 시키면 됩니다. 아니면 그냥 잘못된 부분을 고치고 한 번 더 세이브를 해도 무방합니다.

**Q. `.env` 파일도 GitHub에 올려야 하나요?**

**A.** **절대 안 됩니다!** 이 파일에는 여러분의 API 키 같은 소중한 비밀번호가 들어있습니다. 금고에 넣는 건 좋지만, GitHub은 기본적으로 남들도 볼 수 있는 공간(Public)인 경우가 많거든요. `.gitignore`라는 파일에 `.env`를 적어두면 Git이 알아서 "이건 비밀이니까 세이브하지 않을게"라고 빼줍니다. 이 설정도 코덱스에게 "내 API 키가 GitHub에 안 올라가게 .gitignore 설정해줘"라고 시키세요.

## 한 줄 정리

Git은 내 소중한 코드를 지켜주는 **무한 세이브 타임머신**이며, GitHub은 이를 전 세계 어디서든 꺼내 볼 수 있게 해주는 **안전한 온라인 보관함**입니다.

자, 이제 여러분의 코드는 안전하게 금고에 보관되었습니다. 그런데 금고 안에만 있으면 남들이 볼 수가 없겠죠? 다음 섹션에서는 이 금고에 담긴 코드를 실제 주소가 있는 웹사이트로 변신시키는 마법, 'Vercel 배포'를 배워보겠습니다. 드디어 여러분의 캐릭터가 여러분의 컴퓨터를 벗어나 전 세계 사람들을 만날 시간입니다!


## 05.2 [실습] Vercel로 배포하기 — 내 서비스에 진짜 링크가 생긴다

자, 이제 진짜 마법을 부릴 시간입니다. 앞 섹션에서 우리는 깃허브(GitHub)라는 튼튼한 금고에 우리 소스 코드를 안전하게 보관했습니다. 하지만 솔직히 말씀드리면, 금고에 코드가 들어있다고 해서 세상이 바뀌지는 않습니다. 금고 문을 열고 코드를 꺼내서, 누구나 볼 수 있는 '전시실'에 올려두어야 비로소 사람들이 여러분의 서비스를 써볼 수 있겠죠.

우리는 그 전시실로 **'버셀(Vercel)'**이라는 곳을 사용할 겁니다. 

**"버셀은 여러분의 코드를 웹사이트로 변신시켜 주는 자동 요리 기계입니다."**

깃허브가 레시피와 재료를 담은 바구니라면, 버셀은 그 바구니를 건네받아 순식간에 요리를 완성하고 손님 식탁(브라우저)에 내놓는 아주 유능한 셰프와 같습니다. 무엇보다 개인용으로는 평생 '무료'로 쓸 수 있다는 점이 우리 같은 입문자들에게는 가장 큰 매력입니다.

---

## 깃허브가 보관함이라면, 버셀은 방송국입니다

우리가 만든 캐릭터 채팅 서비스를 친구에게 보여준다고 상상해 보세요. "내 컴퓨터에 있는 `index.html` 파일을 너한테 메일로 보낼 테니까 한번 열어봐"라고 하면 친구가 좋아할까요? 아마 "귀찮게 뭘 그런 걸 보내..."라며 읽지 않을 가능성이 큽니다.

하지만 카톡으로 `https://my-character-chat.vercel.app` 같은 짧은 링크 하나만 딱 보낸다면 어떨까요? 친구는 그냥 클릭만 하면 됩니다. 스마트폰에서도, 태블릿에서도 여러분의 캐릭터와 바로 대화를 나눌 수 있죠. 

이게 바로 **'배포(Deploy)'**의 힘입니다. 내 컴퓨터라는 좁은 방 안에서만 돌아가던 프로그램을 전 세계 사람들이 접속할 수 있는 공용 공간으로 끌어올리는 작업이죠. 자, 이제 주저하지 말고 여러분의 첫 번째 서비스를 세상에 내보내 봅시다.

## STEP 1. 버셀 가입하고 깃허브 연결하기

가장 먼저 할 일은 버셀의 회원이 되는 것입니다. 다행히 우리는 이미 깃허브 계정이 있으니, 따로 복잡하게 가입할 필요가 없습니다.

01 브라우저를 열고 [vercel.com](https://vercel.com/signup)에 접속하세요.
02 **'Continue with GitHub'** 버튼을 누르세요.
03 깃허브 로그인 창이 뜨면 승인 버튼을 누릅니다.

이게 끝입니다. 이제 버셀과 깃허브는 서로 '아는 사이'가 되었습니다. 여러분이 깃허브 금고에 코드를 넣으면, 버셀이 슬쩍 보고 "오, 새 코드가 들어왔네? 내가 웹사이트로 만들어줄게!"라고 반응할 준비를 마친 겁니다.

---

## STEP 2. 코덱스에게 "배포해줘"라고 시키기

원래 배포는 꽤 까다로운 작업입니다. 터미널에 복잡한 명령어를 치고, 설정을 맞추고, 에러가 나면 구글을 뒤져야 하죠. 하지만 우리에게는 누가 있죠? 바로 박사급 조수, 코덱스가 있습니다. 

**"배포의 전 과정도 코덱스에게 통째로 맡기면 됩니다."**

01 VS Code를 열고 터미널에서 `codex`를 실행하세요.
02 코덱스에게 다음과 같이 지시하세요.
> "지금 내가 만든 캐릭터 채팅 서비스를 Vercel로 배포하고 싶어. Vercel CLI를 설치하고 로그인하는 것부터 실제 배포까지 네가 다 알아서 진행해줘."

03 그러면 코덱스가 알아서 'Vercel CLI'라는 도구를 설치하기 시작할 겁니다. 중간에 "이걸 설치할까요?"라고 물어보면 당연히 "Yes"를 선택하세요.
04 설치가 끝나면 코덱스가 "버셀에 로그인해야 하니 브라우저 창에서 승인해달라"고 할 겁니다. 자동으로 열리는 브라우저 창에서 **'Verify'** 버튼만 누르면 됩니다.

이제 코덱스가 터미널에 `vercel`이라고 입력하며 배포를 시작할 겁니다. 몇 가지 질문이 나올 텐데, 사실 대부분 그냥 엔터(Enter)만 치면 되는 것들입니다.

> **🙋 잠깐! 코덱스가 질문을 하는데 뭐라고 대답해야 하죠?**
>
> 보통 이런 순서로 물어볼 거예요.
> 1. Set up and deploy? (y/n): **y (네, 할게요)**
> 2. Which scope? (내 이름 선택): **Enter (그냥 엔터)**
> 3. Link to existing project? (y/n): **n (아뇨, 새로 만들게요)**

## 핵심 개념: 환경변수(.env) — 금고에는 넣지 않는 '비밀번호'

여기서 아주 중요한 포인트가 하나 있습니다. 우리가 03장에서 챗GPT(OpenAI)의 API 키를 `.env`라는 파일에 넣었던 거 기억하시죠? 그런데 제가 이전 섹션에서 뭐라고 했나요? **".env 파일은 절대 깃허브 금고에 올리지 마세요"**라고 말씀드렸습니다.

자, 여기서 문제가 생깁니다. 
1. 깃허브에는 API 키가 없습니다. (비밀이니까요)
2. 버셀은 깃허브에서 코드를 가져옵니다.
3. 결과적으로 버셀도 API 키가 뭔지 모릅니다!

그래서 배포된 웹사이트에서 대화를 시도하면 "API 키가 없어서 대답을 못 하겠어요"라는 에러가 날 겁니다. 이걸 해결하려면 버셀 대시보드에 직접 "이게 내 비밀번호야"라고 알려줘야 합니다.

**"환경변수(Environment Variables) 설정은 버셀에게 열쇠를 따로 건네주는 과정입니다."**

01 버셀 사이트(vercel.com)에서 방금 만든 프로젝트를 클릭합니다.
02 상단 메뉴 중 **'Settings'**를 누르고, 왼쪽 메뉴에서 **'Environment Variables'**를 찾으세요.
03 **Key** 칸에는 `OPENAI_API_KEY` (또는 여러분이 정한 이름)를 적으세요.
04 **Value** 칸에는 여러분의 실제 API 키(`sk-...`로 시작하는 긴 문자열)를 복사해서 붙여넣으세요.
05 **'Add'** 버튼을 누릅니다.

이제 버셀도 열쇠를 가졌습니다. 하지만 이미 배포된 사이트는 예전 코드로 돌아가고 있으니, 이 열쇠를 반영해서 다시 한번 배포해야 합니다. 터미널에서 `vercel --prod`라고 한 번 더 치거나, 코덱스에게 "환경변수 설정했으니 다시 배포해줘"라고 시키면 됩니다.

> **💡 팁: 왜 이렇게 복잡하게 하나요?**
>
> 번거로워 보이지만, 이건 보안을 위해 전 세계 개발자들이 지키는 철칙입니다. 현관문 비밀번호를 전단지에 인쇄해서 동네방네 붙이고 다니면 안 되잖아요? 깃허브(코드)는 전단지이고, 버셀(서버)은 우리 집 안이라고 생각하시면 됩니다. 비밀번호는 집 안에서만 조용히 입력하는 게 맞죠.

## 여기서 막혔나요?

**Q. 버셀 배포 중에 "Build Failed"라고 빨간 글씨가 떠요.**

**A.** 보통 두 가지 이유입니다. 첫째, 코덱스가 코드를 짜면서 오타를 냈거나 꼭 필요한 파일을 빠뜨린 경우입니다. 이럴 땐 터미널에 뜬 에러 메시지 전체를 복사해서 코덱스에게 "이것 때문에 배포가 안 된대. 고쳐줘"라고 하세요. 둘째, `package.json` 파일에 '어떻게 실행하는지'에 대한 설명이 빠졌을 때입니다. 이 역시 코덱스에게 "Vercel 배포용 설정 파일을 다시 확인해줘"라고 하면 해결해 줍니다.

**Q. 링크에 들어갔더니 화면은 뜨는데 AI가 답장을 안 해요.**

**A.** 99% 환경변수 문제입니다. 위에서 설명한 'STEP 3'의 환경변수 설정을 제대로 했는지, 그리고 `OPENAI_API_KEY`라는 이름이 코드 안에서 쓰는 이름과 똑같은지 확인하세요. 대소문자 하나만 틀려도 AI는 길을 잃습니다.

**Q. 배포 링크 주소를 제가 원하는 걸로 바꿀 수 있나요?**

**A.** 네! 버셀 설정(Settings)의 **'Domains'** 메뉴에서 바꿀 수 있습니다. `my-sweet-chat` 같은 예쁜 이름을 선점해 보세요. 물론 남이 이미 쓰고 있는 이름은 안 됩니다!

### 실전 루프 돌리기: 5분 만에 반영하는 서비스

실제로 제가 가르쳤던 한 수강생분은 골프 장갑 제작자이셨는데, 처음 만든 앱을 거래처 분들에게 보여드렸다가 "영문 메일 톤이 너무 딱딱하다"는 말을 들으셨어요. 

그분은 당황하지 않고 그 자리에서 코덱스를 열어 "메일 톤을 좀 더 정중하고 비즈니스 매너가 느껴지게 고쳐줘"라고 시키셨죠. 그리고 바로 `git push`! 5분 뒤에 거래처 분에게 "다시 확인해 보세요"라고 링크를 드렸고, 상대방은 "세상에, 이렇게 빨리 반영해주다니!"라며 감탄했다는 일화가 있습니다.

이것이 우리가 배운 **바이브코딩의 진면목**입니다. 
- **관찰(Observe)**: 사용자가 불편해하는 지점을 찾는다.
- **의도 수정(Refine)**: 코덱스에게 피드백을 전달하고 코드를 고친다.
- **배포(Deploy)**: `git push`로 세상을 업데이트한다.

이 루프를 딱 5번만 돌려보세요. 처음에 만든 어설픈 앱은 온데간데없고, 사람들의 진짜 고민을 해결해주는 꽤 괜찮은 서비스가 여러분의 손에 들려 있을 겁니다.

## 여기서 막혔나요?

**Q. `git push`를 했는데 Vercel 사이트에 변화가 없어요.**

**A.** 가끔 깃허브(GitHub)와 버셀(Vercel) 사이의 연결이 지연될 때가 있습니다. Vercel 대시보드의 **'Deployments'** 탭을 클릭해서 지금 새로운 빌드가 진행 중인지 확인해 보세요. 만약 아무런 기록이 없다면, VS Code에서 수정한 내용을 저장(`Ctrl+S` 또는 `Cmd+S`)했는지 먼저 확인하고 다시 세 줄의 명령어를 입력해 보세요.

**Q. 친구가 링크를 눌렀는데 "404 Not Found"라고 뜬대요.**

**A.** 주소를 복사할 때 끝에 점(.)이 붙었거나 오타가 났을 확률이 높습니다. 주소창에 있는 URL을 직접 복사해서 전달했는지 확인해 보세요. 혹은 배포 자체가 실패했을 수도 있으니 Vercel 대시보드에서 상태가 'Ready'인지 확인하는 것이 좋습니다.

**Q. 피드백을 반영했는데 전보다 더 이상해졌다고 해요.**

**A.** 걱정하지 마세요! 우리에게는 **Git이라는 타임머신**이 있잖아요. 이전 상태로 되돌리고 싶다면 코덱스에게 "방금 수정한 게 마음에 안 들어. 이전 버전 코드로 다시 돌려줘"라고 하거나, 깃허브에서 이전 커밋(Commit) 기록을 찾아 복구하면 됩니다. 실패를 두려워하지 말고 마음껏 수정해 보세요.

## 한 줄 정리

링크 공유는 완성의 끝이 아니라 **진짜 쓸모 있는 서비스를 만드는 대화의 시작**이며, `git push` 한 줄로 세상을 즉시 바꾸는 마법을 부릴 수 있게 된 것입니다.

자, 이제 여러분의 서비스는 살아있는 생명체처럼 사용자의 반응을 먹고 쑥쑥 자라기 시작했습니다. 그런데 말이죠, 지금까지 우리는 하나의 서비스를 '만들고 다듬는' 데 집중했습니다. 만약 이런 과정 자체를 AI가 알아서 해준다면 어떨까요? 혹은 내가 잠든 사이에도 AI가 데이터를 수집하고 결과를 보고해준다면요? 

다음 장에서는 드디어 이 책의 또 다른 주인공, **자동화 에이전트 'OpenClaw'**를 만날 시간입니다. 이제 단순히 서비스를 만드는 단계를 넘어, 24시간 나 대신 일하는 '진짜 비서'를 구축하는 세계로 넘어가 보겠습니다!


## 05.4 [실습] 반응을 반영해서 다시 만들기 — 바이브코딩 실전 루프

링크를 보내고 나면, 아마 핸드폰 진동이 멈추지 않을 겁니다. "우와, 이거 네가 만든 거야?"라는 칭찬부터 "야, 이거 글씨가 너무 작아서 안 보여" 같은 냉정한 평가까지 쏟아지겠죠. 

**"사실, 이때부터가 진짜 바이브코딩의 시작입니다."**

처음에 만든 건 그냥 '가설'일 뿐입니다. 진짜 사용자가 내 앱을 만지는 순간, 우리가 미처 생각하지 못했던 수많은 빈틈이 보이기 시작하거든요. 하지만 당황하지 마세요. 우리에게는 코덱스라는 유능한 조수와, `git push` 한 번으로 세상을 바꾸는 Vercel이 있으니까요.

### 실사용자 피드백을 '의도'로 바꾸기

친구나 가족의 피드백을 들을 때 가장 중요한 건, 그들의 말을 그대로 받아적는 게 아니라 **AI가 알아들을 수 있는 '설계도(PRD)'의 언어**로 번역하는 겁니다. 

예를 들어, 친구가 "화면이 너무 복잡해서 뭘 눌러야 할지 모르겠어"라고 했다면, 이걸 어떻게 PRD에 반영해야 할까요? "화면을 예쁘게 해줘"라고 하면 코덱스는 갈 길을 잃습니다. 대신 이렇게 구체적으로 적어주는 거죠.

- **피드백**: "글씨가 너무 작고 버튼이 작아서 누르기 힘들어."
- **의도로 번역**: "모바일 환경을 최우선으로 고려해서 폰트 크기를 키우고, 버튼의 높이를 최소 50px 이상으로 확보해줘."

- **피드백**: "캐릭터가 5명이나 있는데, 매번 새로고침해서 골라야 하니까 귀찮아."
- **의도로 번역**: "메인 화면에 캐릭터 목록 카드를 만들어서 사용자가 클릭 한 번으로 선택할 수 있게 해줘."

**"기획자는 사용자의 투덜거림에서 보석 같은 요구사항을 캐내는 사람입니다."**

이렇게 정리된 요구사항을 우리는 다시 PRD에 업데이트할 겁니다. 04장에서 배웠던 '안 만들 것' 목록을 다시 꺼내 보는 것도 잊지 마세요. 갑자기 욕심이 생겨서 "여기에 결제도 넣고, 회원가입도 넣을까?" 싶겠지만, 일단은 지금 받은 불편함부터 해결하는 게 먼저입니다.

### [실습] PRD 수정하고 5분 만에 재배포하기

자, 이제 실제로 코드를 고쳐볼 시간입니다. 놀랍게도 여러분은 코드를 한 줄도 직접 고칠 필요가 없습니다. 설계도만 고치면 나머지는 코덱스가 다 알아서 할 거니까요.

#### 1단계: PRD.md 파일 업데이트하기

01 VS Code에서 프로젝트 폴더에 있는 `PRD.md` 파일을 엽니다. 
02 피드백받은 내용을 '핵심 기능'이나 '사용자 흐름'에 추가합니다.
03 파일을 저장(`Ctrl+S` 또는 `Cmd+S`)합니다.

## 핵심 기능 (업데이트)
1. 캐릭터 선택 카드 UI 추가 (메인 화면)
2. 모바일 반응형 디자인 강화 (큰 폰트, 큰 버튼)
3. 대화창 상단에 선택한 캐릭터 이름 표시

#### 2단계: 코덱스에게 다시 시키기

01 터미널에서 `codex`를 실행합니다.
02 코덱스에게 업데이트된 PRD를 보여주며 전체 코드를 다시 짜달라고 말합니다.

> "방금 PRD를 수정했어. 사용자 피드백을 반영해서 캐릭터 선택 기능을 추가하고 모바일에서 보기 편하게 고치고 싶어. 수정한 PRD 내용을 바탕으로 전체 코드를 다시 작성해줘."

**확인**: 코덱스가 파일을 하나하나 수정하기 시작할 겁니다. 수정이 끝나면 `npm run dev`를 입력해서 내 컴퓨터에서 먼저 확인해 보세요. 어때요? 친구가 말했던 불편함이 사라졌나요?

#### 3단계: 단 한 줄로 세상에 공개하기

이제 수정된 코드를 전 세계 사람들이 볼 수 있게 올릴 차례입니다. 아까 배웠던 '세 줄의 마법'을 기억하시죠? 터미널에 딱 세 줄만 입력하세요.

01 `git add .` (수정된 모든 파일을 장바구니에 담습니다.)
02 `git commit -m "캐릭터 선택 기능 추가 및 모바일 UI 개선"` (이름표를 붙입니다.)
03 `git push` (Vercel로 보냅니다.)

**"이게 끝입니다. 정말로요."**

이제 1~2분만 기다려 보세요. Vercel이 알아서 여러분의 새로운 코드를 빌드하고, 아까 친구에게 보냈던 그 링크의 내용을 최신 버전으로 바꿔버립니다. 친구에게 "지금 다시 들어가 봐!"라고 말해 보세요. 여러분의 서비스는 이제 한 단계 더 진화했습니다.

### MVP 고도화의 감각: 한 번에 하나씩

바이브코딩의 핵심은 완벽한 앱을 한 번에 만드는 게 아닙니다. **'만들고 -> 보여주고 -> 고치는' 루프를 얼마나 빠르게 돌리느냐**가 실력입니다.

제가 스터디를 운영하면서 본 가장 안타까운 분들은, 피드백을 10개 받았다고 해서 그걸 다 고치기 전까지는 절대 배포하지 않는 분들입니다. 그러면 결국 지쳐서 포기하게 돼요. 

**"한 번에 딱 한 가지 피드백만 반영하세요."**

글씨 크기가 작다는 말이 제일 많았나요? 그럼 그것만 고쳐서 바로 `git push` 하세요. 캐릭터 목록이 필요하다는 말이 다음인가요? 그럼 그다음 루프에서 그것만 고치세요. 이렇게 루프를 5번만 돌려보면, 여러분의 서비스는 어느새 전문가가 만든 것처럼 탄탄해져 있을 겁니다.

| 단계 | 행동 | 소요 시간 |
|---|---|---|
| 1회차 | 핵심 기능 구현 (MVP) | 30분 |
| 2회차 | 버그 수정 (글씨 깨짐 등) | 10분 |
| 3회차 | 디자인 개선 (색상, 배치) | 15분 |
| 4회차 | 편의 기능 추가 (캐릭터 선택) | 20분 |
| 5회차 | 문구 다듬기 (말투 수정) | 10분 |

이 루프를 한 번 돌 때마다 여러분의 서비스는 '진짜 쓸모'에 가까워집니다. 떡집 사장님의 주문 정리 앱도 처음엔 그냥 텍스트 박스 하나였지만, 이런 루프를 거치며 "주소 자동 완성", "주문 내역 엑셀 다운로드" 같은 강력한 기능이 붙게 되는 거죠.

### 결제가 필요하다면 — 부록 A 참고

이렇게 서비스를 다듬다 보면, 주변에서 "이거 돈 내고 쓰고 싶은데?"라는 반응이 나올 때가 있습니다. 혹은 "이 기능을 쓰려면 비용이 드는데, 사용자한테 돈을 좀 받아야 할 것 같아"라는 생각이 들 수도 있죠.

**"돈을 받는 순간, 서비스는 책임이 됩니다."**

하지만 너무 겁먹지 마세요. 요즘은 결제 연동도 AI와 함께라면 하루면 충분하거든요. 실제 카드로 결제하고 내 통장에 돈이 들어오는 과정은 조금 더 복잡한 설정이 필요하기 때문에, 이 부분은 **부록 A (PG 연동 실전)**에서 따로 자세히 다루겠습니다. 

지금 당장은 결제 버튼을 넣기보다, "이 서비스가 유료라면 얼마를 내실 용의가 있나요?"라고 물어보는 것만으로도 충분합니다. 그 가치가 증명되었을 때 부록을 펴보셔도 늦지 않습니다.
