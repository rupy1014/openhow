# 05장 의도를 다듬고 다시 만들기 — PRD와 피드백 루프

> "코드를 고치지 마세요. 의도를 고치세요."

---

앞 장에서 우리는 코덱스와 함께 캐릭터 채팅 서비스를 뚝딱 만들어봤습니다. 어떠셨나요? 생각보다 너무 쉬워서 놀라셨나요, 아니면 "내가 원하는 건 이게 아닌데..." 싶어 답답하셨나요?

아마 후자였을 가능성이 큽니다. 왜냐하면 우리는 아직 AI에게 '제대로' 명령을 내리는 법을 배우지 않았거든요. 마치 유능하지만 눈치가 전혀 없는 신입 사원에게 "그냥 알아서 잘해와"라고 말한 것과 비슷합니다. 이 신입 사원은 밤을 새워서 뭔가를 만들어 오긴 하겠지만, 여러분의 마음에 쏙 들 확률은 극히 낮죠.

이제부터는 그 신입 사원의 손을 잡고 "우리가 만들려는 건 바로 이거야"라고 명확하게 보여주는 법을 배울 겁니다. 바로 **PRD(기획서)**의 세계입니다.

---

## 05.1 [실습] MVP 기획서(PRD) 한 장 만들기

### 뭘 만들지 모르겠다면: "요즘 가장 귀찮은 일이 뭐예요?"

제가 오프라인 강의에서 수강생분들을 처음 만나면 항상 던지는 질문이 있습니다.

**"요즘 일하시면서 가장 귀찮거나 반복되는 일이 뭐예요?"**

코딩을 배우러 왔는데 웬 뚱딴지같은 소리냐고요? 아닙니다. 이게 바로 모든 위대한 프로젝트의 시작이거든요. 제가 만난 수강생분들의 사례를 한번 들어보세요.

- **떡집 사장님**: "매일 아침 쏟아지는 주문 문자를 엑셀에 옮겨 적는 게 너무 힘들어요. 누가 대신 정리 좀 안 해주나?"
- **목공예 작가님**: "나무 종류마다 관리법이 다른데, 손님들이 똑같은 질문을 매번 하세요. 밤낮없이 답변해 드리는 게 일입니다."
- **골프 장갑 제작자**: "해외 바이어들에게 영어로 메일을 보내야 하는데, 번역기 돌리고 다듬는 데만 한 시간이 걸려요."

어때요? 거창한 기술이 필요한 게 아닙니다. **"누가 대신 안 해주나" 싶은 바로 그 지점**이 여러분의 첫 번째 프로젝트가 되어야 합니다. 그래야 끝까지 만들 힘이 생기거든요.

<!-- IMG: 귀찮은 반복 업무(엑셀 입력, 반복 상담, 메일 번역)에 시달리던 사람들이 AI 조수를 만나고 웃는 모습의 삽화 -->

### PRD란: 코덱스에게 넘길 설계도, AI가 읽을 수 있는 기획서

코덱스에게 일을 시킬 때 가장 큰 실수는 "채팅 사이트 만들어줘"라고 한 줄로 퉁치는 겁니다. 코덱스는 천재적인 코딩 실력을 갖췄지만, 여러분이 떡집 사장님인지 골프 장갑 제작자인지는 모릅니다.

지배인인 여러분이 주방장인 코덱스에게 "아무거나 맛있는 거 해와"라고 하면, 주방장은 스테이크를 내올지 떡볶이를 내올지 몰라 당황할 수밖에 없습니다.

그래서 우리는 **PRD(Product Requirements Document, 기획서)**를 씁니다. 거창하게 들리지만, 실은 '코덱스에게 넘길 설계도'이자 'AI가 읽을 수 있는 기획서'일 뿐입니다.

### PRD 6가지 항목

코덱스가 헷갈리지 않게 딱 6가지만 정해주면 됩니다.

| 항목 | 설명 | 예시 (캐릭터 채팅) |
| :--- | :--- | :--- |
| **① 한 줄 요약** | 이 서비스의 정체성을 한 문장으로 정의 | 좋아하는 캐릭터와 몰입해서 대화하는 웹 채팅 서비스 |
| **② 대상 사용자** | 누가 이 서비스를 쓰나요? | 특정 캐릭터의 말투로 위로받고 싶은 팬들 |
| **③ 핵심 기능** | 반드시 있어야 하는 기능 딱 3가지 | 캐릭터 프로필 설정, 실시간 채팅, 캐릭터 말투 |
| **④ 안 만들 것** | **(가장 중요)** 이번에는 절대 안 할 일 | 로그인, 이미지 생성, 유료 결제, 회원가입 |
| **⑤ 사용자 흐름** | 사용자가 들어와서 나갈 때까지의 순서 | 캐릭터 선택 → 대화 시작 → 답장 확인 → 종료 |
| **⑥ 성공 기준** | 어떤 상태면 '완성'이라고 볼 수 있나요? | 설정한 말투로 AI가 답장하고, 대화가 화면에 잘 보임 |

**여기서 꿀팁! "안 만들 것"을 정하는 게 가장 중요합니다.** 처음에 욕심을 부려서 로그인이나 결제 기능을 넣으려고 하면, 코드가 복잡해지고 결국 완성하지 못할 확률이 90%입니다. 일단은 '한 입 크기'로 쪼개서 시작하는 게 비결입니다.

### [실습] 04장 캐릭터 채팅의 PRD를 코덱스에게 작성시키고, 직접 수정해보기

자, 이제 직접 해볼까요? 04장에서 만들었던 캐릭터 채팅을 제대로 된 PRD 기반으로 다시 설계해볼 겁니다. 여러분이 직접 다 쓸 필요 없습니다. 코덱스에게 초안을 잡으라고 시키면 되거든요.

01 VS Code를 열고 터미널에서 `codex`를 실행하세요. (이미 켜져 있다면 그대로 씁니다.)

02 코덱스에게 다음과 같이 첫 번째 지시를 내립니다.
> "내가 '캐릭터와 대화하는 채팅 서비스'를 만들려고 해. 바이브코딩을 위한 PRD 6항목을 형식에 맞춰서 작성해줘. 핵심 기능은 아주 심플하게 MVP(최소 기능 제품) 수준으로 잡아줘."

03 코덱스가 작성해준 PRD를 찬찬히 읽어보세요.

04 내용을 여러분의 입맛에 맞게 수정합니다. 예를 들어, "안 만들 것" 항목에 "디자인은 나중에 고칠 거니까 지금은 아주 단순하게만 해줘" 같은 내용을 추가해 보세요.

**확인**: PRD 초안이 나왔나요? 이제 여러분은 그냥 "채팅 사이트"가 아니라 "특정 목적과 규칙이 있는 제품"을 설계한 기획자가 된 겁니다.

---

### 결과 비교: PRD 없이 시킨 것 vs PRD 넘기고 시킨 것

자, 이제 이 PRD의 힘을 확인해 볼 시간입니다.

**❌ 케이스 A: PRD 없이 시켰을 때** ("채팅 사이트 만들어줘")
- 코덱스가 자기 마음대로 로그인을 넣거나, 너무 복잡한 기능을 넣으려다 에러가 납니다.
- 화면 디자인이 여러분의 취향과 전혀 딴판인 경우가 많습니다.
- 나중에 "이거 고쳐줘"라고 하면 전체가 꼬이기 시작합니다.

**✅ 케이스 B: PRD를 넘기고 시켰을 때** ("이 PRD 바탕으로 만들어줘")
- 코덱스가 '안 만들 것'을 알기 때문에 핵심 기능만 깔끔하게 구현합니다.
- 여러분이 정한 '사용자 흐름'을 따르기 때문에 처음부터 끝까지 막힘이 없습니다.
- 코드가 훨씬 간결해서 나중에 고치기도 쉽습니다.

**"설계도가 있으면 요리 속도가 5배는 빨라집니다."**

실제로 PRD를 복사해서 코덱스에게 "이 문서의 내용대로 폴더 구조를 잡고 코드를 작성해줘"라고 시켜보세요. 04장에서 한참 걸렸던 작업이 훨씬 정교하고 빠르게 끝나는 걸 경험하실 겁니다.

## 05.2 코드를 고치지 마, 의도를 고쳐

바이브코딩을 시작한 분들이 가장 먼저, 그리고 가장 깊게 빠지는 함정이 하나 있습니다. 바로 **코덱스가 짜준 코드를 직접 수정하려고 덤비는 것**입니다.

"어? 여기 글자 크기만 조금 키우면 될 것 같은데?", "이 버튼 색깔만 빨간색으로 바꾸면 끝날 것 같은데?"라는 생각이 드는 순간, 여러분은 마우스 커서를 코드 한복판으로 가져갑니다. 하지만 솔직히 말씀드릴게요. 그 순간부터 여러분의 프로젝트는 꼬이기 시작합니다.

### 코드를 직접 수정하면 왜 꼬이나

**첫째, 코덱스가 맥락을 잃어버립니다.**

코덱스는 여러분이 넘겨준 PRD와 이전 대화를 바탕으로 '전체적인 집의 구조'를 머릿속에 그리고 코드를 짭니다. 그런데 주인이 갑자기 나타나서 거실 벽을 허물고 창문을 새로 낸다고 해봅시다. 코덱스 입장에서는 "어? 내가 생각한 하중 설계랑 다른데?"라며 당황하기 시작합니다.

이 상태에서 다시 질문을 던지면 코덱스는 여러분이 고친 부분을 무시하거나, 본인이 짰던 원래 구조와 충돌하는 엉뚱한 코드를 내놓습니다. 이게 바로 **'코드 꼬임'**의 정체입니다.

**둘째, '누더기 코드'가 됩니다.**

전문 개발자들은 코드 한 줄을 고칠 때도 전체 시스템에 미칠 영향을 고려합니다. 하지만 우리는 어떤가요? 당장 눈에 보이는 글자 색깔, 버튼 위치만 고칩니다. 이렇게 땜질식으로 고쳐진 코드는 시간이 지날수록 앞뒤가 맞지 않는 '누더기'가 됩니다. 나중에 진짜 큰 기능을 추가하려고 할 때, 이 누더기 코드들이 발목을 잡습니다.

<!-- IMG: 코드 한 줄을 고치려다 전체 건물이 무너지는 것을 보고 당황하는 초보 기획자 삽화 -->

### 의도(PRD)를 먼저 다듬고, 코덱스에게 다시 시키는 게 더 빠름

코드가 마음에 안 든다면, 코드를 보지 말고 **여러분의 의도**를 다시 보세요. 코드는 결과물일 뿐입니다. 진짜 본체는 여러분의 머릿속에 있는, 그리고 PRD 문서에 적혀 있는 '의도'입니다.

AI와 협업할 때 가장 중요한 원칙은 **"결과물이 틀렸다면 지시 사항(Input)이 잘못된 것이다"**라고 가정하는 겁니다. 요리가 짜다면 요리사의 손을 붙잡고 나무랄 게 아니라, 레시피에 "소금 양을 절반으로 줄여줘"라고 적어주는 게 맞습니다.

### 나쁜 예시 vs 좋은 예시

| 상황 | ❌ 나쁜 예시 (코드를 고침) | ✅ 좋은 예시 (의도를 고침) |
| :--- | :--- | :--- |
| **디자인 수정** | "12번 줄 `font-size: 16px`를 `20px`로 바꿔줘." | "가독성이 떨어져. 본문 폰트를 시원하게 키워주고, 제목과 구분되게 해줘." |
| **기능 변경** | "alert 창 뜨는 코드를 삭제해줘." | "팝업이 번거로워. 화면 하단에 부드러운 알림이 나타나게 PRD를 수정할게." |
| **에러 발생** | "여기 `undefined` 뜨는 부분 봐줘." | "이름 없이 시작하면 에러가 나. '익명의 팬'으로 처리하도록 보완해줘." |

어때요? 차이가 느껴지시나요? 왼쪽은 코덱스를 단순한 '타자수'로 부려먹는 방식이고, 오른쪽은 코덱스를 '전문 개발 팀장'으로 대우하는 방식입니다. 팀장님에게는 상세한 코드 한 줄보다 명확한 **'목표와 의도'**를 전달하는 게 훨씬 효과적입니다.

## 05.3 [실습] 피드백으로 PRD 다듬고 다시 만들기

### 보여주기의 기술

**완벽주의는 바이브코딩의 최대 적입니다.**

"아직 디자인이 좀 허술한데...", "기능 하나만 더 넣고 보여줘야지." 이런 생각이 드는 순간, 여러분의 프로젝트는 멈추게 됩니다. 혼자서 끙끙대며 100점짜리 결과물을 만들려 하지 마세요. **60점짜리라도 좋으니 일단 누군가에게 보여주는 것.** 그것이 바이브코딩을 성공으로 이끄는 가장 빠른 지름길입니다.

사람들에게 여러분의 결과물을 보여줄 때, 절대로 하지 말아야 할 질문이 있습니다. 바로 **"이거 좋나요?"** 혹은 **"괜찮아요?"**입니다.

이런 질문을 받으면 사람들은 대개 예의상 "와, 좋네요!"라고 답합니다. 하지만 이런 칭찬은 여러분의 서비스를 발전시키는 데 아무런 도움이 되지 않습니다. 우리는 칭찬이 아니라 '데이터'가 필요하거든요.

진짜 피드백을 받고 싶다면 질문을 이렇게 바꿔보세요.

- **❌ 나쁜 질문**: "제가 만든 캐릭터 채팅인데, 어떤 것 같아요?"
- **✅ 좋은 질문**: "한번 써보시겠어요? 혹시 쓰다가 **어디서 멈추셨나요?**"

사용자가 버튼을 못 찾아서 머뭇거리거나, 대화가 끊겨서 당황하는 그 순간이 바로 우리가 고쳐야 할 '진짜 문제'입니다.

---

### [실습] 피드백 3개를 PRD에 반영 → 코덱스에게 다시 시키기 → 결과 비교

자, 이제 04장에서 만든 '캐릭터 채팅'을 친구나 가족에게 보여줬다고 가정해봅시다. 그리고 다음과 같은 3가지 피드백을 받았다고 해볼게요.

1. "글씨가 너무 작아서 읽기 힘들어요."
2. "캐릭터가 너무 로봇처럼 딱딱하게 말해요."
3. "내가 무슨 말을 했는지 기록이 안 남아서 아쉬워요."

이 피드백들을 어떻게 반영할까요? 코드를 한 줄씩 고치는 게 아니라, **PRD를 수정해서 코덱스에게 다시 시키는 과정**을 함께 해보겠습니다.

#### 1단계. PRD 업데이트하기

기존 PRD에 피드백 내용을 '의도' 중심으로 녹여냅니다.

<!-- IMG: 기존 PRD와 피드백이 반영된 수정 PRD를 나란히 비교하는 모습 -->

**수정된 PRD 항목 (예시)**

| 항목 | 수정 내용 (피드백 반영) |
| :--- | :--- |
| **③ 핵심 기능** | 캐릭터 프로필 설정, 실시간 채팅, **대화 내용 로컬 저장(새로고침해도 유지)** |
| **디자인 원칙** | **모바일에서도 읽기 편하도록 폰트 크기를 키우고**, 가독성 높은 폰트 사용 |
| **캐릭터 설정** | 단순 답변이 아니라, **최대한 감정적이고 친근한 캐릭터 특유 말투** 사용 |

#### 2단계. 코덱스에게 '의도' 전달하기

수정된 PRD 전체를 복사해서 코덱스에게 전달합니다. 이때 중요한 건 **"무엇이 변했는지"**를 명확히 알려주는 겁니다.

01 코덱스에게 선언하기:
> "기존 캐릭터 채팅 서비스를 업데이트하려고 해. 사용자 피드백을 받아서 PRD를 수정했어. 특히 **폰트 크기 확대**, **대화 내용 저장 기능 추가**, **말투 개선**이 핵심이야. 수정된 PRD를 보내줄 테니, 전체 코드를 다시 작성해줘."

02 수정된 PRD 전문을 붙여넣습니다.

#### 3단계. 결과 비교하기

코덱스가 새로 짜준 코드를 적용해보세요. 단순히 글자색 하나 바꾼 게 아니라, 서비스의 '바이브' 자체가 달라진 것을 느낄 수 있을 겁니다.

- **이전**: "안녕하세요. 무엇을 도와드릴까요?" (딱딱함)
- **이후**: "어이, 이제 왔어? 기다리고 있었다구! 오늘은 무슨 일이 있어?" (캐릭터 몰입도 상승)

**확인**: `localStorage` 같은 복잡한 기술 용어를 몰라도, "대화 내용을 저장해줘"라는 의도만 PRD에 적었을 뿐인데 코덱스가 알아서 관련 코드를 넣어줬나요? 이것이 바로 우리가 코드를 공부할 시간에 '의도'에 집중해야 하는 이유입니다.

### 핵심 루프: 만들기 → 보여주기 → 반응 관찰 → 의도 수정 → 다시 만들기

바이브코딩의 승패는 머리가 얼마나 좋으냐가 아니라, 이 **루프(Loop)**를 얼마나 많이, 빠르게 돌리느냐에 달려 있습니다.

1. **만들기(Build)**: 코덱스와 함께 PRD 기반으로 빠르게 MVP를 만듭니다.
2. **보여주기(Show)**: "부족한데..."라는 마음을 누르고 일단 남에게 보여줍니다.
3. **반응 관찰(Observe)**: 사용자가 어디서 헤매는지, 어떤 표정을 짓는지 관찰합니다.
4. **의도 수정(Refine)**: 관찰한 내용을 바탕으로 PRD를 수정합니다.
5. **다시 만들기(Re-build)**: 수정한 PRD를 코덱스에게 주고 전체를 다시 업데이트합니다.

**이 사이클을 많이 돌리는 게 승리입니다.** 5번만 돌려보세요. 여러분이 처음에 머릿속으로 상상했던 것보다 훨씬 더 근사하고 쓸모 있는 서비스가 눈앞에 나타날 겁니다.

> **🙋 질문이요! 매번 코드를 새로 짜달라고 하면 너무 오래 걸리지 않나요?**
>
> 맞습니다. 대화가 길어지면 코덱스도 예전 코드를 잊어버리거나 헷갈려 할 수 있죠. 그럴 땐 **`/compact`** 명령어를 입력해서 대화 내용을 압축하거나, 아예 새 대화창을 열고 최신 PRD만 딱 넣어서 "새로 만들어줘"라고 하는 게 가장 깔끔합니다.

> **Part 2 예고**: 스킬과 에이전트로 이 루프를 자동화하는 방법을 배우게 됩니다.

## 여기서 막혔나요?

**Q. PRD 6가지 항목을 다 채우기가 너무 힘들어요.**

**A.** 완벽할 필요 없습니다. 코덱스에게 "나 떡집 사장님인데, 이런 이런 게 귀찮아. 이걸 해결할 서비스 PRD 좀 대신 써줘"라고 하면 코덱스가 알아서 항목을 채워줍니다. 여러분은 그게 맞는지 틀린지만 검수하시면 됩니다.

**Q. 의도를 고쳐도 코덱스가 자꾸 똑같은 실수를 반복해요.**

**A.** 대화가 너무 길어지면 코덱스도 집중력이 떨어집니다. 이럴 땐 새 대화창을 열고(**`/clear`**), 수정한 최신 PRD를 다시 입력한 뒤 "처음부터 다시 만들어줘"라고 하는 게 훨씬 빠릅니다. 이전의 잘못된 기억을 지워주는 거죠.

**Q. 피드백을 받았는데, 제가 봐도 너무 구현하기 어려운 기능 같아요.**

**A.** 그럴 땐 당당하게 **'안 만들 것(Out of Scope)'** 목록에 넣으세요. 모든 피드백을 다 들어줄 필요는 없습니다. "그 기능은 나중에 더 큰 서비스가 되면 넣을게요"라고 말하는 것도 지휘자의 중요한 덕목입니다.

**Q. 사람들에게 보여주는 게 너무 부끄러워요.**

**A.** 저도 그랬습니다. 하지만 기억하세요. 사람들은 여러분의 코드 실력을 평가하려는 게 아니라, 여러분이 만든 '가치'를 보려 합니다. 떡집 사장님의 주문 정리 앱이 디자인이 구리다고 욕할 사람은 아무도 없습니다. 오히려 "우와, 이런 걸 직접 만드셨어요?"라며 눈을 반짝일걸요?

## 한 줄 정리

완벽한 코드를 짜려 하지 말고, **사용자의 피드백을 PRD에 담아 코덱스에게 전달하는 루프**를 무한 반복하세요. 그것이 바이브코딩의 전부입니다.

자, 이제 기획서를 쓰고, 피드백을 반영해 서비스를 다듬는 법까지 익히셨습니다. 이제 여러분의 서비스는 꽤 쓸만해졌을 거예요. 하지만 아직 이 서비스는 여러분의 컴퓨터 안에서만 잠자고 있습니다. 다음 장에서는 드디어 이 서비스를 전 세계 사람들에게 공개할 시간입니다! 여러분의 컴퓨터가 꺼져 있어도 24시간 내내 작동하는 '온라인 주소'를 만드는 법을 배워보겠습니다.
