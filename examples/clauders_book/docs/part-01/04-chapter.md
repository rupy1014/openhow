# 04장 첫 서비스 만들기 — AI 캐릭터 채팅

> "완벽하게 만들려고 시간 쓰지 말고, 일단 굴러가게만 만들어서 확인해라."

---

## 04.1 완성된 화면부터 보기 — 목적지를 먼저 보여주기

앞 장에서 우리는 프롬프트의 기술을 배웠습니다. 수직 슬라이싱, 한 입 크기로 쪼개기, 맥락 넘기기. 어떠셨나요? "오, 이렇게 시키면 AI가 진짜 알아듣는구나?" 싶으셨을 거예요.

이제는 그 기술을 들고 진짜 서비스를 만들러 갈 시간입니다. 단순히 텍스트 파일을 만지는 수준을 넘어, 우리가 매일 쓰는 '카카오톡'이나 '챗GPT' 같은 진짜 서비스를 만들어볼 겁니다.

솔직히 말씀드리면, 여기서부터 진짜 재미가 시작됩니다. 내가 상상한 캐릭터가 화면에 나타나고, 내가 정한 말투로 말을 걸어오는 순간의 짜릿함은 직접 겪어보지 않으면 모릅니다.

자, 복잡한 이론은 잠시 접어두고 일단 우리가 무엇을 만들지 눈으로 먼저 확인해 봅시다.

### 스크린샷: 우리가 만들 서비스의 완성 모습

우리가 여행을 갈 때 지도를 먼저 펼쳐보듯이, 코딩을 시작할 때도 '완성된 모습'을 머릿속에 그리는 게 가장 중요합니다. 그래야 길을 잃지 않거든요.

자, 아래 화면을 한번 보세요. 우리가 이번 장에서 함께 만들 'AI 캐릭터 채팅' 서비스의 완성된 모습입니다.

<!-- IMG: 깔끔한 디자인의 채팅 화면. 왼쪽에는 캐릭터 프로필 사진이 있고, 오른쪽에는 사용자와 대화한 말풍선이 정렬되어 있는 모습 -->

어때요? 생각보다 그럴싸하죠? 왼쪽에는 우리가 정한 캐릭터의 얼굴이 있고, 아래에는 메시지를 입력할 수 있는 창이 있습니다. 여러분이 "오늘 점심 뭐 먹을까?"라고 물어보면 AI가 대답을 해주는 식입니다.

하지만 평범한 챗GPT와는 조금 다릅니다. 이 AI는 여러분이 부여한 '성격'과 '말투'를 가지고 있거든요.

<!-- IMG: '피곤한 박 대리' 캐릭터가 "부장님 눈치 보느라 점심도 못 먹었습니다... 퇴근하고 싶네요."라고 답변하는 대화 장면 -->

이 캐릭터의 이름은 '박 대리'입니다. 항상 피곤에 찌들어 있고, 말투는 조금 까칠하지만 미워할 수 없는 직장인 컨셉이죠. 여러분이 질문을 던지면 박 대리는 그 컨셉에 맞춰서 대답합니다. 단순히 지식을 알려주는 기계가 아니라, 여러분이 상상한 개성을 가진 '디지털 생명체'를 만드는 셈입니다.

### 목표 선언: "이걸 지금부터 30분 안에 만든다"

**"이런 걸 제가 어떻게 만들어요? 개발자도 아닌데..."**

지금 이런 생각이 드셨다면 아주 정상입니다. 예전 같았으면 이런 채팅 서비스를 하나 만들려면 개발자 세 명이 붙어서 한 달은 꼬박 일해야 했습니다. 화면을 디자인하고, 서버를 구축하고, AI 모델을 연결하는 과정 하나하나가 거대한 산이었으니까요.

하지만 우리에게는 **코덱스(Codex)**라는 강력한 조수가 있습니다. 여러분이 할 일은 "채팅 화면 만들어줘", "박 대리 말투로 설정해줘"라고 명확하게 지시하는 것뿐입니다. 나머지는 코덱스가 알아서 코드를 짜고 파일을 만들어줄 겁니다.

제대로 된 방법만 알면, 이 화면을 띄우는 데 **딱 30분이면 충분합니다.** 거짓말 같으시죠? 이 장을 끝낼 때쯤이면 여러분의 컴퓨터에서 직접 대화하고 있는 박 대리를 만나게 되실 겁니다.

### 린스타트업의 핵심: 가장 빨리, 가장 싸게, 핵심만 검증하기

여기서 아주 중요한 개념 하나를 짚고 넘어가야 합니다. 바로 **'린 스타트업(Lean Startup)'**입니다. 실리콘밸리의 수많은 천재들이 입에 달고 사는 말인데요. 핵심은 간단합니다. **"완벽하게 만들려고 시간 쓰지 말고, 일단 굴러가게만 만들어서 확인해라"**는 겁니다.

우리가 서비스를 만드는 건 식당을 하나 차리는 것과 똑같습니다. 식당을 차릴 때 가장 먼저 확인해야 할 게 뭘까요? 인테리어가 예쁜지, 서빙 직원이 친절한지가 아닙니다. 바로 **"내 음식이 맛있는가?"**입니다.

- **나쁜 예시**: 인테리어에 1억 쓰고, 주방 기구 제일 비싼 거 사고, 메뉴판 50페이지 만들어서 1년 뒤에 오픈하기. (그러다 음식 맛없으면 망합니다.)
- **좋은 예시**: 일단 메뉴 하나만 개발해서 집 앞에서 팝업 스토어로 팔아보기. 손님들이 "오, 맛있는데?" 하면 그때 가게를 구하기.

우리 프로젝트도 마찬가지입니다. 우리의 핵심 가치는 "내가 만든 캐릭터와 대화하는 재미"입니다. 이 재미가 있는지 확인하는 데는 로그인 기능, 친구 초대 기능, 다크 모드 같은 건 전혀 필요 없습니다. 그런 부가적인 기능들을 붙이느라 일주일을 허비하는 게 바로 '망하는 지름길'입니다.

## 04.2 MVP란 — "안 만들 것"을 정하는 게 기획이다

### MVP(최소 기능 제품)의 뜻

**MVP(Minimum Viable Product, 최소 기능 제품)**란, 핵심 경험 하나만 돌아가면 시장에 내놓을 수 있는 제품을 뜻합니다.

유명한 기술 전문가 지아오나 장(Jiaona Zhang)은 이런 말을 했습니다.
> "탄 피자를 내놓고 사람들이 피자를 좋아하는지 테스트할 수는 없다."

최소한으로 만들되, 최소한 **'먹을 수는 있는 수준'**이어야 한다는 뜻입니다. 화면이 너무 깨져서 글자가 안 보이거나, 버튼을 눌러도 반응이 없다면 그건 제품이 아닙니다. 최소한 캐릭터의 말투가 생생하게 살아있고, 대화가 끊기지 않고 이어지는 '재미'는 보장되어야 하죠.

### 캐릭터 챗의 MVP 정의

우리가 30분 안에 완성할 '진짜 제품'의 범위를 정해봅시다. "이것 없으면 서비스가 아니다" 싶은 것만 남기는 겁니다.

**✅ 만들 것**

| 항목 | 이유 |
| :--- | :--- |
| **캐릭터 소개 화면** | 내가 누구와 대화하는지 보여주는 건 필수 경험입니다. |
| **대화 기능** | 대화가 오가는 모습이 눈에 보여야 하니까요. |
| **캐릭터 말투** | 이게 없으면 그냥 챗GPT랑 다를 게 없습니다. 이 서비스의 심장입니다. |

**❌ 안 만들 것**

| 항목 | 이유 |
| :--- | :--- |
| **로그인 / 회원가입** | 나 혼자 써보는데 로그인은 사치입니다. 복잡도만 3배 올라가요. |
| **친구 초대** | 당장은 나 혼자 써볼 거니까요. |
| **이미지 저장** | 캐릭터가 그림까지 그려주면 좋겠지만, 지금은 말부터 트게 합시다. |
| **다크모드** | 디자인은 나중에 생각해도 늦지 않습니다. |

**"무엇을 안 만들까"를 정하는 게 기획의 핵심입니다.**

### 흔한 실수: 완벽함은 바이브코딩의 적

제가 수강생분들을 지도해보면, 처음 시작할 때 욕심을 부리는 분들이 참 많습니다. "캐릭터 10명에, 결제도 넣고, 모바일 앱도 만들고 싶어요."

**자, 여기가 중요합니다.** 그렇게 생각하는 순간 프로젝트는 산으로 갑니다. 아니, 산으로 가기도 전에 입구에서 지쳐 쓰러집니다.

많은 분이 "기왕 만드는 거 남들한테 보여줘도 부끄럽지 않게..."라며 완벽을 기하려 합니다. 하지만 제가 장담하건대, **만들기 전에는 무엇이 중요한지 절대 모릅니다.** 머릿속으로는 "유료 결제 기능이 제일 중요해"라고 생각했지만, 막상 만들어보니 사람들이 "말투가 너무 기계 같아서 재미없어"라고 할 수도 있습니다. 그럼 결제 기능 만드느라 보낸 일주일은 그냥 버리는 시간이 됩니다.

차라리 30분 만에 대화 기능만 만들어서 친구에게 보여주세요. 그리고 "야, 이거 말투 대박인데?"라는 소리를 들으면 그때 기능을 하나씩 붙여가는 겁니다. **굴러가기만 하면 됩니다. 예쁜 건 나중에 생각하세요.**

## 04.3 [실습] 코덱스와 함께 만들기 — 시키고, 확인하고, 다시 시키기

자, 이제 식당 메뉴판은 다 짰습니다. 이제는 주방장인 코덱스에게 요리를 시킬 차례입니다. 그런데 여기서 아주 중요한 원칙이 하나 있습니다.

**"한 번에 다 시키면 AI는 반드시 딴짓을 합니다."**

주방장에게 "코스 요리 전부 다 해와!"라고 하면, 주방장은 당황해서 스테이크는 태우고 파스타는 덜 익혀올 겁니다. 코덱스도 똑같습니다. "채팅 서비스 다 만들어줘"라고 한마디만 던지면, 코덱스는 자기 마음대로 수백 줄의 복잡한 코드를 짜버립니다.

그래서 우리는 **'한 입 크기'**로 쪼개서 시킬 겁니다. 03장에서 배운 수직 슬라이싱을 실전에 적용하는 거죠. 에피타이저 하나 나오고 나면 맛을 보고, 그다음에 메인 요리를 시키는 식입니다. 지금부터 딱 4단계만 거쳐서 우리만의 '박 대리' 챗봇을 완성해 봅시다.

---

### STEP 1. "이 이미지랑 똑같은 채팅 화면 만들어줘" (화면)

가장 먼저 할 일은 우리 서비스의 '얼굴'인 화면을 만드는 겁니다. 복잡한 로직은 나중에 생각하세요. 일단 눈에 보이는 게 있어야 의욕이 생기거든요.

01 구글이나 핀터레스트에서 마음에 드는 채팅 화면 스크린샷을 하나 찾으세요. 혹은 제가 제공해 드린 샘플 이미지를 쓰셔도 좋습니다.

02 코덱스(VS Code의 터미널)를 열고 다음과 같이 말하세요.
> **"이 이미지랑 똑같은 레이아웃의 채팅 화면을 HTML과 CSS로 만들어줘. 아주 심플하게, 배경은 흰색이고 말풍선은 파란색이었으면 좋겠어."**

<!-- IMG: 코덱스가 첫 번째 명령어로 만들어낸 깨끗한 채팅 화면 레이아웃 -->

03 코덱스가 만든 `index.html` 파일을 브라우저로 열어보세요. (파일을 오른쪽 클릭해서 [브라우저에서 열기]를 누르면 됩니다.)

04 결과를 확인하고 커밋(세이브)합니다.

**확인**: 어때요? 아직 메시지가 오가지는 않지만, 그럴싸한 채팅창 모양이 떴나요? 만약 위치가 조금 이상하다면 "가운데 정렬이 안 됐어, 다시 해줘"라고 한마디만 더 하면 됩니다.

---

### STEP 2. "입력창 만들어줘" (기능)

화면이 나왔으니 이제 사용자가 글을 쓸 수 있게 만들어야 합니다. 지금은 글자를 쳐도 아무 일도 일어나지 않죠? 이제 '동작'을 넣어줄 시간입니다.

01 코덱스에게 아래와 같이 이어서 시킵니다.
> **"채팅 입력창에 메시지를 쓰고 Enter를 누르거나 [전송] 버튼을 누르면, 내가 쓴 글이 말풍선으로 화면에 뜨게 해줘."**

02 코덱스가 코드를 수정해주면 다시 브라우저를 새로고침(F5) 하세요.

03 입력창에 "안녕?"이라고 치고 전송을 눌러보세요.

04 잘 되면 커밋합니다.

**확인**: 내가 쓴 글이 오른쪽 말풍선에 예쁘게 올라오나요? 아직 AI의 답장은 없지만, 일단 내가 시킨 대로 '입력' 기능이 돌아가기 시작한 겁니다. 축하합니다! 여러분은 방금 서비스의 50%를 완성하신 거예요.

---

### STEP 3. "AI 응답 연결해줘" (핵심 가치)

이제 대망의 'AI 뇌'를 연결할 차례입니다. 이게 바로 우리 서비스의 핵심 가치죠. 캐릭터가 내 말을 알아듣고 대답하게 만드는 마법의 단계입니다.

01 코덱스에게 이렇게 주문하세요.
> **"이제 내가 메시지를 보내면 AI가 대답하게 하고 싶어. OpenRouter API(프로그램끼리 대화하는 규칙)를 연결해서 실제 AI 응답이 오게 해줘."**

> **🙋 질문이요! API 연결이 어렵진 않나요?**
> 걱정 마세요. 코덱스에게 "OpenRouter API를 연결해줘"라고 한마디만 하면, 코덱스가 알아서 코드를 짜줍니다. 여러분이 할 일은 API 키(열쇠)만 발급받아서 환경변수(.env, 비밀번호 보관 파일)에 넣어주는 것뿐입니다.

02 이제 다시 테스트해 보세요. 내가 말을 걸면 AI의 답장이 왼쪽 말풍선에 뜨나요?

03 잘 되면 커밋합니다.

**확인**: 답장이 잘 온다면 이제 구조는 완벽합니다.

---

### STEP 4. "캐릭터 성격 입혀줘: 박 대리" (톤)

자, 이제 이 서비스에 '바이브'를 불어넣을 차례입니다. 그냥 AI는 재미없잖아요? 우리가 기획했던 '항상 피곤한 박 대리'를 소환해 봅시다.

01 코덱스에게 캐릭터의 '페르소나'를 입력합니다.
> **"이제 AI의 성격을 설정할 거야. 이름은 '박 대리'고, 3년 차 직장인이야. 항상 피곤에 찌들어 있고, 퇴근하고 싶어 하는 말투를 써야 해. 반말로 짧게 대답해줘. 한 문장을 넘기지 마."**

<!-- IMG: 박 대리 캐릭터의 성격 설정(System Prompt)이 들어간 코드 영역 강조 -->

02 자, 이제 다시 말을 걸어보세요. "박 대리님, 오늘 야근하세요?"라고 물어볼까요?

03 "말도 마, 지금 집 가고 싶어 죽겠어..." 같은 찰진 대답이 오나요?

**확인**: 말투가 우리가 상상한 대로 나왔나요? 만약 너무 예의 바르게 대답한다면 "좀 더 건방지게 대답해줘"라고 피드백을 주면 됩니다.

### 피드백 루프 — 팀장이 일하는 법

방금 여러분이 하신 과정이 바로 **'피드백 루프'**입니다. 훌륭한 팀장은 신입 사원에게 일을 시키고 가만히 있지 않습니다. 중간중간 결과물을 보고 "이건 이렇게 고쳐줘", "저건 저렇게 바꿔줘"라고 계속 방향을 잡아주죠.

바이브코딩도 똑같습니다. 한 번에 완벽한 코드가 나오길 기대하지 마세요. 대신 다음과 같이 대화하며 다듬어 나가는 겁니다.

- **"너무 친절해, 까칠하게 대답해줘."**
- **"대답이 너무 길어, 한 문장으로 줄여줘."**
- **"퇴근하고 싶다는 뉘앙스를 좀 더 섞어줘."**

이렇게 3번 정도만 왔다 갔다 하면, 여러분의 머릿속에만 있던 그 캐릭터가 화면 밖으로 튀어나오게 됩니다. 이게 바로 코딩 한 줄 몰라도 서비스를 만드는 '바이브'의 힘입니다.

## 04.4 화면·서버·데이터·API — 식당 비유로 이해하기

자, 방금 박 대리랑 대화 한 판 해보셨나요? 신기하죠? 내가 시키는 대로 투덜거리는 AI 캐릭터를 보고 있으면 "진짜 세상 좋아졌구나" 싶으실 겁니다.

그런데 마음 한구석엔 이런 걱정이 슬슬 피어오를 거예요. **"코드가 이렇게 많은데, 내가 이걸 다 이해해야 하나?"**

솔직히 말씀드릴게요. **아니요, 다 몰라도 됩니다.**

우리는 요리사가 되려는 게 아니라, 멋진 식당을 경영하는 '지배인'이 되려는 거니까요. 지배인이 주방장만큼 칼질을 잘할 필요는 없습니다. 대신 식당이 어떻게 돌아가는지, 홀은 어디고 주방은 어디인지 그 '구조'만 알면 됩니다.

### 서비스 구조 = 식당

우리가 방금 만든 '박 대리 채팅 서비스'는 아주 작은 간이 식당과 같습니다. 이 식당은 크게 네 가지 요소로 구성되어 있어요.

**1. 화면(Frontend) = 홀**

가장 먼저 눈에 보이는 채팅창, 전송 버튼, 박 대리의 프로필 이미지... 이 모든 것은 식당의 **'홀'**입니다. 손님이 들어와서 앉고, 메뉴판을 보고, 음식을 기다리는 공간이죠.

**2. 서버(Backend) = 주방**

손님의 주문을 받아 음식을 실제로 만드는 곳입니다. 여러분이 메시지를 보내면 "이 캐릭터는 이런 말투로 대답해야 해"라고 판단하고 AI에게 물어보는 과정이 주방에서 일어납니다.

**3. 데이터(Database) = 식재료**

음식을 만들 때 필요한 재료들입니다. 캐릭터의 이름, 성격 설정, 이전 대화 내용 등이 여기에 저장됩니다.

**4. API(프로그램끼리 대화하는 규칙) = 주문서**

홀에서 주방으로 "여기 스테이크 하나요!"라고 전달하는 종이입니다. 화면에서 입력한 메시지를 서버로 보내주는 연결 통로죠. **"API는 주문서다."** 이것만 기억하세요.

우리가 OpenRouter API를 쓴다는 건, 우리 식당 주방에서 직접 요리하기 힘들어서 'AI 전문 요리소'라는 외부 업체에 주문서를 보내 요리를 떼오는 것과 같습니다.

<!-- IMG: 식당 비유 인포그래픽 — 홀(화면), 주방(서버), 식재료(데이터), 주문서(API)를 한눈에 보여주는 도식 -->

### 우리 역할 = 지배인, 코드는 주방장(코덱스)에게 맡기기

지금 우리가 만든 서비스는 주방장(코덱스)이 홀 서빙까지 다 해주는 작은 1인 식당입니다. 여러분은 식당 주인으로서 "오늘 메뉴는 딱 피자 하나야. 다른 건 주문받지 마!"라고 메뉴판만 잘 짜주면 됩니다.

많은 분이 바이브코딩을 시작하면서 "내가 이 코드를 한 줄 한 줄 다 짤 줄 알아야 하나?"라고 자책하십니다. 다시 한번 강조하지만, **절대 아닙니다.** 여러분은 주방장이 요리하는 과정을 지켜보면서 "어, 소금이 좀 짠데? 다시 해줘"라고 **피드백**만 주면 됩니다.

### 지금은 "이런 게 있구나" 정도면 충분

처음 식당을 차리는데 냉장고 온도를 몇 도로 맞춰야 하는지, 배수관 지름이 몇 센티미터인지부터 공부하면 지쳐서 오픈도 못 합니다. 지금 우리가 만든 박 대리 채팅방은 비록 작지만, 현대적인 웹 서비스가 갖춰야 할 모든 요소를 다 가지고 있습니다.

1. **눈에 보이는 화면**이 있고,
2. **사용자의 입력**을 받고,
3. **외부 AI 서버와 통신**해서,
4. **결과를 다시 화면에 보여주는**

이 거대한 순환 고리를 여러분은 단 30분 만에 완성하신 겁니다. "아, 코덱스가 짜준 그 복잡한 코드들이 사실은 홀 꾸미고 주문서 보내는 용도였구나!"라고 이해하셨다면 이번 섹션의 목표는 200% 달성입니다.

## 04.5 [실습] 에러가 나면 — 디버깅 기초

### 빨간 글씨가 떴다고 당황하지 말 것

솔직히 말씀드릴게요. 지금까지 실습을 하면서 에러 한 번도 안 나신 분은 거의 없을 겁니다. 화면이 하얗게만 나오거나, 코덱스가 짜준 코드가 돌아가지 않거나, "Unauthorized"라는 알 수 없는 영어가 뜨거나.

**에러는 AI도 사람도 피할 수 없는 일상입니다.** 전문 개발자들도 하루에 수십 번씩 에러를 만납니다. 중요한 건 에러가 '나느냐 안 나느냐'가 아니라, **'고칠 수 있느냐 없느냐'**입니다. 그리고 우리에게는 코덱스라는 유능한 수리공이 있으니까요. 고치면 되는 겁니다.

**에러 메시지는 AI가 읽을 수 있는 단서입니다.** 여러분이 읽을 필요 없어요. 코덱스에게 넘기면 됩니다.

---

### 에러 해결 3단계

에러가 나면 당황하지 말고 이 3단계만 따라하세요.

**① 에러 메시지 전체를 복사**

터미널이든, 브라우저든, 빨간 글씨가 뜨면 그 메시지를 전체 선택해서 복사합니다. 이게 코덱스에게 넘길 '진료 기록'입니다.

**② 코덱스에게 "이 에러 해결해줘" + 붙여넣기**

코덱스를 열고 이렇게 말하세요.
> **"이 에러가 나는데 고쳐줘."** 그리고 복사한 에러 메시지를 통째로 붙여넣으세요.

코덱스는 에러 메시지를 읽고, 원인을 파악하고, 코드를 수정해줄 겁니다.

**③ 코덱스가 고친 결과 확인**

수정이 끝나면 브라우저를 새로고침하거나 서버를 다시 실행해서 확인합니다. 에러가 사라졌으면 커밋하세요.

---

### "3번 규칙" — 같은 에러가 3번 반복되면 되돌리기

가끔 코덱스에게 에러를 넘겼는데, 고쳤다고 했는데 또 같은 에러가 나는 경우가 있습니다. 한 번, 두 번까지는 괜찮아요. 하지만 **같은 에러가 3번 반복되면, 그건 접근 방식 자체가 잘못된 겁니다.**

이럴 때는 코덱스에게 이렇게 말하세요.
> **"마지막 잘 됐을 때로 되돌려줘."**

코덱스가 git reset을 사용해서 코드를 이전 상태로 돌려줄 겁니다. 되돌린 후에는 프롬프트를 다시 써서 다른 방법으로 시도하세요. 같은 방법으로 세 번 실패했으면, 다른 길을 찾는 게 맞습니다.

---

### 브라우저 개발자 도구(F12) 맛보기

여기서 유용한 도구 하나를 살짝 알려드릴게요. 브라우저에서 `F12` 키를 눌러보세요. (맥에서는 `Cmd + Option + I`) 뭔가 복잡한 창이 아래에 뜰 겁니다. 이걸 '개발자 도구'라고 부릅니다.

여기서 **Console** 탭만 기억하세요.

- **빨간 글씨 = 에러**: 뭔가 잘못되었다는 뜻입니다. 이 메시지를 복사해서 코덱스에게 넘기면 됩니다.
- **노란 글씨 = 경고**: 당장 문제가 되진 않지만, "나중에 문제가 될 수도 있어"라는 알림입니다. 지금은 무시해도 괜찮습니다.

에러가 보이면 복사해서 코덱스에게 넘기세요. 지금은 "이런 게 있구나" 수준이면 충분합니다. 나중에 서비스가 복잡해지면 자연스럽게 익숙해질 거예요.

## 여기서 막혔나요?

**Q. 코덱스가 짜준 코드를 실행했는데 화면이 하얗게만 나와요.**

**A.** 당황하지 마세요! 브라우저에서 `F12`를 누르고 Console 탭을 확인해 보세요. 빨간색 글씨로 에러 메시지가 떠 있을 겁니다. 그 메시지를 그대로 복사해서 코덱스에게 던져주세요. **"화면이 안 나와. 콘솔에 이런 에러가 뜨는데 고쳐줘."**라고 하면 코덱스가 알아서 수술을 시작할 겁니다.

**Q. API 키를 넣었는데 "Unauthorized"라고 에러가 나요.**

**A.** 여러분의 API 키가 유효한지, 혹은 결제 수단이 등록되어 있는지 확인해 보세요. 가장 흔한 실수는 키 앞뒤에 공백이 들어가는 경우입니다. 메모장에 다시 복사해서 깔끔하게 넣어보세요.

**Q. "안 만들 것" 리스트를 적을 때 어디까지 적어야 할지 모르겠어요.**

**A.** "이거 없어도 오늘 내가 테스트해보는 데 지장 없나?"를 생각해보세요. "나중에 친구들한테 배포할 때 필요하지 않을까?" 싶은 건 전부 **'안 만들 것'** 리스트로 보내버리세요.

**Q. AI한테 "안 만들 것"을 말했는데도 자꾸 복잡한 코드를 짜줘요.**

**A.** 그럴 땐 더 단호하게 말씀하세요. "너 너무 똑똑하게 굴지 마. 나는 아주 초보적인 수준의 HTML과 CSS 파일 하나씩만 원해. 외부 라이브러리(React, Vue 등)는 절대 쓰지 마."라고요. AI는 때로 너무 유능해서 탈입니다. 우리가 고삐를 꽉 쥐어야 합니다.

## 한 줄 정리

**프롬프트에 30초 더 쓰면, 수정에 30분 줄어듭니다.** MVP를 한 입 크기로 쪼개서 시키고, 결과를 보고, 의도를 담아 다시 시키는 루프. 그것이 바이브코딩의 전부입니다.

자, 어떠신가요? 여러분의 컴퓨터에서 드디어 '말을 하는' 서비스가 돌아가기 시작했습니다. 비록 짧은 30분이었지만, 여러분은 기획부터 화면 구성, 기능 구현, 캐릭터 톤 설정, 그리고 에러 해결까지 서비스 개발의 전 과정을 경험하신 겁니다. 이제 이 튼튼한 뼈대 위에 살을 붙이는 건 시간문제입니다. 다음 장에서는 이 MVP를 바탕으로, 어떻게 하면 더 정교한 기획서(PRD)를 써서 AI를 더 잘 부릴 수 있는지 깊게 들어가 보겠습니다.
