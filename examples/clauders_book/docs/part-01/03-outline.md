# 03장 개요 — 바이브코딩 — "만들어줘"만으로는 안 되는 이유

## 장의 역할
02장에서 "만들어줘"로 성공했지만, 복잡한 것은 그렇게 안 된다는 현실을 보여주고, 바이브코딩의 올바른 프로세스를 가르친다.

## 독자가 읽고 남겨야 할 변화
- "만들어줘"만으로는 70%까지밖에 안 간다는 인식
- PRD(기획서) 한 장을 스스로 쓸 수 있는 능력
- 기술 선택 + 레퍼런스를 코덱스에게 넘기는 습관
- "만들고→보고→고치기" 루프에 대한 감각

## 핵심 메시지
- 바이브코딩 = 70/30 문제. 70%는 AI가 해주지만 나머지 30%가 결과를 결정
- 아이디어는 귀찮음에서 시작한다 — "이거 매번 수동으로 하기 귀찮아"
- PRD는 거창한 문서가 아니라 A4 한 장짜리 "뭘 만들지 메모"
- 기술 선택과 레퍼런스를 넘기면 코덱스의 정확도가 올라간다
- 한 번에 완성하려 하지 말고, 만들고→보고→고치기를 반복

## 소단원별 전개
### 03.1 바이브코딩이란 — 70/30 문제
바이브코딩의 정의. "만들어줘"로 70%는 되지만 나머지 30%에서 삽질. 그 30%를 줄이는 방법이 이 장의 내용.

### 03.2 아이디어는 귀찮음에서 시작한다
"매번 수동으로 하는 일"에서 아이디어를 뽑는 법. 거창한 기획이 아니라 "귀찮은 것 리스트."

### 03.3 [실습] MVP 기획서(PRD) 한 장 만들기
실제로 PRD를 써보는 실습. 제목/문제/해결/MVP범위/기술스택 5줄짜리.

### 03.4 MVP에서 진짜 중요한 한 가지 고르기
PRD에 적은 것 중에서 "진짜 이것만 있으면 쓸 수 있다"를 고르는 법. 나머지는 나중에.

### 03.5 [실습] 기술 선택과 레퍼런스 넘기기
"React로 만들어줘" 대신 "이 문서 참고해서 만들어줘" — 레퍼런스를 주면 정확도가 어떻게 달라지는지 실습.

### 03.6 만들고→보고→고치기 — 코덱스와 일하는 루프
완벽한 프롬프트를 쓰려 하지 말고, 일단 시키고 → 결과 보고 → 구체적으로 수정 요청. 이 루프가 바이브코딩의 핵심.

## 꼭 넣을 장면 / 사례 / 실습
- "만들어줘" 한 줄로 시킨 결과 vs PRD 넘기고 시킨 결과 비교
- PRD 실습 (독자가 자기 아이디어로 작성)
- 레퍼런스 URL 넘기기 전/후 비교
- 수정 요청 3라운드 예시
