> "혼자서 다 잘하는 AI보다, 역할이 나뉜 AI가 더 오래 갑니다."

"AI가 팀처럼 일한다"는 말, 한 번쯤 들어보셨을 겁니다. 그런데 이 말을 듣고 머릿속에 떠오르는 장면은 사람마다 다릅니다. 누군가는 로봇 여러 대가 줄지어 서 있는 공장을 떠올리고, 누군가는 채팅창 여러 개가 동시에 돌아가는 장면을 상상하죠.

사실 핵심은 훨씬 단순합니다. **역할을 나누고, 판단과 실행을 분리하고, 규칙과 기록을 남기는 것.** 우리가 Part 3에서 설치하고 만져본 OpenClaw 안에 이 구조가 이미 들어 있습니다. 이번 장에서는 그 구조를 하나씩 꺼내 보겠습니다.

## 12.1 역할을 나누면 왜 일이 빨라질까

회사에서 한 사람이 기획도 하고, 디자인도 하고, 개발도 하고, 고객 응대까지 하면 어떻게 될까요? 처음 며칠은 괜찮을 수 있습니다. 하지만 일주일만 지나면 맥락이 뒤섞이고, 실수가 늘고, 결국 번아웃이 찾아옵니다.

AI도 마찬가지입니다. 하나의 AI에게 모든 일을 몰아주면 금방 복잡해집니다. 대화가 길어지고, 톤이 섞이고, 어제의 임시 실험이 오늘의 공식 작업을 오염시킵니다. "내가 지금 무엇을 시키는지"조차 흐려질 때가 옵니다.

그래서 OpenClaw에는 **스킬**이라는 개념이 있습니다. 스킬은 "자주 쓰는 절차를 다시 쓰기 쉽게 적어 둔 규칙 파일"에 가깝습니다. 예를 들어 아침 브리프, 회의 준비, 하루 마감 정리처럼 이미 잘 되던 프롬프트가 있다면, 그 형식만 스킬로 묶으면 됩니다.

![스킬 목록을 팀 조직도처럼 보기](/__content__/images/ch12-01.png)

팀 조직도를 떠올려 보세요. 대표가 있고, 그 아래 기획팀, 개발팀, 운영팀이 있죠. OpenClaw의 스킬 구조도 비슷합니다. 메인 OpenClaw는 조정자 역할을 맡고, 각 스킬은 전문 영역을 담당합니다. 웹 탐색 스킬은 자료를 읽고, 요약 스킬은 긴 텍스트를 줄이고, 메신저 연결 스킬은 그 결과를 여러분이 늘 보는 곳으로 가져옵니다.

실제로 터미널에서 `openclaw skills list`를 입력하면 지금 설치된 스킬 목록이 쭉 나옵니다. 새 기능을 설치하는 명령이 아니라, 먼저 무엇이 이미 있는지 확인하는 조회 명령입니다. 처음에는 기본 번들 스킬과 외부 스킬 한두 개 정도면 충분합니다. 중요한 것은 스킬 수가 아니라, 내가 반복하는 절차가 파일로 분리되어 다음 주에도 같은 품질로 돌아오는지입니다.

한 가지 실제 사례를 들어보겠습니다. 1인 사업자 A씨는 매일 아침 경쟁사 소식을 검색하고, 요약해서, 텔레그램으로 보내는 일을 했습니다. 처음에는 하나의 대화창에서 전부 처리했죠. 그런데 일주일쯤 지나자 대화가 너무 길어져서 이전 요약과 오늘 요약이 섞이기 시작했습니다. 역할을 나눈 뒤로는 달라졌습니다. 수집 담당 스킬이 기사를 모으고, 요약 담당 스킬이 정리하고, 메신저 스킬이 발송합니다. 각자 맡은 일만 하니까 결과가 훨씬 깔끔해졌습니다.

## 12.2 누가 판단하고 누가 실행할까

역할을 나눴으면 다음 질문이 자연스럽게 따라옵니다. **"그래서 누가 결정하고, 누가 실행하나요?"**

회사에 비유하면 쉽습니다. 보드(이사회)가 방향을 정하고, CEO가 전략을 세우고, 팀원이 실행합니다. OpenClaw에서도 이 구조가 그대로 적용됩니다.

| 역할 | 회사에서는 | OpenClaw에서는 |
|------|----------|-------------|
| 방향 결정 | 보드(이사회) | **사용자(여러분)** |
| 전략 수립 | CEO | **메인 OpenClaw** |
| 전문 실행 | 팀원 | **스킬 / 하위 OpenClaw** |

여러분이 "매일 아침 7시에 뉴스 브리프를 만들어줘"라고 지시하면, 메인 OpenClaw가 그 일을 더 작은 단위로 쪼갭니다. 기사 수집, 중복 제거, 요약, 발송. 각 단계를 적절한 스킬에 배정하고, 진행 상태를 지켜봅니다. 문제가 생기면 위로 올립니다.

핵심은 이겁니다. **메인 OpenClaw는 직접 다 처리하는 작업자가 아니라 조정자에 가깝습니다.** 사용자의 요청을 받고, 어떤 역할에 넘길지 정하고, 다시 결과를 모아 마지막 답을 만듭니다. 전문 역할은 자기 일만 맡는 식이죠. 코딩 담당은 코드와 검토만, 조사 담당은 브리프와 비교표만, 콘텐츠 담당은 초안과 재가공만 맡습니다.

이런 분리가 왜 중요할까요? 준비 담당과 실행 담당만 갈라져도 안정성이 크게 올라가기 때문입니다. 하나는 자료를 모으고 조건을 정리하고, 다른 하나는 실제 실행과 초안을 맡습니다. 깊게 도는 일을 한곳에 몰아두지 않는 것이 핵심입니다.

![판단과 실행의 분리](/__content__/images/ch12-02.png)

전문 역할에 꼭 강한 모델이 필요한 것도 아닙니다. 메인 조정자만 무거운 모델을 쓰고, 조사나 요약처럼 형식이 분명한 역할은 더 저렴한 모델로 돌리는 편이 전체 비용과 안정성 모두에 유리합니다.

## 12.3 승인과 기록은 왜 필요할까

여기까지 읽으셨다면 이런 생각이 드실 겁니다. "역할도 나누고 실행도 자동으로 되면, 그냥 다 맡겨도 되는 거 아닌가요?"

솔직히 말씀드리면, 그렇게 했다가 낭패를 본 사례가 적지 않습니다.

예를 들어 AI에게 고객 응대 메일을 완전 자동으로 보내게 설정했다고 합시다. 처음 이틀은 잘 돌아갑니다. 그런데 셋째 날, AI가 환불 정책을 잘못 해석해서 "무조건 환불 가능합니다"라는 답변을 수십 통 보냅니다. 사람이 중간에 한 번만 확인했더라면 막을 수 있는 사고입니다. 이런 유형의 문제는 자동화를 도입하는 팀에서 흔히 겪는 일입니다.

이래서 **승인**이 필요합니다. OpenClaw에서 승인은 속도를 늦추는 장치가 아니라, 사고를 줄이는 장치입니다. 회사로 치면 매니저가 결재 도장을 찍는 것과 같습니다. AI가 새 직원을 뽑겠다고 하면(새 에이전트 추가), 전략을 바꾸겠다고 하면(워크플로우 변경), 예산을 초과하겠다고 하면 — 사람이 한 번 확인합니다.

그리고 **standing orders**가 있습니다. 이건 "팀 정책"에 해당합니다. "이런 건 항상 이렇게 해"라는 규칙을 미리 적어두는 겁니다.

예를 들어 이런 식입니다.

- "이 표현은 쓰지 말기"
- "브리프는 표보다 글머리표로"
- "회의 전 질문은 다섯 개 이하"
- "외부 발행 전에 반드시 사람 확인"

그리고 **보안 규칙**도 standing orders에 넣어야 합니다. 9장에서 설정한 보안 원칙들을 기억하시죠? 그 원칙들을 팀 정책으로 명문화하는 겁니다.

- "API 키를 코드나 메시지에 절대 노출하지 말 것"
- "외부 서비스에 데이터를 보내기 전에 개인정보가 포함됐는지 확인할 것"
- "새로운 MCP 스킬을 설치할 때는 반드시 출처를 검증할 것"
- "파일 접근은 프로젝트 디렉터리 안으로만 제한할 것"

보안 전문가들은 AI 에이전트를 **"외부 계약자"**와 같다고 말합니다. 유능하지만, 우리 조직의 모든 것을 알 필요는 없습니다. 최소한의 접근 권한만 주고, 중요한 결정에는 사람의 확인을 거치게 하는 것 — 이게 보안 업계에서 말하는 "최소 권한 원칙"이고, standing orders로 쉽게 구현할 수 있습니다.

이런 규칙이 열 개 이하라면 설정 파일 한 곳에 모아두면 됩니다. 에이전트가 매번 사과하고 같은 실수를 반복하는 대신, 규칙 파일을 한 번 보고 처음부터 맞게 실행합니다. 좋은 운영은 교정을 많이 하는 운영이 아니라, 반복 교정을 점점 구조로 옮기는 운영입니다.

:::tip 직접 써보기
Claude Code를 열고 이렇게 시켜보세요.

```
OpenClaw의 standing orders 파일을 만들어줘.
아래 규칙 3개를 넣어줘:
1. 외부 발행 전에 반드시 사람 확인
2. API 키를 메시지에 노출하지 말 것
3. 보고서는 항상 글머리표 형식으로
```

파일이 만들어지면 한번 열어보세요. "아, 이렇게 규칙을 적어두면 되는 거구나"라는 감각이 잡힐 겁니다. 규칙은 나중에 얼마든지 추가하거나 수정할 수 있습니다.
:::

![Standing Orders — 팀 정책 설정](/__content__/images/ch12-03.png)

그다음은 **하트비트**입니다. 하트비트는 "정기 점검"에 해당합니다. OpenClaw의 AI는 계속 떠 있지 않습니다. 필요할 때 깨어났다, 잠깐 일하고, 다시 잠드는 구조입니다. 이 한 번의 깨어남이 하트비트입니다.

하트비트는 긴 문서를 쓰는 기능보다 짧은 확인에 더 잘 맞습니다. 오늘 일정 확인, 미응답 메시지 확인, 밤새 끝난 작업 요약처럼 짧게 끝나는 점검이 딱 맞죠. 반대로 긴 조사나 긴 초안 작성은 예약 실행이나 별도 작업으로 뺍니다.

하트비트와 cron을 섞어 쓰면 구조가 더 깔끔해집니다. cron은 정해진 시각에 깨우고, 하트비트는 그 이후에 짧은 상태 확인을 맡습니다. 즉 정시 실행은 cron, 계속 짧게 확인은 하트비트라고 보면 됩니다.

```
openclaw cron add \
  --name "Ops sweep" \
  --cron "0 6 * * *" \
  --message "점검 실행: 상태 요약만 남겨줘"
```

이 예시는 매일 아침 6시에 별도 세션으로 점검을 돌리고, 문제가 있으면 요약만 남기는 방식입니다. 사람이 직접 브라우저를 돌며 확인하는 번거로움 대신, 정해진 형식으로 줄이는 자동 점검과 잘 맞습니다.

마지막으로 **기록**입니다. 기록이 왜 중요할까요? 기록이 없으면 개선이 불가능하기 때문입니다. 운영이 길어질수록 교정은 사실상 개선 루프가 됩니다. 일일 작업 기록을 남기고, 무엇이 잘됐고 무엇이 틀렸는지 짧게 적고, 반복되는 실수는 규칙으로 올리고, 잘 굳어진 절차는 스킬로 바꾸면 됩니다. 이 루프가 자리 잡으면 OpenClaw는 한 번 쓰고 마는 도구보다 같이 자라는 도구에 가까워집니다.

## 12.4 사람은 왜 끝까지 남을까

여기까지 읽으시면서 혹시 이런 기대가 생기셨나요? "이 정도면 다 자동화할 수 있는 거 아닌가?"

솔직히 말씀드리겠습니다. 아닙니다.

11장에서도 다뤘지만, AI 자동화에는 분명한 경계가 있습니다. 스킬이 아무리 잘 나뉘어 있어도, 하트비트가 아무리 부지런히 돌아도, **"이 방향이 맞는가"를 판단하는 건 결국 사람의 몫**입니다.

AI는 주어진 규칙 안에서 빠르고 정확하게 실행합니다. 하지만 규칙 자체를 만들고, 상황이 바뀌었을 때 규칙을 고치고, "이번엔 예외를 둬야 한다"고 결정하는 건 사람만 할 수 있습니다. 승인 흐름이 존재하는 이유도 바로 이것입니다. 속도를 위해 사람을 빼는 게 아니라, 사고를 줄이기 위해 사람을 남기는 겁니다.

OpenClaw의 구조를 다시 정리해 보겠습니다.

| 구조 | 팀에서는 | 하는 일 |
|------|---------|--------|
| 스킬 | 팀원의 전문 영역 | 반복 절차를 규칙 파일로 분리 |
| Standing Orders | 팀 정책 | "이런 건 항상 이렇게 해" (보안 규칙 포함) |
| 하트비트 | 정기 점검 | 짧은 상태 확인, 깨어났다 잠드는 주기 |
| Cron | 스케줄러 | 정해진 시각에 자동 실행 |
| 승인 | 매니저 결재 | 중요한 결정에 사람 확인 |
| 보안 | 출입 관리 | API 키 보호, 접근 범위 제한, 최소 권한 |
| 기록 | 업무 일지 | 개선 루프의 재료 |

이 일곱 가지가 "AI가 팀처럼 일한다"는 말의 실체입니다. 마법이 아니라 구조입니다. 그리고 이 구조의 꼭대기에는 언제나 사람이 있습니다.

자, 이제 준비가 됐습니다. Part 3에서 우리는 OpenClaw를 설치하고, 구조를 읽고, 한계를 확인하고, 팀 운영의 뼈대를 이해했습니다. Part 4에서는 이 구조 위에 진짜 자동화를 얹습니다. 매일 아침 뉴스 보고가 텔레그램으로 도착하고, "이것도 발행해줘" 한마디면 SNS에 올라가는 경험. 그 이야기를 바로 다음 장에서 시작합니다.

## 실무에 어떻게 쓸까?

**1인 사업자라면** — 메인 OpenClaw가 전체 방향을 잡고, 수집 스킬과 요약 스킬로 아침 브리프를 만들고, cron으로 매일 같은 시각에 돌리세요. 승인은 외부 발행 직전에만 걸면 됩니다.

**팀에서 쓴다면** — standing orders에 팀 규칙을 적어두세요. "보고서 형식은 항상 이렇게", "고객 응대 톤은 이 범위 안에서"처럼요. 사수-부사수 같은 리뷰 구조도 만들 수 있습니다. 실무 담당 OpenClaw가 초안을 만들고, 리뷰 담당 OpenClaw가 그 결과를 한 번 더 읽고 수정 방향만 남기는 식입니다.

**개발자라면** — 여러 하위 OpenClaw를 둘 때 기록과 규칙의 가치를 체감하게 됩니다. 어디에 기록을 남기는지, 누구에게 먼저 보고하는지, 어떤 채널에서는 침묵하고 어떤 채널에서만 답하는지. 이런 협업 규칙을 문서로 적어 두면 덜 흔들립니다.

## 한 줄 정리

AI가 팀처럼 일한다는 건 마법이 아니라 구조입니다. 역할을 나누고, 판단과 실행을 분리하고, 승인과 기록을 남기는 것 — 그리고 그 꼭대기에 사람이 남는 것, 그게 전부입니다.
