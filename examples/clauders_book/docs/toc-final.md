# 바로바로 코덱스 + 오픈클로 에이전트 자동화 

> 독자 여정: 설치하고 만든다(Part 1) → omx로 자동화를 체험한다(Part 2) → 에이전트에게 맡긴다(Part 3) → 세상에 내보낸다(Part 4)
> 감정선: "오 되네!" → "$write 했더니 글이 나왔어!" → "자고 일어나니 뉴스가 와 있네" → "세상에 나갔다!"
> 원칙: 먼저 써보고, 결과를 보고, 그다음에 "왜"를 이해한다 (snackable concepts)

## Part 1. 코덱스로 바이브코딩 시작하기

[01장] 한 줄 설치, 바로 실습

01.1 코덱스란 무엇인가
  - ChatGPT vs 코덱스
    - ChatGPT: "이거 어떻게 해?" → 브라우저에서 답변을 생성
    - 코덱스: "이거 해줘" → 내 컴퓨터에서 파일을 직접 만들고 고침
    - 핵심 차이: 질문하면 답변 vs 시키면 실행
  - GUI vs CLI
    - GUI(브라우저): 보고 클릭하는 방식, 사람이 쓰기 좋은 화면
    - CLI(터미널): 말하고 실행하는 방식, AI가 일하기 좋은 작업대
    - 이 책에서 CLI를 쓰는 이유: 프로젝트 전체를 읽고→만들고→수정하고→실행하는 흐름을 이어서 할 수 있음
  - 한눈에 비교표
    - ChatGPT = 대화형 도우미 (설명, 아이디어, 초안)
    - Codex = 실행형 비서 (만들기, 수정하기, 반복 작업)
01.2 [실습] 터미널 열고 한 줄로 설치하기
  - 터미널 열기
    - Windows: PowerShell 검색 → 관리자 권한으로 실행
    - Mac: Command+Space → Terminal 입력
  - 한 줄 설치 스크립트
    - 스크립트 한 줄 복사 → 터미널에 붙여넣기 → Enter
    - Node.js 포함 필요한 것이 자동으로 설치됨
    - 설치 확인: 새 터미널에서 `codex --version` 실행 → 버전 번호 나오면 성공
  - 요금제 안내
    - ChatGPT 계정으로 로그인하면 바로 시작 (별도 API 키 발급 불필요)
    - Free: 비추 (한시적 프로모션, 사용량 제한 심함)
    - Plus (월 $20, 약 2.9만 원): 이 책 기준, 실습 전부 가능
    - Pro (월 $200): 잘 활용하게 되면 올리기
01.3 VS Code 설치하고 둘러보기
  - VS Code 설치
    - code.visualstudio.com 접속 → Download → 설치 (다음, 다음, 완료)
  - 알아야 할 세 곳
    - 왼쪽 Explorer: 파일·폴더를 보는 곳 (윈도우 탐색기와 비슷)
    - 가운데 에디터: 파일 내용을 보고 수정하는 곳
    - 오른쪽 Copilot: ❌ 닫기 — 우리는 코덱스를 쓸 것
  - VS Code 안에서 터미널 열기
    - 상단 메뉴 "터미널 → 새 터미널" 또는 Ctrl+`
    - 화면 아래에 뜨는 검은 창이 터미널
    - 터미널이 뜬다고 코덱스가 켜진 게 아님 — `codex` 직접 입력 필요
01.4 `codex`와 `dscodex` — 묻고 실행 vs 바로 실행
  - `codex` (기본)
    - 파일 수정 전마다 "이거 해도 될까요?" 확인
    - 처음 배울 때 안전한 모드
  - `dscodex` (자동 승인)
    - 확인 없이 바로 실행 → 속도 빠름
    - 원래 명령어 `codex --dangerously-bypass-approvals-and-sandbox`의 줄임말
    - 익숙해진 뒤 추천
  - 안전 범위
    - 지정한 폴더 안에서만 작동
    - 인터넷 결제, 메일 발송 같은 건 하지 않음
01.5 프로젝트란 — 폴더 하나가 프로젝트
  - 프로젝트 = 폴더 하나
    - 폴더 안에 파일이 쌓여서 결과물(홈페이지, 앱, 자동화 도구)이 됨
    - 코덱스는 현재 폴더 안의 파일만 보고 고침 → 폴더 = AI의 작업 범위
  - AGENTS.md 맛보기
    - "이 프로젝트는 이런 프로젝트야"라고 코덱스에게 알려주는 파일
    - 07장에서 상세히 다룸
01.6 [실습] 코덱스에게 첫 번째 일 시키기
  - 프로젝트 만들기
    - 바탕화면에 `my-first-project` 폴더 만들기
    - VS Code에서 파일 → 폴더 열기 → 해당 폴더 선택
  - 파일 만들기
    - "자기소개.md 파일을 만들어줘. 이름은 홍길동, 직업은 떡집 사장님, 취미는 등산이야"
    - "오늘할일.md 파일을 만들어줘. 체크리스트로" → Explorer에 파일 두 개 생김
  - 파일 수정하기
    - "자기소개.md에 좋아하는 음식: 김치찌개를 추가해줘" → 파일 내용이 바뀜
  - 핵심 정리
    - 만들기, 수정하기 — 이 두 가지가 앞으로 할 일의 전부
    - 코드를 직접 짜는 게 아니라 의도를 전달하고 결과를 판단하는 사람이 되는 것

[02장] AI 캐릭터 채팅 — 30분 만에 서비스 만들기

02.1 완성된 화면부터 보기 — MVP 이미지 두 장
  - 스크린샷 1: 채팅창 인터페이스와 캐릭터 프로필
  - 스크린샷 2: 캐릭터가 설정된 말투로 대답하는 대화 장면
  - 목표 선언
    - "이걸 지금부터 30분 안에 만든다"
    - 예전 방식이면 며칠 밤샘, 지금은 30분
02.2 [실습] 이미지 주고 화면 만들기
  - 이미지 업로드
    - 완성 화면 스크린샷(또는 손그림 스케치)을 코덱스 채팅창에 올리기
    - 지시: "이 이미지랑 똑같은 채팅 화면을 만들어줘. HTML과 CSS로. 아직 기능은 빼고 화면만"
  - 결과 확인
    - 코덱스가 코드를 쫘르륵 생성 → 브라우저에서 열어보기
    - 완성 화면과 비교하기
  - 피드백 루프
    - "버튼이 너무 작아" → 고쳐줌
    - "배경색 좀 더 연하게" → 고쳐줌
    - 마음에 들 때까지 고치라고 시키기 — 우리는 팀장이니까
02.3 화면·서버·데이터·API — 식당 비유로 이해하기
  - 서비스 구조 = 식당
    - 화면(프론트엔드) = 홀: 손님이 메뉴 보고 주문하는 공간
    - 서버(백엔드) = 주방: AI에게 대답을 요청하고 받아오는 곳, 눈에 안 보임
    - 데이터(DB) = 식재료: 캐릭터 설정, 대화 내역이 저장되는 창고
    - API = 주문서: 홀과 주방 사이를 오가는 통로
  - 전체 흐름
    - 채팅 입력 → API(주문서) → 서버(주방) → AI → 서버 → 화면(홀)
    - 우리 역할 = 지배인, 세부 코드는 주방장(코덱스)에게 맡기기
02.4 [실습] 캐릭터에 성격 입히기 — 고치고 다시 시키기
  - 캐릭터 설정 지시
    - 예시: "이름은 박 대리, 30대 직장인, 항상 피곤, 반말 섞어서, 두 문장 이내"
    - 구체적으로 정해줄수록 캐릭터가 살아남 → 프롬프트 엔지니어링의 시작
  - 톤 수정 루프 (3회)
    - 피드백 1: "박 대리가 너무 친절해. 좀 더 까칠하게 해줘"
    - 피드백 2: "말투는 좋은데 대답이 너무 길어. 무조건 한 문장으로 줄여"
    - 피드백 3: "말 끝마다 '퇴근하고 싶다'는 말을 랜덤하게 섞어줘"
    - 3번이면 내가 상상한 캐릭터가 나옴 — 이게 팀장이 일하는 법
  - [완성 코드 GitHub 링크 제공]
02.5 MVP는 어디까지인가
  - 성공 기준 3가지
    - 캐릭터 소개가 화면에 나온다 ✓
    - 내가 말을 걸면 대답이 온다 ✓
    - 캐릭터 말투가 살아있다 ✓
  - 안 만들 것 리스트
    - 로그인, 친구초대, 이미지 저장, 다크모드 — 전부 나중에
    - "무엇을 안 만들까"를 정하는 게 기획의 핵심
  - 핵심 경험이 완성되었으면 시장에 내놓을 수 있는 제품

[03장] 바이브코딩 — "만들어줘"만으로는 안 되는 이유

03.1 AI에게 일을 잘 시키는 두 가지
  - 첫째: '안 만들 것'부터 말하기
    - "로그인은 나중에 빼줘"
    - "데이터베이스 없이 메모리에만 저장되게 해줘"
    - "디자인은 예쁘지 않아도 되니까 기능만 돌아가게 해줘"
    - 범위를 좁혀줘야 AI가 가볍고 정확한 코드를 냄
  - 둘째: '한 입 크기'로 쪼개서 시키기
    - 한 번에 전체를 시키면 수백 줄이 쏟아져서 검토 불가
    - 적당한 크기 = "내가 10분 안에 확인 가능한 크기"
    - 수직 슬라이싱: 빵을 층별로 따로 만드는 게 아니라, 맛볼 수 있게 한 조각씩 자르기
  - 02장 복기
    - ① "화면에 '안녕'이라고만 뜨게 해줘" → ② "입력창 만들어줘" → ③ "버튼 누르면 위에 나오게" → ④ "AI 응답 연결해줘"
    - 한 단계씩 10분마다 확인하며 나아가는 게 바이브코딩
03.2 아이디어는 귀찮음에서 시작한다
  - "요즘 가장 귀찮은 일이 뭐예요?"
    - 거창한 아이디어보다 내 불편함이 먼저
  - 실제 수강생 사례
    - 떡집 사장: 주문 문자를 장부에 옮겨 적는 게 일 → 문자 넣으면 자동 정리해주는 도구
    - 목공예 작가: 나무 종류별 특징 반복 질문 → 나무 사진 올리면 알려주는 챗봇
    - 골프장갑 제작자: 해외 바이어 메일 번역이 고역 → 제품 정보가 입력된 비즈니스 메일 비서
  - 자동화 후보 찾기
    - 엑셀에서 반복하는 일, 매번 같은 질문에 답변하는 일
    - "누가 대신 안 해주나" 싶은 지점이 첫 프로젝트
03.3 [실습] MVP 기획서(PRD) 한 장 만들기
  - PRD란
    - 코덱스에게 넘길 설계도, AI가 읽을 수 있는 기획서
  - PRD 6가지 항목
    - ① 한줄 요약
    - ② 대상 사용자
    - ③ 핵심 기능
    - ④ 안 만들 것
    - ⑤ 사용자 흐름
    - ⑥ 성공 기준
  - [실습] 02장 캐릭터 채팅의 PRD를 코덱스에게 작성시키고, 직접 수정해보기
  - 결과 비교: PRD 없이 시킨 것 vs PRD 넘기고 시킨 것
03.4 작게 시작해야 끝까지 간다
  - 흔한 실수
    - "캐릭터 10명, 유료 결제, 모바일 앱" 한꺼번에 잡기 → 99% 포기
    - 구현해야 할 게 너무 많으면 바이브가 안 살고 지침
  - 무조건 작게
    - 캐릭터 10명? → 1명부터 제대로 대화하게
    - 유료 결제? → 나 혼자 써보고 편한지부터 확인
  - 완벽함은 바이브코딩의 적
    - 굴러가기만 하면 된다
    - 예쁜 건 나중에 "세련된 디자인으로 CSS 입혀줘" 한 문장이면 됨
03.5 [실습] 기술 선택과 레퍼런스 넘기기
  - 기술 선택
    - 코덱스에게 물어봐도 됨: "이런 서비스 만들려면 뭘 써야 해?"
    - 단, 3가지 기준은 사람이 판단: 배포 가능성 / 디버깅 용이성 / 확장성
  - 레퍼런스 넘기기
    - 공식 문서 URL, 비슷한 서비스 스크린샷을 넘기면 정확도가 올라감
    - [실습] 만들고 싶은 서비스의 레퍼런스 스크린샷 3장 모아서 코덱스에게 넘기기
03.6 만들고→보여주고→다시 고치기 — 나만의 UX 인터뷰
  - 왜 보여줘야 하나
    - "아직 부족한데…" 싶을 때가 바로 보여줘야 할 때
    - 혼자서는 절대 못 보는 구멍이 있음 — 사용자를 만나야 보임
  - 스토리를 입혀서 뿌리기
    - 단순히 "이거 써봐" 대신, 배경 이야기를 곁들이기
    - "바이브코딩이라는 걸 처음 해봤는데, 이런 고객이 이런 문제가 있을 것 같아서 만들어봤어"
    - "혹시 써보고 솔직한 피드백 주시면, 커피 한 잔 사드릴게요"
    - 이야기가 붙으면 상대방도 진지하게 봐줌 — 그냥 링크만 던지면 "좋네요" 끝
  - 모아놓고 보여주기 — 미니 UX 인터뷰
    - 링크만 뿌리는 것보다 3~5명 모아서 직접 보여주는 게 10배 효과적
    - 카페든 회의실이든, 옆에서 쓰는 걸 지켜보기
    - 어디서 멈추는지, 어디서 갸우뚱하는지, 어디서 화면을 닫는지 관찰
    - 말로 물어보면 예의상 "좋네요" — 행동을 보면 진짜가 나옴
  - 질문하는 법
    - ❌ "이거 좋나요?" → 예의상 "좋네요"
    - ✅ "어디서 멈추셨어요?"
    - ✅ "뭐가 제일 헷갈리세요?"
    - ✅ "이거 없으면 어떻게 하고 계셨어요?" (기존 대안 파악)
  - 핵심 루프
    - 빨리 만들어서 → 모아서 보여주고 → 반응 관찰하고 → AI와 함께 고치기
    - 이 사이클을 많이 돌리는 게 승리
    - 빨리 틀려보는 것이 가장 빨리 성공하는 길
    - 피드백은 기능 추가 요청이 아니라 "어디서 막혔는지"에 집중

[04장] 배포해서 세상에 보여주기

04.1 git과 GitHub — 무한 세이브 슬롯과 온라인 보관함
  - git = 무한 세이브 슬롯
    - 코드가 꼬여도 잘 됐을 때로 되돌리는 시간 여행 장치
    - 게임에서 보스 전 세이브하는 것과 같음
  - GitHub = 온라인 보관함
    - 내 컴퓨터가 고장 나도 코드는 안전
    - 배포도 여기 올린 코드에서 시작됨
  - [실습] 첫 번째 세이브 포인트 찍기
    - `git status` — 어떤 파일이 바뀌었는지 확인
    - `git add .` — 바뀐 파일들을 세이브할 가방에 담기
    - `git commit -m "캐릭터 챗 첫 완성"` — 세이브에 이름 붙이기
    - `git push` — GitHub으로 올리기
  - GitHub 계정 연결
    - 코덱스에게 "내 프로젝트를 GitHub에 올리고 싶어. 단계별로 알려줘" 시키면 됨
04.2 [실습] Vercel로 배포하기 — 내 서비스에 진짜 링크가 생긴다
  - Vercel이란
    - GitHub 코드를 가져다가 `https://내-프로젝트.vercel.app` 주소를 만들어주는 서비스
    - 개인용 무료 — 예전에는 서버 한 대에 월 몇만 원
  - 배포 3단계 — Vercel CLI로 터미널에서 바로
    - ① vercel.com 회원가입 (GitHub 계정으로 가입하면 끝)
    - ② 코덱스에게 "이 프로젝트 Vercel로 배포해줘" 시키기 → CLI 설치 + 로그인 + 배포까지 알아서 진행
    - ③ 터미널에 뜨는 URL이 내 서비스 주소 — 브라우저 대시보드 조작 필요 없음
  - 환경변수를 따로 넣는 이유
    - `.env` 파일에 키가 적혀 있는 채로 GitHub에 올리면 누군가 훔쳐 쓸 수 있음
    - `.gitignore`로 `.env`는 안 올리고, Vercel에만 살짝 알려주는 방식
  - 배포 확인
    - "Congratulations!" 화면 + 내 서비스 주소 확인
    - 스마트폰으로 접속 — 내 컴퓨터 꺼져 있어도 전 세계에서 접속 가능
  - [완성 코드 GitHub 링크 제공]
04.3 링크를 보내고 반응을 받기 — 이제부터가 진짜 시작
  - 링크 공유
    - 가족·친구·단톡방에 "내가 AI 캐릭터 챗 만들었는데, 대화해 봐!"
  - 예상치 못한 반응들
    - "와, 진짜 너가 만든 거야?" (응원)
    - "내 폰에서는 화면이 좀 잘리는데?" (버그 제보)
    - "답변 속도가 좀 느린 것 같아" (성능 피드백)
    - "사진 업로드 기능도 있으면 좋겠다" (기능 제안)
  - 배포는 기술적 마무리가 아니라 "진짜 공부"의 시작
    - 사용자를 만나야 내가 몰랐던 구멍이 보임
  - 자동 재배포
    - 모바일 깨지면 → "반응형으로 수정해줘" → git push → Vercel이 알아서 새 버전 배포

[05장] 피드백 반영하기 — 의도 엔지니어링으로 프로젝트 다듬기

05.1 링크 공유하고 반응 읽기
  - 누구에게 보여줄까
    - 첫 사용자 5명 찾기 (가족, 동료, 친구)
    - 구체적으로 물어보기: "이 버튼 누르면 뭘 기대했어?"
  - 반응에서 진짜 신호 골라내기
    - "좋아요"는 예의 → 무시해도 됨
    - "여기서 멈칫했어요"가 진짜 피드백
  - 피벗 판단 기준
    - 계속 고칠지, 방향을 바꿀지 결정하는 법
05.2 코드를 고치지 마, 의도를 고쳐
  - 코드를 직접 수정하면 왜 꼬이나
    - 수정할수록 코덱스가 맥락을 잃는 문제
    - 의도(PRD)를 먼저 다듬고, 코덱스에게 다시 시키는 게 더 빠름
  - 나쁜 예시 vs 좋은 예시
    - ❌ "이 줄 고쳐줘"
    - ✅ "PRD의 ③번 기능을 이렇게 바꿨어, 다시 만들어줘"
05.3 [실습] 피드백으로 PRD 다듬고 다시 만들기
  - 피드백 3개를 03장에서 만든 PRD에 반영하기
  - 수정된 PRD를 코덱스에게 넘기고 결과 비교
  - 수정 전/후 차이 확인 — 실제로 뭐가 달라졌는지
05.4 의도를 다듬는 습관
  - "의도 → 구현 → 피드백 → 의도 수정" 루프
    - 이 루프를 빨리 돌릴수록 좋은 결과물이 나옴
  - [실습] 02장 캐릭터 채팅에 새 기능 하나 추가하기
    - PRD 수정 → 코덱스에게 시키기 → 결과 확인 → PRD 다시 수정
  - Part 2 예고: omx는 이 루프를 자동화한 도구

[06장] PG 붙이기 — 결제가 되면 서비스다

06.1 결제는 왜 마지막에 붙이나
  - 서비스가 먼저 돌아가야 결제를 붙일 의미가 있음

    - 카드사와 내 서비스 사이의 중개자
  - 주요 PG 비교
    - 부트페이: 특징, 수수료
    - 토스페이먼츠: 특징, 수수료
    - 포트원: 특징, 수수료
  - 사업자등록증 없이 테스트할 수 있는 PG와 테스트 모드 안내
06.3 [실습] 테스트 결제 연동하기
  - 테스트 모드로 PG 연동
    - 테스트 모드 키 발급받기
    - 02장 캐릭터 채팅에 "유료 캐릭터" 결제 버튼 추가
    - 테스트 모드로 결제 진행하고 결과 확인
  - [완성 코드 GitHub 링크 제공]
06.4 결제 검증 체크리스트
  - 실결제 전 반드시 확인할 것
    - 금액 검증
    - 중복 결제 방지
    - 환불 처리
  - 흔히 놓치는 실수 세 가지

    - 환경변수 누락

## Part 2. omx로 콘텐츠 자동화 체험하기

> omx(oh my codex) = 코덱스용 자동화 커맨드 모음. 설치하면 $write, $news 같은 명령어를 바로 쓸 수 있다.
> Part 2 감정선: "omx 설치했더니 커맨드가 생겼네" → "$write 했더니 글이 나왔어!" → "뉴스봇도 되네" → "아, 이래서 이렇게 만든 거구나"

[07장] omx 설치하고 자동화 맛보기

07.1 omx란 — "해줘"를 한 단계 올리기
  - Part 1에서는 코덱스에게 하나씩 시켰다
    - "파일 만들어줘", "이거 고쳐줘" — 한 번에 한 가지
  - omx는 여러 단계를 한 줄로 묶은 커맨드 모음
    - $write → 소재 수집 + 초안 + 퇴고까지 한 번에
    - $news → 뉴스 수집 + 분류 + 요약까지 한 번에
  - omx = oh my codex
    - 코덱스의 커스텀 커맨드 기능을 활용한 자동화 도구
    - 설치하면 바로 사용 — 설정 파일을 직접 만들 필요 없음
07.2 [실습] omx 설치하기
  - 한 줄 설치
    - 설치 명령어 → ~/.codex/commands/omx/ 에 커맨드가 설치됨
  - 설치 확인
    - 코덱스에서 $write, $news 커맨드가 보이는지 확인
  - 같이 설치되는 것들 — 지금은 몰라도 됨
    - skills/ — 커맨드별 작업 순서 정의
    - prompts/ — AI 역할별 지시서
    - AGENTS.md — 프로젝트 기본 규칙
07.3 [실습] $write로 블로그 글 한 편 뽑아보기
  - "AI 코딩 에이전트 입문" 주제로 $write 실행
  - 결과 확인 — 블로그 글이 나옴
  - ChatGPT에게 "블로그 글 써줘" vs $write — 뭐가 다른가
    - $write는 수집→초안→퇴고를 나눠서 처리
    - 각 단계에 전문가(에이전트)가 따로 있음
    - 한 번에 시키면 들쭉날쭉, 나눠서 시키면 안정됨
07.4 열어보기 — omx 안에는 뭐가 들어 있나
  - 스킬(skill)
    - 여러 단계를 한 줄로 묶은 레시피
    - skills/write/SKILL.md — 입력(주제) → 중간 단계 → 출력(완성 글)
  - 에이전트(agent)
    - "수집 담당", "글쓰기 담당"처럼 역할이 정해진 AI 전문가
    - prompts/writer.md, prompts/editor.md — 역할별 지시서
  - 파이프라인
    - 스킬이 에이전트들을 순서대로(또는 동시에) 부리는 전체 흐름
    - 같은 개념의 다른 이름들: 워크플로우, 오케스트레이션, 멀티에이전트
    - 이 책에서는 **파이프라인** 하나로 통일
  - AGENTS.md
    - 프로젝트 전체에 적용되는 규칙 파일
    - "한국어로 써줘", "2000자 이내" 같은 전역 지시
  - 이해 안 해도 쓸 수 있다
    - omx가 다 세팅해뒀으니, 궁금할 때 열어보면 됨
    - 수정하고 싶으면 해당 파일만 고치면 됨
07.5 [실습] AGENTS.md 한 줄 바꿔보기
  - "모든 글을 ~합니다 체로 써줘" 추가 → $write 다시 실행 → 톤 변화 확인
  - AGENTS.md는 프로젝트의 헌법 — 모든 커맨드에 자동 적용

[08장] $write 깊게 쓰기 — 블로그 자동화

08.1 톤이 안 맞을 때 — 레퍼런스 문서 고치기
  - $write로 뽑은 글이 너무 딱딱하다면
    - prompts/writer.md 열고 "캐주얼한 톤으로" 한 줄 추가
    - 다시 $write → 톤이 바뀜
  - 톤가이드(docs/tone-guide.md)
    - 말투, 금지 표현, 예시 스타일을 모아둔 파일
    - 한번 잡아두면 다음 글부터 자동 반영
08.2 [실습] 내 블로그에 맞게 커스텀하기
  - 톤가이드 수정 → $write → 결과 비교
  - 용어맵(docs/term-map.md) 만들기 — "바이브코딩" not "바이브 코딩"
  - 피드백 루프: 글 → 수정 요청 → 레퍼런스 업데이트 → 다음 글 품질 향상
08.3 결과가 달라지는 이유 — 컨텍스트와 레퍼런스
  - 같은 $write인데 왜 결과가 다를까
    - 레퍼런스 문서의 차이: 톤가이드가 다르면 같은 주제도 다른 글
    - 내 폴더에 뭐가 있느냐: 소재가 달라지면 예시가 달라짐
  - 컨텍스트 윈도우
    - AI가 한 번에 읽을 수 있는 양의 한계
    - 넘치면 앞의 지시를 잊어버림
  - 실전 팁
    - 레퍼런스 문서는 짧고 명확하게
    - 중요한 규칙은 AGENTS.md에 박아두기 (대화로 전달 ✕)
08.4 열어보기 — $write 파이프라인의 실제 흐름
  - ① 레퍼런스 읽기 (톤가이드, 용어맵)
  - ② 소재 수집 (로컬 + 웹) — 병렬로 동시에
  - ③ 초안 작성 (@writer 에이전트)
  - ④ 퇴고 (@editor 에이전트)
  - ⑤ 품질 체크 — 미달이면 ③→④ 반복
  - 왜 이렇게 나뉘어 있나
    - 한 에이전트에게 다 시키면 품질이 들쭉날쭉
    - 역할별 전문가가 하면 안정됨 — 회사의 분업과 같음
  - [완성 코드 GitHub 링크 제공]

[09장] $news로 뉴스봇 만들기

09.1 블로그와 뼈대가 같다
  - 블로그: 소재 수집 → 집필 → 퇴고 → 발행
  - 뉴스봇: 뉴스 수집 → 분류 → 요약 → 발송
  - "수집→처리→출력" — 입력 소스와 출력 채널만 다름
09.2 [실습] $news 써보기
  - 소스 등록 — sources.json에 URL 3개
    - RSS 피드: 웹사이트가 새 글 올릴 때마다 보내주는 알림
    - GeekNews, TechCrunch, 네이버 뉴스 등 예시
  - $news 실행 → 뉴스 3줄 요약이 나옴
  - 결과 확인 — 카테고리별 분류 + 핵심 요약
09.3 [실습] 요약 커스텀하기
  - 분류 기준 수정 — "AI/개발/비즈니스" 카테고리 변경
  - 요약 톤 조정 — prompts/summarizer.md 수정
  - 품질 규칙: "핵심 숫자와 출처 URL 반드시 포함"
  - [완성 코드 GitHub 링크 제공]
09.4 패턴 정리 — 블로그와 뉴스봇에서 배운 것
  - 두 프로젝트에서 반복된 패턴
    - ① 체인: A → B → C 순서대로
    - ② 병렬: 독립적인 단계는 동시에
    - ③ 품질 루프: 미달이면 재실행
    - ④ 레퍼런스 분리: 톤·용어·소스를 별도 파일로
  - "이 패턴이면 유튜브든 웹소설이든 확장 가능"
09.5 의도 엔지니어링이란 — omx가 "왜"를 다루는 법
  - omx의 각 커맨드는 "의도"를 구조화한 것
    - $write = "좋은 블로그 글을 만들겠다"는 의도를 파이프라인으로 실현
    - $news = "매일 핵심 뉴스를 받아보겠다"는 의도를 파이프라인으로 실현
  - 03장의 PRD도 의도 문서
    - 서비스의 의도: "누구를 위해, 뭘 만들고, 뭘 안 만들까"
  - omx 커맨드 = 반복 작업의 의도
    - 한번 정의하면 계속 재사용
    - 의도가 명확할수록 → 파이프라인이 잘 돌고 → 결과가 좋아짐
  - "의도를 코드로 만든 것" — 이게 자동화의 본질
  - 다음 파트 예고: 이걸 내가 안 시켜도 알아서 돌게 만드는 게 오픈클로

## Part 3. 오픈클로 — 로컬 AI 에이전트에게 일을 맡기다

> 이 파트의 모든 실습은 오픈클로 위에서 진행됩니다.

[10장] 오픈클로 설치하고 첫 대화하기

10.1 코덱스와 뭐가 다른가 — 24시간 돌아가는 로컬 에이전트
  - 코덱스 vs 오픈클로
    - 코덱스: 내가 시킬 때만 일함, 노트북 닫으면 끝
    - 오픈클로: cron으로 알아서 돌아감, 맥미니·서버처럼 상시 켜둔 머신이 기본
  - 실행 환경이 다르다
    - 코덱스 — 내 작업용 노트북에서 대화하듯 사용, 뚜껑 닫으면 멈춤
    - 오픈클로 — 맥미니·라즈베리파이·클라우드 VM 등 "꺼지지 않는 컴퓨터"에 설치해서 24시간 가동
    - 왜 따로 머신이 필요한가: 자고 있을 때도, 주말에도 cron이 돌아야 하니까
  - 권한이 크니까 격리가 필요하다
    - 오픈클로는 파일 읽기·쓰기, 외부 API 호출, 터미널 명령 실행 등 권한이 넓음
    - 내 작업 폴더를 통째로 건드릴 수 있으므로, 전용 폴더(워크스페이스)로 격리
    - 실수 방지 세 가지: ① 전용 사용자 계정, ② 워크스페이스 밖 접근 차단, ③ 위험 명령 허용 목록
  - 코덱스 OAuth 연동
    - 오픈클로에서 코덱스 계정으로 로그인 → 추가 API 과금 없이 사용 가능
  - omx 커맨드가 그대로 동작한다
    - Part 2에서 쓴 $write, $news를 오픈클로가 cron으로 대신 실행
    - skills/, prompts/, AGENTS.md 구조가 동일 — 새로 배울 것 없음
  - 같이 쓰면 좋은 이유
    - 코덱스(omx)로 만들고 다듬기 → 오픈클로에게 맡겨서 24시간 자동 실행

    - 쪼갤수록 결과가 오히려 떨어지는 지점이 있음
  - 병렬이 좋을 때 vs 순차가 좋을 때
    - 병렬: 입력이 서로 독립적일 때 (로컬 수집 + 웹 리서치)
    - 순차: 앞 단계 결과가 다음 단계 품질을 좌우할 때 (집필 → 퇴고)
  - 실전 결론
    - omx의 $write도 핵심 흐름은 순차 (수집→집필→퇴고)
    - 병렬은 수집처럼 "많이 모으는" 단계에서만 효과적
    - "되는데 안 쓰는 이유"를 아는 게 진짜 노하우
