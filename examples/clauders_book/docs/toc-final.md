# 바로바로 코덱스 + 오픈클로 에이전트 자동화 

> 독자 여정: 설치하고 만든다(Part 1) → omx로 자동화를 체험한다(Part 2) → 에이전트에게 맡긴다(Part 3) → 세상에 내보낸다(Part 4)
> 감정선: "오 되네!" → "$write 했더니 글이 나왔어!" → "자고 일어나니 뉴스가 와 있네" → "세상에 나갔다!"
> 원칙: 먼저 써보고, 결과를 보고, 그다음에 "왜"를 이해한다 (snackable concepts)

## Part 1. 코덱스로 바이브코딩 시작하기

[01장] 한 줄 설치, 바로 실습

01.1 코덱스란 무엇인가
  - ChatGPT vs 코덱스
    - ChatGPT: "이거 어떻게 해?" → 브라우저에서 답변을 생성
    - 코덱스: "이거 해줘" → 내 컴퓨터에서 파일을 직접 만들고 고침
    - 핵심 차이: 질문하면 답변 vs 시키면 실행
  - GUI vs CLI
    - GUI(브라우저): 보고 클릭하는 방식, 사람이 쓰기 좋은 화면
    - CLI(터미널): 말하고 실행하는 방식, AI가 일하기 좋은 작업대
    - 이 책에서 CLI를 쓰는 이유: 프로젝트 전체를 읽고→만들고→수정하고→실행하는 흐름을 이어서 할 수 있음
  - 한눈에 비교표
    - ChatGPT = 대화형 도우미 (설명, 아이디어, 초안)
    - Codex = 실행형 비서 (만들기, 수정하기, 반복 작업)
01.2 [실습] 터미널 열고 한 줄로 설치하기
  - 터미널 열기
    - Windows: PowerShell 검색 → 관리자 권한으로 실행
    - Mac: Command+Space → Terminal 입력
  - 한 줄 설치 스크립트
    - 스크립트 한 줄 복사 → 터미널에 붙여넣기 → Enter
    - Node.js 포함 필요한 것이 자동으로 설치됨
    - 설치 확인: 새 터미널에서 `codex --version` 실행 → 버전 번호 나오면 성공
  - 요금제 안내
    - ChatGPT 계정으로 로그인하면 바로 시작 (별도 API 키 발급 불필요)
    - Free: 비추 (한시적 프로모션, 사용량 제한 심함)
    - Plus (월 $20, 약 2.9만 원): 이 책 기준, 실습 전부 가능
    - Pro (월 $200): 잘 활용하게 되면 올리기
01.3 VS Code 설치하고 둘러보기
  - VS Code 설치
    - code.visualstudio.com 접속 → Download → 설치 (다음, 다음, 완료)
  - 알아야 할 세 곳
    - 왼쪽 Explorer: 파일·폴더를 보는 곳 (윈도우 탐색기와 비슷)
    - 가운데 에디터: 파일 내용을 보고 수정하는 곳
    - 오른쪽 Copilot: ❌ 닫기 — 우리는 코덱스를 쓸 것
  - VS Code 안에서 터미널 열기
    - 상단 메뉴 "터미널 → 새 터미널" 또는 Ctrl+`
    - 화면 아래에 뜨는 검은 창이 터미널
    - 터미널이 뜬다고 코덱스가 켜진 게 아님 — `codex` 직접 입력 필요
01.4 `codex`와 `dscodex` — 묻고 실행 vs 바로 실행
  - `codex` (기본)
    - 파일 수정 전마다 "이거 해도 될까요?" 확인
    - 처음 배울 때 안전한 모드
  - `dscodex` (자동 승인)
    - 확인 없이 바로 실행 → 속도 빠름
    - 원래 명령어 `codex --dangerously-bypass-approvals-and-sandbox`의 줄임말
    - 익숙해진 뒤 추천
  - 안전 범위
    - 지정한 폴더 안에서만 작동
    - 인터넷 결제, 메일 발송 같은 건 하지 않음
01.5 프로젝트란 — 폴더 하나가 프로젝트
  - 프로젝트 = 폴더 하나
    - 폴더 안에 파일이 쌓여서 결과물(홈페이지, 앱, 자동화 도구)이 됨
    - 코덱스는 현재 폴더 안의 파일만 보고 고침 → 폴더 = AI의 작업 범위
  - AGENTS.md 맛보기
    - "이 프로젝트는 이런 프로젝트야"라고 코덱스에게 알려주는 파일
    - 05장에서 상세히 다룸
01.6 [실습] 코덱스에게 첫 번째 일 시키기
  - 프로젝트 만들기
    - 바탕화면에 `my-first-project` 폴더 만들기
    - VS Code에서 파일 → 폴더 열기 → 해당 폴더 선택
  - 파일 만들기
    - "자기소개.md 파일을 만들어줘. 이름은 홍길동, 직업은 떡집 사장님, 취미는 등산이야"
    - "오늘할일.md 파일을 만들어줘. 체크리스트로" → Explorer에 파일 두 개 생김
  - 파일 수정하기
    - "자기소개.md에 좋아하는 음식: 김치찌개를 추가해줘" → 파일 내용이 바뀜
  - 핵심 정리
    - 만들기, 수정하기 — 이 두 가지가 앞으로 할 일의 전부
    - 코드를 직접 짜는 게 아니라 의도를 전달하고 결과를 판단하는 사람이 되는 것

[02장] AI 캐릭터 채팅 — 아이디어에서 MVP까지

02.1 완성된 화면부터 보기 — 목적지를 먼저 보여주기
  - 스크린샷 2장: 채팅 화면 + 캐릭터가 말투대로 대답하는 장면
  - 목표 선언: "이걸 지금부터 30분 안에 만든다"
  - 린스타트업의 핵심: 가장 빨리, 가장 싸게, 핵심만 검증하기
02.2 MVP란 — "안 만들 것"을 정하는 게 기획이다
  - MVP(최소 기능 제품)의 뜻
    - 핵심 경험 하나만 돌아가면 시장에 내놓을 수 있는 제품
  - 캐릭터 챗의 MVP 정의
    - ✅ 만들 것: 캐릭터 소개 화면, 대화 기능, 캐릭터 말투
    - ❌ 안 만들 것: 로그인, 친구초대, 이미지 저장, 다크모드
    - "무엇을 안 만들까"를 정하는 게 기획의 핵심
  - 흔한 실수
    - "캐릭터 10명, 결제, 모바일 앱" 한꺼번에 → 99% 포기
    - 완벽함은 바이브코딩의 적 — 굴러가기만 하면 된다
02.3 [실습] 코덱스와 함께 만들기 — 시키고, 확인하고, 다시 시키기
  - 한 입 크기로 쪼개서 시키기
    - ① "이 이미지랑 똑같은 채팅 화면 만들어줘" (화면)
    - ② "입력창 만들어줘" (기능)
    - ③ "AI 응답 연결해줘" (핵심 가치)
    - ④ "캐릭터 성격 입혀줘: 박 대리, 항상 피곤, 반말, 한 문장" (톤)
  - 피드백 루프 — 팀장이 일하는 법
    - "너무 친절해, 까칠하게" → "대답이 길어, 한 문장으로" → "퇴근하고 싶다를 섞어줘"
    - 3번이면 내가 상상한 캐릭터가 나옴
  - [완성 코드 GitHub 링크 제공]
02.4 화면·서버·데이터·API — 식당 비유로 이해하기
  - 서비스 구조 = 식당
    - 화면 = 홀, 서버 = 주방, 데이터 = 식재료, API = 주문서
    - 우리 역할 = 지배인, 코드는 주방장(코덱스)에게 맡기기
  - 지금은 "이런 게 있구나" 정도면 충분
[03장] 바이브코딩 — PRD와 피드백 루프

03.1 [실습] MVP 기획서(PRD) 한 장 만들기
  - 뭘 만들지 모르겠다면: "요즘 가장 귀찮은 일이 뭐예요?"부터 시작
    - 엑셀 반복, 매일 같은 답변, "누가 대신 안 해주나" = 첫 프로젝트
  - PRD란: 코덱스에게 넘길 설계도, AI가 읽을 수 있는 기획서
  - PRD 6가지 항목
    - ① 한줄 요약 ② 대상 사용자 ③ 핵심 기능
    - ④ 안 만들 것 ⑤ 사용자 흐름 ⑥ 성공 기준
  - [실습] 02장 캐릭터 채팅의 PRD를 코덱스에게 작성시키고, 직접 수정해보기
  - 결과 비교: PRD 없이 시킨 것 vs PRD 넘기고 시킨 것
03.2 코드를 고치지 마, 의도를 고쳐
  - 코드를 직접 수정하면 왜 꼬이나
    - 수정할수록 코덱스가 맥락을 잃는 문제
    - 의도(PRD)를 먼저 다듬고, 코덱스에게 다시 시키는 게 더 빠름
  - 나쁜 예시 vs 좋은 예시
    - ❌ "이 줄 고쳐줘"
    - ✅ "PRD의 ③번 기능을 이렇게 바꿨어, 다시 만들어줘"
  - 레퍼런스 넘기기 팁
    - 공식 문서 URL, 비슷한 서비스 스크린샷을 넘기면 정확도가 올라감
03.3 [실습] 피드백으로 PRD 다듬고 다시 만들기
  - 보여주기의 기술
    - "아직 부족한데…" 싶을 때가 바로 보여줘야 할 때
    - ❌ "이거 좋나요?" → ✅ "어디서 멈추셨어요?"
  - [실습] 피드백 3개를 PRD에 반영 → 코덱스에게 다시 시키기 → 결과 비교
  - 핵심 루프: 만들기 → 보여주기 → 반응 관찰 → 의도 수정 → 다시 만들기
    - 이 사이클을 많이 돌리는 게 승리
    - Part 2 예고: omx는 이 루프를 자동화한 도구

[04장] 배포해서 세상에 보여주기

04.1 git과 GitHub — 무한 세이브 슬롯과 온라인 보관함
  - git = 무한 세이브 슬롯
    - 코드가 꼬여도 잘 됐을 때로 되돌리는 시간 여행 장치
  - GitHub = 온라인 보관함
    - 내 컴퓨터가 고장 나도 코드는 안전, 배포도 여기서 시작
  - [실습] 첫 번째 세이브 포인트 찍기
    - `git status` → `git add .` → `git commit -m "캐릭터 챗 첫 완성"` → `git push`
  - GitHub 계정 연결은 코덱스에게 시키면 됨
04.2 [실습] Vercel로 배포하기 — 내 서비스에 진짜 링크가 생긴다
  - Vercel = GitHub 코드 → `https://내-프로젝트.vercel.app` 주소 (개인용 무료)
  - 배포 3단계 — 터미널에서 바로
    - ① vercel.com 가입 (GitHub 계정)
    - ② 코덱스에게 "Vercel로 배포해줘" → CLI 설치+로그인+배포까지 진행
    - ③ URL 확인 → 스마트폰으로 접속
  - 환경변수를 따로 넣는 이유 (.env는 GitHub에 안 올리는 게 철칙)
  - [완성 코드 GitHub 링크 제공]
04.3 링크를 보내고 반응을 받기
  - 가족·친구·단톡방에 링크 공유
  - 예상치 못한 반응들: 응원, 버그 제보, 성능 피드백, 기능 제안
  - 자동 재배포: 코드 수정 → git push → Vercel이 알아서 새 버전 배포

## Part 2. omx로 콘텐츠 자동화 체험하기

> omx(oh my codex) = 코덱스용 자동화 커맨드 모음. 설치하면 $write, $news 같은 명령어를 바로 쓸 수 있다.
> Part 2 감정선: "omx 설치했더니 커맨드가 생겼네" → "$write 했더니 글이 나왔어!" → "뉴스봇도 되네" → "아, 이래서 이렇게 만든 거구나"

[05장] omx 설치하고 자동화 맛보기

05.1 omx란 — "해줘"를 한 단계 올리기
  - Part 1에서는 코덱스에게 하나씩 시켰다
    - "파일 만들어줘", "이거 고쳐줘" — 한 번에 한 가지
  - omx는 여러 단계를 한 줄로 묶은 커맨드 모음
    - $write → 소재 수집 + 초안 + 퇴고까지 한 번에
    - $news → 뉴스 수집 + 분류 + 요약까지 한 번에
  - omx = oh my codex
    - 코덱스의 커스텀 커맨드 기능을 활용한 자동화 도구
    - 설치하면 바로 사용 — 설정 파일을 직접 만들 필요 없음
05.2 [실습] omx 설치하기
  - 한 줄 설치
    - 설치 명령어 → ~/.codex/commands/omx/ 에 커맨드가 설치됨
  - 설치 확인
    - 코덱스에서 $write, $news 커맨드가 보이는지 확인
  - 같이 설치되는 것들 — 지금은 몰라도 됨
    - skills/ — 커맨드별 작업 순서 정의
    - prompts/ — AI 역할별 지시서
    - AGENTS.md — 프로젝트 기본 규칙
05.3 [실습] $write로 블로그 글 한 편 뽑아보기
  - "AI 코딩 에이전트 입문" 주제로 $write 실행
  - 결과 확인 — 블로그 글이 나옴
  - ChatGPT에게 "블로그 글 써줘" vs $write — 뭐가 다른가
    - $write는 수집→초안→퇴고를 나눠서 처리
    - 각 단계에 전문가(에이전트)가 따로 있음
    - 한 번에 시키면 들쭉날쭉, 나눠서 시키면 안정됨
05.4 열어보기 — omx 안에는 뭐가 들어 있나
  - 스킬(skill)
    - 여러 단계를 한 줄로 묶은 레시피
    - skills/write/SKILL.md — 입력(주제) → 중간 단계 → 출력(완성 글)
  - 에이전트(agent)
    - "수집 담당", "글쓰기 담당"처럼 역할이 정해진 AI 전문가
    - prompts/writer.md, prompts/editor.md — 역할별 지시서
  - 파이프라인
    - 스킬이 에이전트들을 순서대로(또는 동시에) 부리는 전체 흐름
    - 같은 개념의 다른 이름들: 워크플로우, 오케스트레이션, 멀티에이전트
    - 이 책에서는 **파이프라인** 하나로 통일
  - AGENTS.md
    - 프로젝트 전체에 적용되는 규칙 파일
    - "한국어로 써줘", "2000자 이내" 같은 전역 지시
  - 이해 안 해도 쓸 수 있다
    - omx가 다 세팅해뒀으니, 궁금할 때 열어보면 됨
    - 수정하고 싶으면 해당 파일만 고치면 됨
05.5 [실습] AGENTS.md 한 줄 바꿔보기
  - "모든 글을 ~합니다 체로 써줘" 추가 → $write 다시 실행 → 톤 변화 확인
  - AGENTS.md는 프로젝트의 헌법 — 모든 커맨드에 자동 적용

[06장] $write 깊게 쓰기 — 블로그 자동화

06.1 톤이 안 맞을 때 — 레퍼런스 문서 고치기
  - $write로 뽑은 글이 너무 딱딱하다면
    - prompts/writer.md 열고 "캐주얼한 톤으로" 한 줄 추가
    - 다시 $write → 톤이 바뀜
  - 톤가이드(docs/tone-guide.md)
    - 말투, 금지 표현, 예시 스타일을 모아둔 파일
    - 한번 잡아두면 다음 글부터 자동 반영
06.2 [실습] 내 블로그에 맞게 커스텀하기
  - 톤가이드 수정 → $write → 결과 비교
  - 용어맵(docs/term-map.md) 만들기 — "바이브코딩" not "바이브 코딩"
  - 피드백 루프: 글 → 수정 요청 → 레퍼런스 업데이트 → 다음 글 품질 향상
06.3 결과가 달라지는 이유 — 컨텍스트와 레퍼런스
  - 같은 $write인데 왜 결과가 다를까
    - 레퍼런스 문서의 차이: 톤가이드가 다르면 같은 주제도 다른 글
    - 내 폴더에 뭐가 있느냐: 소재가 달라지면 예시가 달라짐
  - 컨텍스트 윈도우
    - AI가 한 번에 읽을 수 있는 양의 한계
    - 넘치면 앞의 지시를 잊어버림
  - 실전 팁
    - 레퍼런스 문서는 짧고 명확하게
    - 중요한 규칙은 AGENTS.md에 박아두기 (대화로 전달 ✕)
06.4 열어보기 — $write 파이프라인의 실제 흐름
  - ① 레퍼런스 읽기 (톤가이드, 용어맵)
  - ② 소재 수집 (로컬 + 웹) — 병렬로 동시에
  - ③ 초안 작성 (@writer 에이전트)
  - ④ 퇴고 (@editor 에이전트)
  - ⑤ 품질 체크 — 미달이면 ③→④ 반복
  - 왜 이렇게 나뉘어 있나
    - 한 에이전트에게 다 시키면 품질이 들쭉날쭉
    - 역할별 전문가가 하면 안정됨 — 회사의 분업과 같음
  - [완성 코드 GitHub 링크 제공]

[07장] $news로 뉴스봇 만들기

07.1 블로그와 뼈대가 같다
  - 블로그: 소재 수집 → 집필 → 퇴고 → 발행
  - 뉴스봇: 뉴스 수집 → 분류 → 요약 → 발송
  - "수집→처리→출력" — 입력 소스와 출력 채널만 다름
07.2 [실습] $news 써보기
  - 소스 등록 — sources.json에 URL 3개
    - RSS 피드: 웹사이트가 새 글 올릴 때마다 보내주는 알림
    - GeekNews, TechCrunch, 네이버 뉴스 등 예시
  - $news 실행 → 뉴스 3줄 요약이 나옴
  - 결과 확인 — 카테고리별 분류 + 핵심 요약
07.3 [실습] 요약 커스텀하기
  - 분류 기준 수정 — "AI/개발/비즈니스" 카테고리 변경
  - 요약 톤 조정 — prompts/summarizer.md 수정
  - 품질 규칙: "핵심 숫자와 출처 URL 반드시 포함"
  - [완성 코드 GitHub 링크 제공]
07.4 패턴 정리 — 블로그와 뉴스봇에서 배운 것
  - 두 프로젝트에서 반복된 패턴
    - ① 체인: A → B → C 순서대로
    - ② 병렬: 독립적인 단계는 동시에
    - ③ 품질 루프: 미달이면 재실행
    - ④ 레퍼런스 분리: 톤·용어·소스를 별도 파일로
  - "이 패턴이면 유튜브든 웹소설이든 확장 가능"
07.5 의도 엔지니어링이란 — omx가 "왜"를 다루는 법
  - omx의 각 커맨드는 "의도"를 구조화한 것
    - $write = "좋은 블로그 글을 만들겠다"는 의도를 파이프라인으로 실현
    - $news = "매일 핵심 뉴스를 받아보겠다"는 의도를 파이프라인으로 실현
  - 03장의 PRD도 의도 문서
    - 서비스의 의도: "누구를 위해, 뭘 만들고, 뭘 안 만들까"
  - omx 커맨드 = 반복 작업의 의도
    - 한번 정의하면 계속 재사용
    - 의도가 명확할수록 → 파이프라인이 잘 돌고 → 결과가 좋아짐
  - "의도를 코드로 만든 것" — 이게 자동화의 본질
  - 다음 파트 예고: 이걸 내가 안 시켜도 알아서 돌게 만드는 게 오픈클로

## Part 3. 오픈클로 — 로컬 AI 에이전트에게 일을 맡기다

> 이 파트의 모든 실습은 오픈클로 위에서 진행됩니다.

[08장] 오픈클로 설치하고 첫 대화하기

08.1 코덱스와 뭐가 다른가 — 24시간 돌아가는 로컬 에이전트
  - 코덱스 vs 오픈클로
    - 코덱스: 내가 시킬 때만 일함, 노트북 닫으면 끝
    - 오픈클로: cron으로 알아서 돌아감, 맥미니·서버처럼 상시 켜둔 머신이 기본
  - 실행 환경이 다르다
    - 코덱스 — 내 작업용 노트북에서 대화하듯 사용, 뚜껑 닫으면 멈춤
    - 오픈클로 — 맥미니·라즈베리파이·클라우드 VM 등 "꺼지지 않는 컴퓨터"에 설치해서 24시간 가동
    - 왜 따로 머신이 필요한가: 자고 있을 때도, 주말에도 cron이 돌아야 하니까
  - 권한이 크니까 격리가 필요하다
    - 오픈클로는 파일 읽기·쓰기, 외부 API 호출, 터미널 명령 실행 등 권한이 넓음
    - 내 작업 폴더를 통째로 건드릴 수 있으므로, 전용 폴더(워크스페이스)로 격리
    - 실수 방지 세 가지: ① 전용 사용자 계정, ② 워크스페이스 밖 접근 차단, ③ 위험 명령 허용 목록
  - 코덱스 OAuth 연동
    - 오픈클로에서 코덱스 계정으로 로그인 → 추가 API 과금 없이 사용 가능
  - omx 커맨드가 그대로 동작한다
    - Part 2에서 쓴 $write, $news를 오픈클로가 cron으로 대신 실행
    - skills/, prompts/, AGENTS.md 구조가 동일 — 새로 배울 것 없음
  - 같이 쓰면 좋은 이유
    - 코덱스(omx)로 만들고 다듬기 → 오픈클로에게 맡겨서 24시간 자동 실행
08.2 [실습] 오픈클로 설치하기 (macOS / Windows)
  - 설치 전 준비물
    - Node.js, Git, 터미널 접근
  - macOS 설치
    - 명령어 한 줄씩 따라하기
  - Windows 설치

  - 설치 확인
    - 오픈클로 웹 대시보드 접속하기
  - [설치 과정 영상 링크 제공]
08.3 [실습] 채널 연결하고 첫 메시지 보내기

10.2 [실습] 글쓰기 맡기고 품질 루프 확인하기

10.3 피드백이 쌓이면 글이 좋아진다 — MEMORY.md의 역할

[11장] 뉴스봇을 오픈클로에게 맡기기 — MCP와 하네스 엔지니어링

11.1 [실습] 뉴스봇 프로젝트를 오픈클로에 연결하기
  - 07장 프로젝트 폴더 그대로 연결

    - 수집 주기, 분류 기준, 요약 톤
  - Slack에서 "오늘 뉴스 요약해줘" 보내고 파이프라인 동작 확인
11.2 [실습] MCP로 외부 서비스 연결하기 — Slack, Notion, Firecrawl
  - MCP(Model Context Protocol)란
    - 오픈클로가 외부 서비스의 기능을 도구처럼 쓸 수 있게 해주는 표준 프로토콜
    - 예: Slack에 메시지 보내기, Notion에 DB 행 추가, 웹페이지 스크래핑
  - [실습] Slack MCP 연결
    - 봇 토큰 등록 → 오픈클로가 Slack 채널에 직접 메시지 보내기
  - [실습] Notion MCP 연결
    - 뉴스 아카이브 DB에 요약 자동 저장
  - [실습] Firecrawl MCP 연결
    - RSS가 없는 사이트도 웹 스크래핑으로 수집
    - 마크다운으로 받아서 토큰 절감 (스크린샷 대비 10배 효율)
11.3 [실습] cron으로 수집→분류→발송 자동화하기
  - 매일 아침 8시 자동 뉴스 수집 cron 설정
  - 파이프라인 한 번에 돌리기
    - 수집(collector) → 분류·요약(summarizer) → Slack 발송 + Notion 저장
  - 실행 로그에서 각 단계 확인
    - 수집된 기사 수, 분류 결과, 요약 품질 점수
    - 오류 발생 시 어디서 끊겼는지 로그로 파악
11.4 하네스 엔지니어링 — 에이전트를 안전하게 다루는 법
  - 하네스(harness)란
    - 에이전트에게 달리는 고삐 — 실행 범위와 권한을 제한하는 장치
  - 왜 필요한가
    - cron으로 자동 실행 = 내가 안 보는 사이에 AI가 행동
    - 잘못된 요약이 Slack에 바로 나가면 곤란
  - 승인 규칙 설정
    - "외부 발송(Slack, SNS)은 미리보기 → 사람 승인 → 발송"
    - "파일 삭제는 반드시 사람이 확인"
  - 실행 범위 제한
    - 특정 폴더만 접근 허용
    - 특정 MCP 도구만 호출 허용
  - [실습] 뉴스봇에 "Slack 발송 전 미리보기 → 승인 → 발송" 규칙 설정
11.5 [칼럼] 파이프라인, 어디까지 쪼개야 할까
  - omx의 $write, $news를 쓰다 보면 궁금해짐: "더 쪼개면 더 좋아지나?"
    - 기술적으로는 에이전트 수십 개를 동시에 돌릴 수 있음
    - 하지만 에이전트 간 정보 전달 비용이 큼
    - 쪼갤수록 결과가 오히려 떨어지는 지점이 있음
  - 병렬이 좋을 때 vs 순차가 좋을 때
    - 병렬: 입력이 서로 독립적일 때 (로컬 수집 + 웹 리서치)
    - 순차: 앞 단계 결과가 다음 단계 품질을 좌우할 때 (집필 → 퇴고)
  - 실전 결론
    - omx의 $write도 핵심 흐름은 순차 (수집→집필→퇴고)
    - 병렬은 수집처럼 "많이 모으는" 단계에서만 효과적
    - "되는데 안 쓰는 이유"를 아는 게 진짜 노하우
