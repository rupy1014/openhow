# 바로바로 코덱스 + 오픈클로 에이전트 자동화 

> 독자 여정: 설치하고 만든다(Part 1) → 코덱스로 자동화 파이프라인을 설계한다(Part 2) → 에이전트에게 맡긴다(Part 3) → 세상에 내보낸다(Part 4)
> 감정선: "오 되네!" → "$write 했더니 글이 나왔어!" → "자고 일어나니 뉴스가 와 있네" → "세상에 나갔다!"
> 원칙: 먼저 써보고, 결과를 보고, 그다음에 "왜"를 이해한다 (snackable concepts)

## Part 1. 코덱스로 바이브코딩 시작하기

[01장] 한 줄 설치, 바로 실습

01.1 코덱스란 무엇인가
  - ChatGPT vs 코덱스
    - ChatGPT: "이거 어떻게 해?" → 브라우저에서 답변을 생성
    - 코덱스: "이거 해줘" → 내 컴퓨터에서 파일을 직접 만들고 고침
    - 핵심 차이: 질문하면 답변 vs 시키면 실행
  - GUI vs CLI
    - GUI(브라우저): 보고 클릭하는 방식, 사람이 쓰기 좋은 화면
    - CLI(터미널): 말하고 실행하는 방식, AI가 일하기 좋은 작업대
    - 이 책에서 CLI를 쓰는 이유: 프로젝트 전체를 읽고→만들고→수정하고→실행하는 흐름을 이어서 할 수 있음
  - 한눈에 비교표
    - ChatGPT = 대화형 도우미 (설명, 아이디어, 초안)
    - Codex = 실행형 비서 (만들기, 수정하기, 반복 작업)
01.2 [실습] 터미널 열고 한 줄로 설치하기
  - 터미널 열기
    - Windows: PowerShell 검색 → 관리자 권한으로 실행
    - Mac: Command+Space → Terminal 입력
  - 한 줄 설치 스크립트
    - 스크립트 한 줄 복사 → 터미널에 붙여넣기 → Enter
    - Node.js 포함 필요한 것이 자동으로 설치됨
    - 설치 확인: 새 터미널에서 `codex --version` 실행 → 버전 번호 나오면 성공
  - 요금제 안내
    - ChatGPT 계정으로 로그인하면 바로 시작 (별도 API 키 발급 불필요)
    - Free: 비추 (한시적 프로모션, 사용량 제한 심함)
    - Plus (월 $20, 약 2.9만 원): 이 책 기준, 실습 전부 가능
    - Pro (월 $200): 잘 활용하게 되면 올리기
01.3 VS Code 설치하고 둘러보기
  - VS Code 설치
    - code.visualstudio.com 접속 → Download → 설치 (다음, 다음, 완료)
  - 알아야 할 세 곳
    - 왼쪽 Explorer: 파일·폴더를 보는 곳 (윈도우 탐색기와 비슷)
    - 가운데 에디터: 파일 내용을 보고 수정하는 곳
    - 오른쪽 Copilot: ❌ 닫기 — 우리는 코덱스를 쓸 것
  - VS Code 안에서 터미널 열기
    - 상단 메뉴 "터미널 → 새 터미널" 또는 Ctrl+`
    - 화면 아래에 뜨는 검은 창이 터미널
    - 터미널이 뜬다고 코덱스가 켜진 게 아님 — `codex` 직접 입력 필요
01.4 `codex`와 `dscodex` — 묻고 실행 vs 바로 실행
  - `codex` (기본)
    - 파일 수정 전마다 "이거 해도 될까요?" 확인
    - 처음 배울 때 안전한 모드
  - `dscodex` (자동 승인)
    - 확인 없이 바로 실행 → 속도 빠름
    - 원래 명령어 `codex --dangerously-bypass-approvals-and-sandbox`의 줄임말
    - 익숙해진 뒤 추천
  - 안전 범위
    - 지정한 폴더 안에서만 작동
    - 인터넷 결제, 메일 발송 같은 건 하지 않음
01.5 프로젝트란 — 폴더 하나가 프로젝트
  - 프로젝트 = 폴더 하나
    - 폴더 안에 파일이 쌓여서 결과물(홈페이지, 앱, 자동화 도구)이 됨
    - 코덱스는 현재 폴더 안의 파일만 보고 고침 → 폴더 = AI의 작업 범위
  - AGENTS.md 맛보기
    - "이 프로젝트는 이런 프로젝트야"라고 코덱스에게 알려주는 파일
    - 05장에서 상세히 다룸
01.6 [실습] 코덱스에게 첫 번째 일 시키기
  - 프로젝트 만들기
    - 바탕화면에 `my-first-project` 폴더 만들기
    - VS Code에서 파일 → 폴더 열기 → 해당 폴더 선택
  - 파일 만들기
    - "자기소개.md 파일을 만들어줘. 이름은 홍길동, 직업은 떡집 사장님, 취미는 등산이야"
    - "오늘할일.md 파일을 만들어줘. 체크리스트로" → Explorer에 파일 두 개 생김
  - 파일 수정하기
    - "자기소개.md에 좋아하는 음식: 김치찌개를 추가해줘" → 파일 내용이 바뀜
  - 핵심 정리
    - 만들기, 수정하기 — 이 두 가지가 앞으로 할 일의 전부
    - 코드를 직접 짜는 게 아니라 의도를 전달하고 결과를 판단하는 사람이 되는 것

[02장] AI 캐릭터 채팅 — 아이디어에서 MVP까지

02.1 완성된 화면부터 보기 — 목적지를 먼저 보여주기
  - 스크린샷 2장: 채팅 화면 + 캐릭터가 말투대로 대답하는 장면
  - 목표 선언: "이걸 지금부터 30분 안에 만든다"
  - 린스타트업의 핵심: 가장 빨리, 가장 싸게, 핵심만 검증하기
02.2 MVP란 — "안 만들 것"을 정하는 게 기획이다
  - MVP(최소 기능 제품)의 뜻
    - 핵심 경험 하나만 돌아가면 시장에 내놓을 수 있는 제품
  - 캐릭터 챗의 MVP 정의
    - ✅ 만들 것: 캐릭터 소개 화면, 대화 기능, 캐릭터 말투
    - ❌ 안 만들 것: 로그인, 친구초대, 이미지 저장, 다크모드
    - "무엇을 안 만들까"를 정하는 게 기획의 핵심
  - 흔한 실수
    - "캐릭터 10명, 결제, 모바일 앱" 한꺼번에 → 99% 포기
    - 완벽함은 바이브코딩의 적 — 굴러가기만 하면 된다
02.3 [실습] 코덱스와 함께 만들기 — 시키고, 확인하고, 다시 시키기
  - 한 입 크기로 쪼개서 시키기
    - ① "이 이미지랑 똑같은 채팅 화면 만들어줘" (화면)
    - ② "입력창 만들어줘" (기능)
    - ③ "AI 응답 연결해줘" (핵심 가치)
    - ④ "캐릭터 성격 입혀줘: 박 대리, 항상 피곤, 반말, 한 문장" (톤)
  - 피드백 루프 — 팀장이 일하는 법
    - "너무 친절해, 까칠하게" → "대답이 길어, 한 문장으로" → "퇴근하고 싶다를 섞어줘"
    - 3번이면 내가 상상한 캐릭터가 나옴
  - [완성 코드 GitHub 링크 제공]
02.4 화면·서버·데이터·API — 식당 비유로 이해하기
  - 서비스 구조 = 식당
    - 화면 = 홀, 서버 = 주방, 데이터 = 식재료, API = 주문서
    - 우리 역할 = 지배인, 코드는 주방장(코덱스)에게 맡기기
  - 지금은 "이런 게 있구나" 정도면 충분

[03장] 바이브코딩 — PRD와 피드백 루프

03.1 [실습] MVP 기획서(PRD) 한 장 만들기
  - 뭘 만들지 모르겠다면: "요즘 가장 귀찮은 일이 뭐예요?"부터 시작
    - 엑셀 반복, 매일 같은 답변, "누가 대신 안 해주나" = 첫 프로젝트
  - PRD란: 코덱스에게 넘길 설계도, AI가 읽을 수 있는 기획서
  - PRD 6가지 항목
    - ① 한줄 요약 ② 대상 사용자 ③ 핵심 기능
    - ④ 안 만들 것 ⑤ 사용자 흐름 ⑥ 성공 기준
  - [실습] 02장 캐릭터 채팅의 PRD를 코덱스에게 작성시키고, 직접 수정해보기
  - 결과 비교: PRD 없이 시킨 것 vs PRD 넘기고 시킨 것
03.2 코드를 고치지 마, 의도를 고쳐
  - 코드를 직접 수정하면 왜 꼬이나
    - 수정할수록 코덱스가 맥락을 잃는 문제
    - 의도(PRD)를 먼저 다듬고, 코덱스에게 다시 시키는 게 더 빠름
  - 나쁜 예시 vs 좋은 예시
    - ❌ "이 줄 고쳐줘"
    - ✅ "PRD의 ③번 기능을 이렇게 바꿨어, 다시 만들어줘"
  - 레퍼런스 넘기기 팁
    - 공식 문서 URL, 비슷한 서비스 스크린샷을 넘기면 정확도가 올라감
03.3 [실습] 피드백으로 PRD 다듬고 다시 만들기
  - 보여주기의 기술
    - "아직 부족한데…" 싶을 때가 바로 보여줘야 할 때
    - ❌ "이거 좋나요?" → ✅ "어디서 멈추셨어요?"
  - [실습] 피드백 3개를 PRD에 반영 → 코덱스에게 다시 시키기 → 결과 비교
  - 핵심 루프: 만들기 → 보여주기 → 반응 관찰 → 의도 수정 → 다시 만들기
    - 이 사이클을 많이 돌리는 게 승리
    - Part 2 예고: 스킬과 에이전트로 이 루프를 자동화한다

[04장] 배포해서 세상에 보여주기

04.1 git과 GitHub — 무한 세이브 슬롯과 온라인 보관함
  - git = 무한 세이브 슬롯
    - 코드가 꼬여도 잘 됐을 때로 되돌리는 시간 여행 장치
  - GitHub = 온라인 보관함
    - 내 컴퓨터가 고장 나도 코드는 안전, 배포도 여기서 시작
  - [실습] 첫 번째 세이브 포인트 찍기
    - `git status` → `git add .` → `git commit -m "캐릭터 챗 첫 완성"` → `git push`
  - GitHub 계정 연결은 코덱스에게 시키면 됨
04.2 [실습] Vercel로 배포하기 — 내 서비스에 진짜 링크가 생긴다
  - Vercel = GitHub 코드 → `https://내-프로젝트.vercel.app` 주소 (개인용 무료)
  - 배포 3단계 — 터미널에서 바로
    - ① vercel.com 가입 (GitHub 계정)
    - ② 코덱스에게 "Vercel로 배포해줘" → CLI 설치+로그인+배포까지 진행
    - ③ URL 확인 → 스마트폰으로 접속
  - 환경변수를 따로 넣는 이유 (.env는 GitHub에 안 올리는 게 철칙)
  - [완성 코드 GitHub 링크 제공]
04.3 링크를 보내고 반응을 받기
  - 가족·친구·단톡방에 링크 공유
  - 예상치 못한 반응들: 응원, 버그 제보, 성능 피드백, 기능 제안
  - 자동 재배포: 코드 수정 → git push → Vercel이 알아서 새 버전 배포
04.4 [실습] 반응을 반영해서 다시 만들기 — 바이브코딩 실전 루프
  - 실사용자 피드백을 의도로 바꾸기
    - "모바일에서 글씨가 너무 작아" → PRD에 "모바일 반응형 필수" 추가
    - "캐릭터 목록이 있으면 좋겠다" → PRD에 기능 추가 (단, "안 만들 것"도 다시 점검)
  - [실습] PRD 수정 → 코덱스에게 다시 시키기 → 재배포
    - 03장에서 배운 피드백 루프를 실제 사용자 반응으로 돌리는 것
    - git push만 하면 Vercel이 자동 재배포 — 5분 만에 반영
  - MVP 고도화의 감각
    - 한 번에 다 고치지 말고, 피드백 하나씩 반영 → 재배포 → 반응 확인
    - 이 루프를 빨리 돌릴수록 서비스가 빨리 좋아짐
  - 결제가 필요하다면 — 부록 A 참고
    - "사람들이 돈 내고 쓰겠다"는 확인이 되면 결제를 붙일 때
    - PG 연동은 부록 A에서 테스트 결제까지 실습

## Part 2. 코덱스로 콘텐츠 자동화 설계하기

> 코덱스의 스킬(.codex/skills/)과 에이전트(.codex/agents/) 구조로 콘텐츠 자동화를 직접 설계한다. 단순 태스크부터 파이프라인 스킬까지.
> Part 2 감정선: "스킬을 만들 수 있구나" → "$write 했더니 글이 나왔어!" → "뉴스봇 파이프라인도 만들었네" → "아, 이걸 오픈클로에 넘기면 되겠다"

[05장] 스킬과 에이전트 — 자동화의 뼈대

05.1 "해줘"를 한 단계 올리기
  - Part 1에서는 코덱스에게 하나씩 시켰다
    - "파일 만들어줘", "이거 고쳐줘" — 한 번에 한 가지 = 단일 태스크
  - 반복 작업은 매번 시키면 비효율
    - "블로그 글 써줘"를 시킬 때마다 톤, 분량, 형식을 다시 설명해야 함
    - 한번 정해둔 규칙을 파일로 저장하면 → 매번 같은 품질
  - 코덱스의 스킬(skill) — 단일 태스크도, 파이프라인도 될 수 있다
    - .codex/skills/ 폴더에 SKILL.md 하나 = 스킬 하나
    - 단순 스킬: "파일 정리해줘" 같은 한 가지 일
    - 파이프라인 스킬: 여러 에이전트가 순서대로 일하는 흐름 (수집→집필→퇴고)
    - $write 치면 → 정해진 절차대로 자동 실행
    - 설치할 것 없음 — 폴더에 파일만 만들면 끝
05.2 .codex/ 구조 — 자동화 프로젝트의 뼈대
  - 프로젝트에 세 가지를 세팅하면 자동화가 된다
    - .codex/skills/<이름>/SKILL.md — 스킬 정의 ($이름으로 호출하는 자동화 레시피)
    - .codex/agents/ — 에이전트 정의 (역할이 정해진 AI 전문가, TOML 파일)
    - AGENTS.md — 프로젝트 전체에 적용되는 규칙 (헌법)
  - 스킬의 두 가지 유형
    - 단순 스킬: 에이전트 하나가 한 가지 일 (예: $plan = 계획 세우기)
    - 파이프라인 스킬: 에이전트 여러 개가 순서대로 일하는 흐름 (예: $write = 수집→집필→퇴고)
    - SKILL.md 안에 "어떤 에이전트를, 어떤 순서로, 결과물이 뭔지" 정의
    - $write, $news, $plan 처럼 $이름으로 호출 — 단순이든 파이프라인이든 사용법은 동일
  - 에이전트(agent)란
    - "수집 담당", "글쓰기 담당"처럼 역할이 정해진 AI 전문가

    - 하나에 다 시키면 들쭉날쭉, 역할을 나누면 안정됨
    - 단순 스킬은 에이전트 1개, 파이프라인 스킬은 여러 에이전트가 순서대로 동작
  - 실제 프로젝트 예시 — oh-my-codex
    - GitHub에 공개된 코덱스 자동화 프로젝트 (37개 스킬)
    - .codex/skills/, .codex/agents/ 구조가 이 책에서 만드는 것과 동일
    - 코드 자동화용이지만, 뼈대 패턴은 콘텐츠 자동화에도 그대로 적용
05.3 [실습] 첫 파이프라인 스킬 만들기 — $write
  - 프로젝트 폴더에 .codex/ 구조 만들기

05.4 [실습] AGENTS.md로 전체 톤 잡기

[06장] 파이프라인 설계하기 — 블로그 자동화

06.1 파이프라인 스킬을 열어보기
  - $write가 실제로 하는 일 — SKILL.md의 단계별 흐름
    - ① 레퍼런스 읽기 (톤가이드, 용어맵)
    - ② 소재 수집 (로컬 파일 + 웹 검색) — 병렬로 동시에
    - ③ 초안 작성 (집필 담당)
    - ④ 퇴고 (퇴고 담당)
    - ⑤ 품질 체크 — 미달이면 ③→④ 반복
  - 왜 이렇게 나뉘어 있나
    - 한 에이전트에게 다 시키면 품질이 들쭉날쭉
    - 역할별 전문가가 하면 안정됨 — 회사의 분업과 같음
  - 파이프라인 스킬은 에이전트 수로 규모가 결정된다
    - 블로그 $write: 집필 담당 → 퇴고 담당 = 2 에이전트
    - 유튜브 대본: 소재수집 담당 → 집필 담당 → 퇴고 담당 = 3~4 에이전트
    - 뼈대는 같고, SKILL.md에 에이전트를 추가하면 됨
06.2 [실습] 톤과 레퍼런스 다듬기
  - 톤이 안 맞을 때
    - agents/writer.toml 열고 톤 지시 수정 → 다시 $write → 톤이 바뀜
  - 피드백 루프: 글 → 수정 요청 → 레퍼런스 업데이트 → 다음 글 품질 향상
  - 결과가 달라지는 이유 — 컨텍스트와 레퍼런스
    - 레퍼런스 문서의 차이: 톤가이드가 다르면 같은 주제도 다른 글
    - 컨텍스트 윈도우: AI가 한 번에 읽을 수 있는 양의 한계, 넘치면 앞의 지시를 잊어버림

[08장] 오픈클로 설치하고 첫 대화하기

08.1 코덱스와 뭐가 다른가 — 24시간 돌아가는 로컬 에이전트
  - 코덱스 vs 오픈클로
    - 코덱스: 내 노트북에서 대화하듯 사용, 뚜껑 닫으면 끝
    - 오픈클로: 맥미니·미니PC·클라우드 VM 등 "꺼지지 않는 컴퓨터"에서 cron으로 24시간 가동
    - 코덱스로 파이프라인을 만들고 다듬기 → 오픈클로에게 맡겨서 자동 실행
  - 권한이 크니까 격리가 필요하다
    - 파일 읽기·쓰기, 외부 API 호출, 터미널 명령 등 권한이 넓음
    - 전용 폴더(워크스페이스)로 격리: ① 전용 계정, ② 워크스페이스 밖 접근 차단, ③ 위험 명령 허용 목록
  - 코덱스 OAuth 연동
    - 오픈클로에서 코덱스 계정으로 로그인 → 추가 API 과금 없이 사용 가능
  - Part 2에서 만든 skills/, agents/, AGENTS.md를 오픈클로가 그대로 읽음
    - 10장·11장에서 블로그·뉴스봇을 실제로 연결
08.2 [실습] 오픈클로 설치하기 (macOS / Windows)

    - 예: Telegram/Slack에 메시지 보내기, Notion에 DB 행 추가, 웹페이지 조작
  - [실습] Telegram MCP 연결 (Slack도 동일한 방식)
    - 봇 토큰 등록 → 오픈클로가 Telegram 채널에 직접 메시지 보내기
  - [실습] Notion MCP 연결
    - 뉴스 아카이브 DB에 요약 자동 저장
  - [실습] Playwright MCP 연결
    - RSS가 없는 사이트도 브라우저 자동화로 수집
    - 로그인이 필요한 페이지, 동적 렌더링 페이지도 접근 가능
11.3 [실습] cron으로 수집→분류→발송 자동화하기
  - 매일 아침 8시 자동 뉴스 수집 cron 설정
  - 파이프라인 한 번에 돌리기
    - 수집 담당 → 분류·요약 담당 → Telegram 발송 + Notion 저장
  - 실행 로그에서 각 단계 확인
    - 수집된 기사 수, 분류 결과, 요약 품질 점수
    - 오류 발생 시 맥미니·미니PC에 접속 → 코덱스에게 "에러 로그 보여줘" 시켜서 원인 파악
11.4 하네스 엔지니어링 — 에이전트를 안전하게 다루는 법
  - 하네스(harness)란
    - 에이전트에게 달리는 고삐 — 실행 범위와 권한을 제한하는 장치
  - 왜 필요한가
    - cron으로 자동 실행 = 내가 안 보는 사이에 AI가 행동
    - 잘못된 요약이 Telegram에 바로 나가면 곤란
  - 승인 규칙 설정
    - "외부 발송(Telegram, SNS)은 미리보기 → 사람 승인 → 발송"
    - "파일 삭제는 반드시 사람이 확인"
  - 실행 범위 제한
    - 특정 폴더만 접근 허용
    - 특정 MCP 도구만 호출 허용
  - [실습] 뉴스봇에 "Telegram 발송 전 미리보기 → 승인 → 발송" 규칙 설정
11.5 [칼럼] 멀티 에이전트, 정말 필요할까
  - "에이전트를 여러 개 돌리면 더 좋아지지 않나?"
    - 오픈클로에서 에이전트를 여러 개 동시에 띄울 수는 있음
    - 하지만 에이전트 하나가 호출될 때마다 토큰이 소모됨
    - 에이전트끼리 정보를 넘길 때도 토큰 — 쪼갤수록 비용이 기하급수적으로 늘어남
  - 하나의 파이프라인 스킬 안에서 순차 처리가 낫다
    - $write: 수집→집필→퇴고를 하나의 파이프라인 스킬 안에서 순차 실행 — 컨텍스트 유지, 토큰 절감
    - $news: 수집→분류→요약→발송도 마찬가지
    - 별도 에이전트로 분리하면 컨텍스트가 끊기고, 같은 정보를 다시 넘겨줘야 함
  - 실전 결론
    - 멀티 에이전트는 "완전히 다른 스킬"일 때만 의미 있음 (예: $write와 $news를 각각 cron으로 실행)
    - 하나의 스킬 안에서 쪼개는 건 토큰 낭비 — "할 수 있지만 안 하는 이유"를 아는 게 노하우

    - 에이전트 10종: 집필, 퇴고, 교정, 냉정한 독자, 일관성 검수 담당 등

  - 내 반복 업무에 자동화 붙이기
    - 업종이 달라도 "수집→처리→발행" 뼈대는 같다
    - skills/에 파이프라인, agents/에 역할 정의 → cron으로 자동 실행

    - 경쟁사 모니터링: Firecrawl 수집 → 변동 감지 → Telegram 알림
    - 주간 리포트: 데이터 수집 → 마크다운 → PDF 자동 생성
    - 고객 문의 분류: 메일 수집 → 카테고리 분류 → 담당자 배정

  - 주요 PG 비교: 부트페이, 토스페이먼츠, 포트원
  - 사업자등록증 없이 테스트할 수 있는 PG와 테스트 모드 안내

  - 테스트 모드 키 발급 → "유료 캐릭터" 결제 버튼 추가 → 결제 테스트
