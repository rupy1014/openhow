# 바로바로 코덱스 + 오픈클로 에이전트 자동화 — 최종 목차

> 독자 여정: 설치하고 만든다(Part 1) → 자동화를 배운다(Part 2) → 에이전트에게 맡긴다(Part 3) → 세상에 내보낸다(Part 4)
> 감정선: "오 되네!" → "이렇게 하는 거구나" → "자동으로 되네!" → "에이전트가 알아서 한다" → "세상에 나갔다!"
> 패턴: (바로 배워) 개념 설명 → (바로 쓰는) 실습으로 이해

---

## Part 1. 코덱스로 바이브코딩 시작하기

[01장] 한 줄 설치, 바로 실습

01.1 코덱스란 무엇인가
  - ChatGPT vs 코덱스
    - ChatGPT: "이거 어떻게 해?" → 브라우저에서 답변을 생성
    - 코덱스: "이거 해줘" → 내 컴퓨터에서 파일을 직접 만들고 고침
    - 핵심 차이: 질문하면 답변 vs 시키면 실행
  - GUI vs CLI
    - GUI(브라우저): 보고 클릭하는 방식, 사람이 쓰기 좋은 화면
    - CLI(터미널): 말하고 실행하는 방식, AI가 일하기 좋은 작업대
    - 이 책에서 CLI를 쓰는 이유: 프로젝트 전체를 읽고→만들고→수정하고→실행하는 흐름을 이어서 할 수 있음
  - 한눈에 비교표
    - ChatGPT = 대화형 도우미 (설명, 아이디어, 초안)
    - Codex = 실행형 비서 (만들기, 수정하기, 반복 작업)
01.2 [실습] 터미널 열고 한 줄로 설치하기
  - 터미널 열기
    - Windows: PowerShell 검색 → 관리자 권한으로 실행
    - Mac: Command+Space → Terminal 입력
  - 한 줄 설치 스크립트
    - 스크립트 한 줄 복사 → 터미널에 붙여넣기 → Enter
    - Node.js 포함 필요한 것이 자동으로 설치됨
    - 설치 확인: 새 터미널에서 `codex --version` 실행 → 버전 번호 나오면 성공
  - 요금제 안내
    - ChatGPT 계정으로 로그인하면 바로 시작 (별도 API 키 발급 불필요)
    - Free: 비추 (한시적 프로모션, 사용량 제한 심함)
    - Plus (월 $20, 약 2.9만 원): 이 책 기준, 실습 전부 가능
    - Pro (월 $200): 잘 활용하게 되면 올리기
01.3 VS Code 설치하고 둘러보기
  - VS Code 설치
    - code.visualstudio.com 접속 → Download → 설치 (다음, 다음, 완료)
  - 알아야 할 세 곳
    - 왼쪽 Explorer: 파일·폴더를 보는 곳 (윈도우 탐색기와 비슷)
    - 가운데 에디터: 파일 내용을 보고 수정하는 곳
    - 오른쪽 Copilot: ❌ 닫기 — 우리는 코덱스를 쓸 것
  - VS Code 안에서 터미널 열기
    - 상단 메뉴 "터미널 → 새 터미널" 또는 Ctrl+`
    - 화면 아래에 뜨는 검은 창이 터미널
    - 터미널이 뜬다고 코덱스가 켜진 게 아님 — `codex` 직접 입력 필요
01.4 `codex`와 `dscodex` — 묻고 실행 vs 바로 실행
  - `codex` (기본)
    - 파일 수정 전마다 "이거 해도 될까요?" 확인
    - 처음 배울 때 안전한 모드
  - `dscodex` (자동 승인)
    - 확인 없이 바로 실행 → 속도 빠름
    - 원래 명령어 `codex --dangerously-bypass-approvals-and-sandbox`의 줄임말
    - 익숙해진 뒤 추천
  - 안전 범위
    - 지정한 폴더 안에서만 작동
    - 인터넷 결제, 메일 발송 같은 건 하지 않음
01.5 프로젝트란 — 폴더 하나가 프로젝트
  - 프로젝트 = 폴더 하나
    - 폴더 안에 파일이 쌓여서 결과물(홈페이지, 앱, 자동화 도구)이 됨
    - 코덱스는 현재 폴더 안의 파일만 보고 고침 → 폴더 = AI의 작업 범위
  - AGENTS.md 맛보기
    - "이 프로젝트는 이런 프로젝트야"라고 코덱스에게 알려주는 파일
    - 07장에서 상세히 다룸
01.6 [실습] 코덱스에게 첫 번째 일 시키기
  - 프로젝트 만들기
    - 바탕화면에 `my-first-project` 폴더 만들기
    - VS Code에서 파일 → 폴더 열기 → 해당 폴더 선택
  - 파일 만들기
    - "자기소개.md 파일을 만들어줘. 이름은 홍길동, 직업은 떡집 사장님, 취미는 등산이야"
    - "오늘할일.md 파일을 만들어줘. 체크리스트로" → Explorer에 파일 두 개 생김
  - 파일 수정하기
    - "자기소개.md에 좋아하는 음식: 김치찌개를 추가해줘" → 파일 내용이 바뀜
  - 핵심 정리
    - 만들기, 수정하기 — 이 두 가지가 앞으로 할 일의 전부
    - 코드를 직접 짜는 게 아니라 의도를 전달하고 결과를 판단하는 사람이 되는 것

[02장] AI 캐릭터 채팅 — 30분 만에 서비스 만들기

02.1 완성된 화면부터 보기 — MVP 이미지 두 장
  - 스크린샷 1: 채팅창 인터페이스와 캐릭터 프로필
  - 스크린샷 2: 캐릭터가 설정된 말투로 대답하는 대화 장면
  - 목표 선언
    - "이걸 지금부터 30분 안에 만든다"
    - 예전 방식이면 며칠 밤샘, 지금은 30분
02.2 [실습] 이미지 주고 화면 만들기
  - 이미지 업로드
    - 완성 화면 스크린샷(또는 손그림 스케치)을 코덱스 채팅창에 올리기
    - 지시: "이 이미지랑 똑같은 채팅 화면을 만들어줘. HTML과 CSS로. 아직 기능은 빼고 화면만"
  - 결과 확인
    - 코덱스가 코드를 쫘르륵 생성 → 브라우저에서 열어보기
    - 완성 화면과 비교하기
  - 피드백 루프
    - "버튼이 너무 작아" → 고쳐줌
    - "배경색 좀 더 연하게" → 고쳐줌
    - 마음에 들 때까지 고치라고 시키기 — 우리는 팀장이니까
02.3 화면·서버·데이터·API — 식당 비유로 이해하기
  - 서비스 구조 = 식당
    - 화면(프론트엔드) = 홀: 손님이 메뉴 보고 주문하는 공간
    - 서버(백엔드) = 주방: AI에게 대답을 요청하고 받아오는 곳, 눈에 안 보임
    - 데이터(DB) = 식재료: 캐릭터 설정, 대화 내역이 저장되는 창고
    - API = 주문서: 홀과 주방 사이를 오가는 통로
  - 전체 흐름
    - 채팅 입력 → API(주문서) → 서버(주방) → AI → 서버 → 화면(홀)
    - 우리 역할 = 지배인, 세부 코드는 주방장(코덱스)에게 맡기기
02.4 [실습] 캐릭터에 성격 입히기 — 고치고 다시 시키기
  - 캐릭터 설정 지시
    - 예시: "이름은 박 대리, 30대 직장인, 항상 피곤, 반말 섞어서, 두 문장 이내"
    - 구체적으로 정해줄수록 캐릭터가 살아남 → 프롬프트 엔지니어링의 시작
  - 톤 수정 루프 (3회)
    - 피드백 1: "박 대리가 너무 친절해. 좀 더 까칠하게 해줘"
    - 피드백 2: "말투는 좋은데 대답이 너무 길어. 무조건 한 문장으로 줄여"
    - 피드백 3: "말 끝마다 '퇴근하고 싶다'는 말을 랜덤하게 섞어줘"
    - 3번이면 내가 상상한 캐릭터가 나옴 — 이게 팀장이 일하는 법
  - [완성 코드 GitHub 링크 제공]
02.5 MVP는 어디까지인가
  - 성공 기준 3가지
    - 캐릭터 소개가 화면에 나온다 ✓
    - 내가 말을 걸면 대답이 온다 ✓
    - 캐릭터 말투가 살아있다 ✓
  - 안 만들 것 리스트
    - 로그인, 친구초대, 이미지 저장, 다크모드 — 전부 나중에
    - "무엇을 안 만들까"를 정하는 게 기획의 핵심
  - 핵심 경험이 완성되었으면 시장에 내놓을 수 있는 제품

[03장] 바이브코딩 — "만들어줘"만으로는 안 되는 이유

03.1 AI에게 일을 잘 시키는 두 가지
  - 첫째: '안 만들 것'부터 말하기
    - "로그인은 나중에 빼줘"
    - "데이터베이스 없이 메모리에만 저장되게 해줘"
    - "디자인은 예쁘지 않아도 되니까 기능만 돌아가게 해줘"
    - 범위를 좁혀줘야 AI가 가볍고 정확한 코드를 냄
  - 둘째: '한 입 크기'로 쪼개서 시키기
    - 한 번에 전체를 시키면 수백 줄이 쏟아져서 검토 불가
    - 적당한 크기 = "내가 10분 안에 확인 가능한 크기"
    - 수직 슬라이싱: 빵을 층별로 따로 만드는 게 아니라, 맛볼 수 있게 한 조각씩 자르기
  - 02장 복기
    - ① "화면에 '안녕'이라고만 뜨게 해줘" → ② "입력창 만들어줘" → ③ "버튼 누르면 위에 나오게" → ④ "AI 응답 연결해줘"
    - 한 단계씩 10분마다 확인하며 나아가는 게 바이브코딩
03.2 아이디어는 귀찮음에서 시작한다
  - "요즘 가장 귀찮은 일이 뭐예요?"
    - 거창한 아이디어보다 내 불편함이 먼저
  - 실제 수강생 사례
    - 떡집 사장: 주문 문자를 장부에 옮겨 적는 게 일 → 문자 넣으면 자동 정리해주는 도구
    - 목공예 작가: 나무 종류별 특징 반복 질문 → 나무 사진 올리면 알려주는 챗봇
    - 골프장갑 제작자: 해외 바이어 메일 번역이 고역 → 제품 정보가 입력된 비즈니스 메일 비서
  - 자동화 후보 찾기
    - 엑셀에서 반복하는 일, 매번 같은 질문에 답변하는 일
    - "누가 대신 안 해주나" 싶은 지점이 첫 프로젝트
03.3 [실습] MVP 기획서(PRD) 한 장 만들기
  - PRD란
    - 코덱스에게 넘길 설계도, AI가 읽을 수 있는 기획서
  - PRD 6가지 항목
    - ① 한줄 요약
    - ② 대상 사용자
    - ③ 핵심 기능
    - ④ 안 만들 것
    - ⑤ 사용자 흐름
    - ⑥ 성공 기준
  - [실습] 02장 캐릭터 채팅의 PRD를 코덱스에게 작성시키고, 직접 수정해보기
  - 결과 비교: PRD 없이 시킨 것 vs PRD 넘기고 시킨 것
03.4 작게 시작해야 끝까지 간다
  - 흔한 실수
    - "캐릭터 10명, 유료 결제, 모바일 앱" 한꺼번에 잡기 → 99% 포기
    - 구현해야 할 게 너무 많으면 바이브가 안 살고 지침
  - 무조건 작게
    - 캐릭터 10명? → 1명부터 제대로 대화하게
    - 유료 결제? → 나 혼자 써보고 편한지부터 확인
  - 완벽함은 바이브코딩의 적
    - 굴러가기만 하면 된다
    - 예쁜 건 나중에 "세련된 디자인으로 CSS 입혀줘" 한 문장이면 됨
03.5 [실습] 기술 선택과 레퍼런스 넘기기
  - 기술 선택
    - 코덱스에게 물어봐도 됨: "이런 서비스 만들려면 뭘 써야 해?"
    - 단, 3가지 기준은 사람이 판단: 배포 가능성 / 디버깅 용이성 / 확장성
  - 레퍼런스 넘기기
    - 공식 문서 URL, 비슷한 서비스 스크린샷을 넘기면 정확도가 올라감
    - [실습] 만들고 싶은 서비스의 레퍼런스 스크린샷 3장 모아서 코덱스에게 넘기기
03.6 만들고→보여주고→다시 고치기 — 나만의 UX 인터뷰
  - 왜 보여줘야 하나
    - "아직 부족한데…" 싶을 때가 바로 보여줘야 할 때
    - 혼자서는 절대 못 보는 구멍이 있음 — 사용자를 만나야 보임
  - 스토리를 입혀서 뿌리기
    - 단순히 "이거 써봐" 대신, 배경 이야기를 곁들이기
    - "바이브코딩이라는 걸 처음 해봤는데, 이런 고객이 이런 문제가 있을 것 같아서 만들어봤어"
    - "혹시 써보고 솔직한 피드백 주시면, 커피 한 잔 사드릴게요"
    - 이야기가 붙으면 상대방도 진지하게 봐줌 — 그냥 링크만 던지면 "좋네요" 끝
  - 모아놓고 보여주기 — 미니 UX 인터뷰
    - 링크만 뿌리는 것보다 3~5명 모아서 직접 보여주는 게 10배 효과적
    - 카페든 회의실이든, 옆에서 쓰는 걸 지켜보기
    - 어디서 멈추는지, 어디서 갸우뚱하는지, 어디서 화면을 닫는지 관찰
    - 말로 물어보면 예의상 "좋네요" — 행동을 보면 진짜가 나옴
  - 질문하는 법
    - ❌ "이거 좋나요?" → 예의상 "좋네요"
    - ✅ "어디서 멈추셨어요?"
    - ✅ "뭐가 제일 헷갈리세요?"
    - ✅ "이거 없으면 어떻게 하고 계셨어요?" (기존 대안 파악)
  - 핵심 루프
    - 빨리 만들어서 → 모아서 보여주고 → 반응 관찰하고 → AI와 함께 고치기
    - 이 사이클을 많이 돌리는 게 승리
    - 빨리 틀려보는 것이 가장 빨리 성공하는 길
    - 피드백은 기능 추가 요청이 아니라 "어디서 막혔는지"에 집중

[04장] 배포해서 세상에 보여주기

04.1 git과 GitHub — 무한 세이브 슬롯과 온라인 보관함
  - git = 무한 세이브 슬롯
    - 코드가 꼬여도 잘 됐을 때로 되돌리는 시간 여행 장치
    - 게임에서 보스 전 세이브하는 것과 같음
  - GitHub = 온라인 보관함
    - 내 컴퓨터가 고장 나도 코드는 안전

## Part 2. 코덱스로 콘텐츠 자동화 시작하기

[07장] 스킬, 에이전트, AGENTS.md — 코덱스 자동화의 도구들

07.1 자동화란 — 반복을 코덱스에게 넘기기
  - 자동화는 거창한 게 아니다
    - 매번 수작업으로 하던 일을 명령 한 줄로 실행하는 것
  - 어떤 반복이 자동화에 적합할까
    - 매일/매주 반복되는 작업
    - 순서가 정해진 작업
    - 판단이 적은 작업
07.2 스킬과 파이프라인 — 명령 한 줄로 복잡한 작업 실행하기
  - 스킬이란
    - 여러 단계를 `$write`, `$publish` 같은 한 줄로 묶은 것
    - 특정 작업에 특화된 프롬프트+도구+단계 정의
  - 파이프라인이란
    - 스킬이 서브에이전트를 순서대로(또는 동시에) 띄워서 일을 처리하는 전체 흐름
    - 예: 수집 → 집필 → 퇴고 → 발행
    - 같은 개념을 다르게 부르는 말들
      - 워크플로우(workflow): 작업이 흘러가는 순서 — 파이프라인과 같은 뜻
      - 오케스트레이션(orchestration): 서브에이전트를 조율하는 과정 — 파이프라인을 실행하는 행위
      - 멀티 에이전트(multi-agent): 에이전트가 여러 개 참여하는 구조 — 파이프라인의 특성
      - 이 책에서는 **파이프라인** 하나로 통일
  - 스킬 파일 구조
    - `skills/write/SKILL.md` — 스킬 이름 폴더 안에 마크다운으로 정의
    - 입력, 출력, 중간 단계(파이프라인)를 순서대로 적음
  - 스킬을 만들 때 생각할 것
    - 입력은 뭔지
    - 출력은 뭔지
    - 중간에 사람이 확인할 지점은 어디인지
07.3 에이전트 — 역할이 정해진 AI 담당자
  - 에이전트란
    - "조사 담당", "글쓰기 담당"처럼 맡은 일만 하는 전문가
  - 스킬 vs 에이전트
    - 스킬: "무슨 작업을 할지" (작업 단위) — `$write`, `$news`
    - 에이전트: "누가 할지" (역할 단위) — @writer, @editor
  - 내장 에이전트 3종
    - default — 범용 (기본값)
    - worker — 구현 집중 (코드 작성, 파일 생성)
    - explorer — 탐색 집중 (코드베이스 읽기, 검색)
  - 커스텀 에이전트 정의
    - `.codex/agents/writer.toml` — TOML 파일로 역할 정의
    - 필수 필드: `name`, `description`, `developer_instructions`
    - 선택 필드: `model`, `sandbox_mode`, `mcp_servers`
    - `prompts/writer.md`는 역할 계약서 (톤, 금지 표현 등) → TOML의 `developer_instructions`에서 참조
  - 서브에이전트 — 에이전트가 에이전트를 부리는 구조
    - 스킬이 서브에이전트를 생성(spawn)하고, 결과를 기다렸다가 통합
    - 병렬 실행: 서로 의존하지 않는 서브에이전트는 동시에 돌림
    - `/agent` 명령으로 실행 중인 서브에이전트 스레드 전환·점검 가능
07.4 AGENTS.md — 프로젝트에 지침 내려두기
  - AGENTS.md란
    - 코덱스가 프로젝트를 열 때마다 자동으로 읽는 규칙 파일
    - 프로젝트 루트에 `AGENTS.md` 하나만 놓으면 됨
  - 뭘 쓰면 좋을까
    - 프로젝트 설명
    - 코딩 컨벤션
    - 금지 사항
    - 사용할 기술 스택
  - 글로벌 설정
    - `~/.codex/config.toml` — 모든 프로젝트에 적용되는 전역 설정
    - `agents.max_threads` — 동시 실행 가능한 서브에이전트 수 (기본 6)
    - `agents.max_depth` — 서브에이전트 중첩 깊이 (기본 1, 재귀 방지)
    - `agents.job_max_runtime_seconds` — 작업 타임아웃
  - AGENTS.md의 한계
    - 너무 길면 무시됨
    - 모순되면 혼란
  - [실습] 02장 캐릭터 채팅에 AGENTS.md 작성하고 코덱스 동작 차이 확인
07.5 프로젝트 폴더 구조 — 자동화의 설계도
  - 코덱스 자동화 프로젝트의 기본 구조
    - `AGENTS.md` — 프로젝트 규칙 (항상 적용)
    - `skills/` — 스킬 모음 (필요할 때 호출)

    - `docs/` — 레퍼런스 문서 (톤가이드, 용어맵 등)
  - AGENTS.md vs 스킬 vs 에이전트 TOML
    - AGENTS.md: 항상 적용되는 전역 규칙
    - 스킬: 특정 키워드로 호출할 때만 작동 (파이프라인 정의)
    - 에이전트 TOML: 서브에이전트로 spawn될 때 적용되는 역할 정의
  - [실습] "코드 리뷰해줘" 스킬 작성해보기 (`skills/review/SKILL.md`)

[08장] 블로그 연재 자동화 — $write 한 줄로 글 완성하기

08.1 블로그 자동화의 구조 — 스킬이 서브에이전트를 돌리는 파이프라인
  - 실제 프로젝트의 폴더 구조 보기
    - `skills/write/SKILL.md` — $write 스킬 (파이프라인 정의)
    - `.codex/agents/writer.toml` — 집필 서브에이전트 정의 (TOML)
    - `.codex/agents/editor.toml` — 퇴고 서브에이전트 정의 (TOML)
    - `prompts/writer.md` — 집필 역할 계약서 (톤, 구조 규칙)
    - `prompts/editor.md` — 퇴고 역할 계약서 (삭제 기준, 품질 점수)
    - 스킬 = 팀장(파이프라인 정의), 서브에이전트 = 담당자(실행)
  - $write 파이프라인의 실제 흐름
    - ① 준비: 톤가이드·용어맵 등 레퍼런스 문서 읽기
    - ② 병렬 spawn: @collector(로컬 수집)과 @researcher(웹 리서치)를 동시에 띄움
    - ③ 통합 대기: 두 서브에이전트 결과가 돌아올 때까지 기다린 뒤, 소재를 합침
    - ④ 집필 spawn: @writer 서브에이전트가 소재를 받아 초안 작성
    - ⑤ 퇴고 spawn: @editor 서브에이전트가 군살 제거·톤 교정
    - ⑥ 품질 체크: 점수 기준 미달이면 ④→⑤ 재실행 루프
  - 왜 서브에이전트로 나눠야 하나
    - "블로그 글 써줘" 한 문장 → 품질 들쭉날쭉
    - 서브에이전트별로 역할과 품질 기준을 분리하면 결과가 안정됨
    - 병렬 실행 가능한 단계는 동시에 돌려서 속도도 빨라짐
08.2 [실습] 프로젝트 폴더 세팅하기 — 스킬 + 서브에이전트 파일 만들기
  - 스킬 파일 만들기: `skills/write/SKILL.md`
    - 파이프라인 순서 정의 (준비→병렬 수집→집필→퇴고)
    - 어떤 서브에이전트를 spawn하고, 어떤 순서로 통합할지
    - 입력: 주제, 출력: 완성 원고
  - 서브에이전트 TOML 만들기
    - `.codex/agents/writer.toml` — name, description, developer_instructions
    - `.codex/agents/editor.toml` — name, description, developer_instructions
    - TOML은 "이 서브에이전트가 뭘 하는지", prompts/는 "어떻게 하는지"
  - 역할 계약서 만들기
    - `prompts/writer.md` — 집필 역할 계약서
      - 글 구조 규칙 (도입·본론·마무리)
      - 톤 규칙 ("~합니다" 체, 예시 2개 이상 포함)
      - 참고할 레퍼런스 파일 경로
    - `prompts/editor.md` — 퇴고 역할 계약서
      - 삭제 기준 (중복 문장, 불필요한 수식어)
      - 길이 제한 (2000자 이내)
      - 품질 점수 기준 (8점 이상 PASS, 미달 시 재작성)
  - 레퍼런스 문서 만들기
    - `docs/tone-guide.md` — 말투·금지 표현 모음
    - `docs/term-map.md` — 용어 통일 사전 (예: "바이브코딩" not "바이브 코딩")
08.3 파이프라인 설계 — 서브에이전트를 몇 개로, 어떤 순서로
  - 08.2 구조가 파이프라인인 이유
    - `$write` 스킬 = 팀장 (파이프라인 정의, 결과 검수)
    - @writer / @editor = 서브에이전트 (각자 맡은 일만 수행)
  - 순차 vs 병렬 — 언제 동시에 돌리나
    - 서로 의존하지 않는 단계 → 병렬 spawn (예: 로컬 수집 + 웹 리서치)
    - 앞 단계 결과가 필요한 단계 → 순차 spawn (예: 집필 → 퇴고)
  - 실제 프로젝트 사례
    - 웹소설 프로젝트: @writer → @brutal-editor → @proofreader → @cold-reader (신규독자 시뮬)
    - 유튜브 프로젝트: @episode-writer → @episode-proofreader → @learning-tracker (학습 상태 추적)
    - 서브에이전트를 나눌수록 역할이 명확해지고, 품질 체크 포인트가 늘어남
  - 판단 기준
    - 나눠야 할 때: 역할이 다르고 품질 기준도 다를 때
    - 합쳐야 할 때: 단계가 너무 잘게 쪼개져서 오히려 느릴 때
08.4 [실습] $write로 블로그 글 완성하기
  - "AI 코딩 에이전트 입문" 주제로 `$write` 실행
  - 단계별 중간 결과 확인
    - 로컬 수집 결과 → 웹 리서치 결과 → 초안 → 퇴고본
  - 품질 루프 체험
    - 점수 미달이면 자동으로 재작성되는 과정 관찰
  - 수동 톤 조정
    - "도입부를 더 짧게", "예시를 실제 서비스 이름으로 바꿔줘"
    - 피드백을 톤가이드에 반영 → 다음 글부터 자동 적용
  - [완성 코드 GitHub 링크 제공]
08.5 결과가 달라지는 이유 — 컨텍스트와 레퍼런스
  - 같은 $write인데 왜 결과가 다를까
    - 레퍼런스 문서의 차이: 톤가이드가 다르면 같은 주제도 다른 글이 나옴
    - 로컬 소재의 차이: 내 폴더에 뭐가 있느냐에 따라 예시가 달라짐
  - 컨텍스트 윈도우
    - AI가 한 번에 읽을 수 있는 텍스트 양의 한계
    - 넘치면: 앞의 지시를 잊어버림, 레퍼런스를 무시함
  - 실전 팁
    - 레퍼런스 문서는 짧고 명확하게 유지
    - 새 대화를 자주 시작 — 대화가 길어지면 품질 하락
    - 중요한 규칙은 AGENTS.md나 에이전트 파일에 박아두기 (대화로 전달하지 않기)

[09장] 뉴스봇 만들기 — 수집→분류→요약 파이프라인

09.1 뉴스봇의 구조 — 블로그 자동화와 뼈대가 같다

    - ② 병렬: 서로 독립적인 단계는 동시 spawn (로컬 수집 + 웹 리서치)

  - "이 다섯 패턴이면 블로그든 뉴스봇이든 유튜브든 확장 가능"

[10장] 오픈클로 설치하고 첫 대화하기

10.1 코덱스와 뭐가 다른가 — 24시간 돌아가는 로컬 에이전트
  - 코덱스 vs 오픈클로
    - 코덱스: 내가 시킬 때만 일함, 노트북 닫으면 끝
    - 오픈클로: cron으로 알아서 돌아감, 맥미니·서버처럼 상시 켜둔 머신이 기본
  - 실행 환경이 다르다
    - 코덱스 — 내 작업용 노트북에서 대화하듯 사용, 뚜껑 닫으면 멈춤
    - 오픈클로 — 맥미니·라즈베리파이·클라우드 VM 등 "꺼지지 않는 컴퓨터"에 설치해서 24시간 가동
    - 왜 따로 머신이 필요한가: 자고 있을 때도, 주말에도 cron이 돌아야 하니까
  - 권한이 크니까 격리가 필요하다
    - 오픈클로는 파일 읽기·쓰기, 외부 API 호출, 터미널 명령 실행 등 권한이 넓음
    - 내 작업 폴더를 통째로 건드릴 수 있으므로, 전용 폴더(워크스페이스)로 격리
    - 실수 방지 세 가지: ① 전용 사용자 계정, ② 워크스페이스 밖 접근 차단, ③ 위험 명령 허용 목록
  - 코덱스 OAuth 연동
    - 오픈클로에서 코덱스 계정으로 로그인 → 추가 API 과금 없이 사용 가능
  - 같이 쓰면 좋은 이유
    - 코덱스로 만들고 → 오픈클로에게 맡기기 (개발은 코덱스, 운영은 오픈클로)

    - 예: Slack에 메시지 보내기, Notion에 DB 행 추가, 웹페이지 스크래핑
  - [실습] Slack MCP 연결
    - 봇 토큰 등록 → 오픈클로가 Slack 채널에 직접 메시지 보내기
  - [실습] Notion MCP 연결
    - 뉴스 아카이브 DB에 요약 자동 저장
  - [실습] Firecrawl MCP 연결
    - RSS가 없는 사이트도 웹 스크래핑으로 수집
    - 마크다운으로 받아서 토큰 절감 (스크린샷 대비 10배 효율)
13.3 [실습] cron으로 수집→분류→발송 자동화하기
  - 매일 아침 8시 자동 뉴스 수집 cron 설정
  - 파이프라인 한 번에 돌리기
    - 수집(collector) → 분류·요약(summarizer) → Slack 발송 + Notion 저장
  - 실행 로그에서 각 단계 확인
    - 수집된 기사 수, 분류 결과, 요약 품질 점수
    - 오류 발생 시 어디서 끊겼는지 로그로 파악
13.4 하네스 엔지니어링 — 에이전트를 안전하게 다루는 법
  - 하네스(harness)란
    - 에이전트에게 달리는 고삐 — 실행 범위와 권한을 제한하는 장치
  - 왜 필요한가
    - cron으로 자동 실행 = 내가 안 보는 사이에 AI가 행동
    - 잘못된 요약이 Slack에 바로 나가면 곤란
  - 승인 규칙 설정
    - "외부 발송(Slack, SNS)은 미리보기 → 사람 승인 → 발송"
    - "파일 삭제는 반드시 사람이 확인"
  - 실행 범위 제한
    - 특정 폴더만 접근 허용
    - 특정 MCP 도구만 호출 허용
  - [실습] 뉴스봇에 "Slack 발송 전 미리보기 → 승인 → 발송" 규칙 설정
13.5 [칼럼] 파이프라인, 어디까지 쪼개야 할까
  - 서브에이전트를 많이 쪼개면 좋은 것 아닌가?
    - 기술적으로는 서브에이전트 수십 개를 동시에 돌릴 수 있음
    - 하지만 서브에이전트 간 컨텍스트 전달 비용이 큼 (토큰 소모)
    - 쪼갤수록 결과 품질이 오히려 떨어지는 지점이 있음
  - 병렬이 좋을 때 vs 순차가 좋을 때
    - 병렬: 입력이 서로 독립적일 때 (로컬 수집 + 웹 리서치)
    - 순차: 앞 단계 결과가 다음 단계 품질을 좌우할 때 (집필 → 퇴고)
  - 실전 결론
    - 웹소설도 $write → $review → $qa 순서대로 돌림 (핵심 흐름은 순차)
    - 병렬은 수집처럼 "많이 모으는" 단계에서만 효과적
    - "되는데 안 쓰는 이유"를 아는 게 진짜 노하우
