# [부록 A] PG 붙이기 — 결제가 되면 서비스다

05장에서 Vercel로 배포까지 마치고, 주변 사람들에게 링크를 보냈더니 "이거 돈 내고 쓸 수 있어?" 같은 반응이 돌아왔다면, 축하드립니다. 여러분의 사이드 프로젝트가 '서비스'로 진화할 준비가 된 겁니다.

이 부록에서는 **테스트 결제를 직접 붙여보는 것**까지만 다룹니다. 실제 사업자등록을 하고 정식으로 돈을 받는 과정은 그 이후의 일이에요. 지금은 "아, 결제라는 게 이렇게 붙는 거구나"를 몸으로 느끼는 게 목표입니다.

---

## A.1 결제는 왜 마지막에 붙이나

스터디를 운영하면서 가장 많이 받는 질문 중 하나가 이겁니다. "저 결제부터 붙이고 싶은데요." 마음은 이해합니다. 돈이 들어와야 진짜 서비스 같으니까요. 하지만 결제를 먼저 붙이는 건, 식당을 차리면서 메뉴도 정하기 전에 카드 단말기부터 설치하는 것과 같습니다.

### 서비스가 먼저 돌아가야 결제를 붙일 의미가 있다

결제는 여러분의 서비스에 '붙이는' 거지, 결제 자체가 서비스는 아닙니다. 

01 사람들이 써보고 "이건 돈 낼 만해"라는 반응이 나와야 합니다.
02 어떤 기능에 돈을 받을지, 얼마를 받을지가 정해져야 합니다.
03 그래야 결제 버튼을 어디에 놓을지, 무슨 상품을 팔지 설계할 수 있습니다.

05장에서 배포하고 반응을 받는 루프를 먼저 돌리라고 한 이유가 바로 이겁니다.

### 결제가 붙으면 달라지는 것들

결제를 붙이는 순간, '취미 프로젝트'에서 '사업'으로 넘어가는 문턱을 밟게 됩니다. 아직 겁먹을 필요는 없지만, 어떤 것들이 달라지는지는 미리 알아두면 좋습니다.

| 항목 | 무료 서비스일 때 | 결제가 붙으면 |
| :--- | :--- | :--- |
| **법적 요건** | 특별히 없음 | 사업자등록, 통신판매업 신고 |
| **보안** | 기본만 챙기면 됨 | 개인정보 처리, 결제 데이터 보호 |
| **고객 대응** | "버그 고칠게요~" | 환불 정책, 취소 처리 의무 |
| **세금** | 없음 | 부가세, 소득세 신고 |

이 부록에서는 **테스트 모드**로만 실습하기 때문에 위 항목들을 당장 준비할 필요는 없습니다. 하지만 실제로 돈을 받기 시작할 때는 반드시 챙겨야 할 목록이니 머릿속에 넣어두세요.

## A.2 PG란 무엇이고, 뭘 준비해야 하나

### PG(Payment Gateway) = 카드사와 내 서비스 사이의 중개자

여러분이 네이버 쇼핑이나 쿠팡에서 카드 결제를 할 때, 그 돈이 바로 판매자에게 가는 게 아닙니다. 중간에 결제를 대신 처리해주는 회사가 있어요. 그게 바로 **PG사(결제대행사)**입니다.

왜 이런 중개자가 필요할까요?

- **계약의 편의**: PG 없이 카드 결제를 받으려면 신한, 삼성, 현대 등 국내 8~9개 카드사와 일일이 계약해야 합니다. PG를 쓰면 계약 한 번으로 모든 카드 결제를 받을 수 있습니다.
- **보안 책임**: 카드 번호 같은 민감한 정보를 우리 서버에 직접 저장하면 엄청난 보안 책임을 져야 합니다. PG사가 이 보안 시스템을 대신 구축해주고, 사고 시 책임도 집니다.
- **통합 관리**: 카드사별로 제각각인 정산 내역을 PG사가 하나로 묶어서 관리 페이지를 제공합니다.

식당 비유로 하자면, PG사는 **'배달의민족'** 같은 존재입니다. 고객이 음식값을 내면 배민이 받아서 수수료를 떼고 식당에 넘겨주죠. 우리도 마찬가지입니다. 고객이 결제하면 PG사가 받아서 수수료를 떼고 우리 통장에 넣어줍니다.

<!-- IMG: 고객 → PG사(결제대행) → 카드사/은행 → 정산 → 우리 통장, 흐름을 보여주는 간단한 다이어그램 -->

### 결제 한 건이 흐르는 경로

고객이 결제 버튼을 누르면 어떤 일이 벌어질까요? 두 단계로 나뉩니다.

**1단계: 승인 (실시간)**
01 고객이 결제 버튼을 누릅니다.
02 PG사가 제공하는 결제창이 뜹니다.
03 카드 번호를 입력하거나 카카오페이 같은 간편결제로 인증합니다.
04 카드사가 "이 사람 한도 괜찮아요, 승인!"하면 "결제 완료" 화면이 뜹니다.

**2단계: 정산 (며칠 소요)**
01 승인된 거래가 정산 대상으로 확정됩니다.
02 PG사 계약 주기에 따라 우리 통장에 돈이 들어옵니다.

여기서 가장 중요한 건 이겁니다. **결제 승인이 났다고 바로 돈이 들어오는 게 아닙니다.** 보통 영업일 기준 5일(D+5) 정도 걸려요. 이건 모든 온라인 서비스가 마찬가지입니다.

### 테스트 모드 — 사업자등록 없이도 된다

"사업자등록증이 없는데 어떡하죠?" 걱정하지 마세요. 모든 PG사는 **테스트 모드(Sandbox)**를 제공합니다. 실제 돈이 오가지 않는 가상 환경에서 결제 흐름을 마음껏 연습할 수 있습니다.

테스트 모드에서는:
- 사업자등록 없이 바로 시작할 수 있습니다
- 가짜 카드 번호로 결제를 테스트합니다
- 실제 돈이 빠져나가지 않습니다
- 취소, 환불 흐름도 전부 연습할 수 있습니다

우리는 이 부록에서 **테스트 모드만** 사용할 겁니다.

## A.3 [실습] 테스트 결제 연동하기

자, 이제 진짜로 결제 버튼을 붙여봅시다. 05장에서 만든 서비스에 "결제하기" 버튼을 추가하고, 테스트 결제가 되는 것까지 확인할 겁니다.

### STEP 1. 테스트 키 발급받기

어떤 PG사를 쓰든 과정은 비슷합니다. 가입하고, 테스트용 프로젝트를 만들고, API 키를 받는 거예요.

01 PG사 홈페이지에서 회원가입을 합니다.
02 관리자 페이지에 로그인한 뒤, **테스트용 프로젝트**를 생성합니다.
03 프로젝트 설정에서 **테스트 API 키**를 복사해둡니다.

> **테스트 키 vs 운영 키**: PG사는 두 종류의 키를 줍니다. 테스트 키는 가짜 결제용, 운영 키는 진짜 결제용입니다. 지금은 테스트 키만 씁니다. 절대 운영 키를 코드에 직접 넣으면 안 됩니다!

<!-- IMG: PG 관리자 페이지에서 테스트 키를 복사하는 화면 -->

### STEP 2. 코덱스에게 결제 버튼 만들어달라고 하기

05장에서 배운 것처럼, 코덱스에게 시킵니다. 직접 코드를 짜려고 하지 마세요.

01 VS Code에서 프로젝트 폴더를 엽니다.
02 터미널에서 `codex`를 실행합니다.
03 코덱스에게 다음과 같이 말하세요.

> "결제 기능을 추가해줘. PG사 JavaScript SDK를 CDN으로 불러오고, '1,000원 결제하기' 버튼을 만들어줘. 버튼을 누르면 결제창이 뜨도록 해줘. 테스트 모드로 설정하고, application_id는 환경변수에서 가져오게 해줘."

04 코덱스가 HTML 파일에 결제 버튼과 JavaScript 코드를 추가할 겁니다.
05 `.env` 파일에 테스트 키를 넣으라고 안내할 수도 있습니다. 코덱스의 안내를 따르세요.

**확인**: 브라우저에서 페이지를 열었을 때 "1,000원 결제하기" 버튼이 보이나요?

### STEP 3. 테스트 결제 해보기

01 방금 만든 "결제하기" 버튼을 클릭합니다.
02 PG사의 결제창이 뜹니다. 테스트 모드에서는 가상의 카드 정보를 입력할 수 있습니다.
03 결제를 진행합니다.
04 "결제가 완료되었습니다" 화면이 뜨면 성공입니다!

<!-- IMG: 테스트 결제창이 뜨고 결제 완료되는 화면 -->

이 순간을 기억하세요. 여러분이 만든 서비스에서 결제가 '작동'하는 걸 처음 보는 순간입니다. 비록 테스트 모드라 진짜 돈은 안 빠져나가지만, 실제 결제 흐름은 이것과 100% 동일합니다.

### STEP 4. 결제 결과 확인하기

결제가 성공했다고 끝이 아닙니다. 우리 서비스가 "이 사람이 결제했다"는 사실을 알아야 합니다.

01 PG사 관리자 페이지에 로그인합니다.
02 **거래 내역**에서 방금 테스트한 결제가 보이는지 확인합니다.
03 결제 상태가 '완료'로 표시되어 있나요?

> **웹훅(Webhook)이란?** PG사가 "결제 됐어요!"라고 우리 서버에 자동으로 알려주는 장치입니다. 택배로 치면 '배송 완료 알림 문자'와 같은 거예요. 테스트 단계에서는 관리자 페이지에서 눈으로 확인하면 되지만, 실제 서비스에서는 이 웹훅을 반드시 설정해야 합니다. "결제했는데 상품이 안 열려요"라는 CS의 90%가 웹훅 미설정 때문입니다.

### STEP 5. 테스트 결제 취소해보기

결제만큼 중요한 게 **취소**입니다. 고객은 결제 버튼보다 취소 버튼을 더 많이 찾거든요.

01 PG사 관리자 페이지의 거래 내역에서 방금 결제한 건을 찾습니다.
02 **취소** 버튼을 누릅니다.
03 결제 상태가 '취소 완료'로 바뀌는지 확인합니다.

여기까지 했으면 "결제 → 확인 → 취소"의 전체 흐름을 한 바퀴 돌린 겁니다. 축하드립니다!

## A.4 결제 검증 체크리스트

테스트 결제가 한 번 됐다고 안심하면 안 됩니다. "되네요!"라고 체크하고 넘어갔다가 실제 서비스에서 사고가 터지는 경우가 정말 많습니다. 자동차를 사고 시동만 걸어본 채 고속도로에 올라가는 것과 같은 거예요.

### 실제 서비스로 넘어가기 전, 반드시 확인할 것들

테스트 환경과 실제 환경은 결정적으로 다른 점이 3가지 있습니다.

| 항목 | 테스트 환경 | 실제 환경 | 왜 중요한가 |
| :--- | :--- | :--- | :--- |
| **API 키** | 테스트 키 (가짜 결제) | 운영 키 (진짜 결제) | 키를 안 바꾸면 결제창이 안 뜸 |
| **웹훅 주소** | localhost 가능 | 실제 도메인 필수 | 안 바꾸면 결제 확인이 안 됨 |
| **카드 한도** | 무한대 | 고객 카드 상태에 따라 다름 | 테스트에서 안 터지던 에러가 터짐 |

### 금액 검증 — 가장 흔한 실수

결제에서 가장 위험한 버그는 **금액이 안 맞는 것**입니다. 

- 화면에는 10,000원이라고 떠 있는데 실제로는 1,000원만 결제된다면?
- 할인 쿠폰을 적용했는데 결제 금액에 반영이 안 된다면?

코덱스에게 결제 기능을 만들어달라고 할 때, 이렇게 말해보세요.

> "결제 요청 전에 서버에서 금액을 한번 더 검증하는 로직을 넣어줘. 클라이언트에서 보낸 금액과 서버 DB의 상품 가격이 다르면 결제를 막아야 해."

### 취소와 환불 — 헷갈리면 돈이 샌다

이 두 단어는 같은 것 같지만 완전히 다릅니다.

- **취소**: 카드사 전산에서 결제를 되돌리는 것. 카드 결제를 취소하면 한도가 복원됩니다.
- **환불**: 고객 계좌로 직접 돈을 보내는 것. 가상계좌로 입금받은 후에는 이 방법밖에 없습니다.

**원칙**: 카드로 결제한 건은 반드시 카드 취소로 처리합니다. "현금으로 돌려드릴게요"를 하면 안 됩니다. 이건 카드깡 리스크에 노출되는 거예요.

### 흔한 실수 TOP 5

실제로 결제를 붙인 서비스에서 가장 많이 터지는 사고를 정리했습니다. 여러분은 이걸 미리 알고 있으니 같은 실수를 안 하겠죠.

**1. 테스트 키로 실서비스 오픈**
테스트 키를 운영 키로 안 바꾸고 배포하는 겁니다. 고객이 결제 버튼을 누르면 "유효하지 않은 상점"이라는 에러가 뜹니다. 배포 전에 `.env` 파일의 키가 운영 키인지 반드시 확인하세요.

**2. 환경변수 누락**
API 키를 코드에 직접 적어놓는 건 절대 하면 안 됩니다. 05장에서 배웠죠? `.env` 파일에 넣고, `.env`는 GitHub에 올리지 않는 게 철칙입니다. Vercel 같은 배포 서비스에는 환경변수를 별도로 등록해야 합니다.

**3. 웹훅 미설정**
결제는 됐는데 우리 서비스에서 "결제 완료"로 안 바뀌는 사고입니다. PG사가 결제 결과를 알려주려는데 우리 서버 주소를 안 알려줬으니 당연한 거죠. 실서비스에서는 웹훅 URL을 반드시 등록하세요.

**4. 결제 성공만 테스트하고 끝냄**
결제 성공보다 중요한 게 결제 실패, 취소, 환불입니다. 이 세 가지를 테스트하지 않으면 라이브 첫날부터 CS가 폭발합니다.

**5. 라이브 첫날 모니터링 안 함**
오픈 버튼을 누르고 퇴근하면 안 됩니다. 최소 24시간은 결제 로그를 지켜봐야 합니다. 특정 카드사 장애, 특정 브라우저 오류 같은 건 테스트 환경에서는 절대 잡히지 않거든요.

### 라이브 전환 전 최종 점검표

실제로 돈을 받기 시작하기 전에 이 목록을 하나씩 체크하세요.

- [ ] 이용약관에 취소·환불 기준을 명시했는가?
- [ ] 개인정보처리방침 페이지가 있는가?
- [ ] 사이트 하단에 상호, 대표자, 사업자번호, 연락처가 있는가?

**PG 심사**
- [ ] PG사에 가맹 심사를 신청했는가?
- [ ] 심사가 승인되었는가?
- [ ] 운영 키(Production Key)를 발급받았는가?

**기술 점검**
- [ ] 테스트 키를 운영 키로 교체했는가?
- [ ] 웹훅 URL을 실제 서비스 도메인으로 설정했는가?
- [ ] HTTPS가 적용되어 있는가?
- [ ] 서버에서 결제 금액을 검증하는 로직이 있는가?

**결제 테스트**
- [ ] 본인 카드로 실제 1원 결제를 해봤는가?
- [ ] 결제 후 서비스 DB에 주문이 정상 생성되는가?
- [ ] 결제 취소를 해봤는가? 카드사 앱에서 취소 알림이 오는가?
- [ ] 결제 실패 시 고객에게 안내 문구가 뜨는가?

> **PG 심사란?** 실제로 돈을 받으려면 PG사의 '가맹 심사'를 통과해야 합니다. 심사자가 보는 건 코드 품질이 아닙니다. "이 서비스가 실제로 뭘 파는지, 취소·환불을 어떻게 처리하는지"를 화면과 약관으로 확인하는 겁니다. 서비스 소개, 상품 가격, 이용약관, 회사 정보가 사이트에 보여야 심사가 통과됩니다.

## 여기서 막혔나요?

**Q. PG사가 너무 많은데 어디를 써야 하나요?**

**A.** 처음이시라면 하나만 골라서 테스트 모드로 시작하세요. 어떤 PG사든 테스트 모드의 사용법은 거의 비슷합니다. 중요한 건 PG사 선택이 아니라 "결제 흐름을 이해하는 것"입니다. 테스트를 해보고 나면 PG사를 바꾸는 것도 어렵지 않습니다.

**Q. 사업자등록이 없는데 결제를 붙일 수 있나요?**

**A.** 테스트 모드는 사업자등록 없이 됩니다. 하지만 실제로 돈을 받으려면 사업자등록이 필요합니다. 먼저 테스트로 결제 흐름을 익힌 뒤, 서비스에 확신이 생기면 그때 사업자등록을 해도 늦지 않습니다.

**Q. 코덱스에게 결제 기능을 시켰는데 에러가 나요.**

**A.** 결제 연동은 외부 서비스(PG사)와 통신하는 거라 에러가 자주 납니다. 에러 메시지를 그대로 복사해서 코덱스에게 보여주세요. "이 에러가 나는데 고쳐줘"라고 하면 됩니다. 대부분은 API 키가 잘못되었거나, SDK 버전이 안 맞는 문제입니다.

**Q. 결제 수수료는 얼마인가요?**

**A.** PG사마다 다르지만, 보통 결제 금액의 2~3.5% 정도입니다. 월 3만 원짜리 구독 서비스라면 한 건당 700~1,000원 정도가 수수료로 빠진다고 생각하시면 됩니다. 테스트 모드에서는 수수료가 발생하지 않습니다.

**Q. 정기결제(구독)도 코덱스로 만들 수 있나요?**

**A.** 네, 가능합니다. 다만 정기결제는 단건 결제보다 복잡합니다. 빌링키 발급, 자동 결제, 실패 시 재시도, 해지 처리까지 고려해야 하거든요. 먼저 이 부록에서 단건 결제를 마스터하고, 정기결제는 PG사의 공식 문서를 참고하시길 권합니다.

## 한 줄 정리

결제는 생각보다 어렵지 않습니다. 테스트 키를 받고, 코덱스에게 시키고, 결제 버튼을 눌러보면 됩니다.

진짜 어려운 건 코드가 아니라 "무엇을 팔 것인가, 취소는 어떻게 할 것인가"를 정하는 일입니다. 기술은 코덱스에게 맡기고, 여러분은 서비스의 '사장님' 역할에 집중하세요. 결제가 되는 순간, 여러분의 아이디어는 진짜 서비스가 됩니다.
