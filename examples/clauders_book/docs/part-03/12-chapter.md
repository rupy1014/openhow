# 12장 뉴스봇을 오픈클로에게 맡기기 — MCP와 하네스 엔지니어링

> "정보의 바다에서 익사하지 마세요. 이제는 비서가 떠다 주는 맛있는 정보만 골라 먹을 시간입니다."

지난 장에서 우리는 블로그 글을 자동으로 써주는 비서를 맥미니에 입주시켰습니다. 어떠신가요? 아침에 눈을 떴을 때 "주인님, 어제 요청하신 블로그 초안을 다 썼습니다"라는 메시지가 와 있는 그 기분, 정말 짜릿하지 않으셨나요? 

그런데 자동화의 세계는 여기서 끝이 아닙니다. 글을 쓰는 것만큼, 아니 어쩌면 그보다 더 중요한 게 있습니다. 바로 **'세상의 수많은 정보 중에서 나에게 꼭 필요한 것만 골라내는 능력'**입니다. 

사실 우리는 정보 과부하의 시대에 살고 있습니다. 매일 아침 뉴스레터 수십 통이 쏟아지고, 유튜브 알고리즘은 끝도 없이 새로운 영상을 추천하죠. 저와 함께 공부했던 한 수강생분은 매일 아침 업계 동향을 파악하는 데만 꼬박 2시간을 쓰신다고 하더라고요. 그러다 정작 본업을 시작하기도 전에 진이 다 빠져버리는 거죠.

이제 그 2시간을 여러분에게 돌려드리겠습니다. 08장에서 만들었던 '뉴스 요약 봇' 기억하시죠? 그때는 우리가 직접 스크립트를 실행해야 했지만, 이제는 **오픈클로(OpenClaw)라는 수석 비서**에게 이 업무를 완전히 인수인계할 겁니다. 오픈클로는 우리가 잠든 사이에도 뉴스를 읽고, 중요한 것만 추려서 텔레그램으로 보고할 준비가 되어 있습니다.

## 12.1 [실습] 뉴스봇 프로젝트를 오픈클로에 연결하기

자, 이제 본격적으로 뉴스봇을 오픈클로의 지휘 아래에 두어 보겠습니다. 08장에서 만들었던 프로젝트 폴더를 오픈클로가 인식할 수 있는 '워크스페이스'로 등록하는 작업부터 시작합니다.

01 터미널을 열고 여러분의 맥미니나 미니 PC에 접속합니다.

02 오픈클로 설정 파일(`openclaw.json`)을 엽니다. 보통 홈 디렉토리에 있습니다.
```bash

## 여기서 막혔나요?

**Q. 텔레그램에 메시지를 보냈는데 "해당 프로젝트를 찾을 수 없습니다"라고 나와요.**

**A.** `openclaw.json` 파일에 적은 폴더 경로가 실제 경로와 일치하는지 다시 한번 확인해보세요. 특히 `~` 표시(홈 디렉토리)를 썼다면 오픈클로가 실행되는 계정의 홈 디렉토리가 맞는지 체크해야 합니다. 가장 확실한 방법은 `/Users/이름/automation/...`처럼 전체 경로(절대 경로)를 다 적어주는 것입니다.

**Q. 뉴스를 가져오긴 하는데, 제가 원하지 않는 주제도 섞여 있어요.**

**A.** 그럴 땐 `AGENTS.md`를 더 혹독하게(?) 수정해야 합니다. "제외 키워드" 항목을 만들고 "비트코인, 가상화폐, 정치인은 절대 언급하지 마"라고 명시해보세요. 오픈클로는 아주 고지식한 비서라서, 여러분이 명시적으로 금지한 것은 절대 하지 않습니다.

**Q. RSS 주소가 잘못되었다고 에러가 납니다.**

**A.** RSS 피드 주소는 시간이 지나면 바뀌거나 서비스가 종료될 수도 있습니다. 브라우저 주소창에 해당 RSS 주소를 직접 넣어보세요. 외계어 같은 코드(XML)가 화면 가득 뜨면 정상이고, "404 Not Found" 같은 에러가 뜨면 주소가 바뀐 겁니다. 그럴 땐 코덱스에게 "최신 IT 뉴스 RSS 주소 좀 알려줘"라고 물어보세요.

## 한 줄 정리

뉴스봇을 오픈클로에 연결하는 것은 **'잠들지 않는 정보 요원'**에게 나만의 업무 매뉴얼(`AGENTS.md`)을 쥐여주는 과정이며, 이를 통해 우리는 쏟아지는 정보 속에서 나에게 꼭 필요한 정수만 골라 먹을 수 있게 되었습니다.

어떠신가요? 이제 뉴스를 읽기 위해 이 사이트 저 사이트 돌아다닐 필요가 없습니다. 텔레그램 한 줄이면 비서가 알아서 다 해오니까요. 하지만 여기서 만족하기엔 이 비서의 능력이 너무 아깝습니다. 

다음 섹션에서는 이 비서의 손에 더 강력한 도구를 쥐여줘 볼 겁니다. 바로 **MCP(Model Context Protocol)**입니다. 이 도구만 있으면 오픈클로는 단순히 뉴스를 읽는 것을 넘어, 여러분의 노션(Notion)에 정보를 저장하고, 슬랙(Slack)에 공유하며, 심지어 로그인이 필요한 웹사이트까지 직접 들어가서 정보를 캐내 올 수 있게 됩니다. 이제 진짜 '슈퍼 에이전트'가 탄생할 차례입니다. 준비되셨나요? 이어서 달려봅시다!


## 12.2 [실습] MCP로 외부 서비스 연결하기 — Telegram, Notion, Playwright

뉴스봇이 나에게 필요한 정보를 찰떡같이 요약해주는 것까지 확인하셨나요? 아마 터미널 화면에 올라오는 요약본을 보며 "와, 진짜 똑똑하네"라고 감탄하셨을 겁니다. 그런데 여기서 한 가지 아쉬움이 남습니다. 이 똑똑한 요약본을 보려면 매번 컴퓨터 앞에 앉아 터미널을 열어야 하거든요.

**"비서가 요약만 잘하면 뭐 하나요? 보고서도 올리고 기록도 남겨야 진짜 비서죠."**

우리가 원하는 건 이런 겁니다. 아침에 눈을 뜨면 스마트폰 텔레그램으로 뉴스 요약이 와 있고, 나중에 다시 보려고 노션(Notion)을 열면 예쁘게 정리된 데이터베이스가 나를 기다리는 모습이죠. 때로는 RSS가 없는 까다로운 사이트도 척척 들어가서 정보를 긁어오는 능력도 필요합니다. 

이 모든 마법을 가능하게 해주는 기술이 바로 **MCP(Model Context Protocol)**입니다. 말이 조금 어렵죠? 쉽게 생각하세요. MCP는 인공지능 비서에게 '손과 발'을 달아주는 **표준 USB 포트** 같은 겁니다. 

---

### MCP란 무엇일까요?

우리가 컴퓨터에 마우스나 키보드, 프린터를 연결할 때 어떤 구멍에 꽂나요? 맞습니다. 'USB 포트'입니다. 예전에는 프린터 구멍, 마우스 구멍이 다 달라서 복잡했지만, USB가 나오면서 모든 게 하나로 통일되었죠.

MCP도 똑같습니다. 이전에는 AI에게 텔레그램을 시키려면 텔레그램용 코드를 짜야 했고, 노션을 시키려면 노션용 코드를 따로 배워야 했습니다. 하지만 **MCP라는 표준 규격**이 생기면서, 이제는 오픈클로에게 "텔레그램 MCP 연결해"라고 한마디만 하면 끝납니다. 

- **기존 방식**: AI가 서비스를 이해하기 위해 매번 복잡한 사용법(API)을 공부해야 함.
- **MCP 방식**: 서비스마다 규격화된 '도구 세트'가 있고, AI는 그 도구를 꺼내 쓰기만 하면 됨.

자, 이제 이 강력한 도구들을 하나씩 우리 뉴스봇의 손에 쥐여줘 봅시다.

### [실습 1] 텔레그램 MCP 연결: "주인님, 뉴스 도착했습니다!"

가장 먼저 할 일은 보고 체계를 만드는 겁니다. 텔레그램은 자동화 비서와 대화하기에 가장 좋은 채널입니다. 슬랙(Slack)도 방식은 똑같으니, 하나만 제대로 익혀두시면 됩니다.

01 우선 텔레그램에서 **@BotFather**를 찾아 대화를 시작하세요. `/newbot`을 입력하고 이름과 아이디를 정해주면 긴 암호 같은 **'HTTP API Token'**을 줄 겁니다. 이게 우리 비서의 고유 신분증입니다.

02 이제 `openclaw.json` 설정 파일을 엽니다. 이곳에 우리가 받은 토큰을 등록할 겁니다.

```json
{
  "mcpServers": {
    "telegram": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-telegram"],
      "env": {
        "TELEGRAM_BOT_TOKEN": "여러분의_봇_토큰_값"
      }
    }
  }
}

03 오픈클로를 다시 실행한 뒤, 텔레그램 봇에게 말을 걸어보세요. "안녕?"이라고 보내면 됩니다.

### [실습 3] Playwright MCP 연결: "철벽 사이트도 뚫고 들어갑니다"

세상 모든 사이트가 RSS를 제공하면 좋겠지만, 현실은 그렇지 않습니다. 특히 인스타그램, 페이스북 같은 SNS나 보안이 까다로운 대형 포털들은 정보를 쉽게 내주지 않죠. 이럴 때 쓰는 '최종 병기'가 바로 **Playwright(플레이라이트)**입니다.

Playwright는 AI가 직접 **'가상 브라우저'**를 띄우는 도구입니다. 사람이 크롬 브라우저를 켜서 마우스로 클릭하고 스크롤을 내리는 동작을 AI가 그대로 흉내 내는 거죠.

01 터미널에서 필요한 도구를 먼저 설치합니다.
```bash
npx playwright install

02 `openclaw.json`에 Playwright MCP를 등록합니다.
```json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-playwright"]
    }
  }
}

## 여기서 막혔나요?

**Q. npx 명령어를 실행했는데 에러가 나요.**

**A.** 컴퓨터에 Node.js가 설치되어 있는지 확인해 보세요. 터미널에 `node -v`를 입력했을 때 숫자가 나오면 정상입니다. 만약 나오지 않는다면 1장에서 배운 설치 과정을 다시 한번 복습해 보세요.

**Q. 텔레그램 봇이 제 말을 무시해요.**

**A.** 텔레그램 봇에게 먼저 `/start`를 보냈는지 확인하세요. 봇은 보안상 먼저 말을 건 사람에게만 답장할 수 있습니다. 또한 `TELEGRAM_BOT_TOKEN` 뒤에 따옴표(`"`)를 빠뜨리지 않았는지도 체크해 보세요.

**Q. 노션 데이터베이스 ID는 어디서 찾나요?**

**A.** 노션 페이지의 주소창을 보세요. `notion.so/사용자이름/` 뒤에 나오는 **32자리의 복잡한 문자열**이 바로 ID입니다. 물음표(`?`) 앞까지만 복사해서 쓰시면 됩니다.

## 12.3 [실습] cron으로 수집→분류→발송 자동화하기

**"이 모든 게 여러분이 잠든 사이, 맥미니 안에서 자동으로 일어납니다."**

단순히 글자만 요약하던 녀석이 이제는 외부 세계와 소통하고 기록하는 진짜 '에이전트'가 되었습니다. 도구가 손에 익으니 이제 자동화가 훨씬 현실적으로 느껴지시죠? 

그런데 한 가지 문제가 남았습니다. 아무리 MCP를 잘 연결했어도, 결국 우리가 터미널을 열고 명령어를 직접 쳐야 한다면 그건 '반자동'일 뿐입니다. 진정한 자동화는 내가 쿨쿨 자고 있을 때, 혹은 바쁘게 회의하고 있을 때 AI 비서가 알아서 일을 끝내놓는 것이거든요.

이제 11장에서 배웠던 **'비서실장 cron'**을 다시 소환할 시간입니다. 뉴스봇에게 매일 아침 정해진 시간에 일을 시키는 마법의 알람을 설정해 봅시다.

### 매일 아침 8시, 뉴스봇을 깨우는 법

우리가 만든 뉴스봇은 총 네 단계로 움직입니다. 가져오고(수집), 고르고(분류), 요약해서, 보낸다(발송). 이 복잡한 과정을 한 번에 실행해 줄 '실행 스크립트'부터 만들어야 합니다.

**STEP 1. 뉴스봇 전용 실행 스크립트 만들기**

01 VS Code에서 뉴스봇 프로젝트 폴더로 이동합니다.
02 새 파일을 만들고 이름을 `run-newsbot.sh`라고 짓습니다. 확장자 `.sh`는 쉘 스크립트, 즉 '명령어 모음집'이라는 뜻입니다.
03 아래 내용을 복사해서 붙여넣으세요. 여기서 가장 중요한 건 **'절대 경로'**입니다. 

```bash
```
#!/bin/bash

# 1. 프로젝트 폴더로 이동 (반드시 본인의 실제 경로로 수정하세요!)
cd /Users/여러분의이름/automation/newsbot

# 2. 로그를 남길 폴더가 없으면 만듭니다
mkdir -p logs

# 3. 오픈클로를 실행하고 결과를 로그 파일에 기록합니다
# 수집 -> 분류 -> 요약 -> 발송 파이프라인을 한 번에 돌립니다.
/usr/local/bin/openclaw run "RSS에서 뉴스를 가져와서 AI 관련 기사만 골라 요약한 뒤 텔레그램으로 보고해줘." >> logs/newsbot.log 2>&1

echo "[$(date)] 뉴스봇 작업 완료!" >> logs/newsbot.log

04 파일을 저장한 뒤, 터미널에서 이 스크립트에게 실행할 수 있는 '권한'을 줘야 합니다. 아래 명령어를 입력하세요.
```bash
chmod +x run-newsbot.sh

```
**확인**: 터미널에 `./run-newsbot.sh`라고 쳤을 때, 뉴스봇이 평소처럼 작동하고 텔레그램 메시지가 오나요? 만약 그렇다면 '명령어 모음집'은 완벽하게 준비된 겁니다.

### 파이프라인 한 번에 돌리기: 수집부터 저장까지

자, 이제 이 스크립트를 cron에 등록할 차례입니다. 우리가 잠든 새벽이나 바쁜 아침 시간에 비서가 출근하도록 설정하는 거죠.

**STEP 2. crontab에 뉴스봇 알람 등록하기**

01 터미널에 `crontab -e`를 입력합니다. 검은 화면의 에디터가 열릴 겁니다.
02 가장 아랫줄로 내려가서 아래 내용을 입력하세요. 매일 아침 8시에 비서를 깨우라는 뜻입니다.

```bash
```
# 매일 아침 8시, 나만의 뉴스봇 실행
0 8 * * * /Users/여러분의이름/automation/newsbot/run-newsbot.sh

03 저장을 하고 빠져나옵니다. (vi 에디터라면 `:wq`를 입력하세요.)
04 "crontab: installing new crontab"이라는 메시지가 나오면 성공입니다.

이제 여러분은 매일 아침 8시마다 이런 경험을 하게 됩니다.

1. **수집 담당**: 오픈클로가 미리 지정해둔 5~10개의 IT 뉴스 RSS 피드를 샅샅이 훑습니다.
2. **분류·요약 담당**: 수백 개의 기사 중 내가 설정한 키워드(예: #AI #자동화 #신제품)가 들어간 것만 골라냅니다. 그리고 3줄 핵심 요약을 작성하죠.
3. **Telegram 발송**: 요약된 따끈따끈한 뉴스를 여러분의 텔레그램 채널로 즉시 전송합니다.
4. **Notion 저장**: 나중에 레퍼런스로 쓸 수 있게 노션의 '뉴스 아카이브' 데이터베이스에 기사 제목, 요약, 링크를 차곡차곡 쌓아둡니다.

### 오류가 났을 때: 코덱스에게 "에러 좀 봐줘" 시키기

자동화를 돌리다 보면 가끔 비서가 파업할 때가 있습니다. "Permission denied"라거나 "Network error" 같은 무시무시한 빨간 글씨가 로그에 찍히기도 하죠. 이때 당황해서 직접 코드를 고치려고 하지 마세요. 우리에겐 **박사급 인력인 코덱스**가 있잖아요.

오류 해결도 바이브코딩답게 '말'로 해결해 봅시다.

**STEP 4. 로그 기반 트러블슈팅**

01 로그 파일에서 에러가 난 부분을 마우스로 쭉 긁어서 복사합니다.
02 터미널에서 `codex`를 실행하고 이렇게 물어보세요.
> "뉴스봇을 cron으로 돌렸는데 로그에 이런 에러가 찍혔어. 왜 그런 건지 분석해주고 해결 방법도 알려줘. [여기에 로그 복사 붙여넣기]"

03 코덱스가 에러 원인을 분석해 줄 겁니다. 보통은 "파일 권한이 없네요"라거나 "노션 API 키가 만료되었습니다" 같은 아주 명확한 답을 줄 거예요.
04 코덱스가 준 수정 명령어를 그대로 복사해서 터미널에 붙여넣으면 끝입니다.

**"에러 메시지를 읽는 건 사람이 아니라 AI의 몫입니다. 여러분은 그 결과를 보고 판단만 하세요."**

---

## 여기서 막혔나요?

**Q. cron을 설정했는데 텔레그램으로 소식이 안 와요.**

**A.** 가장 흔한 이유는 '절대 경로'를 안 썼기 때문입니다. 스크립트 안에 `openclaw`라고만 쓰면 cron은 그게 어디 있는지 못 찾습니다. 반드시 `/usr/local/bin/openclaw`처럼 **집 주소 전체**를 적어주세요. 11장에서 배운 `which openclaw` 명령어로 경로를 꼭 확인해 보세요.

**Q. 로그 파일을 보려는데 "No such file or directory"라고 나와요.**

**A.** 스크립트를 실행한 위치와 로그가 저장되는 위치가 달라서 그럴 수 있습니다. `mkdir -p ~/automation/newsbot/logs` 명령어로 폴더를 미리 만들어두고, 스크립트 안에서도 로그 경로를 `~/automation/newsbot/logs/newsbot.log`처럼 정확히 적어주는 게 좋습니다.

**Q. 맥미니가 잠자기 모드로 들어가면 뉴스봇도 같이 자나요?**

**A.** 네, 맞습니다. 컴퓨터가 꺼지거나 잠들면 cron도 작동하지 않습니다. 서버로 쓰는 맥미니나 미니PC는 [시스템 설정] -> [에너지 절약]에서 **'디스플레이가 꺼져 있을 때 컴퓨터를 자동으로 자지 않게 하기'** 옵션을 꼭 켜두셔야 합니다. 24시간 깨어있는 사무실을 만들어주는 거죠.

---

## 한 줄 정리

cron은 오픈클로를 깨우는 **마법의 알람**이며, 이를 통해 우리는 **사람의 개입 없이도 매일 아침 최신 뉴스를 배달받는 '무인 정보 공장'**을 가지게 되었습니다.

자, 이제 여러분의 맥미니 안에서는 매일 아침 뉴스봇이 부지런히 돌아가고 있습니다. 그런데 한 가지 걱정이 생깁니다. 만약 비서가 내가 잠든 사이에 텔레그램으로 이상한 가짜 뉴스를 마구 발송하면 어떡하죠? 혹은 노션에 쓰레기 데이터를 수만 개 쌓아버리면요?

다음 섹션에서는 이런 사고를 막기 위한 **'하네스 엔지니어링'**을 배워볼 겁니다. 비서에게 고삐를 채워 안전하게 부리는 법, 기대하셔도 좋습니다!


## 12.4 하네스 엔지니어링 — 에이전트를 안전하게 다루는 법

자, 이제 여러분의 맥미니나 미니PC 안에서는 매일 아침 뉴스봇이 부지런히 돌아가고 있습니다. 내가 자고 있는 사이에도 AI 비서가 뉴스를 긁어모으고, 요약해서, 텔레그램으로 척척 보내주는 장면. 상상만 해도 뿌듯하시죠? 드디어 진정한 '무인 정보 공장'의 주인이 되신 겁니다. 

그런데 한 가지 걱정이 스멀스멀 올라옵니다. **"만약 내가 잠든 사이에 비서가 대형 사고를 치면 어떡하지?"** 

예를 들어볼까요? 뉴스봇이 실수로 가짜 뉴스를 진짜인 줄 알고 수만 명의 구독자가 있는 채널에 발송해버린다면요? 혹은 노션 데이터베이스에 똑같은 뉴스를 수천 개씩 쌓아서 내 소중한 저장 공간을 엉망으로 만든다면요? 생각만 해도 아찔합니다. 유능한 비서일수록 사고를 치면 그 규모도 남다르거든요.

그래서 우리에게는 '고삐'가 필요합니다. 아무리 똑똑한 말이라도 고삐가 없으면 어디로 튈지 모르니까요. 엔지니어들은 이 고삐를 **'하네스(Harness)'**라고 부릅니다. 이번 섹션에서는 AI 에이전트에게 안전벨트를 채우고, 우리가 정한 선을 넘지 못하게 만드는 **'하네스 엔지니어링'**의 정수를 배워보겠습니다. 비서에게 자유를 주되, 통제권은 여전히 우리가 쥐는 법입니다.

---

### 하네스(Harness)란: 에이전트에게 채우는 '안전 고삐'

'하네스'라는 단어가 조금 생소하시죠? 원래는 강아지 가슴줄이나 번지점프를 할 때 몸에 감는 안전 장구를 뜻합니다. 코딩의 세계에서도 비슷합니다. 에이전트가 마음대로 행동하지 못하게 **실행 범위와 권한을 딱딱 정해주는 장치**를 말하죠.

솔직히 말씀드리면, 앞서 배운 `cron`으로 자동 실행을 설정하는 순간 여러분은 에이전트에게 '무한한 자유'를 준 것과 다름없습니다. 사람이 보고 있지 않으니까요. 하네스 엔지니어링은 그 자유에 '책임'이라는 안전장치를 다는 작업입니다. 

**"AI는 시키는 대로만 합니다. 하지만 그 '시키는 대로'의 범위를 정하는 건 주인의 몫입니다."**

<!-- IMG: 폭주하는 AI 로봇의 팔을 사람이 조종간(하네스)으로 꽉 붙잡고 제어하는 모습의 삽화 -->

---

### 왜 하네스가 필요할까요? (실제 사고 사례)

"에이 AI가 사고를 쳐봐야 얼마나 치겠어?"라고 생각하실 수도 있습니다. 하지만 실제로 자동화를 돌리다 보면 이런 일이 빈번하게 일어납니다.

1.  **무한 루프의 공포**: 뉴스봇이 어떤 기사를 읽다가 에러가 났는데, 에이전트가 "다시 해볼까?"를 무한 반복하며 API 사용료를 하룻밤 새 100달러나 써버리는 경우.
2.  **민감 정보 유출**: 에이전트가 "뉴스 요약해서 보내줘"라는 말을 너무 광범위하게 해석해서, 내 컴퓨터 구석에 있던 개인적인 메모장 파일까지 요약해서 텔레그램 채널에 올려버리는 경우.
3.  **데이터 오염**: 요약 톤이 갑자기 바뀌어서 반말과 욕설이 섞인 뉴스가 발송되거나, 노션 DB의 기존 데이터를 몽땅 지워버리고 새로 쓰는 경우.

이런 사고는 기술이 부족해서가 아니라, **'하지 말아야 할 것'**을 가르쳐주지 않았기 때문에 발생합니다. 그래서 우리는 하네스를 통해 에이전트의 행동 반경을 좁혀야 합니다.

---

### 승인 규칙 설정: "내 도장 찍기 전엔 나가지 마"

하네스의 핵심 중의 핵심은 바로 **'승인 규칙(Approval Rules)'**입니다. 에이전트가 위험한 행동을 하기 직전에 "주인님, 이거 해도 될까요?"라고 멈춰 서게 만드는 거죠. 

특히 텔레그램 발송이나 SNS 발행처럼 '밖으로 나가는 일'은 반드시 사람의 눈을 거쳐야 안전합니다. 오픈클로에서는 이 과정을 아주 우아하게 설정할 수 있습니다. 바로 `AGENTS.md` 파일에 **'검수 단계'**를 명시하는 겁니다.

> **🙋 질문이요! 매번 승인하면 자동화가 아니지 않나요?**
> 날카로운 질문입니다! 하지만 '완전 자동'과 '반자동' 사이에는 큰 차이가 있습니다. 처음 1~2주 동안은 승인 단계를 두고 에이전트의 실력을 지켜보세요. 비서가 충분히 신뢰를 쌓았을 때 그때 고삐를 조금씩 풀어주는 게 지혜로운 주인의 자세입니다.

---

### [실습] 뉴스봇에 "발송 전 미리보기 → 승인 → 발송" 규칙 설정하기

자, 이제 우리의 뉴스봇에 안전장치를 달아봅시다. 에이전트가 뉴스를 요약하자마자 텔레그램으로 쏘는 게 아니라, 우리에게 먼저 요약본을 보여주고 승인을 기다리게 만들 겁니다.

01 프로젝트 폴더 안의 `AGENTS.md` 파일을 엽니다. (만약 없다면 새로 만드세요.)

02 아래와 같이 **'Critical Rules(치명적 규칙)'**와 **'Response Format(응답 형식)'**을 추가합니다. 

# 뉴스봇 에이전트 지침서 (AGENTS.md)

## 실행 규칙
1. 모든 뉴스는 요약 후 반드시 `status: needs_review` 상태로 보고하라.
2. **텔레그램 발송(`telegram.send`)은 반드시 사용자의 최종 승인 메시지를 확인한 후에만 실행한다.**
3. 사용자가 "발송해"라고 하면 발송하고, "수정해"라고 하면 요약을 다시 한다.

## 응답 형식
작업 완료 후 반드시 아래 JSON 형식으로 응답하라:
```json
{
  "status": "needs_review",
  "summary": "오늘의 뉴스 요약본 내용...",
  "next_steps": ["사용자 승인 대기", "텔레그램 발송 준비"]
}

03 이제 오픈클로를 실행하고 "오늘 뉴스 요약해서 보내줘"라고 시켜보세요.

04 이전 같으면 바로 텔레그램 메시지가 왔겠지만, 이제 에이전트는 요약본을 화면에 보여주며 멈춰 설 겁니다. "주인님, 요약이 끝났습니다. 이대로 발송할까요?"라고 물어보죠.

```
**확인**: 에이전트가 멋대로 발송하지 않고 여러분의 대답을 기다리고 있나요? 축하합니다! 첫 번째 하네스를 성공적으로 장착하셨습니다.

---

### 실행 범위 제한: "이 방 밖으로는 나가지 마"

두 번째 하네스는 **'접근 권한 제한'**입니다. 에이전트가 내 컴퓨터의 모든 파일을 들여다볼 수 있다면 보안상 위험하겠죠? 그래서 우리는 에이전트에게 "딱 이 폴더 안에서만 놀아라"라고 구역을 정해줍니다.

오픈클로와 코덱스에는 **'신뢰 디렉토리(Trusted Directory)'**라는 개념이 있습니다. 지정된 워크스페이스 밖의 파일은 에이전트가 읽거나 쓰려고 할 때 시스템 차원에서 차단해 버리는 거죠.

또한, MCP 도구 중에서도 '위험한 도구'는 따로 관리해야 합니다. 예를 들어 '파일 삭제' 도구나 '시스템 설정 변경' 도구는 아예 꺼두거나 승인 없이는 못 쓰게 막을 수 있습니다.

| 하네스 종류 | 설정 방법 | 효과 |
| :--- | :--- | :--- |
| **디렉토리 제한** | `openclaw.json`의 `workspace` 경로 지정 | 에이전트가 개인 파일을 엿보는 것을 방지 |
| **MCP 도구 제한** | `config.toml`에서 특정 도구 비활성화 | 파일 삭제 등 치명적 명령 원천 차단 |
| **토큰 한도 설정** | API 설정에서 `Usage Limit` 지정 | 하룻밤 새 수백 달러가 결제되는 비극 방지 |

## 여기서 막혔나요?

**Q. `AGENTS.md`를 고쳤는데도 에이전트가 그냥 무시하고 발송해버려요.**

**A.** 에이전트가 지침을 잊었을 가능성이 큽니다. 그럴 때는 오픈클로 채팅창에 "방금 AGENTS.md에 추가한 규칙 읽었어? 이제부터는 발송 전에 꼭 나한테 물어봐야 해"라고 한 번 더 주의를 주세요. 비서에게도 가끔은 따끔한 교육이 필요합니다.

**Q. 승인 단계가 있으니까 `cron`으로 자동화하는 의미가 없지 않나요?**

**A.** 처음에는 그렇게 느껴지실 수 있습니다. 하지만 하네스의 진가는 **'필터링'**에 있습니다. 매일 아침 100개의 뉴스가 수집된다면, 에이전트가 10개로 요약해두고 여러분은 "발송" 버튼만 한 번 누르면 되는 거죠. 100개를 직접 읽는 것보다 90% 이상의 시간이 절약됩니다. 신뢰가 쌓이면 "키워드 일치율이 90% 이상인 것만 자동 발송해"라는 식으로 규칙을 고도화할 수도 있습니다.

**Q. 에이전트가 자꾸 "권한이 없어서 작업을 못 하겠어요"라고 징징대요.**

**A.** 하네스를 너무 꽉 조였을 때 발생하는 문제입니다. 예를 들어 요약본을 노션에 저장해야 하는데, 노션 폴더에 접근 권한을 주지 않은 경우죠. 에이전트가 작업해야 하는 모든 경로가 `openclaw.json`의 워크스페이스 안에 들어있는지, 혹은 `AGENTS.md`에서 허용한 범위인지 다시 한번 확인해 보세요.

## 한 줄 정리

하네스 엔지니어링은 AI 에이전트에게 채우는 **지혜로운 고삐**이며, 이를 통해 우리는 **사고 걱정 없이 안심하고 잠들 수 있는 '진정한 자동화 시스템'**을 완성하게 됩니다.

자, 이제 여러분은 24시간 돌아가는 뉴스봇과 그 로봇을 제어할 수 있는 고삐까지 손에 쥐었습니다. 완벽합니다! 그런데 문득 이런 생각이 들지 않으신가요? "에이전트 한 명이 수집도 하고 요약도 하고 발송도 하려니 너무 힘들어 보이는데, 비서를 여러 명 고용해서 일을 나눠주면 어떨까?"

다음 섹션에서는 에이전트계의 '조직 관리' 기술을 다뤄보겠습니다. **멀티 에이전트, 과연 정말로 우리에게 필요할까요?** 효율과 비용 사이에서 고민하는 여러분을 위해 정답을 준비했습니다. 함께 보시죠!


## 12.5 [칼럼] 멀티 에이전트, 정말 필요할까 — 효율과 비용 사이의 정답

하네스 엔지니어링으로 안전장치까지 마쳤으니, 이제 여러분의 뉴스봇은 완벽한 시스템을 갖췄습니다. 그런데 시스템을 가만히 보고 있으면 문득 이런 욕심이 생기실 거예요. 

**"비서를 한 명 더 두면 더 빠르고 똑똑하게 일하지 않을까?"**

요즘 AI 업계의 유행어 중 하나가 바로 '멀티 에이전트(Multi-Agent)'입니다. 뉴스 수집은 '수집 비서'가 하고, 요약은 '전문 에디터 비서'가 하고, 발송은 '홍보 담당 비서'가 따로 맡아서 서로 대화하며 일하는 그림이죠. 듣기만 해도 폼나고 든든합니다. 

하지만 솔직히 말씀드리면, **개인 차원의 자동화에서 멀티 에이전트는 '빛 좋은 개살구'가 될 확률이 높습니다.** 왜 그럴까요? 비서가 늘어나면 일도 잘 풀릴 것 같은데, 왜 제가 도시락 싸 들고 말리는지 그 이유를 하나씩 짚어보겠습니다.

---

### "비서가 많으면 좋을 텐데?" — 우리가 빠지기 쉬운 환상

우리는 보통 조직에 사람이 많을수록 큰일을 할 수 있다고 생각합니다. 1명이 10시간 걸릴 일을 10명이 1시간 만에 끝내는 걸 기대하죠. 하지만 AI 에이전트의 세계는 우리가 사는 현실 세계와는 조금 다른 물리 법칙이 작동합니다.

**"AI 에이전트를 늘리는 건, 좁은 주방에 요리사 10명을 밀어 넣는 것과 같습니다."**

식재료를 씻는 사람, 써는 사람, 볶는 사람을 다 따로 두었다고 해봅시다. 그런데 주방이 너무 좁아서 요리사 한 명이 옆 사람에게 재료를 넘겨줄 때마다 "자, 내가 지금 당근을 이만큼 썰었어. 이건 이런 용도니까 네가 받아서 볶아줘"라고 아주 길게 설명해야 합니다. 

이 '설명하는 과정'이 바로 AI에겐 **'토큰(Token)'**입니다. 그리고 이 토큰은 곧 여러분의 지갑에서 나가는 **'돈'**이죠.

---

### 멀티 에이전트의 숨겨진 함정: '토큰 세금'과 '기억상실'

에이전트를 여러 개로 쪼개면 크게 두 가지 치명적인 문제가 발생합니다.

**첫째, 토큰이 기하급수적으로 소모됩니다.** 
오픈클로에서 에이전트 하나를 부를 때마다 그 에이전트에게 '업무 지침(AGENTS.md)'과 '현재 상황'을 매번 새로 알려줘야 합니다. 수집 비서가 일을 끝내고 요약 비서에게 넘길 때, 수집 비서가 읽었던 수많은 뉴스의 맥락을 요약 비서에게도 다 전달해야 하죠. 

결과적으로 똑같은 정보를 에이전트 수만큼 반복해서 읽게 만드는 꼴이 됩니다. 에이전트가 3명이면 비용도 단순 3배가 아니라, 서로 대화하는 비용까지 합쳐져 5배, 10배로 껑충 뜁니다.

**둘째, 컨텍스트(맥락)가 뚝뚝 끊깁니다.**
에이전트가 분리되면 '한 명의 뇌'가 아니라 '여러 명의 독립된 뇌'가 됩니다. 앞에서 수집 비서가 "이 뉴스는 특히 중요해 보여서 가져왔어"라고 생각했어도, 요약 비서에게는 그 '느낌'이 온전히 전달되지 않습니다. 정보를 주고받는 과정에서 중요한 디테일이 빠지거나 왜곡되기 쉽죠.

### 대안: 하나의 파이프라인에서 '순차 처리'하기

그렇다면 어떻게 하는 게 정답일까요? 정답은 **'한 명의 유능한 비서에게 순서대로 일을 시키는 것'**입니다. 오픈클로에서는 이를 '파이프라인 스킬'이라고 부릅니다.

우리가 만든 뉴스봇 스킬(`$news`)을 예로 들어볼까요? 

01 **수집**: 먼저 최신 뉴스를 긁어옵니다.
02 **요약**: 긁어온 뉴스를 그 자리에서 바로 요약합니다.
03 **발송**: 요약된 내용을 텔레그램으로 보냅니다.

이 모든 과정을 **하나의 에이전트가 단 한 번의 대화 흐름(컨텍스트) 안에서** 처리하게 만드는 겁니다. 이렇게 하면 비서가 자기 일을 자기가 기억하고 있기 때문에, 추가 설명이 필요 없습니다. 토큰도 아끼고, 앞뒤 맥락도 완벽하게 이어지죠.

| 구분 | 멀티 에이전트 방식 | 단일 파이프라인 방식 (권장) |
| :--- | :--- | :--- |
| **작동 방식** | 수집 비서 ↔ 요약 비서 ↔ 발송 비서 | 한 명의 비서가 수집→요약→발송 수행 |
| **비용 (토큰)** | 매우 높음 (중복 데이터 전송) | 경제적 (최소한의 컨텍스트 유지) |
| **정확도** | 정보 전달 과정에서 오류 발생 가능 | 처음부터 끝까지 일관성 유지 |
| **관리 난이도** | 복잡함 (여러 개의 AGENTS.md 관리) | 단순함 (하나의 규칙으로 제어) |

### 실전 결론: 언제 멀티 에이전트를 써야 할까?

그럼 멀티 에이전트는 아예 쓸모가 없는 걸까요? 아닙니다. **"완전히 다른 성격의 일을 동시에 해야 할 때"**는 필요합니다. 

예를 들어, 여러분이 '뉴스봇'도 돌리고 '인스타그램 발행 봇'도 돌린다고 해봅시다. 
- **뉴스봇**: 매일 아침 뉴스를 요약해서 나에게 보고하는 일
- **발행 봇**: 내가 쓴 글을 예쁘게 다듬어서 인스타그램에 올리는 일

이 두 가지는 업무 지침(AGENTS.md)도 다르고, 사용하는 도구(MCP)도 완전히 다릅니다. 이럴 때는 억지로 한 명에게 다 시키기보다, 뉴스 담당 비서와 인스타그램 담당 비서를 따로 두는 게 관리 면에서 훨씬 편합니다. 즉, **'스킬 단위'로 에이전트를 나누는 것**이 실전 노하우입니다.

> **💡 저자의 팁: "할 수 있지만 안 하는 이유"를 아는 게 실력입니다.**
> 기술적으로는 에이전트 100명을 띄울 수도 있습니다. 하지만 진짜 고수는 최소한의 에이전트로 최대의 효율을 뽑아냅니다. 처음에는 무조건 **'한 명의 비서에게 여러 일을 순차적으로 시키는 것'**부터 시작하세요. 그러다 비서가 너무 많은 일을 해서 머리가 아파 보일 때(AGENTS.md가 너무 길어질 때), 그때 조심스럽게 분리를 고민하셔도 늦지 않습니다.

## 여기서 막혔나요?

**Q. 에이전트 하나에게 너무 많은 일을 시키면 성능이 떨어지지 않나요?**

**A.** 네, 맞습니다. '컨텍스트 윈도우'라는 한계 때문인데요. 하지만 우리가 만드는 뉴스 요약이나 블로그 발행 정도의 작업은 요즘 AI(Claude 3.5 Sonnet 등)에겐 식은 죽 먹기입니다. 에이전트를 쪼개서 발생하는 손해보다, 한 명에게 몰아줘서 얻는 이득(비용 절감, 일관성)이 99%의 상황에서 훨씬 큽니다.

**Q. 그래도 폼나게 '팀'처럼 운영하고 싶은데 방법이 없을까요?**

**A.** 그럴 때는 오픈클로의 '역할 부여' 기능을 활용해 보세요. 에이전트는 하나지만, 프롬프트 안에서 "너는 이제부터 수집 담당자야... (작업 완료 후) 자, 이제 너는 수석 에디터야"라고 역할을 바꿔주는 거죠. 지갑은 지키면서 기분은 낼 수 있는 가장 영리한 방법입니다.
