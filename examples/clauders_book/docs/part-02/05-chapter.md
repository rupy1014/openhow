> "월 20억 번다더라"는 소문보다, 직접 하나 만들어보는 30분이 더 많은 걸 가르쳐줍니다.

이 장에서는 AI 캐릭터 채팅 서비스를 처음부터 끝까지 한 번에 만들어봅니다. 기획, 개발, 동작 확인까지 한 흐름으로 경험하는 게 목표입니다. 코드를 한 줄도 직접 쓰지 않아도 됩니다. AI에게 시키면 되니까요. 대신 여러분이 해야 할 일은 **무엇을 만들지 결정하고, AI가 엉뚱한 방향으로 가지 않도록 잡아주는 것**입니다.

---

## 완성 기준

- [ ] PRD(기획 문서) 한 장을 AI와 함께 완성했다
- [ ] 화면, 서버, 데이터, API의 역할을 자기 말로 설명할 수 있다
- [ ] 캐릭터를 골라 대화하는 채팅 서비스가 브라우저에서 돌아간다
- [ ] "이번에 안 만들 것" 목록을 직접 정했다

---

## STEP 1. AI에게 일을 잘 시키는 두 가지

서비스를 만들기 전에, 먼저 알아둘 게 있습니다. AI에게 코딩을 시킬 때 결과가 좋아지는 두 가지 습관입니다.

### 1-1. plan 모드 — "코드는 아직 짜지 마"

AI에게 "AI 캐릭터 채팅 서비스 만들어줘"라고 바로 시키면 어떻게 될까요?

AI가 혼자서 기술을 고르고, 화면 구조를 정하고, 로그인 시스템까지 만들어버립니다. 1,500줄짜리 코드가 쏟아져 나오죠. 여러분은 그냥 캐릭터 몇 명이랑 대화하고 싶었을 뿐인데요.

**AI가 여러분 대신 기획을 해버린 겁니다.** 여러분의 의도와는 전혀 다른 방향으로요.

해결법은 간단합니다. 이 한 마디를 먼저 하세요.

```
코드는 아직 짜지 마. 먼저 계획을 보여줘.
```

이렇게 말하면 AI가 복잡한 기술을 안 꺼내고, 화면 구조를 여러분이 결정할 수 있고, 한 번에 수백 줄이 쏟아지지 않습니다. 실제로 이 한마디가 과잉 설계의 90%를 막아줍니다.

계획을 받아보고, 마음에 드는 부분만 "이거 실행해줘"라고 하면 됩니다.

### 1-2. 레퍼런스 주기 — "이거랑 비슷하게 해줘"

두 번째는 레퍼런스입니다. "예쁘게 만들어줘"보다 "이거랑 비슷하게 만들어줘"가 열 배 빠릅니다.

비슷한 서비스의 스크린샷을 캡처해서 AI에게 보여주세요. 말로 "헤더가 있고, 왼쪽에 사이드바가 있고, 가운데에 카드가 3열로 배치되고..."라고 쓰는 것보다 스크린샷 한 장이 훨씬 정확합니다.

```
이 스크린샷처럼 만들어줘.
색상은 파란색 계열로, 캐릭터 카드는 3개만.
```

![레퍼런스 스크린샷을 AI에게 전달하는 장면](/__content__/images/ch05-01.png)

반복되는 규칙이 있다면 `CLAUDE.md` 파일에 적어두면 됩니다. 프로젝트 폴더에 이 파일을 넣어두면 AI가 매번 자동으로 읽습니다.

```markdown
# 프로젝트 규칙
## 기술 스택
- Next.js + API Route
- 외부 라이브러리 최소화
## 금지 사항
- API 키를 코드에 하드코딩 금지
- 한 파일에 300줄 넘기지 않기
```

> **확인**: AI에게 "계획부터 보여줘"라고 했을 때, 코드가 아니라 구조 설명이 나오면 성공입니다.

## STEP 2. 화면, 서버, 데이터, API는 각각 무슨 역할을 할까?

서비스를 만든다고 하면 왠지 복잡하게 느껴집니다. 하지만 뼈대를 네 가지로 나누어 보면 생각보다 단순합니다.

식당에 비유해보겠습니다.

| 역할 | 식당 비유 | 실제 서비스 |
|------|----------|------------|
| **화면(프론트엔드)** | 손님이 앉는 홀 | 브라우저에 보이는 채팅 화면 |
| **서버(백엔드)** | 주방 | 요청을 받아서 처리하는 곳 |
| **데이터(DB)** | 냉장고 | 캐릭터 정보, 대화 기록 저장 |
| **API** | 주문서 | 홀과 주방이 소통하는 약속 |

손님(사용자)이 홀(화면)에서 주문서(API)를 보내면, 주방(서버)이 냉장고(데이터)에서 재료를 꺼내 요리를 만들어 돌려보냅니다.

우리가 만들 캐릭터 채팅 서비스도 똑같습니다.

1. **화면**: 캐릭터를 고르고, 메시지를 입력하는 채팅 화면
2. **서버**: 사용자 메시지를 받아 AI에게 전달하고, 답변을 돌려주는 곳
3. **데이터**: 캐릭터 이름, 성격(system prompt), 대화 기록
4. **API**: 화면과 서버가 주고받는 약속, 그리고 서버가 AI에게 질문하는 약속

![화면, 서버, 데이터, API — 식당 비유로 이해하기](/__content__/images/ch05-02.png)

이 네 가지를 한꺼번에 만들 필요는 없습니다. AI에게 시키면 한 번에 뼈대가 나옵니다. 여러분은 이 구조가 어떻게 연결되는지 감만 잡으면 됩니다.

> **확인**: "화면은 홀, 서버는 주방, API는 주문서"라고 떠올릴 수 있으면 충분합니다.

## STEP 3. 기획부터 배포까지 한 흐름으로 보기

### 3-1. 아이템 선택 — 소문에서 출발하기

"AI 캐릭터 채팅이 월 20억을 번다더라."

이런 소문을 들으면 솔직히 흥미가 생깁니다. 하지만 소문 그대로 따라가면 안 됩니다. 중요한 건 **내가 왜 이걸 만들고 싶은지** 이유를 정하는 겁니다.

아이템 선택에는 항상 가정이 있어야 합니다. 예를 들면 이렇습니다.

- "캐릭터마다 성격이 다르면 사람들이 더 오래 대화하지 않을까?"
- "까칠한 고양이 캐릭터면 재미있지 않을까?"

이 가정이 맞는지는 **만들어봐야** 압니다. 그래서 빠르게 만들어보는 겁니다.

### 3-2. PRD 한 장 정리하기

기획이라고 해서 10페이지짜리 문서를 쓸 필요는 없습니다. PRD(Product Requirements Document)라는 거창한 이름이 붙어 있지만, 실은 A4 한 장이면 됩니다.

AI에게 이렇게 시켜보세요.

```
나 AI 캐릭터 채팅 서비스 만들고 싶어.
- 캐릭터 3명이 있어 (각각 성격이 달라)
- 하나를 골라서 대화할 수 있어
- 한국어로 대화해

위 내용으로 PRD.md를 만들어줘.
한 줄 설명, 대상 사용자, 핵심 기능, 안 만들 것,
사용자 흐름, 성공 기준 — 이 6가지를 포함해서.
코드는 아직 짜지 마.
```

AI가 내놓은 PRD를 확인할 때는 세 가지만 보면 됩니다.

1. **핵심 기능이 3~5개인가?** 많으면 줄이라고 하세요.
2. **"안 만들 것"이 있는가?** 없으면 추가해달라고 하세요.
3. **사용자 흐름이 5단계 이내인가?** 넘으면 줄이라고 하세요.

완성된 PRD는 이런 모습입니다.

```markdown
# PRD: AI 캐릭터 채팅

## 한 줄 설명
AI 캐릭터 3명 중 하나를 골라 한국어로 대화하는 웹앱.

## 핵심 기능
1. 캐릭터 선택 화면 (카드 3개)
2. 채팅 화면 (말풍선 UI)
3. AI 응답 (스트리밍)
4. 한국어 대화

## 안 만들 것
- 로그인/회원가입
- 대화 기록 저장
- 캐릭터 생성/편집
- 음성 대화
- 관리자 페이지

## 사용자 흐름
캐릭터 선택 → 대화 시작 → 메시지 입력 → AI 응답 확인

## 성공 기준
캐릭터를 골라서 10번 이상 대화할 수 있으면 완성.
```

**"안 만들 것"이 5개**나 됩니다. 이게 핵심입니다. AI가 엉뚱한 기능을 추가할 여지를 미리 막아두는 거죠.

> **확인**: PRD에 "안 만들 것" 항목이 3개 이상 있으면 좋은 기획입니다.

### 3-3. 기획 → 개발 → 확인, 이 흐름이 전부입니다

전체 흐름을 한눈에 정리하면 이렇습니다.

```
① 아이디어 → ② PRD 정리 → ③ AI에게 개발 시키기 → ④ 브라우저에서 확인 → ⑤ 고치기
```

여기서 ③~⑤는 계속 반복됩니다. 한 번에 완벽하게 나오는 법이 없거든요. "만들고, 확인하고, 고치는" 루프를 빠르게 도는 게 핵심입니다. 린 스타트업에서 말하는 "Build-Measure-Learn" 사이클과 같은 원리입니다.

## STEP 4. 따라 하며 MVP 완성하기

이제 진짜 만들어봅니다. PRD가 준비되었으니 AI에게 개발을 시킬 차례입니다.

### 4-1. 프로젝트 시작하기

AI에게 이렇게 지시합니다.

```
PRD.md 기반으로 프로젝트를 만들어줘.

## 기술
- Next.js + API Route
- OpenRouter API (환경변수: OPENROUTER_API_KEY)
- 각 캐릭터마다 다른 system prompt

## 캐릭터 3명
1. 까칠한 고양이 "나비" — 반말, 귀찮은 듯이, 가끔 "냥" 붙임
2. 다정한 할머니 "순자" — 따뜻하게, "아이고~" 자주 씀, 밥 먹었냐고 먼저 물어봄
3. 열혈 체육교사 "김코치" — 에너지 넘침, "파이팅!" 자주 씀

## 안 만들 것
- 로그인
- 대화 저장 (새로고침하면 초기화)
- 캐릭터 편집
```

AI가 만들어주는 코드의 뼈대는 이런 구조입니다.

```
app/
├── page.tsx              ← 캐릭터 선택 화면
├── chat/[id]/page.tsx    ← 채팅 화면
├── api/chat/route.ts     ← AI API 호출 (서버)
└── lib/characters.ts     ← 캐릭터 정보 + system prompt
```

아까 배운 네 가지 역할이 그대로 보이죠? `page.tsx`가 화면, `route.ts`가 서버, `characters.ts`가 데이터, 그리고 이들 사이를 오가는 게 API입니다.

![캐릭터 선택 화면 — 세 가지 캐릭터 카드](/__content__/images/ch05-03.png)

### 4-2. 핵심 구조 이해하기

캐릭터의 성격은 **system prompt**로 정합니다. 이건 AI에게 "너는 누구야"를 알려주는 설정입니다.

```typescript
// lib/characters.ts — 캐릭터 정보
export const characters = [
  {
    id: "nabi",
    name: "나비",
    description: "까칠한 고양이",
    avatar: "🐱",
    systemPrompt: `너는 "나비"라는 까칠한 고양이야.
      반말 써. 귀찮은 듯이 대답해. 가끔 "냥" 붙여.`
  },
  // 순자 할머니, 김코치도 같은 구조
];
```

재미있는 건, 이 system prompt만 바꾸면 완전히 다른 서비스가 된다는 겁니다.

| system prompt | 서비스 |
|---------------|--------|
| "너는 까칠한 고양이야" | 캐릭터 채팅 |
| "너는 사주 전문가야" | 운세 서비스 |
| "너는 고객지원 담당자야" | CS 챗봇 |
| "너는 영어 선생님이야" | 영어 회화 앱 |

**같은 코드, 다른 프롬프트.** 이게 AI 서비스의 핵심입니다.

### 4-3. 대화가 이어지는 원리

AI API 자체는 기억력이 없습니다. 매번 새 사람에게 말 거는 것과 같죠. 그래서 **이전 대화 기록을 매번 통째로 보내줘야** 합니다.

```
❌ 기억 없이 매번 새로 시작
나: "오늘 날씨 어때?"    → AI: "서울은 맑아요"
나: "거기 맛집 추천해줘" → AI: "어디요?" (서울을 까먹음)

✅ 대화 기록을 함께 전달
나: [이전 대화 전부] + "거기 맛집 추천해줘"
→ AI: "서울 맛집이요? 광화문 근처에..." (기억하고 있음)
```

코드로 보면 메시지를 배열에 계속 쌓아서 보내는 겁니다. 새 메시지가 올 때마다 배열에 추가하고, 전체를 AI에게 전달합니다. 이 원리만 알면 됩니다. 코드는 AI가 알아서 작성해줍니다.

### 4-4. 브라우저에서 확인하기

개발 서버를 띄우고 브라우저에서 확인합니다.

```bash
npm run dev
```

`http://localhost:3000`에 접속하면 캐릭터 3개가 카드로 보입니다. 하나를 클릭하면 채팅 화면으로 넘어갑니다. 메시지를 입력하면 AI가 글자를 하나씩 타닥타닥 내보내줍니다. 이게 **스트리밍**입니다.

ChatGPT를 써보셨다면 익숙한 느낌이죠? 답변이 한꺼번에 뜨지 않고 글자가 흘러나오는 그것입니다. AI 답변은 길어지면 5~10초 걸리는데, 스트리밍을 쓰면 첫 글자가 0.5초 안에 나옵니다. 체감 속도가 완전히 달라집니다.

![나비 캐릭터와 대화하는 채팅 화면](/__content__/images/ch05-04.png)

> **확인**: 캐릭터를 골라서 10번 이상 대화할 수 있으면, PRD에 적은 성공 기준을 달성한 겁니다.

## STEP 5. MVP는 어디까지일까

욕심이 생기기 시작합니다. "대화 기록을 저장하면 좋겠는데", "캐릭터를 더 추가하고 싶은데", "로그인도 넣을까?"

여기서 멈추는 게 중요합니다.

MVP는 **무엇을 만들지**를 정하는 일이 아닙니다. **무엇을 안 만들지**를 정하는 일입니다.

우리가 아까 PRD에 적은 "안 만들 것" 목록을 다시 볼까요?

| 안 만들 것 | 왜 안 만드나 |
|-----------|-------------|
| 로그인/회원가입 | 핵심 경험(대화)과 무관 |
| 대화 기록 저장 | 새로고침하면 초기화해도 체험은 가능 |
| 캐릭터 생성/편집 | 일단 3명이면 충분 |
| 음성 대화 | 텍스트로도 핵심 경험 가능 |
| 관리자 페이지 | 혼자 쓰니까 불필요 |

이 목록을 정하는 게 기획의 절반입니다. 만들기 전에는 뭐가 중요한지 모릅니다. 머릿속에선 "대화 저장이 필수야"라고 생각했는데, 실제로 만들어보니 "캐릭터 성격 설정"이 훨씬 중요할 수 있습니다.

그래서 **작게 만들고, 써보고, 고칩니다**. 린 스타트업의 핵심이 바로 이 루프입니다.

지금 만든 MVP로 충분히 핵심 경험을 확인할 수 있습니다. 캐릭터를 골라서 대화가 되면 OK. 로그인은 나중에, 결제는 더 나중에.

## 여기서 막혔나요?

**Q. AI가 계획 대신 바로 코드를 만들어요.**

상황: "계획을 보여줘"라고 했는데 코드블록이 쏟아져 나옵니다.

원인:
- 프롬프트에 "코드는 짜지 마"가 빠졌을 수 있습니다
- AI가 간단한 프로젝트라고 판단하면 바로 코드를 생성하기도 합니다

해결:
1. "코드는 아직 짜지 마. 먼저 PRD 문서만 만들어줘."라고 명확히 말하세요
2. 이미 코드가 나왔다면 "잠깐, 코드는 지우고 PRD부터 정리하자"라고 하면 됩니다

**Q. 캐릭터가 설정한 성격대로 말을 안 해요.**

상황: 까칠한 고양이 나비가 갑자기 공손하게 답합니다.

원인:
- system prompt가 너무 짧거나 모호할 수 있습니다
- 대화가 길어지면서 초기 설정이 희석될 수 있습니다

해결:
1. system prompt에 구체적인 말투 예시를 추가하세요 ("예: '...뭐야냥. 갑자기.'처럼 대답해")
2. "절대 ~하지 마"라는 금지 조건을 넣으면 더 잘 지킵니다
3. 대화가 20턴을 넘기면 새로 시작하는 것도 방법입니다

**Q. OpenRouter API 키를 어디에 넣어야 하는지 모르겠어요.**

상황: 코드는 만들어졌는데 "API key not found" 에러가 납니다.

원인:
- 환경변수 파일(`.env.local`)에 API 키를 설정하지 않았습니다

해결:
1. 프로젝트 루트에 `.env.local` 파일을 만드세요
2. `OPENROUTER_API_KEY=여러분의_키` 형식으로 넣으세요
3. 개발 서버를 다시 시작하세요 (`npm run dev`)

**Q. 화면이 안 예뻐요. 디자인을 바꾸고 싶어요.**

상황: 기능은 되는데 못생겼습니다.

원인:
- MVP는 원래 못생겨도 괜찮습니다

해결:
1. 비슷한 서비스의 스크린샷을 캡처하세요
2. AI에게 "이 스크린샷처럼 바꿔줘"라고 보여주세요
3. 색상, 폰트, 레이아웃을 하나씩 지정하면 더 정확합니다
