# 09장 매일 아침 뉴스 요약이 도착한다면 — 뉴스봇 파이프라인

> "자동화의 첫걸음은 복잡한 기술이 아니라, 이미 알고 있는 '구조'를 재발견하는 것입니다."

자, 이제 진짜 '자동화'의 꽃이라 불리는 뉴스봇을 만들어볼 시간입니다. 앞 장에서 우리는 조수들에게 말투를 가르치고, 블로그 글을 쓰게 만드는 법을 배웠습니다. 어떠셨나요? 나만의 톤으로 글이 뽑혀 나올 때의 그 짜릿함, 아직 기억하시죠?

그런데 솔직히 말씀드리면, 블로그 글을 하나하나 뽑아내는 건 여전히 '수동'의 냄새가 좀 납니다. 우리가 일일이 코덱스를 깨워서 "이 주제로 써줘"라고 시켜야 하니까요. 하지만 오늘부터 배울 뉴스봇은 결이 다릅니다. 여러분이 잠든 사이에도 인터넷 바다를 헤엄치며 정보를 물어오고, 스스로 읽고 요약해서, 아침마다 여러분에게 보고서를 올리는 **'24시간 무인 공장'**을 차리는 일이기 때문입니다.

"어휴, 그건 너무 어려울 것 같은데요?"라고 걱정하지 마세요. 사실 여러분은 이미 이 공장의 설계도를 02장에서 배웠습니다. 이름만 '뉴스봇'이지, 그 뼈대는 우리가 앞서 해본 '블로그 쓰기'와 소름 돋게 똑같거든요.

---

## 09.1 블로그와 뼈대가 같다

자동화라고 하면 엄청난 프로그래밍 지식이 필요할 것 같지만, 본질은 아주 단순합니다. **"재료를 가져와서(입력), 맛있게 요리하고(처리), 그릇에 담아 내놓는 것(출력)"**이 전부입니다.

우리가 02장에서 배운 자동화의 구조를 떠올려 보세요. "수집 → 처리 → 출력" 세 단계였죠? 뉴스봇도 이 구조에서 한 발자국도 벗어나지 않습니다. 다만 재료를 내가 직접 넣느냐(블로그), 아니면 AI가 밖에서 주워오느냐(뉴스봇)의 차이일 뿐입니다.

### 블로그와 뉴스봇: 1:1 매칭 테스트

자, 우리가 에이전트와 함께 블로그 글을 쓰던 과정을 복습해 봅시다. 그리고 뉴스봇은 어떻게 돌아갈지 옆에 나란히 놓아볼게요.

| 단계 | 블로그 자동화 ($write) | 뉴스봇 파이프라인 ($news) | 비유 |
| :--- | :--- | :--- | :--- |
| **1. 수집** | 내가 소재를 직접 입력함 | RSS(웹사이트 새 글 알림)로 뉴스 소스에서 가져옴 | 식재료 배달 |
| **2. 분류/집필** | 에이전트가 초안을 작성함 | AI가 분야별로 나누고 핵심 요약함 | 편집장의 기사 분배 |
| **3. 퇴고** | 톤 가이드에 맞춰 다듬음 | 번역투를 없애고 품질 규칙을 적용함 | 데스크의 교정 |
| **4. 발행** | 블로그에 올림 | 카톡, 슬랙, 웹사이트로 발송함 | 신문 배포 |

어때요? 이름만 바뀌었지 흐름은 완벽하게 일치하죠?

**"수집 → 처리 → 출력"** — 02장에서 배운 구조 그대로, 입력 소스와 출력 채널만 다릅니다.

블로그 글을 쓸 때는 입력 소스가 '나의 아이디어'였고, 출력 채널이 '나의 블로그'였습니다. 뉴스봇은 이 입구에 '해외 테크 뉴스'라는 수도꼭지를 틀고, 출구에 '나의 카톡'이라는 바구니를 놓는 것뿐입니다.

<!-- IMG: 블로그 작성 과정과 뉴스봇 자동화 과정이 톱니바퀴처럼 맞물려 돌아가는 비교 삽화 -->

### 왜 이 패턴을 배워야 할까요?

"그냥 챗GPT한테 뉴스 요약해달라고 하면 안 돼요?"라고 물으실 수 있습니다. 물론 되죠. 하지만 그건 '한 번'만 되는 일입니다. 우리가 원하는 건 **'시스템'**입니다.

이 '수집-처리-출력' 패턴을 한 번만 제대로 익혀두면, 여러분은 뉴스봇 말고도 수만 가지 자동화 도구를 복사-붙여넣기 하듯 만들 수 있습니다.

- **경쟁사 모니터링 봇**: 소스만 경쟁사 블로그로 바꾸면 됩니다.
- **채용 공고 알림 봇**: 키워드 필터만 "개발자 채용"으로 걸면 됩니다.
- **논문 요약 봇**: 소스를 arXiv(논문 사이트)로 바꾸고 리뷰어를 "박사님 톤"으로 바꾸면 끝입니다.

결국 자동화는 기술의 문제가 아니라 **'레고 블록을 어떻게 갈아 끼우느냐'**의 문제입니다.

## 여기서 막혔나요?

**Q. 파이프라인이라는 말이 너무 어려워요. 그냥 자동화랑 뭐가 다른가요?**

쉽게 생각해서 **'공장의 컨베이어 벨트'**라고 보시면 됩니다. 자동화가 단순히 "문 열어줘" 같은 동작 하나라면, 파이프라인은 "재료가 들어오면 세척하고, 자르고, 볶아서 포장까지 마쳐라"라는 연속된 공정 전체를 말합니다. 뉴스봇은 이 벨트 위에서 뉴스가 가공되어 나오는 과정인 거죠.

**Q. 코딩을 하나도 모르는데 이 복잡한 단계를 다 설정할 수 있을까요?**

그럼요! 우리는 코드를 짜는 게 아니라 '의도'를 적는 겁니다. "뉴스 가져와", "요약해", "슬랙으로 보내"라고 말하면 코덱스가 그 단계에 필요한 스크립트를 알아서 짜줍니다. 여러분은 그 단계들이 잘 연결되어 있는지(뼈대)만 확인하시면 됩니다.

---

## 한 줄 정리

뉴스봇은 **"수집 → 처리 → 출력"**이라는 익숙한 뼈대 위에 뉴스라는 재료를 얹은 것이며, 이 구조만 익히면 어떤 업무든 자동화 파이프라인으로 만들 수 있습니다.

자, 뼈대가 같다는 걸 확인했으니 이제 실제로 공장을 가동해 볼 차례입니다!

## 09.2 [실습] 뉴스 수집 파이프라인 만들기

이제 말로만 하던 설계도는 그만 보고 직접 공장을 돌려볼 시간입니다. 우리가 만들 뉴스봇은 크게 세 부류의 '부품'으로 구성됩니다. 뉴스를 찾아오는 **수집 에이전트**, 읽기 좋게 요약하는 **요약 에이전트**, 그리고 이 둘에게 업무 지시를 내리는 **스킬 파일**입니다.

"에이전트가 왜 두 명이나 필요하죠?"라고 물으실 수도 있습니다. 하지만 생각해보세요. 맛집을 찾아다니는 '미식가'와 주방에서 요리하는 '셰프'는 역할이 완전히 다릅니다. 한 명에게 "가서 맛있는 거 찾아오고 요리까지 다 해와!"라고 하면 금방 지치거나 실수를 하기 마련이죠. 역할을 나누면 훨씬 정확하고 빨라집니다.

지금부터 저와 함께 뉴스봇 공장의 직원들을 고용하고, 업무 매뉴얼을 작성해 봅시다.

---

## STEP 1. 뉴스봇 공장의 '직원' 고용하기

가장 먼저 할 일은 우리 조수(에이전트)들에게 각각의 성격과 역할을 부여하는 겁니다. 프로젝트 폴더 안에 `.codex/agents/` 폴더를 열어보세요. (07장에서 블로그용으로 만든 `writer.toml`, `editor.toml`이 이미 있을 겁니다.)

### 1-1. 뉴스를 물어오는 '수집가(Collector)'

첫 번째 직원은 인터넷 바다를 헤엄치며 최신 소식을 물어오는 역할을 맡습니다. 이 친구는 복잡하게 생각할 필요 없이, 우리가 준 주소록(RSS)에 새 글이 떴는지만 확인하면 됩니다.

01 `.codex/agents/collector.toml` 파일을 만들고 아래 내용을 복사해서 넣으세요.

```toml
name = "collector"
description = "최신 뉴스 소스에서 데이터를 수집하는 에이전트"
persona = """
당신은 전 세계의 테크 뉴스를 수집하는 정보 요원입니다.
주어진 RSS 피드 주소에서 제목, 링크, 요약문을 빠짐없이 가져오는 것이 당신의 유일한 임무입니다.
데이터를 누락하지 않는 꼼꼼함이 생명입니다.
"""
```

### 1-2. 뉴스를 요리하는 '요약가(Summarizer)'

두 번째 직원은 수집가가 가져온 날것의 정보들을 맛있게 가공하는 셰프입니다. 영문 뉴스는 한글로 번역하고, 너무 긴 내용은 핵심만 추려야 하죠.

01 `.codex/agents/summarizer.toml` 파일을 만들고 아래 내용을 넣으세요.

```toml
name = "summarizer"
description = "수집된 뉴스를 분류하고 한국어로 요약하는 에이전트"
persona = """
당신은 까다로운 편집장입니다.
수집된 뉴스 중에서 독자가 읽을 만한 가치가 있는 것만 골라내고,
'바이브코딩'을 하는 독자들이 바로 이해할 수 있도록 핵심만 3줄로 요약하세요.
전문 용어는 쉬운 말로 풀어서 설명하는 친절함이 필요합니다.
"""
```

> **확인**: `.codex/agents/` 폴더 안에 두 개의 `.toml` 파일이 잘 들어 있나요? 이제 일할 사람들은 준비됐습니다!

## STEP 2. '업무 지침서(SKILL.md)' 작성하기

직원을 고용했으니 이제 "어떻게 일하라"는 매뉴얼을 줘야겠죠? 이게 바로 스킬입니다. 스킬 파일은 조수들이 읽는 일종의 '공정 지도'라고 보시면 됩니다.

01 `.codex/skills/news/` 폴더를 만드세요.
02 그 안에 `SKILL.md` 파일을 만들고 아래 내용을 작성합니다.

```markdown
# 뉴스 수집 및 요약 스킬

이 스킬은 최신 뉴스를 가져와서 분류하고 요약된 브리핑을 생성합니다.

## 공정 단계

1. **수집 단계**: `sources.json`에 등록된 RSS 주소에서 지난 24시간 동안 올라온 뉴스를 모두 가져옵니다. (담당: collector)
2. **분류 단계**: 가져온 기사들을 'AI/개발', '비즈니스', '라이프스타일' 카테고리로 나눕니다. (담당: summarizer)
3. **요약 단계**: 각 기사의 핵심을 3줄 내외의 한국어로 요약합니다. (담당: summarizer)
4. **결과 출력**: 요약된 내용을 `content/YYYY-MM-DD/news-briefing.md` 파일로 저장합니다.

## 품질 규칙
- 반드시 원문의 링크(URL)를 포함해야 합니다.
- 마케팅 과장이 심한 수식어는 삭제하세요.
- 번역투 문장을 자연스러운 구어체로 고치세요.
```

자, 이제 조수들은 이 문서를 보고 "아, 내가 먼저 뉴스를 가져오면, 그다음 친구가 카테고리를 나누고 요약을 해서 파일로 저장해야 하는구나!"라고 완벽하게 이해하게 됩니다.

## STEP 3. 어디서 가져올까? '주소록(sources.json)' 등록하기

공장도 있고 직원도 있고 매뉴얼도 있는데, 정작 뉴스를 어디서 가져올지가 빠졌네요. 우리는 **RSS(웹사이트 새 글 알림)**라는 방식을 쓸 겁니다.

RSS가 뭐냐고요? 쉽게 말해 **'블로그용 택배 알림'**입니다. 우리가 일일이 뉴스 사이트를 방문하지 않아도, 그쪽에서 새 글이 올라올 때마다 "여기 새 글 있어요!" 하고 던져주는 주소죠.

01 프로젝트 루트 폴더(최상위 폴더)에 `sources.json` 파일을 만드세요.
02 제가 추천하는 알짜배기 소스 3개를 먼저 등록해 봅시다.

```json
{
  "sources": [
    {
      "name": "GeekNews",
      "url": "https://news.hada.io/rss",
      "description": "국내 최고의 IT 뉴스 큐레이션"
    },
    {
      "name": "TechCrunch",
      "url": "https://feeds.feedburner.com/TechCrunch",
      "description": "글로벌 기술 트렌드"
    },
    {
      "name": "HackerNews",
      "url": "https://hnrss.org/newest?points=100",
      "description": "실시간 인기 테크 소식"
    }
  ]
}
```

## STEP 4. 공장 가동하기: $news 실행

모든 준비가 끝났습니다! 이제 숨을 한번 크게 들이마시고, 터미널에 명령어를 입력해 볼 시간입니다.

01 터미널을 열고 코덱스를 실행 중인지 확인하세요.
02 터미널에 아래 명령어를 입력하고 Enter를 누르세요.

> **`$news`**

**자, 이제 화면을 주목해 보세요!** 조수들이 바쁘게 움직이기 시작할 겁니다.

```text
1단계: 뉴스 수집 시작 (collector 출동)
  [GeekNews] 12개 확인 -> 3개 신규
  [TechCrunch] 8개 확인 -> 2개 신규
수집 완료!

2단계: 분류 및 요약 (summarizer 출동)
  기사 5개를 'AI/개발' 카테고리로 분류 중...
  한국어로 요약 중 (번역투 제거 완료)
요약 완료!

3단계: 브리핑 파일 생성
  content/2026-04-16/news-briefing.md 저장 성공!
```

어때요? 여러분의 조수들이 협동해서 결과를 만들어내는 과정이 실시간으로 보이나요? 이제 `content/오늘날짜/` 폴더를 열어보세요. 세상에서 단 하나뿐인, 오직 여러분만을 위한 뉴스 브리핑 파일이 만들어져 있을 겁니다.

## 여기서 막혔나요?

**Q. `$news`라고 쳤는데 "그런 스킬을 찾을 수 없습니다"라고 나와요.**

폴더 경로를 다시 한번 확인해 보세요! `.codex/skills/news/` 폴더 안에 `SKILL.md`라는 파일 이름이 정확한가요? 폴더나 파일 이름에 오타가 있으면 코덱스가 업무 지침서를 찾지 못해서 당황할 수 있습니다.

**Q. `sources.json`에 다른 사이트를 추가하고 싶어요. 아무 주소나 넣으면 되나요?**

일반적인 웹사이트 주소(`https://...`)가 아니라 반드시 **RSS 주소**여야 합니다. 보통 뉴스 사이트 하단에 주황색 RSS 아이콘이 있거나, 구글에 "사이트 이름 + RSS"라고 검색하면 쉽게 찾을 수 있습니다. 만약 RSS가 없는 사이트라면 걱정 마세요! Part 3에서 브라우저 자동화로 아무 사이트든 수집하는 방법을 알려드립니다.

**Q. 요약된 내용이 너무 짧아요. 좀 더 자세하게 보고 싶은데 어떡하죠?**

아주 좋은 질문입니다! 바로 그럴 때 우리가 아까 만든 **`SKILL.md`나 `summarizer.toml`을 수정**하는 겁니다. 요약 단계의 지침에 "3줄 요약" 대신 "각 문단별로 상세하게 요약하고 내 견해를 덧붙여줘"라고 적어보세요. 코덱스는 여러분이 시키는 대로 즉시 태도를 바꿀 겁니다.

## 한 줄 정리

성공적으로 뉴스를 수집하셨나요? 축하드립니다! 그런데 지금 만든 요약본, 말투가 좀 딱딱하진 않나요? 다음 섹션에서는 이 요약본을 여러분의 취향에 딱 맞게 변신시키는 **'커스텀의 기술'**을 배워보겠습니다!

## 09.3 [실습] 요약 커스텀하기

자, 이제 여러분만의 '편집장' 모드를 켤 시간입니다. 앞 섹션에서 우리는 뉴스봇의 뼈대를 만들고 실제로 뉴스가 쏟아져 들어오는 장관을 목격했습니다. 그런데 솔직히 말씀드리면, 지금 상태의 뉴스봇은 '남이 차려준 밥상'이나 다름없습니다.

말투는 좀 딱딱하고, 분류는 너무 광범위하죠. "나는 AI 뉴스 중에서도 비즈니스 적용 사례만 보고 싶은데?" 혹은 "나는 너무 진지한 건 싫고, 친구가 말해주듯 편하게 요약해줬으면 좋겠어"라는 생각이 드실 겁니다.

걱정 마세요. 우리가 만든 뉴스봇의 가장 큰 장점은 **'말귀를 알아먹는 시스템'**이라는 점입니다. 코드를 한 줄도 고칠 필요 없습니다. 그저 조수들에게 주는 **'지침서'**만 살짝 수정하면 됩니다.

## STEP 1. 분류 기준 내 입맛대로 바꾸기

가장 먼저 할 일은 '분류'의 기준을 바꾸는 겁니다. 기본 설정은 "AI/개발, 비즈니스, 라이프스타일" 정도로 되어 있을 텐데요. 이걸 여러분이 진짜 관심 있는 분야로 쪼개야 합니다. 비유하자면, 서점의 베스트셀러 코너를 통째로 보는 게 아니라 '자기계발'과 '재테크' 서가만 골라서 보는 것과 같습니다.

01 VS Code 왼쪽 탐색기에서 `.codex/skills/news/SKILL.md` 파일을 클릭하세요.
02 파일 내용 중에서 `## 분류 규칙` 혹은 카테고리 관련 섹션을 찾으세요.
03 기존 카테고리 내용을 지우고 아래와 같이 입력해 보세요.

```markdown
## 분류 규칙 (Categories)
들어오는 모든 뉴스는 반드시 아래 3가지 중 하나로 분류하세요.

1. **실전 AI**: 이론이 아니라, 지금 당장 업무에 써먹을 수 있는 도구나 방법론 (예: Claude 사용법, 프롬프트 팁)
2. **돈 되는 뉴스**: AI 산업의 투자, 매출, 비즈니스 모델 관련 소식 (예: 엔비디아 실적, 스타트업 투자 유치)
3. **개발자 도구**: 코딩 효율을 높여주는 새로운 라이브러리나 서비스 (예: Cursor 업데이트, 새로운 API 출시)
```

04 파일을 저장(`Ctrl+S` 또는 `Cmd+S`)하세요.

**확인**: 이렇게만 해도 뉴스봇의 편집장은 이제부터 기사를 읽을 때 "이건 실전 AI네!", "이건 돈 이야기구나!" 하고 여러분의 기준에 맞춰 라벨을 붙이기 시작합니다.

## STEP 2. 조수의 말투(톤)에 생명 불어넣기

분류를 마쳤다면 이제 '말투'를 고칠 차례입니다. 요약 담당 조수인 `summarizer`의 성격을 바꿔주는 거죠.

여러분은 어떤 스타일이 좋으신가요?
- "부장님께 보고드리는 진지하고 딱딱한 보고서 스타일"

03 아래 예시 중 마음에 드는 스타일 하나를 골라 덮어씌워 보세요.

**옵션 A: 유머러스한 실무자 톤 (추천!)**

**옵션 B: 냉철한 비즈니스 분석가 톤**

## STEP 3. 품질 규칙: "숫자와 링크는 필수!"

AI 조수들은 가끔 너무 신이 나서 중요한 정보를 빼먹고 '요약' 자체에만 집중할 때가 있습니다. 하지만 우리에게 진짜 중요한 건 **"정확한 숫자"**와 **"다시 확인할 수 있는 출처"**죠.

"엔비디아 주가가 올랐다"는 정보보다는 "엔비디아 주가가 어제보다 3.5% 올라서 사상 최고치를 경신했다"는 정보가 훨씬 가치 있으니까요. 이걸 **'품질 규칙'**으로 강제해 보겠습니다.

다시 `agents/summarizer.toml` 파일을 보세요. 지시사항 맨 마지막에 아래 내용을 추가하세요. 이건 조수의 뇌에 직접 새기는 '업무 수칙'입니다.

```toml
[quality_rules]
rules = [
  "원문에 숫자가 있다면 반드시 포함할 것 (금액, 퍼센트, 날짜 등)",
  "기사의 핵심 결론을 맨 앞에 볼드체로 적을 것",
  "참고할 수 있는 원문 URL 링크를 반드시 하단에 표기할 것",
  "모르는 내용은 추측해서 쓰지 말고 생략할 것"
]
```

**확인**: 이제 조수는 요약할 때마다 이 체크리스트를 확인합니다. 숫자가 빠졌으면 다시 넣고, 링크가 없으면 찾아서 붙이게 됩니다.

## 여기서 막혔나요?

**Q. 설정을 고쳤는데도 이전이랑 똑같은 말투로 나와요.**

코덱스가 이전 대화의 기억(컨텍스트)을 붙잡고 있어서 그럴 수 있습니다. 이럴 땐 터미널에 `/refresh`라고 입력해서 바뀐 설정 파일을 강제로 다시 읽게 하거나, 아예 `/clear`로 대화 내용을 비우고 다시 실행해 보세요. 조수에게 "옛날 지침은 잊고, 지금 준 따끈따끈한 새 지침서대로 일해!"라고 따끔하게 말해주는 겁니다.

**Q. 카테고리를 너무 많이 만들었더니 분류가 엉망이에요.**

카테고리는 처음엔 **3~5개** 정도가 적당합니다. 너무 세분화하면 AI 조수도 헷갈려서 기사를 엉뚱한 곳에 집어넣거든요. 분류가 잘 안 된다면 각 카테고리의 설명을 더 구체적으로 적어주거나, 카테고리 수를 줄여보세요.

**Q. 숫자를 포함하라고 했는데 자꾸 빼먹어요.**

그럴 땐 `summarizer.toml`에 **"숫자가 포함되지 않은 보고서는 실패로 간주한다"** 같은 강한 문구를 넣어보세요. 우스갯소리 같지만, AI 모델들은 이런 '부정적인 피드백' 지시를 의외로 진지하게 받아들여서 결과물을 더 꼼꼼하게 만듭니다.

## 09.4 패턴 정리 — 블로그와 뉴스봇에서 배운 것

자, 이제 블로그 글도 써보고 뉴스봇도 돌려봤습니다. 어때요? 두 가지가 완전히 다른 일처럼 보이시나요? 하나는 내 생각을 글로 쓰는 '창작'이고, 하나는 남의 소식을 정리하는 '정보 요약'이니까요.

하지만 눈치 빠른 분들은 이미 느끼셨을 겁니다. 이 두 작업의 속살을 들여다보면, 놀라울 정도로 똑같은 **'뼈대'**를 공유하고 있다는 사실을요. 마치 레고 블록으로 성을 만들든 자동차를 만들든, 결국 사용하는 조각의 규격은 같은 것과 비슷합니다.

우리가 지난 시간 동안 배운 건 단순히 두 가지 도구를 만드는 법이 아닙니다. 어떤 복잡한 업무라도 쪼개고 연결해서 자동화할 수 있는 **'승리의 패턴'**을 익힌 것이죠. 그 핵심 패턴 4가지를 지금부터 하나씩 짚어보겠습니다.

### 1. 체인(Chain): 배턴 터치하며 달리기

가장 기본이 되는 패턴은 **'A가 끝나야 B를 할 수 있는'** 구조입니다. 육상의 이어달리기처럼 앞 사람의 배턴(결과물)을 뒷 사람이 받아서 다음 단계로 넘어가는 방식이죠.

- **블로그**: 소재 수집 → 초안 집필 → 말투 수정 → 최종 발행
- **뉴스봇**: 뉴스 수집(RSS) → 기사 요약 → 채널별 포맷 변환 → 발송

**"앞 단계의 결과물이 뒷 단계의 재료가 됩니다."**

예를 들어 뉴스봇에서 `collector.toml`이 뉴스를 긁어오지 못하면, 아무리 똑똑한 `summarizer.toml`이라도 요약을 할 수 없습니다. 블로그도 마찬가지죠. '소재'가 없으면 '글'이 나올 수 없습니다.

### 2. 병렬(Parallel): 독립적인 단계는 동시에

모든 일을 순서대로만 할 필요는 없습니다. 어떤 일은 동시에 여러 명이 달라붙어서 처리하는 게 훨씬 효율적이죠.

기사가 10개 들어왔을 때, 한 명의 조수가 1번부터 10번까지 순서대로 읽으면 시간이 너무 오래 걸립니다. 하지만 개발 관련 기사는 개발 리뷰어에게, 비즈니스 기사는 비즈니스 리뷰어에게 동시에 뿌려주면 일 처리 속도가 몇 배로 빨라집니다.

<!-- IMG: 중앙의 편집장 AI가 기사 뭉치를 들고, 양옆의 개발/비즈니스/스토리 담당 기자 AI에게 기사를 나누어 주는 모습 -->

### 3. 품질 루프(Quality Loop): 통과 못 하면 다시!

"AI가 가끔 거짓말을 하거나 숫자를 틀리면 어떡하죠?"

이런 걱정을 해결해주는 것이 **'품질 루프'** 패턴입니다. 09.3에서 우리가 `summarizer.toml`에 "숫자를 빼먹으면 실패로 간주한다!"라고 엄포를 놓았던 거 기억하시나요?

단순히 시키고 끝내는 게 아니라, 결과물이 우리가 정한 기준에 맞는지 검사하고, 미달이면 다시 시키는 과정을 추가하는 겁니다.

- **체크리스트 예시**:
  - 번역투가 제거되었는가?
  - 핵심 숫자와 출처 URL이 포함되었는가?
  - 마케팅용 과장 문구는 삭제했는가?

**"검수자가 승인 도장을 찍어야 다음 단계로 넘어갑니다."** 이 루프를 한 번 거칠 때마다 결과물은 '기계가 쓴 글'에서 '사람이 정성 들여 쓴 글'로 탈바꿈합니다.

### 4. 레퍼런스 분리: 톤/용어/소스를 별도 파일로

제가 수강생분들께 가장 강조하는 습관입니다. 바로 **'설정(지침)'과 '데이터(재료)'를 별도의 파일로 나누는 것**이죠.

| 파일 종류 | 역할 | 비유 |
| :--- | :--- | :--- |
| **`SKILL.md`** | 전체적인 업무의 의도와 규칙 정의 | 요리 레시피 북 |
| **`agents/*.toml`** | 각 조수의 성격과 세부 지침 | 주방장의 개성 |
| **`sources.json`** | 가져올 데이터의 주소(RSS 등) | 식재료 공급처 목록 |
| **`docs/*.md`** | 참고할 톤 가이드나 이전 사례 | 예전에 만든 모범 음식 사진 |

이렇게 나눠두면 뭐가 좋을까요? 만약 뉴스 소스를 바꾸고 싶다면 `sources.json`만 수정하면 됩니다. 말투만 바꾸고 싶다면 `agents/*.toml`만 건드리면 되죠. 전체 시스템을 다시 만들 필요 없이, 필요한 부품만 갈아 끼우는 **'모듈형 자동화'**가 가능해지는 겁니다.

### "이 패턴이면 유튜브든 보고서든 확장 가능합니다"

"선생님, 저는 뉴스봇 말고 유튜브 영상을 요약해서 보고서로 만들고 싶은데요?"

축하합니다! 여러분은 이미 그 방법을 알고 계십니다. 방금 배운 4가지 패턴을 그대로 적용해서 '부품'만 갈아 끼우면 되거든요. 에이전트가 2명이든 10명이든 뼈대는 동일합니다. 에이전트 10종짜리 파이프라인 스킬도 결국 `skills/` + `agents/` + `AGENTS.md` 구조입니다. 블로그 `$write`(2 에이전트)와 차이는 에이전트 수뿐이에요.

### 스킬 = 반복 작업의 의도를 SKILL.md 파일로 만든 것

여기서 아주 중요한 개념 하나만 짚고 넘어갈게요.

05장에서 배운 **PRD(기획서)**가 "이 서비스는 무엇인가"라는 **'서비스의 의도'**를 담았다면, **스킬**은 "이 작업은 어떻게 반복 수행하는가"라는 **'반복 작업의 의도'**를 담은 문서입니다.

**"한 번 정의된 의도는 시스템의 자산이 됩니다."**

채팅창에서 "뉴스를 요약해줘"라고 매번 말하는 건 노동입니다. 하지만 그 의도를 `SKILL.md`라는 파일로 박제해두는 순간, 그건 언제든 꺼내 쓸 수 있는 여러분만의 '능력'이 됩니다. 의도가 명확하고 구체적일수록, AI 조수는 여러분의 마음을 독심술이라도 하듯 정확하게 읽어내어 결과물을 가져올 겁니다.

### 다음 파트 예고: 이걸 내가 안 시켜도 알아서 돌게 만드는 게 오픈클로

자, 이제 여러분은 자동화의 설계 도면을 그릴 줄 아는 '시스템 아키텍트'가 되셨습니다! 그런데 이 멋진 뉴스봇 파이프라인, 아직 치명적인 단점이 하나 있습니다. 바로 여러분이 직접 노트북을 열고 `codex`를 실행한 뒤 `$news`를 쳐야만 돌아간다는 거죠.

진정한 자동화라면 우리가 여행을 가 있든, 잠을 자고 있든 알아서 뉴스를 물어와야 하지 않을까요? 드디어 다음 파트에서는 내 컴퓨터가 꺼져 있어도 24시간 쉬지 않고 돌아가는 자동화의 심장, **'오픈클로(OpenClaw)'**의 세계로 입성해 보겠습니다!

## 여기서 막혔나요?

**Q. 패턴이 너무 많아서 뭐부터 적용해야 할지 모르겠어요.**

처음에는 무조건 **'체인'**부터 시작하세요. "가져온다 → 요약한다 → 보낸다" 이 세 단계만 제대로 연결되어도 자동화의 80%는 완성입니다. 병렬이나 품질 루프는 그다음에 욕심이 생길 때 하나씩 추가해도 절대 늦지 않습니다.

**Q. 폴더 구조가 엉키면 어떻게 하나요?**

이 책의 표준 구조를 꼭 지켜주세요. `.codex/skills/` 밑에는 각 스킬의 지침서를, `.codex/agents/` 밑에는 조수의 성격 파일을 넣는 규칙 말이죠. 이 규칙만 잘 지켜도 나중에 프로젝트가 커졌을 때 "이 설정이 어디 있더라?" 하며 헤매는 일을 99% 방지할 수 있습니다.

**Q. AI가 자꾸 제 의도와 다르게 행동해요.**

그럴 땐 해당 스킬의 `SKILL.md` 파일을 열어보세요. 혹시 지시가 너무 추상적이지는 않나요? "잘 요약해줘" 보다는 "1. 핵심 사건, 2. 원인, 3. 전망 순서로 요약해줘"라고 **단계별로** 지시하는 것이 패턴을 활용하는 비결입니다.

## 한 줄 정리

자동화는 **체인, 병렬, 품질 루프, 레퍼런스 분리**라는 4가지 패턴의 조합이며, 한 번 파일로 정의해둔 '스킬'은 여러분이 잠든 사이에도 돌아가는 강력한 무기가 됩니다.
