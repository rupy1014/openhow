> "결제 기능은 벽돌집의 지붕 같은 겁니다. 벽이 다 올라간 다음에 얹어야 안전하죠."

서비스가 배포되고, 주소가 생기고, 친구에게 링크까지 보냈습니다. 그런데 한 가지가 빠져 있죠. 바로 '결제'입니다.

"결제는 처음부터 넣어야 하는 거 아닌가요?"라고 생각하실 수도 있습니다. 사실은 반대입니다. 결제는 서비스의 핵심 흐름이 안정된 뒤에 붙이는 편이 훨씬 안전합니다. 이 장에서는 PG(Payment Gateway)를 고르는 기준, 결제를 붙이기 전에 준비할 것들, 그리고 테스트 결제로 검증하는 과정까지 한 걸음씩 밟아보겠습니다.

---

## 완성 기준

- [ ] 결제를 왜 나중에 붙이는지 이해하기
- [ ] PG 선택 기준 3가지 말할 수 있기
- [ ] 상품/금액/성공·실패 흐름을 먼저 정리하기
- [ ] 테스트 결제를 돌려서 성공과 실패를 모두 확인하기

## STEP 1. 결제는 왜 마지막에 붙이는 게 좋을까

서비스를 만들다 보면 "결제부터 넣자"는 생각이 듭니다. 돈을 받아야 진짜 서비스 같으니까요. 하지만 막상 결제를 먼저 넣으면 어떤 일이 벌어질까요?

### 1-1. 아직 벽도 안 세웠는데 지붕부터 얹으면

예를 들어볼게요. 우리가 만든 캐릭터 채팅 서비스를 떠올려 봅시다. 채팅 흐름이 아직 불안정한데 "프리미엄 캐릭터 잠금 해제" 같은 결제 기능을 먼저 넣었다고 생각해 보세요.

- 채팅 UI를 바꾸면 결제 버튼 위치도 바꿔야 합니다.
- 상품 구조를 바꾸면 결제 금액 로직도 다시 짜야 합니다.
- 로그인 방식을 바꾸면 결제 후 사용자 확인 로직도 흔들립니다.

결국 하나를 고치면 두세 군데를 더 고쳐야 하는 상황이 됩니다. 마치 기초가 안 잡힌 건물에 지붕을 올려놓은 격이죠.

### 1-2. 그러면 언제 붙이는 게 좋을까요?

기준은 간단합니다.

1. **핵심 기능이 돌아갈 때** — 채팅이 되고, 데이터가 저장되고, 사용자가 로그인할 수 있는 상태
2. **화면 구조가 어느 정도 고정됐을 때** — 버튼 위치가 매일 바뀌지 않는 상태
3. **배포가 되어 있을 때** — 실제 주소에서 접속할 수 있는 상태

6장에서 배포까지 마쳤으니, 지금이 딱 좋은 타이밍입니다.

> **확인**: 여러분의 서비스가 배포된 상태이고, 핵심 기능이 정상 작동하고 있다면 결제를 붙일 준비가 된 겁니다.

## STEP 2. 어떤 PG를 고르면 좋을까

PG는 Payment Gateway의 줄임말입니다. 쉽게 말해, 우리 서비스와 카드사·은행 사이에서 결제를 중간에서 처리해주는 서비스입니다.

### 2-1. PG가 하는 일

여러분이 온라인 쇼핑몰에서 카드로 결제할 때를 떠올려 보세요. 결제 버튼을 누르면 결제창이 뜨고, 카드 정보를 입력하면 결제가 됩니다. 이때 그 결제창을 띄워주고, 카드사와 통신하고, 돈이 제대로 빠져나갔는지 확인해주는 게 PG의 역할입니다.

식당 비유로 말하면 이렇습니다.

- **여러분의 서비스** = 식당 (음식을 만드는 곳)
- **PG** = 카드 결제 단말기 (결제를 처리해주는 기계)
- **카드사/은행** = 실제 돈이 오가는 곳

식당이 직접 카드사와 계약하고, 결제 단말기를 만드는 건 현실적으로 어렵잖아요. 그래서 PG 회사의 결제 단말기를 빌려 쓰는 겁니다.

![API를 통한 데이터 흐름](/__content__/images/ch07-01.png)

### 2-2. 국내 PG 선택 기준

국내에서 쓸 수 있는 PG는 여러 가지가 있습니다. 토스페이먼츠, 부트페이, 포트원(구 아임포트), 나이스페이, KG이니시스 등등. 이름이 많아서 혼란스럽죠.

기능만 보면 대부분 비슷합니다. 그래서 초보자가 진짜 봐야 할 기준은 세 가지입니다.

| 기준 | 왜 중요한가요? |
|------|-------------|
| **문서와 테스트 편의성** | 문서가 잘 되어 있어야 AI에게 "이 PG 연동해줘"라고 시킬 때 정확한 코드가 나옵니다 |
| **정산 주기와 수수료** | 매출이 생겼을 때 실제로 내 통장에 언제, 얼마나 들어오는지가 현실입니다 |
| **국내 결제 환경 지원** | 카카오페이, 네이버페이, 토스페이 같은 간편결제를 지원하는지 확인해야 합니다 |

처음이라면 **문서가 잘 되어 있고 테스트 모드 진입이 쉬운 PG**를 고르세요. 문서가 잘 되어 있다는 건, AI한테 연동을 맡겼을 때 정확도가 높아진다는 뜻이기도 합니다.

> **확인**: PG를 하나 골랐다면, 해당 PG의 개발자 문서(docs) 페이지를 열어두세요. 다음 단계에서 바로 쓰게 됩니다.

## STEP 3. 결제 붙이기 전에 무엇을 먼저 준비해야 할까

PG를 골랐다고 바로 코드를 짜면 안 됩니다. 먼저 정리할 게 있습니다. 이걸 건너뛰면 나중에 "이 결제 건은 뭐지?", "환불은 어떻게 하지?" 같은 혼란이 생깁니다.

### 3-1. 상품 구조 정리하기

결제를 붙이려면 "무엇을 파는지"가 명확해야 합니다. 당연한 것 같지만, 막상 정리하려고 하면 애매한 부분이 생깁니다.

예를 들어 캐릭터 채팅 서비스에 프리미엄 기능을 넣는다고 합시다.

```
상품명: 프리미엄 캐릭터 팩
가격: 4,900원
포함 내용: 프리미엄 캐릭터 3종 잠금 해제
유효 기간: 영구
```

이 네 가지만 먼저 적어보세요. "얼마 받을지 아직 모르겠는데요?"라고 해도 괜찮습니다. 테스트 단계에서는 100원이든 1,000원이든 상관없습니다. 구조를 잡는 게 먼저입니다.

### 3-2. 성공/실패/취소 흐름 그려보기

결제에는 '성공'만 있는 게 아닙니다. 실패도 있고, 취소도 있습니다. 이 세 가지 경우를 미리 정리해두면 나중에 코드 짜기가 훨씬 수월합니다.

```
[성공] 결제 완료 → 성공 페이지 표시 → DB에 구매 기록 저장
[실패] 카드 한도 초과 등 → 실패 메시지 표시 → 다시 시도 안내
[취소] 사용자가 결제창에서 닫기 → 원래 페이지로 돌아가기
```

![결제 성공, 실패, 취소 — 세 가지 분기 흐름도](/__content__/images/ch07-01.png)

### 3-3. AI에게 이렇게 정리해서 알려주세요

준비한 내용을 AI에게 전달할 때는 이렇게 해보세요.

```
"결제 기능을 붙이려고 해.
PG는 [선택한 PG 이름]을 쓸 거야.

상품 정보:
- 상품명: 프리미엄 캐릭터 팩
- 가격: 4,900원

결제 흐름:
- 성공하면: /payment/success 페이지로 이동하고 DB에 기록
- 실패하면: 에러 메시지 보여주고 다시 시도 안내
- 취소하면: 원래 페이지로 돌아가기

테스트 모드로 먼저 만들어줘."
```

5장에서 OpenRouter API를 붙이고, 6장에서 환경변수를 관리한 것과 같은 패턴입니다. PG도 결국 외부 서비스의 API를 우리 서비스에 연결하는 것이거든요. API Key를 `.env`에 숨기고, 요청을 보내고, 응답을 받는 구조가 동일합니다.

> **확인**: 상품명, 가격, 성공/실패/취소 흐름을 한 장에 정리했다면 준비가 끝난 겁니다.

## STEP 4. 테스트 결제부터 검증하기

실제 돈이 오가기 전에 반드시 테스트 결제를 해봐야 합니다. 대부분의 PG는 '테스트 모드'를 제공합니다. 실제 카드 번호를 넣지 않아도, 결제 과정 전체를 시뮬레이션할 수 있는 모드입니다.

### 4-1. 테스트 모드에서 확인할 것들

테스트 결제를 돌릴 때는 세 가지를 반드시 확인하세요.

01 **성공 흐름 확인** — 테스트 카드 번호로 결제를 진행합니다. 결제가 완료되면 성공 페이지가 뜨는지, DB에 기록이 남는지 확인합니다.

02 **실패 흐름 확인** — 일부러 잘못된 정보를 넣어봅니다. 에러 메시지가 깔끔하게 뜨는지, 앱이 멈추지 않는지 봅니다. 외부 API 연동에서 배운 `try-catch`와 같은 개념입니다. 결제 서버도 남의 서버이기 때문에, 언제든 실패할 수 있다는 전제로 만들어야 합니다.

03 **취소 흐름 확인** — 결제창에서 뒤로 가기를 눌러봅니다. 이때 화면이 하얗게 멈추거나 에러가 뜨면 안 됩니다. 자연스럽게 원래 페이지로 돌아와야 합니다.

![테스트 결제 성공 화면과 PG 관리자 대시보드](/__content__/images/ch07-02.png)

### 4-2. AI에게 테스트 도움 요청하기

테스트 중에 문제가 생기면, AI에게 이렇게 알려주세요.

```
"테스트 결제를 했는데 성공 페이지로 안 넘어가.
결제창은 뜨고, 결제 버튼도 눌렸는데
성공 콜백이 실행이 안 되는 것 같아.
브라우저 콘솔에 이런 에러가 떠:
[에러 메시지 붙여넣기]"
```

API 디버깅에서 배운 것과 같은 원리입니다. "결제가 안 돼"라고만 말하면 AI도 어디서부터 봐야 할지 모릅니다. **어디까지 됐고, 어디서 끊겼는지**를 알려주면 해결이 빨라집니다.

### 4-3. 테스트가 끝나면 실제 모드로 전환

테스트 결제가 세 가지 흐름 모두 통과했다면, 이제 실제 모드로 전환할 차례입니다. 대부분의 PG에서는 API Key를 '테스트용'에서 '운영용'으로 바꾸면 됩니다. 환경변수(`.env`)에 저장된 키를 운영용으로 교체하고, 배포 서비스(Vercel 등)의 환경변수도 함께 업데이트해주면 됩니다.

6장에서 배운 환경변수 설정, 기억나시죠? 로컬의 `.env`만 바꾸면 안 되고, 배포 플랫폼의 환경변수도 반드시 함께 바꿔야 합니다.

> **확인**: 성공, 실패, 취소 세 가지 흐름이 모두 정상이라면 결제 연동이 완료된 겁니다.

## 여기서 막혔나요?

**Q. 결제창이 아예 안 떠요**

상황: 결제 버튼을 눌렀는데 아무 반응이 없습니다.

원인:
- PG의 JavaScript SDK가 제대로 로드되지 않았을 수 있습니다
- API Key가 `.env`에 없거나, 오타가 있을 수 있습니다
- 테스트 모드가 아닌 운영 모드 키를 넣었을 수 있습니다

해결:
1. 브라우저 개발자 도구(F12) → Console 탭에서 에러 메시지를 확인하세요
2. `.env` 파일에 PG에서 발급받은 테스트용 키가 정확히 들어가 있는지 확인하세요
3. AI에게 "결제 버튼을 눌렀는데 결제창이 안 뜨고, 콘솔에 이런 에러가 떠"라고 에러 메시지와 함께 보여주세요

**Q. 결제는 됐는데 성공 페이지가 안 뜨고 빈 화면이에요**

상황: 결제 자체는 완료됐는데, 성공 후 리다이렉트가 안 됩니다.

원인:
- 성공 콜백 URL이 잘못 설정되어 있을 수 있습니다
- 로컬(`localhost`)과 배포 주소가 섞여 있을 수 있습니다

해결:
1. 성공 시 이동할 페이지(`/payment/success` 등)가 실제로 존재하는지 확인하세요
2. 콜백 URL에 `localhost`가 하드코딩되어 있지 않은지 확인하세요
3. AI에게 "결제 성공 콜백 URL 설정 부분 보여줘"라고 요청하세요

**Q. 테스트 결제 후 환불은 어떻게 하나요?**

상황: 테스트 결제가 쌓이는데, 이걸 취소할 수 있는지 모르겠습니다.

원인:
- 테스트 모드 결제는 실제 돈이 빠지지 않으므로, 환불하지 않아도 됩니다

해결:
1. PG 관리자 대시보드에서 테스트 결제 내역을 확인할 수 있습니다
2. 실제 운영 모드에서는 PG의 환불 API를 연동해야 합니다
3. 처음에는 PG 대시보드에서 수동으로 환불 처리하는 것으로 충분합니다

**Q. 어떤 PG를 써야 할지 정말 모르겠어요**

상황: PG가 너무 많아서 결정을 못 하겠습니다.

해결:
1. 처음이라면 문서가 잘 되어 있고, 회원가입 후 바로 테스트할 수 있는 PG를 고르세요
2. 나중에 PG를 바꾸는 것도 가능합니다. 코드 구조가 크게 달라지지 않거든요
3. "최고의 PG"를 찾느라 시간을 쓰기보다, 일단 하나를 골라서 테스트 결제까지 돌려보는 게 훨씬 중요합니다

## 한 줄 정리

결제는 서비스의 뼈대가 잡힌 뒤에 붙이세요. PG를 고르고, 상품과 흐름을 정리하고, 테스트 결제로 성공·실패·취소를 모두 확인하면 — 그때 실제 모드로 켜는 겁니다.
