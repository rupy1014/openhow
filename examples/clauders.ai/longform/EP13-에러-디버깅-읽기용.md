## 1. 시작 — 빨간 글씨, 가슴 철렁하죠?

만들다가 화면에 빨간 글씨가 좌악 떴어요. //

영어로, 알 수 없는 말이, 길게. //

그 순간 가슴이 철렁 내려앉죠. "아, 내가 뭘 잘못 건드렸나 봐." "이거 다 망한 건가?" //

오늘 그 마음, 제가 확실하게 풀어드릴게요. //

지난 영상에서 우리는 Git이라는 안전망을 깔았어요. 기억나세요? 게임 세이브처럼, 잘 되던 순간을 저장해두는 거요. //

그래서 이제 우리한테는 돌아갈 곳이 있어요. 망쳐도 되돌릴 수 있죠. //

그 안전망을 깔았으니까, 오늘은 한 발 더 나가요. 에러가 떴을 때 당황하지 않고, AI랑 같이 고치는 법. //

이거 하나만 손에 익으면, 빨간 글씨가 더는 안 무서워져요. 천천히 가볼게요.

---

## 2. 먼저 안심부터 — 에러는 망한 신호가 아니에요

본론 들어가기 전에, 제일 중요한 말부터 할게요. //

에러가 떴다고 망한 거, 절대 아니에요. //

이건 제가 분위기 맞춰주려고 하는 말이 아니에요. 진짜예요. //

생각해보면 이래요. 만약에 뭔가 잘못됐는데 화면이 아무 말도 안 해주면, 우리는 어디가 잘못됐는지 영영 모르잖아요. //

근데 에러는, 컴퓨터가 우리한테 "야, 여기 좀 막혔어" 하고 손을 들어주는 거예요. //

어디가 막혔는지 콕 집어서 알려주는 단서. 그게 에러예요. //

그러니까 빨간 글씨를 봤을 때 할 일은, 겁먹는 게 아니라 "오, 단서 나왔네" 하는 거예요. //

AI로 뭔가를 만들면 에러는 무조건 나와요. 10년 한 개발자도 매일 봐요. 에러 없이 가는 사람은 없어요. //

그러니까 "나만 이런가?" 하는 그 걱정, 먼저 내려놓으셔도 돼요. 에러는 만드는 과정의 당연한 일부예요.

## 3. 첫 번째 규칙 — 해석하려고 붙잡지 말고, 일단 복사

자, 그럼 에러가 떴어요. 뭐부터 할까요? //

초보자분들이 제일 많이 하는 실수가 있어요. 빨간 영어 글씨를 혼자 노려보면서, 한 단어씩 해석하려고 끙끙대는 거예요. //

그러지 마세요. 시간만 가요. //

우리한테는 AI가 있잖아요. 해석은 AI한테 시키면 돼요. 우리가 할 일은, 그 에러를 그대로 복사해서 AI한테 주는 거예요. //

여기서 많이 물어보세요. "근데 그 빨간 글씨가 대체 어디 있는 거예요?" //

위치가 정해져 있어요. 딱 세 군데만 기억하시면 돼요. //

**웹사이트를 만들고 있으면, '브라우저 콘솔'.** 크롬 같은 인터넷 창에 숨어 있는 개발자용 화면이에요. //

**앱을 만들고 있으면, 'IDE 로그'.** 앱을 만드는 프로그램 안에 에러를 보여주는 창이 따로 있어요. //

**서버 쪽이면, '터미널'.** 그 검은 창에서 빨간 글씨가 찍혀요. //

용어가 와르르 나왔죠? 지금 다 외우려고 하지 마세요. 몰라도 돼요. //

그냥 "에러는 정해진 곳에 뜬다, 거기서 빨간 글씨를 찾아서 복사한다." 이거 하나만요. //

다음 장에서, 제일 흔한 '브라우저 콘솔' 여는 법부터 천천히 보여드릴게요.

---

## 4. 브라우저 콘솔, 이렇게 열어요

웹을 만들고 있다고 해볼게요. 제일 흔한 경우니까요. //

화면은 멀쩡해 보이는데 버튼을 눌러도 반응이 없어요. 뭔가 이상하죠. //

이럴 때, 화면 안쪽에서는 에러가 나고 있을 수 있어요. 그걸 보는 곳이 브라우저 콘솔이에요. //

여는 법은 간단해요. //

**윈도우 컴퓨터면, 키보드에서 F12를 누르세요.** //

**맥이면, Command 키랑 Option 키랑 J를 같이 누르세요.** //

그러면 화면 옆이나 아래에 새로운 창이 하나 열려요. 거기서 'Console'이라고 적힌 탭을 찾아 눌러요. //

거기에 빨간 글씨가 있으면, 그게 바로 에러예요. //

이런 식으로 생겼어요. 예를 들면요. //

"TypeError: Cannot read properties of undefined." //

지금 이게 무슨 뜻인지 몰라도 전혀 상관없어요. 진짜로요. //

우리가 할 일은 딱 하나예요. 그 빨간 줄을 마우스로 드래그해서, 통째로 복사하는 거예요.

## 5. 영어 무서워 마세요, 그냥 그대로 복사

여기서 많은 분들이 멈칫하세요. //

"에러가 다 영어인데… 나는 영어 울렁증 있는데…" //

괜찮아요. 영어 하나도 못 해도 돼요. 읽을 필요 자체가 없어요. //

해석은 우리가 하는 게 아니라, AI가 하는 거니까요. //

그러니까 영어 글씨를 보고 무서워하지 마세요. 그냥, 있는 그대로, 통째로 복사하면 끝이에요. //

자, 그럼 실제로 어떻게 흘러가는지 한 장면 보여드릴게요. //

피드백 받는 화면을 만들고 있었다고 해볼게요. 목록을 띄웠더니 화면이 하얗게 비고, 콘솔에 빨간 에러가 떴어요. //

"TypeError: Cannot read properties of undefined." //

여기서 우리는 해석 안 해요. 그 줄을 드래그해서 복사하고, AI한테 이렇게 붙여넣어요. //

"브라우저 콘솔에 이런 에러가 떴어. (붙여넣기) 피드백 목록 화면을 열었을 때 났어. 원래는 목록이 보여야 하는데 화면이 하얘. 초보자도 이해하게 원인 설명해주고 고쳐줘." //

그러면 AI가 답해요. "이건 아직 데이터가 안 들어왔는데 화면이 먼저 읽으려고 해서 난 거야. 이렇게 고치면 돼." 하고 코드를 고쳐줘요. //

다시 화면을 새로고침하면, 목록이 짠 하고 떠요. 해결. //

방금 우리가 영어 한 줄 해석했나요? 아니죠. 복사, 붙여넣기, 상황 설명. 그게 다였어요.

## 6. 에러 볼 때 딱 세 가지만 — 왓, 웨어, 웬

방금처럼 통째로 복사하는 게 기본이에요. //

근데 여기서 한 발만 더 나가면, 훨씬 빨라져요. 에러를 '읽는 법'을 살짝만 알면요. //

겁먹지 마세요. 영어 전부를 읽는 게 아니에요. 딱 세 가지만 봐요. //

**첫째, 왓(WHAT). 무슨 에러인가.** 에러 이름이에요. 보통 맨 앞에 나와요. //

**둘째, 웨어(WHERE). 어디서 났나.** 어떤 파일, 몇 번째 줄인지요. //

**셋째, 웬(WHEN). 언제 났나.** 내가 무슨 행동을 했을 때 떴는지요. //

아까 그 에러를 다시 볼게요. //

"TypeError: Cannot read properties of undefined, at FeedbackList 12번째 줄." //

여기서 왓은 'TypeError', 무슨 에러인지. 웨어는 'FeedbackList 파일 12번째 줄', 어디서 났는지. 웬은 '피드백 목록을 열었을 때', 언제 났는지요. //

이렇게 세 칸으로만 나눠도, 원인이 확 좁혀져요. //

그리고 이것도 AI한테 시키면 돼요. 이렇게요. //

"이 에러에서 왓, 웨어, 웬을 나눠서 초보자 기준으로 설명해줘. 그리고 왜 이런 에러가 나는지도 알려줘." //

그럼 AI가 세 칸으로 정리해서 쉽게 풀어줘요. 우리는 보기만 하면 되고요.

## 7. 자주 만나는 에러들, 미리 인사만 해둬요

에러 이름이 영어라서 더 무섭게 느껴지죠. //

근데 자주 나오는 애들은 정해져 있어요. 미리 얼굴만 익혀두면, 다음에 봤을 때 덜 놀라요. //

외우라는 거 아니에요. "아, 이런 애가 있구나" 정도면 충분해요. //

**TypeError.** 값의 모양이 예상이랑 달라요. 보통 아직 데이터가 없는데 읽으려고 할 때 나요. //

**ReferenceError.** 그런 이름을 못 찾겠대요. 변수 이름 오타거나, 뭘 빼먹었을 때요. //

**SyntaxError.** 코드 문법이 틀렸어요. 괄호나 따옴표가 짝이 안 맞을 때 잘 나요. //

**404.** 주소를 못 찾는 거예요. 길을 잘못 적었을 때요. //

**401이나 403.** 권한 문제예요. 로그인이나 열쇠가 안 맞을 때요. //

**500.** 서버 안쪽에서 뭔가 터진 거예요. //

**Failed to fetch.** 요청을 보냈는데 실패했어요. 주소가 틀렸거나, 서버가 안 켜졌거나, 여러 이유가 있어요. //

지금 이거 하나도 안 외우셔도 돼요. //

"이런 종류가 있구나, 이름이 무서워 보여도 뜻은 별거 아니구나." 그 느낌만 가져가시면 돼요.

## 8. AI한테 줄 때, 이 다섯 가지를 같이

자, 이제 핵심이에요. //

에러만 툭 던지면 어떻게 될까요? AI가 상황을 모르니까, 추측을 많이 해요. //

추측이 많아지면, 엉뚱한 곳을 고칠 확률이 올라가요. //

그래서 에러를 줄 때, 같이 줘야 할 게 다섯 가지 있어요. 어렵지 않아요. //

**첫째, 내가 하던 작업.** 지금 무슨 기능을 만들거나 고치고 있었는지요. //

**둘째, 기대한 동작.** 원래는 어떻게 돼야 하는지요. //

**셋째, 실제 현상.** 지금은 어떻게 이상하게 되고 있는지요. //

**넷째, 에러 로그.** 아까 복사한 그 빨간 글씨요. //

**다섯째, 수정 범위.** 어디까지 고쳐도 되고, 어디는 건드리면 안 되는지요. //

말로 하니까 많아 보이죠? 그냥 친구한테 상황 설명하듯 하면 돼요. //

복사해서 바로 쓰실 수 있게, 틀을 하나 드릴게요. 빈칸만 채우시면 돼요. //

"지금 (무슨 기능)을 만들고 있었어. 원래는 (이렇게) 돼야 하는데, 지금은 (이렇게) 돼. 에러는 이거야. (붙여넣기) 원인을 먼저 설명해주고, 꼭 필요한 부분만 고쳐줘. 왜 났는지도 초보자 기준으로 알려줘." //

이 틀 하나만 있으면, 에러 대응의 절반은 끝난 거예요.

## 9. "고쳐줘"만 반복하면 왜 꼬이냐면요

여기서 초보자분들이 제일 많이 빠지는 함정 하나를 짚을게요. //

에러가 났을 때 그냥 "이거 안 돼, 고쳐줘"만 계속 말하는 거예요. //

이 말만 해도 AI가 뭔가를 바꿔주긴 해요. 운 좋으면 한 번에 해결되고요. //

근데 진짜 원인을 못 잡은 채로 "고쳐줘"만 반복하면, 이런 일이 생겨요. //

A 파일을 고쳐요. 그럼 에러가 살짝 바뀌어요. //

그래서 B 파일을 고쳐요. 그랬더니 멀쩡하던 다른 기능이 깨져요. //

그래서 C 파일을 고쳐요. 그랬더니 맨 처음 그 에러가 다시 나와요. //

같은 자리를 뱅뱅 도는 거죠. 시간만 가고, 코드는 더 꼬여요. //

그래서 한 번 고친 다음에는, 꼭 한 가지를 더 물어보세요. //

"왜 이 에러가 난 거야?" //

"방금 수정은 뭘 고친 거야?" //

이걸 물어보면 뭐가 좋냐면요. //

그냥 고치기만 하면, 다음에 똑같은 문제가 나도 또 "고쳐줘" 해야 해요. //

근데 왜 났는지를 한 번 이해해두면, 다음엔 내가 먼저 알아채요. "아, 이거 그때 그거네" 하고요. //

그러면서 개발 지식이 슬금슬금 쌓여요. 이게 진짜 남는 거예요.

## 10. 에러는 현상이고, 진짜 원인은 더 앞에 있을 수 있어요

조금만 더 깊이 들어가 볼게요. 어렵지 않으니까 따라오세요. //

에러 메시지는 보통 '지금 터진 현상'을 보여줘요. //

근데 진짜 원인은 그 자리가 아니라, 더 앞에 있을 때가 많아요. //

예를 들어볼게요. //

화면에 "값이 비었다"는 에러가 떴어요. 겉으로는 화면 문제 같죠. //

근데 진짜 원인은, 그 화면에 들어와야 할 데이터가 애초에 안 만들어진 거일 수 있어요. //

또, "저장이 안 된다"는 에러가 떴어요. 겉으로는 저장 버튼 문제 같죠. //

근데 진짜는, 누가 저장하는지 정보가 빠졌거나, 저장할 내용이 제대로 안 정해진 거일 수 있어요. //

그래서 땜질만 하면, 잠깐 됐다가 또 터져요. //

이럴 때 AI한테 이렇게 물어보면 좋아요. //

"이 에러가 이 줄만의 문제인지, 아니면 데이터 흐름이나 구조가 잘못된 신호인지 봐줘. 근본 원인 후보를 세 개로 나눠서 설명해줘." //

이렇게 물으면, 겉만 고치는 게 아니라 진짜 원인을 같이 볼 수 있어요. //

지금 이게 어렵게 들려도 괜찮아요. 이런 질문을 한 번 해본다는 것만 기억하시면 돼요.

## 11. 수정 범위를 정해주세요 — "여기까지만"

또 하나, 초보자분들이 놀라는 순간이 있어요. //

에러 하나 고쳐달라고 했는데, AI가 엉뚱한 데까지 같이 바꿔버리는 거예요. //

디자인이 바뀌어 있거나, 멀쩡하던 다른 기능이 건드려져 있거나요. //

이거, AI가 못해서가 아니에요. 우리가 "여기까지만"이라고 안 말해줘서 그래요. //

그러니까 범위를 같이 정해주세요. 이렇게요. //

"이 에러만 고쳐줘. 디자인은 건드리지 마. 새 라이브러리는 추가하지 마. 기존에 잘 되던 동작은 그대로 둬. 고친 파일이랑 이유는 알려줘." //

그리고 이 말도 알아두시면 좋아요. //

"일단 원인 분석만 해줘. 아직 코드는 고치지 마." //

바로 고치기 전에, 원인부터 보고 싶을 때가 있거든요. 그럴 때 쓰는 말이에요. //

범위를 정해주는 것만으로도, 엉뚱한 곳이 바뀌는 사고가 확 줄어요.

---

## 12. 3번 룰 — 같은 에러 세 번이면 멈춰요

자, 그래도 안 풀릴 때가 있어요. 누구나 있어요. //

같은 에러를 세 번 고쳤는데, 계속 또 나와요. //

이럴 때 제일 중요한 규칙 하나. 세 번째에는, 멈추세요. //

이게 '3번 룰'이에요. //

여기서 "다시 고쳐줘"만 더 하면, 코드가 점점 더 꼬여요. 빠져나오기 더 힘들어져요. //

그러니까 세 번째엔 고치라고 하지 말고, 이렇게 말하세요. //

"이 에러를 세 번 고쳤는데 계속 나. 지금까지 어떤 수정을 했는지 정리해줘. 근본 원인 가설을 다시 세우고, 마지막으로 잘 되던 커밋이랑 비교해줘." //

기억나시죠? 지난 영상에서 우리가 깔아둔 그 안전망. 커밋이요. //

기능 하나 될 때마다 세이브해뒀잖아요. //

그 세이브 지점이, 바로 지금 같은 순간을 위한 거예요. //

너무 꼬였다 싶으면, 마지막으로 잘 되던 커밋으로 되돌리면 돼요. //

되돌릴 때도 그냥 되돌리지 말고, 먼저 물어보세요. //

"마지막으로 정상이던 커밋으로 돌아가는 방법 알려줘. 되돌리면 어떤 변경이 사라지는지도 먼저 설명해줘." //

뭐가 사라지는지 알고 되돌리면, 마음이 훨씬 편해요. //

그래서 기능마다 커밋을 남기는 게 그렇게 중요했던 거예요. 꼬였을 때 돌아갈 곳이 있어야 하니까요.

## 13. 디버깅하다 보면, 개발 지식이 쌓여요

마지막으로, 좀 좋은 얘기 하나 할게요. //

처음에는 에러가 그냥 다 무섭게만 보여요. 다 똑같은 빨간 글씨 같죠. //

근데 몇 번 고치다 보면, 신기하게 패턴이 보여요. //

"아, 이건 데이터가 아직 안 들어와서 나는 거구나." //

"아, 이건 주소를 잘못 적은 거구나." //

"아, 이건 배포할 때 뭘 빼먹은 거구나." //

이게 바로 개발 지식이에요. //

책으로 미리 외우는 것보다, 내 프로젝트에서 진짜 터진 에러를 보면서 배우는 게 훨씬 잘 남아요. //

그래서 AI가 고쳐준 다음에는, 한 번씩 이렇게 물어보세요. //

"이번 에러에서 내가 배워야 할 개념 세 개만 정리해줘. 다음에 같은 문제가 나면 뭘 먼저 확인하면 되는지도 알려줘." //

이렇게 한 번씩만 챙겨도, 다음번엔 AI한테 던지는 질문 수준이 달라져 있을 거예요. //

에러는 귀찮은 방해물이 아니라, 나를 가르쳐주는 선생님이에요. 진짜로요.

## 14. 마무리 + 다음 영상

자, 오늘 거 정리할게요. //

에러가 떴다고 망한 거 아니에요. 어디 막혔는지 알려주는 단서예요. //

해석하려고 붙잡지 말고, 통째로 복사해서 AI한테 줘요. 영어 무서워 마시고, 그냥 그대로요. //

볼 때는 딱 세 가지. 왓, 웨어, 웬. 무슨 에러, 어디서, 언제요. //

줄 때는 다섯 가지. 내가 하던 작업, 기대한 동작, 실제 현상, 에러 로그, 수정 범위. //

"고쳐줘"만 반복하지 말고, "왜 났어?"까지 물어요. //

그리고 같은 에러 세 번이면 멈추고, 마지막으로 잘 되던 커밋으로 돌아가요. //

이걸 몇 번만 해보시면, 정말로 에러가 더는 안 무서워져요. 약속할게요. //

자, 이제 우리 손에 만든 게 있고, 에러도 같이 고칠 수 있게 됐어요. //

근데 그거, 아직은 내 컴퓨터 안에서만 돌아가는 상태예요. 나만 볼 수 있죠. //

다음 영상에서는, 이걸 진짜 인터넷 주소로 만들어서 남한테 보내는 법. 배포를 해볼게요. //

딱 한 시간이면, "이거 내가 만든 거야" 하면서 친구한테 링크를 카톡으로 보낼 수 있어요. //

그 짜릿한 순간, 다음 영상에서 같이 만들어봐요. //

에러는 적이 아니라 단서다. 이거 하나만 챙겨 가셔도 오늘은 충분해요. 그럼 다음 영상에서, 만든 걸 세상에 내보내러 같이 가봐요.
