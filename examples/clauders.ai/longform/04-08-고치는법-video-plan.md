# [서비스 만들기 8강] 고치는 법 — 에러, 안 무서워지는 법

> **롱폼 비디오 플랜** · 목표 길이 3~5분 · 톤 해요체
> **원본**: `docs/build-service/07-fix.md` + 쇼츠 `04-build-service-shorts.md [고치는 법] 1~5`
> **한 문장 콘셉트**: 에러는 망한 게 아니라 "어디가 막혔는지" 알려주는 신호. 통째로 복사해서, WHAT·WHERE·WHEN으로 보고, 클로드한테 단서까지 줘서 고친다.
> **시리즈 위치**: ← 7강 Git · **(이 편) 8강 고치는 법** · → 9강 배포
> **이 편에서 큐레이션한 비트**: 쇼츠 5편 중 [1]에러=신호 · [3]WHAT/WHERE/WHEN · [2]"고쳐줘"만 반복 금지 · [4]3번 룰. ([5]에러 5요소는 챕터2에 녹임.)

## 0. 콜드오픈 / 훅 (0:00–0:18)

**[화면]** 화면 가득 빨간 에러 로그(`TypeError: Cannot read properties of undefined`)가 떠 있다 → 천천히 줌인.
**[자막]** 에러 = 망한 거 아님

**나레이션**
"빨간 글씨 보면 가슴 철렁하죠?

근데 그거, 망한 신호 아니에요.

어디가 막혔는지
콕 집어주는 단서예요."

**[전환]** 화면이 차분한 작업 화면으로 바뀜.
"AI로 서비스 만들면 에러는 무조건 나와요.
오늘 이거 끝나면, 에러가 떠도
당황 안 하고 고치는 흐름이 손에 잡혀요."

## 1. 챕터1 — 에러는 "해석"하지 말고 "복사"부터 (0:18–1:30)

**[화면]** 웹 화면에서 버튼을 눌렀는데 아무 반응 없음 → 개발자 도구 열기(F12) → Console 탭의 빨간 줄 강조.
**[데모]** 콘솔 에러 한 줄을 드래그로 통째로 복사 → 클로드 코드 입력창에 붙여넣기.
**[자막]** 웹=브라우저 콘솔 · 앱=IDE 로그 · 서버=터미널

**나레이션**
"초보자가 제일 많이 하는 실수가,
영어 에러를 혼자 해석하려고 붙잡고 있는 거예요.

그러지 마세요.
에러는 보이는 곳이 정해져 있어요.

웹이면 브라우저 콘솔,
앱이면 IDE 로그,
서버면 터미널 로그.

빨간 글씨를 찾으면,
해석하지 말고 통째로 복사해서
클로드한테 그대로 주면 돼요."

**토킹포인트**
- "화면은 멀쩡한데 안 되는 것 같을 때도, 콘솔 안에선 에러가 나고 있는 경우가 많다."
- 위쪽 첫 에러 + 내 파일 이름이 나온 줄이 제일 중요 — 그 줄은 꼭 포함.
- 영어 읽기 싫으면 "초보자 기준으로 해석해줘"만 붙이면 됨.

**[전환]** "근데 여기서 한 발 더 나가야 진짜 빨라져요."

## 2. 챕터2 — "고쳐줘"만 반복하면 왜 꼬이나 (1:30–3:15)

**[화면]** "이거 안 돼, 고쳐줘"를 세 번 반복하는 채팅 → 그때마다 다른 파일이 바뀌고 다른 기능이 깨지는 모습(빠른 컷).
**[자막]** 고쳐줘 반복 = 같은 자리 뱅뱅

**나레이션**
"'이거 안 돼, 고쳐줘.'
이 말만 해도 클로드가 뭔가 바꾸긴 해요.

근데 진짜 원인을 못 잡은 상태면
이런 루프에 빠져요.

A 파일 고치면 에러가 바뀌고,
B 파일 고치면 다른 게 깨지고,
C 파일 고치면 처음 에러가 다시 나와요.

시간이랑 토큰만 쓰고 더 꼬이는 거죠."

**[화면 전환]** 에러 한 줄을 세 칸으로 분해하는 그래픽:
`TypeError` / `FeedbackList.tsx:12` / "목록 화면 열었을 때"
**[자막]** WHAT · WHERE · WHEN

**나레이션 (이어서)**
"그래서 에러를 볼 때
영어를 다 읽으려 하지 말고
딱 세 가지만 보세요.

WHAT, 무슨 에러인가.
WHERE, 어떤 파일 몇 번째 줄인가.
WHEN, 내가 뭘 했을 때 났나.

이 세 칸으로 나누면 원인이 확 좁혀져요."

**[데모]** 클로드에게 보내는 메시지를 실제로 타이핑:
```
이 에러를 WHAT/WHERE/WHEN으로 나눠서 초보자 기준으로 설명해줘.
그리고 고치기 전에, 원인이 이 줄만의 문제인지
데이터 흐름이 잘못된 신호인지도 같이 봐줘.
```

**토킹포인트 (원본 doc에서 깊이 보강)**
- 에러만 던지면 클로드가 추측을 많이 함 → 엉뚱한 파일 고칠 확률↑.
- 그래서 최소 5가지를 같이: **내가 하던 작업 / 기대한 동작 / 실제 현상 / 에러 로그 / 수정 범위.**
- 특히 수정 범위: "이 에러만, 디자인은 건드리지 마, 기존 동작 유지"로 좁혀주기.
- 한 번 고친 뒤엔 꼭 "왜 났어?"를 물어야 다음에 같은 문제가 안 생김 = 개발 지식이 쌓이는 지점.

**[전환]** "그래도 계속 안 될 때가 있죠. 그때 멈추는 기준이 있어요."

## 3. 챕터3 — 3번 룰 + 커밋으로 되돌리기 (3:15–4:20)

**[화면]** 같은 에러가 3번 반복되는 로그 → 멈춤 표시(✋) → `git log`에서 마지막 정상 커밋으로 되돌아가는 장면.
**[자막]** 같은 에러 3번 = 멈춰

**나레이션**
"같은 에러를 세 번 고쳤는데 또 나요?
그럼 멈추는 게 좋아요.

거기서 '다시 고쳐줘'만 더 하면
코드가 더 꼬여요.

그럴 땐 이렇게 말하세요."

**[데모]** 타이핑:
```
이 에러를 3번 고쳤는데 계속 나.
지금까지 어떤 수정이 있었는지 정리해줘.
근본 원인 가설을 다시 세우고,
마지막으로 잘 되던 커밋과 비교해줘.
```

**나레이션 (이어서)**
"필요하면 마지막으로 잘 되던 커밋으로 되돌리면 돼요.

그래서 7강에서 본 것처럼,
기능마다 커밋을 남기는 게 중요해요.

꼬였을 때 돌아갈 지점이 있어야 하니까요."

**토킹포인트**
- 되돌리기 전 "되돌리면 뭐가 사라지는지" 먼저 물어보기(7강과 연결).
- 무조건 되돌리기가 정답은 아님 — 작게 고칠 수 있으면 고치고, 너무 꼬였으면 되돌리기.

**[자막]**
1) 에러 = 단서, 통째로 복사

**나레이션**

에러는 실패가 아니라 단서예요.
해석하지 말고 통째로 복사,

'왜 났어?'까지 물어요.

세 번 고쳐도 안 되면 멈추고,
마지막 정상 커밋으로 돌아가요.

이걸 몇 번 하다 보면
에러가 더는 안 무서워져요."

다음 편에선 이걸 진짜 주소로 만들어서
남한테 보내는 법, 배포를 해볼게요."

## 촬영 노트

- **데모 환경**: 실제 작은 웹앱 1개(피드백 폼 정도) — 일부러 에러 하나 심어두고 콘솔/수정/되돌리기를 실연. 한 프로젝트로 8·9강 연속 촬영하면 "이어지게"가 자연스러움.
- **B롤**: 빨간 콘솔 로그 클로즈업, F12 누르는 손, 커밋 히스토리 스크롤, 세 칸 분해 그래픽.
- **자막 키워드(원문 표기)**: `브라우저 콘솔` `WHAT / WHERE / WHEN` `3번 룰` `정상 커밋으로 되돌리기` `작업·기대·현상·로그·범위`.
- **TTS/발음**: 나레이션에서 WHAT/WHERE/WHEN은 "왓·웨어·웬", IDE는 "아이디이", Git/커밋은 "깃·커밋". 화면 자막은 원문 표기.
- **길이 조절**: 타이트하면 챕터3의 데모 프롬프트를 자막 카드로 대체. 여유 있으면 챕터2의 "에러 5요소"를 짧은 데모로 추가.
- **리스크**: 실연 중 진짜 에러가 안 나면 미리 녹화한 콘솔 화면으로 대체.
