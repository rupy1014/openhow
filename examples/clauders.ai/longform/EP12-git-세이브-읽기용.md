# [EP12] 읽기용 대본 — 망쳐도 괜찮아요: Git으로 되돌리기 (게임 세이브)

> 단계 4(만들기) 두 번째. 첫 화면(EP11)을 만든 사람이 "이거 망치면 어떡하지?" 걱정될 때 보는 안전망 영상. 카메라 보고 처음부터 끝까지 읽는 완성 대본. 약 10~12분.
> 톤: 친절·쉬움·완전 초보 배려. "몰라도 돼요, 천천히." 겁주기·하이프·과장·사기훅·날조 금지.
> 핵심 비유: commit = 게임 세이브 / 되돌리기 = 불러오기 / GitHub = 클라우드 세이브.
> docs 근거: build-service/06-git.
> `//` = 살짝 쉬는 지점. 그 외엔 자연스럽게 이어서.

---

## 1. 시작 — 만들고 나니까 무서워지죠?

지난 영상에서 우리, 첫 화면 만들어봤잖아요. //

"자기소개 페이지 만들어줘" 했더니, 진짜로 화면에 딱 떴죠. 그거 좀 신기했어요. //

그런데 그렇게 하나 만들고 나면, 묘하게 이런 마음이 들어요. //

"이거 이제 손대기 무서운데?" //

색깔 좀 바꿔보고 싶고, 글자도 고치고 싶은데. 괜히 건드렸다가 잘 되던 게 망가지면 어떡하나, 싶은 거죠. //

오늘은 바로 그 걱정을 없애주는 영상이에요. //

망쳐도 괜찮아요. 정말로요. 되돌릴 수 있는 안전장치가 있거든요. 오늘은 그걸 같이 깔아둘 거예요.

---

## 2. 게임 세이브, 다들 해보셨죠?

본론 들어가기 전에, 비유 하나만 먼저 깔고 갈게요. 이거 하나 잡으면 오늘 내용 절반은 끝나요. //

게임 해보신 적 있으세요? //

어려운 보스전 들어가기 직전에, 우리 꼭 세이브하잖아요. //

그리고 잘 싸워서 보스 깼어요. 그러면 또 세이브하죠. "여기까지 잘 왔다" 하고요. //

그러다 다음 구간에서 죽어버렸어요. 그래도 괜찮아요. 마지막 세이브를 불러오면, 보스 깬 그 시점으로 딱 돌아가니까요. //

오늘 배울 게 정확히 이거예요. //

잘 된 순간을 세이브해두고, 망가지면 그 세이브로 불러오기. //

이걸 컴퓨터에서 해주는 도구의 이름이, 바로 'Git'이에요.

---

## 3. Git이 뭐예요? (몰라도 돼요, 천천히)

자, 'Git'이라는 단어 나왔죠. //

이름이 좀 딱딱하죠? 발음도 "깃"이라고 해요. //

근데 이거, 뜻 몰라도 돼요. 천천히 갈게요. 우리가 외울 단어는 아니에요. //

Git은 한마디로, 내 작업이 어떻게 바뀌었는지 시점별로 기록해주는 도구예요. //

서비스 하나 만든다고 쳐볼게요. 이런 변화들이 순서대로 생기잖아요. //

첫 화면을 만들었다. 문의 폼을 추가했다. 저장 기능을 붙였다. 디자인을 고쳤다. //

Git은 이 순간들을 하나하나 세이브 지점으로 남겨둘 수 있어요. //

A 지점, 첫 화면 완성. B 지점, 문의 폼 완성. C 지점, 저장 기능 완성. 이런 식으로요. //

그러면 나중에 D 지점에서 뭔가 망가졌을 때, "C로 돌아가자" 할 수 있는 거예요. //

그래서 Git은 비개발자한테 어려운 도구가 아니라, 만들다가 넘어져도 다시 일어나게 해주는 안전장치예요. 이 느낌만 가져가시면 돼요.

---

## 4. commit이 바로 '세이브하기'예요

Git을 쓰다 보면 제일 자주 보는 단어가 하나 있어요. //

'commit'이에요. "커밋"이라고 읽어요. //

이것도 어렵게 생각하실 거 없어요. commit이 바로 그 '세이브하기' 버튼이에요. //

"지금 이 상태를 기록해둬. 나중에 필요하면 여기로 돌아올 수 있게." 딱 이 뜻이에요. //

그럼 어떻게 세이브하느냐. 우리는 명령어 칠 거 없어요. 그냥 AI한테 말로 하면 돼요. //

예를 들어 첫 화면이 잘 떴어요. 그러면 이렇게 말하는 거예요. //

"첫 화면이 정상적으로 뜨는 것까지 확인했어. 지금 상태를 commit 해줘. 메시지는 '첫 화면 완성'으로 해줘." //

이렇게요. //

여기서 '메시지'는, 게임으로 치면 세이브 슬롯에 붙이는 이름표예요. //

"첫 화면 완성", "문의 폼 추가", "모바일 화면 수정". 이 정도면 충분해요. 거창하게 안 써도 돼요. //

나중에 "아, 이 세이브가 뭐가 되던 시점이었지?" 하고 알아볼 수만 있으면 되거든요.

---

## 5. 언제 세이브해요? — 직접 확인하고, 잘 될 때만

그럼 commit은, 그러니까 세이브는 언제 하는 게 좋을까요? //

기준이 딱 하나예요. 단순해요. //

내가 브라우저에서 직접 확인했고, 그 기능이 잘 됐을 때. //

흐름으로 보면 이래요. 기능 만들기. 브라우저에서 내가 직접 확인. 잘 되면 commit. 그다음 기능으로 넘어가기. //

게임에서도 그렇잖아요. 절벽에서 떨어지는 중에 세이브하는 사람은 없죠. 발 딛고 안전하게 서 있을 때 세이브하잖아요. //

commit도 똑같아요. 잘 되는 걸 눈으로 확인한 지점에서 남기는 거예요. //

그래서 이런 상태에서는 세이브 안 하는 게 좋아요. //

에러가 아직 나고 있다. 화면이 깨져 있다. 버튼이 안 눌린다. 아니면, 내가 아직 확인을 안 해봤다. //

특히 마지막이 중요해요. AI가 "아마 잘 될 거예요"라고만 말한 상태요. //

그건 아직 확인이 아니에요. 한 번 직접 눌러보고, 진짜 되는 걸 본 다음에 세이브하는 거예요. //

왜 이렇게까지 하냐면요. 망가졌을 때 돌아갈 세이브가, 알고 보니 거기도 망가져 있으면. 그건 세이브를 안 한 거나 마찬가지거든요. //

그래서 commit 전에는 꼭 한 번, 내 손으로 눌러봐요.

---

## 6. 망가지면 불러오면 돼요 (되돌리기)

자, 이제 제일 마음 편해지는 부분이에요. //

만들다 보면 망가질 수 있어요. 이건 누구나 그래요. //

디자인만 고치려고 했는데 제출 버튼이 안 눌린다. 저장 기능 붙였더니 첫 화면이 안 뜬다. //

이럴 때 세이브, 그러니까 commit이 있으면, AI한테 이렇게 말하면 돼요. //

"마지막으로 정상 동작하던 commit을 찾아줘. 지금이랑 비교해서 뭐가 망가졌는지 설명해줘. 필요하면 그 시점으로 되돌려줘." //

게임으로 치면 마지막 세이브 불러오기예요. 보스 깼던 그 시점으로 다시 돌아가는 거죠. //

그런데 여기서, 오늘 제일 중요한 친절 팁 하나 알려드릴게요. //

되돌리기 전에, 먼저 물어보세요. //

"되돌리면 지금까지 작업한 것 중에 뭐가 사라지는지 먼저 알려줘. 안전하게 되돌리는 방법으로 설명해줘." //

이걸 왜 먼저 물어보냐면요. 되돌린다는 건, 세이브 이후에 한 작업은 사라질 수도 있다는 뜻이거든요. //

게임에서 세이브 불러오면, 그 뒤에 한 건 없던 일이 되잖아요. 그거랑 같아요. //

그러니까 무조건 되돌리기부터 누르지 말고, "뭐가 사라져?" 하고 한 번 확인하는 거예요. //

확인해보고, 작게 고칠 수 있으면 그냥 고치면 돼요. 너무 꼬였다 싶으면 그때 되돌리면 되고요. //

여기서 진짜 핵심은 이거예요. 세이브가 있으니까 '선택지'가 생긴다는 거. 망해도 돌아갈 곳이 있다는 거요.

## 7. commit이랑 push, 뭐가 달라요?

이제 단어 하나만 더 풀고 갈게요. 'push'예요. "푸시"라고 읽어요. //

이거 헷갈리기 쉬운데, 게임 세이브로 비유하면 한 번에 정리돼요. //

commit은, 내 컴퓨터 안에 세이브하는 거예요. //

push는, 그 세이브를 인터넷에 한 번 더 올려두는 거예요. 클라우드 세이브처럼요. //

그 클라우드 저장 공간 이름이 'GitHub'예요. "깃허브"라고 읽어요. //

정리하면 이래요. commit은 내 컴퓨터에 기록. push는 그걸 GitHub에 올리기. //

그럼 왜 굳이 인터넷에 또 올리냐고요? //

생각해보면, 세이브가 내 컴퓨터 안에만 있으면 좀 불안하잖아요. //

컴퓨터가 고장 날 수도 있고, 폴더를 실수로 지울 수도 있고요. 다른 컴퓨터에서 이어서 하고 싶을 수도 있죠. //

GitHub에 올려두면 그게 다 해결돼요. 백업이 되고, 집 컴퓨터에서도 회사 컴퓨터에서도 이어서 작업할 수 있어요. //

나중에 배포할 때도, 그러니까 내가 만든 걸 진짜 인터넷 주소로 내보낼 때도 이 GitHub랑 연결해서 쓰거든요. 그 얘긴 다음다음 영상에서 할게요. //

그래서 보통 흐름은 이래요. 브라우저에서 잘 되는 거 확인. commit으로 세이브. 그리고 push로 GitHub에 백업. //

말로 시킬 땐 이렇게 한 번에 해도 돼요. //

"지금 기능 잘 되는 거 확인했어. commit하고 push까지 해줘. 메시지는 '문의 저장 추가'로." //

이렇게 해두면, 컴퓨터가 바뀌어도 마음이 편해요.

---

## 8. 명령어, 안 외워도 돼요

여기까지 들으면서 혹시 "이걸 다 외워야 하나" 싶으셨다면, 안심하셔도 돼요. //

하나도 안 외워도 돼요. 진짜로요. //

우리가 할 일은 명령어를 치는 게 아니라, AI한테 상황을 말로 설명하는 거예요. //

자주 쓰는 말, 딱 네 마디만 기억하셔도 돼요. //

하나. "지금 뭐가 바뀌었는지 변경사항 확인해줘." //

둘. "브라우저에서 확인했어. commit 해줘. 메시지는 '○○ 완성'으로." //

셋. "commit하고 GitHub에 push해줘." //

넷. "되돌리고 싶은데, 되돌리면 뭐가 사라지는지 먼저 알려줘." //

이 네 마디면 초보 단계에선 충분해요. //

가끔 'revert'나 'reset' 같은 어려운 단어가 화면에 보일 수도 있어요. //

근데 그것도 몰라도 돼요. "되돌리는 방법이 여러 가지 있구나" 정도만 아셔도 돼요. //

실제로 되돌리기 전에는, 아까 말한 것처럼 AI한테 "뭐가 사라져?" 하고 먼저 물어보면 되니까요.

---

## 9. 마무리 + 다음 영상

자, 오늘 거 정리할게요. //

Git은 게임 세이브 같은 거예요. 잘 된 순간을 기록해두는 안전장치요. //

commit은 세이브하기. 되돌리기는 불러오기. //

세이브는 내가 직접 확인하고 잘 될 때만. 절벽에서 떨어지는 중엔 세이브 안 해요. //

망가지면 되돌리면 되는데, 그 전에 꼭 "뭐가 사라져?" 하고 먼저 물어보기. //

그리고 commit은 내 컴퓨터 세이브, push는 GitHub에 올리는 클라우드 백업. //

이제 첫 화면 만들고 나서 "손대기 무섭다" 했던 그 마음, 좀 가벼워지셨으면 좋겠어요. 세이브해두고, 마음껏 건드려보세요. //

그런데 이렇게 만들다 보면, 빨간 글씨로 에러라는 게 뜰 때가 있어요. 처음 보면 좀 철렁하죠. //

다음 영상 제목이 그래서 이거예요. "에러 떴다고 망한 거 아니에요." //

에러가 떠도 괜찮아요. 그게 무슨 뜻인지, AI한테 어떻게 보여주고 같이 고치는지, 다음 영상에서 천천히 같이 해볼게요. //

세이브 하나 깔아둔 것만으로 마음이 한결 든든해졌을 거예요. 다음 영상에선 그 빨간 에러도 단서로 바꾸는 법으로 이어갈게요. 거기서 봬요.
