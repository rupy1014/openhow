# [EP8] 읽기용 대본 — 명령어 한 줄로 블로그 글이 완성됩니다 (/write 전 과정 공개)

> "AI 입문 정주행" 단계 3(자동화)의 매직 모먼트 편. `/write` 한 줄로 글 한 편이 나오는 전 과정을 손잡고 보여주는 완성 대본. 약 15~20분.
> 톤: 친절·쉬움·완전 초보 배려. "몰라도 돼요, 천천히." 겁주기·하이프·과장 금지. 비유로 풀어주기.
> docs 근거: automation/02-delegate-blog (series-plan / tone-and-manner / writer·style-editor·proofreader 등 실제 구조 그대로).
> 연속성: EP7(자동화 4장치) 받아서 시작 → EP9(자동화 패턴 + 내 일 적용) 예고로 마무리.
> `//` = 살짝 쉬는 지점. 그 외엔 자연스럽게 이어서.

---

## 1. 지난 시간 받기 — 자동화 4장치, 기억나세요?

지난 영상에서 우리, 자동화 4장치를 봤어요. //

다시 한 번만 짚을게요. 외우려고 하지 말고, 그냥 그림처럼 떠올려 보세요. //

커맨드는 단축키. 에이전트는 담당자. 스킬은 알아서 꺼내 쓰는 능력. 훅은 자동. //

이 네 개를 "각각 뭔지" 본 게 지난 시간이었어요. //

근데 솔직히, 설명만 들으면 좀 붕 떠 있죠. "그래서 이걸 합치면 뭐가 되는데?" 싶고요. //

그래서 오늘은, 그중에 딱 두 개를 골라서 실제로 엮어볼 거예요. 커맨드, 그러니까 단축키 하나랑. 에이전트, 그러니까 담당자 몇 명을요. //

그리고 그 둘을 엮으면 어떤 일이 벌어지는지, 처음부터 끝까지 손잡고 같이 해볼게요.

## 2. 오늘은 이 한 줄을 보여드릴게요

먼저 결론부터 보여드릴게요. //

오늘 우리가 만들 건, 이거예요. 검은 창에 이렇게 한 줄을 칩니다. //

`/write 1화` //

이게 다예요. 띄어쓰기 포함해서 글자 몇 개. //

그리고 한 2~3분 정도 기다려요. 화면에서는 뭐가 막 지나가요. "누가 회차를 확인하고", "누가 초안을 쓰고", "누가 다듬고" 하면서요. //

그러다 보면, 폴더 안에 글 한 편이 딱 생겨 있어요. 제목 붙고, 문단 나뉘고, 마무리까지 된 초안이요. //

이게 오늘의 '매직 모먼트'예요. 명령어 한 줄로 블로그 글 한 편이 나오는 순간. //

근데 저는 마술을 보여주려는 게 아니에요. 오히려 반대예요. 이 한 줄 안에서 무슨 일이 벌어지는지, 뚜껑을 다 열어서 보여드릴 거예요. //

다 보고 나면 "아, 마법이 아니라 그냥 순서를 박아둔 거구나" 하고 김이 살짝 빠질 수도 있어요. 그게 제 목표예요. 김이 빠져야 내 일에도 써먹을 수 있거든요. //

오늘 좀 길어요. 15분쯤 걸려요. 대신 한 번 보고 나면 이 구조가 머리에 통째로 들어와요. 천천히 갈게요.

## 3. 먼저, '워크플로우'가 뭔지부터

`/write` 만들기에 들어가기 전에, 단어 하나만 풀고 갈게요. 워크플로우. //

영어라서 어렵게 들리는데, 뜻은 단순해요. //

워크플로우는, 어떤 결과물 하나가 나오기까지의 과정을 순서대로 묶어둔 거예요. //

예를 들어 볼게요. 블로그 글 한 편이 나오려면 보통 이런 순서를 거치잖아요. 오늘 뭐 쓸지 소재를 정하고. 누구한테 하는 말인지 독자를 떠올리고. 어떻게 풀어갈지 흐름을 잡고. 초안을 쓰고. 말투를 다듬고. 마지막으로 검수하고. //

이 "정하고 → 떠올리고 → 잡고 → 쓰고 → 다듬고 → 검수하고"를 한 줄에 꿰어둔 게 워크플로우예요. //

그리고 자동화는, 이 순서를 명령어 한 줄로 실행되게 만드는 거예요. 매번 손으로 하던 순서를, 미리 박아두는 거죠. //

여기서 한 가지만 안심시켜 드릴게요. 오늘 예시는 블로그 글이에요. 근데 블로그가 특별해서 고른 게 아니에요. //

연재 글은 회차마다 구조가 비슷하고, 말투가 흔들리기 쉽고, 앞 회차 맥락이 계속 쌓여요. 그래서 자동화 감각을 연습하기에 딱 좋은 예시인 거예요. //

이걸 회사 일로 바꾸면 그대로 똑같아요. 주간 리포트, 제안서, 회의록, 고객 메일, 유튜브 대본. 반복해서 나오는 결과물이면 다 같은 방식으로 만들 수 있어요. //

그러니까 오늘 핵심 문장은 이거 하나예요. **반복되는 결과물이 있으면, 그게 나오는 과정을 문서랑 담당자 흐름으로 쪼갠다.** //

이 말이 지금 당장 와닿지 않아도 괜찮아요. 끝까지 보고 나면 저절로 이해돼요.

## 4. 부담되면, 복붙으로 한 번에 깔 수도 있어요

본격적으로 만들기 전에, 마음 편한 길 하나를 먼저 알려드릴게요. //

지금부터 우리는 폴더 만들고, 문서 적고, 담당자 파일 만들고… 하나씩 손으로 만들 거예요. //

근데 "처음부터 그걸 다 어떻게 만들어" 싶으면요. 복붙 세팅 파일이라는 게 있어요. //

이 세팅 파일 안에는, 오늘 우리가 만들 게 전부 들어 있어요. 프로젝트 맥락 파일이랑, 말투 기준 문서랑, 검수 체크리스트랑, `/write` 명령어랑, 담당자 다섯 명 파일까지요. //

이걸 통째로 복사해서 Claude한테 붙여넣으면, Claude가 폴더랑 파일을 알아서 다 만들어줘요. //

그러니까 오늘 영상은 두 가지로 쓸 수 있어요. //

하나. "난 일단 돌아가는 걸 먼저 보고 싶어" 하면, 복붙으로 깔고 곧장 실행해 보세요. //

둘. "근데 이게 왜 이렇게 생겼는지 알고 싶어" 하면, 지금부터 제가 푸는 설명을 같이 들으세요. //

복붙만 해도 돌아가긴 해요. 근데 결과물이 내 글처럼 나오느냐는, 결국 그 안의 기준 문서를 내가 얼마나 잘 다듬느냐에서 갈려요. 그래서 저는 두 번째 길, 그러니까 "왜 이렇게 생겼나"를 같이 보는 걸 추천해요. //

자, 그럼 직접 만들어 볼게요.

## 5. Step 1 — 작업실(폴더)부터 차려요

제일 먼저 할 일은, 작업실을 차리는 거예요. //

지난 단계에서 봤죠. 프로젝트는 AI가 일하는 작업실이고, 그 작업실은 그냥 폴더 하나예요. //

오늘은 `my-blog`라는 이름으로 폴더를 만들게요. 이름은 마음대로 바꿔도 돼요. //

이 폴더 안이 어떻게 생겼는지, 화면 보면서 천천히 설명할게요. 지금 다 외우라는 거 절대 아니에요. "아, 칸이 이렇게 나뉘는구나" 정도만 보세요. //

```text
my-blog/
├── CLAUDE.md          ← 이 프로젝트가 뭔지 (작업실 안내문)
├── series-plan.md     ← 전체 연재 목차와 회차별 의도
├── docs/              ← 기준 문서들이 모이는 곳
│   ├── tone-and-manner.md   ← 말투, 문체 기준
│   ├── article-structure.md ← 글 구조 기준
│   └── checklist.md         ← 검수 항목과 통과 점수
├── references/        ← 참고 자료
│   ├── raw/                 ← 원본 PDF, PPT
│   └── processed/           ← 읽기 쉽게 바꾼 자료
├── drafts/            ← 작업 중인 초안이 쌓이는 곳
├── posts/             ← 검수 통과한 최종본이 가는 곳
├── reviews/           ← 검수 기록이 남는 곳
└── .claude/           ← AI한테 주는 설정이 모이는 곳
    ├── commands/
    │   └── write.md        ← /write 명령어의 실행 흐름
    └── agents/             ← 담당자들이 사는 곳
        ├── series-manager.md
        ├── story-planner.md
        ├── writer.md
        ├── style-editor.md
        └── proofreader.md
```

복잡해 보이죠? 근데 칸마다 하는 일은 단순해요. //

위쪽은 '기준'이에요. 이 프로젝트가 뭔지, 말투는 어떤지, 글 구조는 어떤지, 검수는 어떻게 하는지. //

아래쪽 `drafts`, `posts`, `reviews`는 '결과가 쌓이는 곳'이에요. 작업 중인 글은 `drafts`에, 통과한 최종본은 `posts`에, 검수 기록은 `reviews`에 들어가요. //

그리고 맨 아래 `.claude` 폴더. 여기가 오늘의 핵심이에요. 명령어 `/write`도 여기 살고, 담당자들도 여기 살아요. //

지금은 "기준 / 결과 / 설정, 이렇게 세 덩어리구나"만 기억하면 충분해요.

## 6. Step 2 — AI한테 줄 '기준 문서'를 적어요

작업실을 차렸으면, 이제 안에 기준 문서를 채워요. //

제일 먼저 `CLAUDE.md`. 이건 이 프로젝트의 첫 장이에요. AI가 일을 시작할 때 제일 먼저 읽는 안내문이라고 보면 돼요. //

여기엔 거창한 거 안 적어요. 이 프로젝트가 뭔지, 독자가 누군지, 결과물은 어때야 하는지. 딱 이 세 가지예요. //

예를 들면 이렇게요. "이 블로그는 카페 창업 준비 과정을 기록하는 블로그다. 독자는 카페 창업을 고민하지만 아직 실행 전인 직장인. 결과물은 경험담처럼 읽혀야 하고, 강의체로 쓰지 않고, 현실 비용을 숨기지 않는다." //

이런 게 적혀 있어야, `/write`가 매번 같은 방향에서 출발해요. 이 파일이 없으면 매번 다른 글이 나와요. //

그다음은 말투 기준이에요. `docs/tone-and-manner.md`에 적어요. //

여기엔 "친한 선배가 옆에서 말하듯 쓴다" 같은 기본 톤이랑, 자주 쓰는 표현이랑, 피할 표현을 적어요. 피할 표현엔 "무조건 성공한다", "누구나 쉽게 월 천만 원" 같은 과장된 말들을 넣어두는 거죠. //

글 구조 기준은 `docs/article-structure.md`에 따로 둘 수 있어요. 서두는 어떻게, 본문은 어떻게, 마무리는 어떻게. //

마지막으로 `docs/checklist.md`. 이게 좀 중요해요. //

여기엔 검수 항목을 적는데, 한 줄을 꼭 넣어요. 통과 점수 기준이에요. 예를 들면 "체크리스트 80점 이상이면 통과, 미만이면 다시 보낸다." //

이 한 줄이 왜 중요하냐면요. 이게 있어야 나중에 검수 담당자가 점수로 합격·불합격을 판정할 수 있거든요. 이건 뒤에서 다시 나와요. 일단 "80점" 이 숫자만 기억해 두세요. //

여기까지 정리하면요. 문서를 나눠 둔 이유는 간단해요. 글쓰기라는 게 한 덩어리가 아니라, 소재 고르고, 독자 잡고, 초안 쓰고, 다듬고, 검수하는 여러 단계잖아요. 그래서 단계마다 필요한 기준을 따로 적어둔 거예요.

## 7. (잠깐) 원본 자료는 .md로 바꿔두면 편해요

이 부분은 살짝 곁가지라, 짧게만 짚고 갈게요. 어려우면 흘려들어도 돼요. //

회사에서 쓰던 자료가 있죠. 예전에 쓴 글, 브랜드 소개 PPT, 가이드 PDF 같은 거요. //

그런 건 `references/raw` 폴더에 그냥 넣어두면 돼요. 원본 보관용이에요. //

근데 AI가 실제로 참고할 기준은, 마크다운이라는 형식으로 뽑아두는 게 편해요. 마크다운은 그냥 글씨 위주의 가벼운 텍스트 문서라고 보면 돼요. 확장자가 `.md`로 끝나는 거요. //

왜 굳이 바꾸냐면, PDF 같은 건 AI가 읽을 수는 있는데 좀 무겁고, 매번 필요한 부분만 꺼내 쓰기가 번거로워요. //

방법은 간단해요. AI한테 이렇게 시키면 돼요. "이 PDF 내용을, 내가 글쓰기 기준으로 참고할 수 있게 마크다운으로 정리해줘. 목차랑, 자주 쓰는 표현이랑, 글 구조랑, 피할 표현을 나눠서 정리해줘." //

그러면 깔끔한 `.md` 문서가 `references/processed` 폴더에 생겨요. //

딱 하나만 당부할게요. 나온 문서는 꼭 한 번 읽어보세요. 내 의도랑 다르면 그 문서를 고치고요. 자동화는 이 문서를 기준으로 움직이니까, 기준이 어긋나면 결과도 어긋나거든요.

## 8. Step 3 — /write 한 줄을 만들어요

자, 이제 오늘의 주인공. `/write` 명령어를 만들 차례예요. //

`/write` 같은 명령어는 `.claude/commands` 폴더 안에 `write.md`라는 파일로 만들어요. //

이 파일에 뭘 적느냐면요. "`/write`를 쳤을 때, 무슨 일이 어떤 순서로 일어날지"를 적어요. 그게 다예요. //

쉽게 비유하면, 식당 주방에 붙여둔 조리 순서표 같은 거예요. "1번, 재료 확인. 2번, 밑간. 3번, 조리…" 이런 거요. 이 순서표를 한 번 잘 만들어두면, 다음부턴 "그거 해줘" 한마디면 끝나는 거죠. //

`write.md` 안에는 크게 두 가지를 적어요. //

하나는, 시작할 때 읽을 문서들. 아까 만든 `CLAUDE.md`, `series-plan.md`, 말투 문서, 구조 문서, 체크리스트, 그리고 관련 샘플들이요. //

다른 하나는, 실행 흐름이에요. 진짜 순서표죠. 이게 오늘의 심장이라, 천천히 읽어드릴게요. //

하나. `series-manager`가 `series-plan.md`를 보고, 이번 회차가 전체 연재에서 어디쯤인지 위치를 확인해요. //

둘. `story-planner`가 독자 관점이랑 전개 방식을 정리해요. //

셋. `writer`가 말투랑 구조 문서를 참고해서 초안을 써요. //

넷. `style-editor`가 말투 기준에 맞게 초안을 다듬어요. //

다섯. `proofreader`가 체크리스트 기준으로 검수해요. //

여섯. 80점 이상이면, `posts` 폴더에 최종본으로 저장해요. //

일곱. 80점 미만이면, 다시 다듬는 단계로 돌려보내요. 최대 세 번까지요. //

이게 `write.md`에 적히는 흐름이에요. 이제 `/write 1화`라고 치면, 방금 이 일곱 단계가 한 번에 쭉 이어서 돌아가요. //

여기서 `series-manager`, `story-planner`, `writer` 같은 이름들이 막 나왔죠. 이게 '담당자'예요. 다음 칸에서 이게 뭔지 제대로 풀어드릴게요.

## 9. 담당자(에이전트)는 왜 나눠요?

여기가 오늘 영상에서 제일 궁금하실 부분일 거예요. "글 하나 쓰는데 왜 담당자를 다섯 명이나 만들어?" //

이유가 하나 있어요. AI의 기억 용량 때문이에요. //

조금 풀어볼게요. 나랑 직접 대화하고 있는 Claude를, '마스터 에이전트'라고 부를게요. 한 명의 메인 담당자라고 보면 돼요. //

이 마스터 에이전트는 진짜 바빠요. 나랑 대화도 해야 하고, 프로젝트 문서도 읽어야 하고, 필요한 파일도 찾아야 하고, 결과도 보고해야 하고, 다음에 뭘 할지도 판단해야 해요. //

그래서 이 친구 머릿속은 이미 꽉 차 있다고 보면 돼요. 대화 내용도 있고, 프로젝트 맥락도 있고, 방금 내가 한 요청도 있고요. //

이 상태에서 초안 쓰기, 말투 다듬기, 검수까지 전부 이 한 명한테 시키면, 기준들이 서로 섞여요. 말투 보다가 검수 기준이 흐려지고, 검수하다가 초안 의도가 흐려지고요. //

그래서 중요한 작업은 따로 담당자한테 맡겨요. 이 따로 부르는 담당자를 '서브 에이전트'라고 해요. 마스터가 전체 흐름을 잡고, 서브 에이전트들을 한 명씩 불러서 자기 일만 시키는 거죠. //

핵심은 이거예요. 담당자를 나눌 때, 사람 이름부터 만들지 마세요. 먼저 문서를 봐요. //

우리한테 있는 기준 문서가 이렇잖아요. 연재 계획, 글 구조, 말투, 체크리스트. //

이걸 누가 맡을지를 정하는 게 담당자 나누기예요. //

`series-manager`는 연재 계획을 맡고. `story-planner`는 연재 계획이랑 글 구조를 맡고. `writer`는 프로젝트 맥락이랑 글 구조랑 관련 샘플을 맡고. `style-editor`는 말투 문서를 맡고. `proofreader`는 체크리스트를 맡아요. //

이렇게 해두면, `/write`가 돌 때 담당자마다 자기 기준 문서만 딱 들고 들어가요. //

검수 담당자가 모든 기획 대화를 다 알 필요는 없잖아요. 자기 체크리스트랑 방금 나온 초안만 보면 돼요. 그래야 더 안정적이고요. //

그리고 담당자 파일은 길 필요 없어요. "너는 무슨 담당자다", "어떤 문서를 맡는다", "무슨 일을 한다", "무슨 일은 안 한다." 이 정도면 충분해요. //

예를 들어 `writer` 담당자 파일엔 이렇게 적혀요. "너는 블로그 초안을 작성하는 담당자다. 맡는 문서는 프로젝트 맥락이랑 말투랑 구조 문서. 하는 일은 회차 의도를 바탕으로 초안 쓰기. 하지 않을 일은 전체 목차를 새로 바꾸거나, 최종 검수까지 혼자 하는 것." //

담당자를 많이, 멋있게 만드는 게 목적이 아니에요. 머릿속을 분리하고, 각 기준 문서를 실제 단계에 딱딱 배치하려고 나누는 거예요. //

참고로요. 이렇게 여러 담당자를 순서대로 엮은 걸, 워크플로우라고 했죠. 앞 단계 결과가 다음 단계로 넘어가니까 '파이프라인'이라고 부르기도 하고, 여럿을 조율한다고 해서 '오케스트레이션'이라고 부르기도 해요. 셋 다 같은 그림이에요. 단어 지금 외우지 마세요.

---

## 10. 자, 이제 진짜로 눌러볼게요 — /write 1화

여기까지 왔으면 다 차린 거예요. 이제 진짜로 눌러볼게요. //

검은 창에 칩니다. `/write 1화`. 엔터. //

자, 이제부터 화면을 같이 봐요. 뭐가 막 지나가죠? 이 한 줄이 방금 뭘 한 거냐면요. 하나씩 짚어드릴게요. //

지금 제일 먼저, 마스터 에이전트가 내 요청을 받았어요. "1화 글을 써달라는 거구나" 하고요. //

그다음, `series-manager`를 불러요. 화면에 이 담당자가 일하는 게 보이죠. 얘가 연재 계획을 펼쳐서 "1화는 전체에서 도입부에 해당하고, 이런 의도였지" 하고 위치를 확인해요. //

확인이 끝나면, `story-planner`로 넘어가요. 얘는 "이 글을 누구한테, 어떤 순서로 풀까"를 잡아요. 독자 관점이랑 전개 방식을 정리하는 거죠. //

전개가 잡히면, `writer`가 들어와요. 여기서 처음으로 진짜 글이 써져요. 말투 기준이랑 구조 기준을 들고, 초안을 쭉 작성해요. 이 초안은 `drafts` 폴더에 쌓여요. //

초안이 나오면 바로 끝이 아니에요. `style-editor`가 받아요. 얘는 말투 문서를 들고, 초안을 내 말투에 맞게 다듬어요. 강의체로 쓴 부분이 있으면 경험담처럼 고치고요. //

다듬기가 끝나면, 마지막으로 `proofreader`가 와요. 체크리스트를 펼쳐서 항목 하나하나 점검하고, 점수를 매겨요. //

그리고 80점을 넘으면, 통과예요. 이 글이 `posts` 폴더로 최종본이 돼서 저장돼요. 검수 기록은 `reviews` 폴더에 따로 남고요. //

자, 한 2~3분 지났어요. 화면 보세요. `drafts` 폴더 안에 1화 글이 딱 떠 있죠. 제목 붙고, 문단 나뉘고, 마무리까지 된 글 한 편이요. 통과했으면 `posts` 폴더에 최종본으로도 들어가 있고요. //

이게 다예요. `/write 1화` 한 줄. //

근데 이제 보이시죠? 이 한 줄 안에서, 사실은 담당자 다섯 명이 순서대로 일을 한 거예요. 회차 확인하고, 전개 잡고, 초안 쓰고, 다듬고, 검수하고. //

마법처럼 보였던 게, 알고 보니 잘 짜인 순서표였던 거예요. 이걸 한 번 만들어두면, 2화, 3화, 10화도 똑같이 `/write 2화`, `/write 3화` 한 줄이면 돼요.

## 11. 80점을 못 넘으면 어떻게 돼요?

좋은 질문이 하나 남았어요. "검수에서 80점을 못 넘으면?" //

사실 이 부분이, 담당자 워크플로우가 진짜 힘을 쓰는 지점이에요. //

`proofreader`가 검수하다가 이렇게 판단했다고 해볼게요. "점수 76점. 문제는 설명이 독자 수준에 비해 어렵고, 경험담처럼 안 읽히고, 마지막 행동 제안이 약하다. 수정 지시는, 문장을 더 짧게 나누고, 예시를 하나 추가하고, 마지막에 독자가 오늘 해볼 일을 넣어라." //

76점이면 80점에 못 미치죠. 그러면 어떻게 되냐면요. 끝내지 않아요. 다시 다듬는 단계로 돌려보내요. //

`writer`나 `style-editor`가 그 수정 지시를 받아서 한 번 더 고쳐요. 그리고 다시 `proofreader`한테 가서 또 검수받아요. //

이걸 통과할 때까지 도는데, 무한정 도는 건 아니에요. 최대 세 번까지로 정해뒀어요. //

여기서 자동화의 진짜 모습이 보여요. 자동화는 한 번에 완벽하게 써내는 게 아니에요. //

만들고, 읽어보고, 기준에 맞게 고치고. 이 과정을 흐름 안에 미리 넣어두는 거예요. 사람이 글 쓸 때 초안 쓰고 다시 고치는 거랑 똑같죠. 그걸 자동으로 돌게 해둔 것뿐이에요. //

그래서 아까 6번 칸에서 "80점이라는 숫자를 기억해 두세요" 했던 거예요. 그 한 줄이 있어야, 여기서 합격·불합격이랑 다시 돌리기가 작동하거든요.

## 12. 더 좋게 만드는 비결 — 문서를 고쳐요

자, 한 편 나왔어요. 근데 읽어보니 좀 아쉬워요. 어떻게 더 좋게 만들까요? //

여기서 초보분들이 제일 많이 하는 실수가 있어요. 결과가 맘에 안 들면, 프롬프트를 점점 더 길게 다시 쓰는 거예요. //

그렇게 하지 마세요. 프롬프트 말고, 문서를 고치세요. //

무슨 말이냐면요. 예를 들어 1화 초안을 읽었는데 너무 강의체였어요. 그러면 AI한테 이렇게 시키는 거예요. //

"1화 초안을 읽어보니 너무 강의체야. `docs/tone-and-manner.md`에 '강의체를 피하고 경험담처럼 쓴다'는 기준을 추가해줘. 그리고 `proofreader`가 이 기준도 검수하도록 `docs/checklist.md`도 고쳐줘." //

이렇게 기준 문서를 고쳐두면요. 다음에 `/write 2화`를 칠 때부터는, 그 기준이 자동으로 적용돼요. 매번 다시 설명 안 해도 되는 거죠. //

이게 자동화를 내 작업 방식에 점점 가깝게 만드는 방법이에요. 결과 보고, 문서 고치고, 다시 실행하고. 이걸 몇 번 반복하면, 어느새 내 손맛에 맞는 글이 나와요. //

그리고 마지막으로 하나만 더, 솔직하게 말씀드릴게요. //

오늘 우리가 본 건 '자동화의 기술'이에요. 단축키 만들고, 담당자 나누고, 순서표 묶는 방법이요. 이건 이 영상 따라 하면 누구나 할 수 있어요. //

근데 결과물의 완성도를 진짜로 가르는 건, 그 위에 올라타는 '내 일에 대한 이해'예요. //

예를 들어 마케팅을 잘 아는 분이 이걸 만들면요. 검색에 잘 잡히는 글 기준을 알고, 첫 문단에서 독자가 어디서 이탈하는지 알고, 자기 회사 브랜드 표현을 알아요. 그래서 그분의 자동화엔 검색용 담당자가 따로 있고, 브랜드 점검 담당자가 따로 있고, 기준 문서가 더 잘게 쪼개져 있어요. //

같은 `/write` 구조라도, 누가 만드느냐에 따라 결과 차이가 큰 이유예요. //

그러니까 너무 걱정 마세요. 자기 일을 제일 잘 아는 사람은, 다른 누구도 아닌 본인이거든요. 자동화는 그 지식을 문서랑 단계로 꺼내주는 도구일 뿐이에요. 본인이 그 일을 잘하는 만큼, 자동화도 잘 돌아가요.

## 13. 마무리 + 다음 영상

오늘 거 정리할게요. //

워크플로우는, 결과물 하나가 나오는 과정을 순서대로 묶어둔 거예요. //

우리는 그걸 위해 작업실(폴더)을 차리고, 기준 문서를 적고, `/write`라는 순서표를 만들고, 담당자 다섯 명을 문서별로 나눴어요. //

담당자를 나눈 이유는, AI 한 명한테 다 시키면 기준이 섞이니까, 각자 자기 문서만 들고 일하게 하려는 거였고요. //

그리고 `/write 1화` 한 줄을 치면, 회차 확인 → 전개 → 초안 → 다듬기 → 검수가 한 번에 돌고, 80점을 넘으면 글 한 편이 완성됐죠. 못 넘으면 다시 돌고요. //

오늘 우리가 한 건 딱 하나예요. `/write` 하나를 깊게 파본 거. //

근데 자동화가 이렇게 글 쓰는 데만 되는 건 당연히 아니겠죠. //

다음 영상에서는, "이런 것도 자동화돼요"를 보여드릴게요. 자동화에 자주 쓰이는 패턴 몇 가지를 쉽게 풀고요. 그다음, 제일 중요한 거. 그 패턴을 '내 일'에 어떻게 적용하는지요. //

거창한 거 말고, 본인이 매일 하는 귀찮은 일 딱 하나를 자동화해보는, 작은 숙제도 하나 드릴 거예요. //

오늘 `/write` 한 번 만들어봤으면, 그걸로 이미 절반은 온 거예요. 천천히 같이 가요. //

마법처럼 보이던 게 알고 보니 잘 짜인 순서표였다는 거, 이거 하나 챙기셨으면 오늘은 충분해요. 다음엔 이 구조를 내 일에 어떻게 옮기는지, 같이 해봐요.
