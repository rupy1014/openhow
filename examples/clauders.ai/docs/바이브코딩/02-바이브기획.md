**코드부터 짜면 안 돼. 기획부터야.**

"AI 캐릭터 채팅 만들어줘"라고 하면 뭐가 나올까?

AI가 알아서 기술을 골라. 화면 구조도 정해. 기능도 넣어.

근데 그게 네가 원한 거야? 아마 아닐 거야.

---

## 왜 기획 없이 시작하면 망해?

실제로 해보면 이래:

```
나: "AI 캐릭터 채팅 서비스 만들어줘"
```

AI가 뭘 하냐:

- Next.js + TypeScript + Prisma + PostgreSQL을 깔아
- 로그인 시스템을 만들어
- 관리자 페이지를 만들어
- 다크모드를 넣어
- 1,500줄짜리 코드가 나와

너는 그냥 캐릭터 5개랑 대화하고 싶었을 뿐인데.

**AI가 네 대신 기획을 해버린 거야.** 네 의도랑 전혀 다른 방향으로.

---

## 제1원칙: "코드는 짜지 마"

이 한 줄이 전부야:

```
코드는 아직 짜지 마. 먼저 계획을 보여줘.
```

이 말을 먼저 하면:

- AI가 복잡한 기술을 안 골라
- 화면 구조를 네가 정할 수 있어
- 한 번에 수백 줄이 안 쏟아져

Peter Yang(바이브코딩 12원칙 저자)이 이렇게 말했어:

> "이 한마디가 90%의 과잉 설계를 막아준다."

계획을 보고, 마음에 드는 부분만 "이거 실행해줘"라고 하면 돼.

---

## 거창한 기획도 함정이야

여기서 많이들 실수해.

"기획부터 하라니까" → 로그인, 결제, 관리자 페이지, 알림, 통계... 10페이지짜리 기획서를 써.

이것도 똑같이 망해. 왜?

**만들기 전에는 뭐가 중요한지 모르거든.**

머릿속에선 "결제 기능이 필수야"라고 생각했는데, 실제로 만들어보니 "캐릭터 성격 설정"이 훨씬 중요할 수 있어.

안 만들어보면 몰라. 진짜야.

---

## 린 스타트업이 뭐야?

에릭 리스(Eric Ries)가 만든 개념이야. 핵심은 간단해:

> "가장 작은 걸 먼저 만들고, 써보고, 고쳐."

이걸 **만들기 → 써보기 → 고치기** 루프라고 해.

스타트업도 이렇게 해. 처음부터 완벽한 서비스 안 만들어. 핵심 하나만 빠르게 만들어서 사람들한테 보여주고, 반응 보고 방향을 잡아.

바이브코딩이랑 완벽하게 맞아. AI한테 시키면 30분이면 뭔가 돌아가거든. 10페이지 기획서 쓰는 동안 바이브코딩으로는 이미 3번 만들고 고칠 수 있어.

---

## MVP로 시작하고, MLP로 키워

바이브코딩의 여정은 두 단계야.

**MVP** — Minimum **Viable** Product. 핵심 기능 딱 하나가 돌아가는 최소 버전. **3일이면 돼.**

**MLP** — Minimum **Lovable** Product. MVP를 다듬고 피드백 반복해서, 사람들이 **진짜 좋아하는** 제품으로 만든 것. **3개월이 걸려.**

| | MVP (3일) | MLP (3개월) |
|---|---|---|
| **풀네임** | Minimum Viable Product | Minimum Lovable Product |
| **기준** | "돌아가?" | "써보고 좋아?" |
| **하는 일** | 아이디어 → 기획 → 빌드 → 배포 | 피드백 → 다듬기 → 유통 → 검증 → 반복 |
| **병목** | 코딩 (AI가 해줌) | 시장 (사람이 찾아야 함) |
| **성공 기준** | "돌아가네" | "다른 사람한테 보여주고 싶어" |

옛날엔 MVP 만드는 데 개발자 3명이 3개월 걸렸어. 만드는 게 비쌌으니까 "최소한만 만들어서 검증하자"가 전부였어.

**지금은 달라.** 바이브코딩으로 3일이면 MVP가 나와. 너만 그런 게 아니야. Y Combinator 2025년 겨울 배치의 25%가 코드의 95%를 AI로 짰어.

만드는 건 쉬워졌어. 그러면 뭐가 어려워졌냐?

**사람들한테 쓰게 만드는 거야.** "돌아가기만 하는" 앱은 이제 넘쳐. 그냥 돌아가는 건 아무도 안 써. 써보고 **"오, 이거 좋은데?"**가 나와야 써.

Brian de Haaff(Aha! CEO)가 처음 제안한 MLP 개념이야. Webflow SVP Jiaona Zhang은 이렇게 말했어:

> "탄 피자를 내놓고 사람들이 피자를 좋아하는지 테스트할 수는 없어."

대충 만든 걸로는 아이디어가 좋은지 나쁜지도 판단할 수 없다는 거야.

그래서 이 시리즈의 구조가 이래:

```
MVP 만들기 (3일)          → MLP로 키우기 (3개월)
기획 → 빌드 → 배포          피드백 → 다듬기 → 유통 → 첫 매출
이 시리즈 전반부              이 시리즈 후반부
```

지금은 MVP부터 만들어. MLP로 키우는 건 [PMF 찾기](./08-1-PMF찾기)에서 다룰 거야.

---

## "안 만들 것"이 기획의 절반이야

MLP는 "작게, 근데 좋게"야. 좋게 만들려면 **빼야 해.**

AI한테 "쇼핑몰 만들어줘"라고 하면 회원가입, CMS, 장바구니, 결제, 리뷰, 포인트, 관리자 대시보드, 다크모드를 다 넣어. 너는 상품 3개 보여주는 페이지가 필요했을 뿐인데.

**시키지 않으면 AI는 항상 과잉 설계해.** "하지 마"를 안 말하면 = "해도 돼"로 받아들여.

| AI가 넣는 것 | 너한테 필요해? | 결과 |
|-------------|-------------|------|
| 로그인/회원가입 | MVP에선 거의 불필요 | 복잡도 3배 |
| 다크모드 | 있으면 좋지만 지금은 아냐 | CSS 코드 2배 |
| 관리자 페이지 | 너 혼자 쓰는 서비스인데? | 화면 2배 |
| 다국어 지원 (i18n) | 한국어만 하면 되는데 | 코드 복잡도 ↑ |
| 반응형 전체 지원 | 데스크톱에서만 쓸 건데 | CSS 3배 |

PRD를 받으면 각 기능마다 물어봐: **"이 기능이 없으면 서비스가 안 돌아가?"**

"없어도 돌아가" → 안 만들 것 목록에 넣어.

```
안 만들 것:
- 로그인/회원가입 (인증 없이 바로 사용)
- 대화 기록 저장 (새로고침하면 초기화)
- 관리자 페이지 (캐릭터는 코드에 하드코딩)
- 다크모드
- 모바일 최적화 (데스크톱 우선)
```

괄호 안에 **왜 안 만드는지** 이유를 쓰면 AI가 더 잘 이해해.

빼는 이유는 하나야: **남긴 것에 집중해서 "써보고 좋게" 만들려고.**

로그인을 안 만들면 → 그 시간에 대화 경험을 다듬을 수 있어.
다크모드를 안 만들면 → 그 시간에 첫 화면 인상을 좋게 만들 수 있어.

---

## 기획 = MVP PRD 한 장

그래서 기획이라고 거창한 게 아니야.

**PRD**(Product Requirements Document) = "내가 뭘 만들고 싶은지 정리한 문서".

A4 한 장이면 돼. 10장짜리 기획서가 아니야.

이걸 AI한테 먼저 만들어달라고 해.

```
나 AI 캐릭터 채팅 서비스 만들고 싶어.
MVP 기준으로 PRD.md 정리해줘. 코드는 아직 짜지 마.
핵심 기능 하나만 먼저 돌아가게 해줘.
```

포인트는 **"MVP 기준으로"**야. 이 말 하나가 AI의 과잉 기획을 막아줘. MLP로 다듬는 건 배포하고 피드백 받은 뒤에 해.

AI가 코드 대신 문서를 내놓아.

그 문서를 읽고, 마음에 안 드는 건 바꾸라고 하면 돼.

**코드는 PRD가 확정된 다음에.**

---

## 같은 프로젝트, 세 가지 결과

| | 기획 없이 | 거창한 기획 | MVP 기획 |
|---|---|---|---|
| 첫 프롬프트 | "채팅 서비스 만들어줘" | "전체 기능 기획서 만들어줘" | "MVP PRD 만들어줘" |
| AI가 하는 일 | 기술 선택 + 코드 생성 | 10페이지 문서 작성 | 핵심 1개 정리 |
| 결과물 | 1,500줄 코드 | 안 만들어지는 기획서 | 바로 만들 수 있는 1장 |
| 첫 동작까지 | 모름 | 한참 | 30분 |
| 수정 비용 | 처음부터 다시 | 기획서부터 다시 | 고치면서 진행 |

**작게 만들고, 써보고, 고치는 게 이겨.**

---

## 한 줄 정리

"코드는 짜지 마"를 먼저 말하고, MVP 한 장으로 시작해. 3일 안에 만들고, 3개월에 걸쳐 MLP로 키워.
