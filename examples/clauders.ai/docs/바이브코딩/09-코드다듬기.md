**AI가 짠 코드, 작동한다고 끝이 아니야.**

AI가 만든 코드의 약 45%에 문제가 있다는 조사가 있어.

근데 코드를 직접 읽으라는 게 아니야. **AI한테 검토를 시키고, AI한테 정리를 시키는 거야.**

---

## 왜 다듬어야 해?

Simon Willison(AI 분야 유명 개발자)의 원칙이 있어:

> "내가 다른 사람한테 이 코드가 뭘 하는지 설명 못 하면, 커밋하지 않는다."

코드를 한 줄씩 이해할 필요는 없어. 근데 **"이 파일이 뭘 하는지"는 알아야 해.**

AI가 짠 코드는 잘하는 신입이 짠 코드야. 기능은 돌아가. 근데 구조가 엉키고, 같은 코드가 여기저기 흩어지고, 안 쓰는 파일이 남아있어.

이걸 안 다듬으면? 3번째 기능 추가할 때 "어디를 고쳐야 하는지 모르겠어"가 와.

---

## 1단계: 리뷰 — 뭐가 문제인지 찾기

기능을 다 만들었으면, 배포 전에 이 한마디를 해봐.

```text:Claude 프롬프트
이 프로젝트 전체 코드를 리뷰해줘.
문제가 있는 부분, 개선할 부분을 알려줘.
```

Claude가 이런 식으로 알려줘:

```
- src/api/chat.js: API 키가 클라이언트에 노출됨
- src/components/Card.jsx: 같은 스타일 코드가 3곳에 반복됨
- src/utils/format.js: 사용하지 않는 함수 2개
- src/components/ChatPage.jsx: 파일이 400줄로 너무 길어
```

전부 고칠 필요 없어. **위험한 것만 먼저 고쳐.** API 키 노출은 바로 고치고, 나머지는 다음에 해도 돼.

---

## 2단계: 리팩토링 — 구조 정리하기

리뷰에서 "파일이 너무 길다", "코드가 반복된다"가 나왔으면 정리할 차례야.

리팩토링은 **기능은 안 바꾸고, 구조만 정리하는 거야.** 서랍 정리랑 같아. 물건은 그대로인데 찾기 쉬워져.

**긴 파일 쪼개기**

```text:Claude 프롬프트
src/components/ChatPage.jsx가 너무 길어.
UI 부분과 API 호출 부분을 분리해줘.
기존 기능은 그대로 유지해.
```

**반복 코드 합치기**

```text:Claude 프롬프트
이 프로젝트에서 비슷한 코드가 반복되는 곳을 찾아줘.
공통 함수로 합칠 수 있으면 합쳐줘.
```

**안 쓰는 코드 정리**

```text:Claude 프롬프트
사용하지 않는 파일, 함수, 변수를 찾아서 삭제해줘.
```

핵심은 **"기존 기능은 그대로 유지해"**야. 이걸 안 넣으면 AI가 기능까지 바꿔버릴 수 있어.

---

## 주의할 점

**한 번에 하나씩 해.** 여러 개를 동시에 바꾸면 뭐가 망가뜨린 건지 모르겠어.

```
❌ "파일 구조 전체를 리팩토링해줘"
✅ "ChatPage.jsx만 정리해줘. 다른 파일은 건드리지 마."
```

정리할 때마다 저장(git commit)해. 망가지면 되돌릴 수 있어.

정리한 다음에는 브라우저에서 같은 동작을 해봐. 달라진 게 있으면 되돌려.

## 언제 해?

| 타이밍 | 뭘 해 |
|--------|------|
| 기능 하나 끝났을 때 | 간단히 리뷰 |
| 배포 전에 | 리뷰 + 위험한 것 수정 |
| 피드백 반영 후에 | 리뷰 + 리팩토링 |

처음부터 할 필요 없어. **작동하는 게 먼저야.** 코드가 엉켜서 "고치려니까 어디가 뭔지 모르겠어"가 오면 그때 해.

## MVP 배포 vs 라이브 출시

Vercel 무료 URL로 배포한 거랑, 실제 서비스를 운영하는 건 달라.

| | MVP 배포 | 라이브 출시 |
|---|---|---|
| **URL** | `xxx.vercel.app` | `myservice.com` |
| **사용자** | 테스트 5명 | 실사용자 |
| **에러 대응** | 직접 확인 | 알림이 와야 해 |
| **목적** | "이거 되나?" 검증 | "이걸로 사업 하겠다" |

MVP로 검증이 끝나고 MLP로 다듬었으면, 이제 진짜로 전환할 차례야.

## 출시 전 보안 점검

바이브코딩 앱 5,600개를 스캔한 결과, **2,000개 이상에 보안 취약점**이 있었어. 이 3가지만 확인하면 대부분 막을 수 있어.

**1. API 키가 코드에 있는지** — 코드에 직접 적혀있으면 GitHub에 올라가. 남이 내 돈으로 API를 쓸 수 있어.

**2. 로그인 우회가 되는지** — URL을 직접 치면 로그인 없이 들어갈 수 있는 경우. AI가 인증 체크를 빼먹는 경우가 꽤 많아.

**3. 남의 데이터가 보이는지** — URL에서 ID를 바꾸면 남의 데이터가 보여? 그게 이 문제야.

```text:Claude 프롬프트
이 프로젝트 전체 보안 점검을 해줘.
1. API 키, 비밀번호가 코드에 노출되어 있는지
2. 인증 없이 접근 가능한 페이지나 API가 있는지
3. 다른 사용자의 데이터에 접근할 수 있는지
```

## 언제 라이브로 가?

3가지 조건이 맞으면 가.

**1. 피드백 루프를 2~3회 돌렸어.** 배포 → 피드백 → 수정 → 다시 배포. 최소 2번.

**2. 보안 점검을 했어.** API 키, 인증, 데이터 접근 — 위의 3가지를 확인했어.

**3. "보여주고 싶어?"에 "응"이 나왔어.** 5명 중 2~3명이 "이거 좋은데?"라고 하면 가능성이 있어.

출시 준비: 커스텀 도메인 연결(Vercel → Settings → Domains), 에러 모니터링(Vercel Analytics), 사용자 100명 넘으면 Pro 플랜($20/월) 고려.
