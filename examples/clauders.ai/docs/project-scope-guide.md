# 프로젝트 범위 제약 가이드

## 핵심 요약

**클로더즈 1기의 프로젝트 범위는 4주 안에 링크로 보여줄 수 있는 한 가지 동작으로 잡는다. 대상 사용자, 핵심 문제, 첫 동작, 안 만들 것을 정하면 AI가 프로젝트를 이해하기 쉬워지고 완주 가능성도 올라간다.**

이 문서는 아이디어를 막는 문서가 아니다. AI가 일할 수 있는 프로젝트 환경을 만들기 위해 범위를 선명하게 정하는 문서다.

원포인트는 이거야.

> 4주 안에 배포할 한 가지 동작을 정해라.

## 1. 범위는 AI가 일할 수 있는 환경이다

프로젝트 범위가 흐리면 AI도 흐리게 움직인다.

```text
창작자를 위한 콘텐츠 운영 플랫폼 만들어줘.
```

이렇게 말하면 AI는 일정 관리, 자동화, 분석, 게시, 자산 관리까지 전부 떠올릴 수 있다. 결과가 커지고, 파일이 늘어나고, 4주 안에 마무리하기 어려워진다.

범위가 선명하면 작업이 안정된다.

```text
1인 크리에이터가 이번 주 올릴 콘텐츠 3개를 정리하는 캘린더를 만든다.
첫 버전은 제목, 채널, 게시 예정일만 저장한다.
```

이 정도면 AI가 무엇을 만들고, 무엇을 빼야 하는지 이해한다.

## 2. 기본 원칙 5가지

### 1) 4주 안에 첫 링크가 나온다

링크가 열려야 피드백을 받을 수 있다. 첫 링크가 나오면 이후 수정도 쉬워진다.

### 2) 사용자 한 명의 문제를 잡는다

대상을 넓히면 기능도 넓어진다.

```text
모든 직장인
→ 매주 회의록을 정리하는 팀장 1명
```

```text
모든 자영업자
→ 매주 인스타 게시글을 쓰는 1인 카페 사장 1명
```

### 3) 첫 MVP는 한 가지 동작을 증명한다

첫 버전은 한 가지 동작만 보여주면 된다.

예:

- 글 초안 1개 생성
- 문의 1개 분류
- 기록 1개 저장
- 대시보드 카드 1개 표시
- 회의록에서 액션 아이템 5개 추출

### 4) 운영 부담이 큰 기능은 뺀다

아래 기능은 첫 4주에서 빼는 편이 안전하다.

- 결제
- 실시간 협업
- 복잡한 권한 체계
- 금융·의료·법률 고위험 판단
- 개인정보를 많이 다루는 기능

### 5) 안 만들 것을 문서에 남긴다

프로젝트가 커지는 순간을 막으려면 `안 만들 것`을 먼저 적는다.

```markdown
## 이번 버전에서 안 만들 것
- 결제
- 회원가입
- 관리자 페이지
- 실시간 채팅
```

이 항목은 `docs/context.md`나 `CLAUDE.md`에 연결해둔다.

## 3. 4주 프로젝트로 좋은 형태

### A. 개인 생산성 / 내부 도구

- 회의록 → 액션 아이템 변환기
- 블로그 초안 생성기
- 고객 문의 정리 보드
- 경쟁사 모니터링 정리판
- 오늘 할 일 정리 도구

### B. 간단한 콘텐츠/정보 서비스

- 자기소개/포트폴리오 페이지
- 링크 모음 + 추천 문구 페이지
- 뉴스 요약 웹앱
- 자료 큐레이션 페이지
- AI 캐릭터 챗 데모

### C. 데이터 저장/조회 중심 MVP

- 문의 기록 저장 도구
- 습관 기록기
- 팀 공지 보드
- 읽은 자료 아카이브
- 개인 대시보드 1페이지

공통점은 입력, 처리, 출력이 보인다는 것이다.

```text
회의록 입력 → 액션 아이템 추출 → 담당자별 목록 표시
```

```text
책 제목 입력 → 한 문단 리뷰 저장 → 목록에서 다시 보기
```

## 4. 1기에서 기본 제외하는 형태

### A. 기술 과부하가 큰 것

- iOS / Android 네이티브 앱
- 실시간 멀티유저 협업
- 화상통화 / 스트리밍
- 복잡한 소셜 네트워크

### B. 운영 리스크가 큰 것

- 결제 필수 서비스
- 금융 / 의료 / 법률 고위험 도메인
- 개인정보를 과도하게 다루는 서비스
- 관리자 권한 체계가 복잡한 B2B SaaS

### C. 4주 안에 검증이 어려운 것

- 사용자 3종 이상 권한 구조
- 마켓플레이스 / 양면 플랫폼
- 추천 알고리즘 고도화
- 고급 대시보드 + 리포트 + 자동화 묶음

제외는 포기가 아니다. 첫 버전의 바깥에 두는 것이다.

## 5. 애매할 때 쓰는 7문항 체크

아래 질문에 답한다.

| 질문 | 예 / 아니오 |
| --- | --- |
| 1. 1주 안에 첫 화면 또는 첫 동작을 눈으로 볼 수 있는가? |  |
| 2. 2주 안에 핵심 기능 1개를 만들 수 있는가? |  |
| 3. 3주 안에 저장 또는 외부 연동 1개를 붙일 수 있는가? |  |
| 4. 4주 안에 링크 배포가 가능한가? |  |
| 5. 결제 없이도 핵심 가치가 설명되는가? |  |
| 6. 사용자 권한이 1종 또는 2종 이하인가? |  |
| 7. 실패해도 복구 가능한 실험인가? |  |

`아니오`가 많으면 범위를 줄인다.

줄이는 방법은 간단하다.

```text
사용자 종류 줄이기
기능 수 줄이기
화면 수 줄이기
자동화 범위 줄이기
외부 연동 빼기
```

## 6. 빠른 판단표

| 프로젝트 특징 | 판단 | 처리 |
| --- | --- | --- |
| 화면 1~3개 + 저장 1개 + 배포 가능 | 추천 | 바로 브리프로 정리 |
| 로그인 없이 데모 가능 | 가능 | 첫 버전은 로그인 제외 |
| 결제가 있어야 핵심이 성립 | 위험 | 결제 없는 데모 흐름으로 재설계 |
| 실시간 동시 접속이 핵심 | 제외 | 비동기 기록/조회 방식으로 변경 |
| 사용자 반응만 보면 되는 도구 | 추천 | 링크와 피드백 수집까지 진행 |

## 7. 예시 변환

### 예시 1

```text
창작자를 위한 올인원 콘텐츠 운영 플랫폼
```

줄인 버전:

```text
1인 크리에이터가 이번 주 올릴 콘텐츠 3개를 정리하는 캘린더
```

첫 MVP:

- 콘텐츠 제목 입력
- 채널 선택
- 게시 예정일 저장
- 이번 주 목록 보기

안 만들 것:

- 자동 게시
- 성과 분석
- 팀 협업
- 결제

### 예시 2

```text
회사 전체 ERP + 결재 + 근태 + 인사 시스템
```

줄인 버전:

```text
우리 팀 회의록에서 액션 아이템만 뽑아주는 내부 도구
```

첫 MVP:

- 회의록 붙여넣기
- 액션 아이템 추출
- 담당자/마감일 표로 보기

안 만들 것:

- 로그인
- 결재선
- 인사 정보 연동
- 알림 자동 발송

## 8. 수강생에게 주는 안내 문장

```text
이번 4주는 큰 서비스를 완성하는 시간이 아니라,
내 문제를 설명하고 링크로 보여주는 첫 버전을 만드는 시간입니다.
```

```text
이번에 뺀 기능은 버린 게 아니라 다음 버전 후보입니다.
먼저 한 가지 동작을 링크로 보여주세요.
```

```text
Claude에게 일을 잘 시키려면 프로젝트 범위가 선명해야 합니다.
대상, 핵심 동작, 안 만들 것을 문서에 남겨주세요.
```

## 9. 프로젝트 문서에 남길 형식

`docs/context.md`에 아래 블록을 둔다.

```markdown
## 프로젝트 범위

### 대상 사용자
- [누구]

### 핵심 문제
- [어떤 반복/불편/판단]

### 첫 MVP 동작
- [입력]
- [처리]
- [출력]

### 이번 버전에서 안 만들 것
- [제외 기능 1]
- [제외 기능 2]
- [제외 기능 3]
```

`CLAUDE.md`에는 위치를 연결한다.

```markdown
## 프로젝트 맥락
- 범위 기준은 `docs/context.md`의 "프로젝트 범위"를 따른다.
```

## 자주 헷갈리는 포인트

- **아이디어를 줄이면 초라해지나?**
  아니다. 첫 버전은 문제와 동작을 확인하는 장치다.

- **로그인/결제 없으면 서비스가 아닌가?**
  첫 링크에서는 핵심 동작이 보이면 된다. 로그인과 결제는 다음 단계에서 판단한다.

- **다 들어가야 남에게 보여줄 수 있지 않나?**
  보여줄 것은 기능 개수가 아니라 대상과 문제, 첫 동작이다.

## 바로 실행할 다음 단계

1. 내 아이디어를 한 문장으로 쓴다.
2. 대상 사용자 1명을 정한다.
3. 첫 MVP 동작을 입력/처리/출력으로 나눈다.
4. 안 만들 것 5개를 적는다.
5. 7문항 체크를 돌린다.
6. `docs/context.md`에 남긴다.
