# 서비스 만들기 쇼츠 대본

## BS-00. AI 시대엔 더 작게 검증해야 해요

- **Source**: `build-service/00-overview.md`
- **Hook**: AI로 빨리 만들수록 더 작게 검증해야 해요.
- **시청자 고통**: AI로 크게 만들다가 검증 전에 지침
- **팩트체크/보강**: 린 스타트업의 build-measure-learn 흐름과 정합. “작게 검증” 중심으로 유지.
- **Script**:

```text
AI가 코드를 빨리 만들어주니까,
이제 크게 만들어도 될 것 같죠?

반대예요.

더 작게 검증해야 해요.

예전엔 MVP 한 번 만드는 데 몇 달이 걸렸어요.
지금은 며칠 만에도 가능해요.

그래서 중요한 건 코드 속도가 아니에요.

고객 가설,
MVP 범위,
배포,
피드백,
다음 가설.

이 한 바퀴를 얼마나 빨리 돌리는지가 중요해요.

AI에게 한 번에 만들어달라고 하는 게 서비스 만들기가 아니에요.

작게 만들고,
사람에게 보여주고,
배우는 게 서비스 만들기예요.
```

- **Visual**: 고객 가설 → MVP → 배포 → 피드백 루프
- **CTA**: 만들기 전에 이번 실험의 한 바퀴를 먼저 적어보세요.

## BS-01. 아이디어는 대박 예감이 아니에요

- **Source**: `build-service/01-idea.md`
- **Hook**: 아이디어는 “이거 대박”이 아니에요.
- **시청자 고통**: 아이디어를 기능 목록으로만 생각함
- **팩트체크/보강**: 고객/문제/해결 가설은 MVP 검증 프레임과 정합. 대박 예측처럼 말하지 않음.
- **Script**:

```text
아이디어는 “이거 만들면 대박”이 아니에요.

가설이에요.

어떤 고객이,
어떤 문제를 겪고 있고,
이렇게 풀면 반응할 것 같다는 가설이에요.

이 세 줄이 아이디어의 시작이에요.

고객이 넓으면 기능도 넓어져요.
기능이 넓어지면 출시를 못 해요.

처음엔 작고 좁게 잡아야 해요.

전 국민을 위한 서비스 말고,
이번 주에 실제로 보여줄 수 있는 한 사람을 떠올려보세요.

아이디어는 머릿속에서 커지는 게 아니라,
고객 앞에서 선명해져요.
```

- **Visual**: “대박 앱” 텍스트가 지워지고 `고객/문제/해결` 3줄로 바뀜
- **CTA**: 여러분의 아이디어를 고객·문제·해결 3줄로 써보세요.

## BS-02. 기획은 정답 문서가 아니에요

- **Source**: `build-service/02-lean-plan.md`
- **Hook**: PRD, IA, 와이어프레임. 이름에 겁먹지 마세요.
- **시청자 고통**: PRD/IA/와이어프레임 용어에서 멈춤
- **팩트체크/보강**: 기획 산출물을 정답 절차가 아니라 의도 표현 방식으로 설명. 교육용 단순화.
- **Script**:

```text
기획 용어가 갑자기 많이 나와요.

PRD,
사용자 흐름,
IA,
와이어프레임,
MVP 범위.

그런데 이건 시험 범위가 아니에요.

만들기 전에 의도를 선명하게 하는 여러 방식이에요.

글로 쓰면 PRD.
사용자 순서로 보면 사용자 흐름.
화면 구조로 보면 IA.
대충 화면 뼈대를 그리면 와이어프레임.
어디까지 만들지 자르면 MVP 범위.

정답 절차는 없어요.

AI가 덜 추측하게 만들 수 있으면 그게 좋은 기획이에요.
```

- **Visual**: 같은 아이디어가 글/흐름도/화면 스케치로 바뀜
- **CTA**: 오늘은 용어보다 “AI가 덜 추측하게 만들기”만 기억해요.

## BS-03. PRD는 대화 뒤에 만들어요

- **Source**: `build-service/03-prd.md`
- **Hook**: 빈 문서에 PRD부터 쓰려고 하지 마세요.
- **시청자 고통**: 빈 PRD 양식 앞에서 멈춤
- **팩트체크/보강**: AI와 대화 후 문서화하는 흐름은 실무형 보조 패턴. PRD 완성 자동화 과장 금지.
- **Script**:

```text
PRD를 처음부터 빈 문서에 쓰려고 하면 막혀요.

대상 고객은?
핵심 가설은?
검증 기준은?

이런 말부터 나오면 손이 멈춰요.

먼저 Claude랑 이야기해요.

“이런 거 만들고 싶은데 어디서부터 해야 할지 모르겠어.”

이렇게 시작해도 돼요.

Claude가 질문하게 하고,
레퍼런스를 같이 보고,
여러분이 선택해요.

방향이 잡히면 그때 말해요.

“이 대화를 기반으로 prd.md를 만들어주세요.”

PRD는 시작점이 아니라,
대화가 정리된 결과물이에요.
```

- **Visual**: 채팅 대화 → `prd.md` 생성
- **CTA**: PRD 양식부터 열지 말고, Claude에게 질문부터 시켜보세요.

## BS-04. 기술 선택은 멋진 스택 고르기가 아니에요

- **Source**: `build-service/04-tech.md`
- **Hook**: 좋은 기술 선택은 덜 만드는 선택이에요.
- **시청자 고통**: 스택부터 고르다가 범위가 커짐
- **팩트체크/보강**: MVP는 학습을 위한 최소 제품이라는 관점과 정합. 기술 선택을 실험 장비로 표현.
- **Script**:

```text
기술 선택은 멋진 스택 고르기가 아니에요.

이번 실험에 필요한 구조만 남기는 일이에요.

처음부터 이렇게 말할 필요 없어요.

Next.js 쓰고,
DB 붙이고,
API 만들고,
로그인 넣고.

먼저 물어봐야 할 건 이거예요.

화면만 보여줘도 배울 수 있나요?
진짜 API 호출이 필요한가요?
저장해야 하나요?
사용자마다 달라야 하나요?

답이 아니면 만들지 않아도 돼요.

MVP의 기술 선택은 개발자 자랑이 아니라,
고객 반응을 보기 위한 최소 장비예요.
```

- **Visual**: 과한 기술 스택이 하나씩 꺼지고 `이번 실험에 필요한 것`만 남음
- **CTA**: 기능을 붙이기 전에 “이걸 안 만들면 뭘 못 배우지?”라고 물어보세요.

## BS-05. 프론트엔드와 백엔드는 이렇게 나뉩니다

- **Source**: `build-service/05-build-frontend.md`
- **Hook**: 화면과 화면 뒤를 구분하면 코드가 덜 무서워져요.
- **시청자 고통**: 프론트/백엔드 구분이 안 돼 코드가 무서움
- **팩트체크/보강**: 프론트=사용자 화면, 백엔드=서버 처리라는 입문용 설명. 보안/비밀값은 백엔드에서 다뤄야 한다는 점 유지.
- **Script**:

```text
서비스는 크게 두 부분이에요.

고객이 보는 곳.
그리고 뒤에서 처리하는 곳.

고객이 보고,
누르고,
입력하는 화면이 프론트엔드예요.

버튼을 누른 뒤 입력을 검사하고,
비밀 키를 숨기고,
외부 API를 부르고,
DB에 저장하는 곳이 백엔드예요.

코드를 외울 필요는 없어요.

이 파일은 화면을 그리는 파일이구나.
이 버튼은 서버에 요청을 보내는 버튼이구나.
이 기능은 비밀 키 때문에 화면만으로는 안 되는구나.

이 정도 감각이면 AI가 만든 코드를 읽기 시작할 수 있어요.
```

- **Visual**: 화면 버튼 → API 화살표 → 서버/DB
- **CTA**: 여러분의 기능 하나를 프론트 일인지 백엔드 일인지 나눠보세요.

## BS-06. Git은 세이브 포인트예요

- **Source**: `build-service/06-git.md`
- **Hook**: AI로 만들수록 Git이 더 필요해요.
- **시청자 고통**: AI가 고치다 망가뜨렸을 때 되돌릴 지점이 없음
- **팩트체크/보강**: Git commit은 변경 기록 저장이라는 공식 Git 개념과 정합. 세이브 포인트 비유 유지.
- **Script**:

```text
Git은 어려운 개발자 도구처럼 보이지만,
처음엔 세이브 포인트라고 생각하면 돼요.

게임할 때 보스 앞에서 저장하죠.

서비스도 같아요.

기능 하나가 잘 됐을 때,
“여기까지 정상”이라고 기록해두는 거예요.

AI로 만들다 보면 갑자기 화면이 안 뜨고,
버튼 하나 고쳤는데 다른 기능이 망가지고,
에러 고치다 파일이 더 꼬일 수 있어요.

그때 Git 기록이 있으면 말할 수 있어요.

마지막으로 잘 되던 지점으로 돌아가달라고 말할 수 있어요.

Git은 개발자 자격증이 아니라 안전장치예요.
```

- **Visual**: 게임 세이브 슬롯 → git commit 기록
- **CTA**: 잘 됐을 때 바로 commit. 고장 난 뒤가 아니에요.

## BS-07. 에러는 망한 게 아니라 단서예요

- **Source**: `build-service/07-fix.md`
- **Hook**: 에러가 나오면 망한 게 아니에요.
- **시청자 고통**: 에러가 나오면 “고쳐주세요”만 계속 반복함
- **팩트체크/보강**: 로그/재현 상황/기대 동작을 같이 전달하는 디버깅 원칙과 정합. 원인 확인 문구 유지.
- **Script**:

```text
에러가 나오면 망한 게 아니에요.

어디가 막혔는지 알려주는 신호가 나온 거예요.

그런데 초보자가 제일 많이 하는 말이 있어요.

“이거 안 돼요. 고쳐주세요.”

이 말만 반복하면 Claude가 엉뚱한 파일까지 바꿀 수 있어요.

대신 네 가지를 같이 주세요.

무슨 작업을 하다가,
어떤 현상이 생겼고,
원래는 어떻게 돼야 했고,
에러 로그는 뭐라고 나왔는지.

디버깅은 에러를 없애는 일이 아니에요.

끊긴 위치를 찾아서 AI에게 단서를 넘기는 일이에요.
```

- **Visual**: 에러 로그 + `작업/현상/기대/로그` 체크리스트
- **CTA**: 다음 에러는 “고쳐주세요” 한마디 대신 네 가지 단서로 넘겨보세요.

## BS-08. 배포는 고객 검증의 문이에요

- **Source**: `build-service/08-deploy.md`
- **Hook**: 내 컴퓨터에서만 되면 아직 검증이 아니에요.
- **시청자 고통**: localhost와 배포 URL 차이를 모름
- **팩트체크/보강**: Vercel CLI/Git 연동/환경변수 공식 문서와 정합. 환경변수는 배포 환경에도 별도 설정 필요 보강.
- **Script**:

```text
내 컴퓨터에서만 돌아가는 서비스는 아직 고객이 볼 수 없어요.

`localhost:3000`은 여러분만 보는 주소예요.

배포하면 달라져요.

고객에게 보낼 수 있는 URL이 생겨요.

처음엔 Vercel 같은 배포 서비스를 쓰면 충분해요.
Next.js 프로젝트와 잘 맞고,
GitHub 연결이나 CLI 배포 흐름을 잡기 좋아요.

다만 환경변수는 로컬과 배포 환경에 따로 넣어야 해요.

배포는 마지막 장식이 아니에요.

고객 검증을 시작하는 문이에요.

링크가 있어야 누군가 눌러보고,
막히고,
말해줄 수 있어요.
```

- **Visual**: `localhost` 잠긴 화면 → `vercel.app` 공개 링크
- **CTA**: 오늘 목표를 “완성”이 아니라 “URL 만들기”로 바꿔보세요.

## BS-09. 피드백은 칭찬 받는 시간이 아니에요

- **Source**: `build-service/09-feedback.md`
- **Hook**: 배포했으면 이제 진짜 시작이에요.
- **시청자 고통**: 피드백을 “어때요?”로 물어봐서 쓸모없는 답만 받음
- **팩트체크/보강**: 고객 인터뷰는 구체적 행동/막힘을 물어야 한다는 방향으로 보강. 칭찬 수집 아님.
- **Script**:

```text
배포했으면 끝?

아니에요.
이제 피드백 받아야 진짜 시작이에요.

중요한 건 아무한테나 보내는 게 아니에요.

여러분의 가설에 맞는 고객 5명에게 보내세요.
가능하면 모르는 사람 2명도 포함해요.

그리고 이렇게 묻지 마세요.

“어때?”

너무 넓어요.

대신 물어보세요.

어디서 막혔나요?
비슷한 문제를 마지막으로 어떻게 해결했나요?
지금 이 링크를 다시 열 이유가 있나요?
돈을 낸다면 어떤 조건이 필요할까요?

피드백은 칭찬 모으기가 아니에요.
고객을 이해하는 시간이다.
```

- **Visual**: URL 공유 → 5명 피드백 표
- **CTA**: 여러분의 MVP를 보여줄 5명을 지금 적어보세요.

## BS-10. PMF는 “좋아요”가 아니에요

- **Source**: `build-service/10-pmf.md`
- **Hook**: 제품이 작동한다고 시장이 있는 건 아니에요.
- **시청자 고통**: 좋아요를 PMF로 착각함
- **팩트체크/보강**: PMF는 반복 사용/지불/추천 같은 행동 신호를 봐야 한다는 스타트업 교육 프레임과 정합.
- **Script**:

```text
AI 덕분에 작동하는 제품은 빨리 만들 수 있어요.

그런데 작동한다고 시장이 있는 건 아니에요.

진짜 어려운 건 이거예요.

누구에게,
어떤 문제로,
어떤 차별점으로 들어갈 것인가요.

친구가 좋다고 말해도,
그게 PMF는 아니에요.

고객이 다시 쓰고,
대체재와 비교하고,
돈이나 시간을 내고,
주변에 말하고 싶어질 때 신호가 생겨요.

PMF는 한 번에 찾는 정답이 아니에요.

가설을 세우고,
보여주고,
반응을 보고,
다시 좁히는 과정이에요.
```

- **Visual**: `좋아요` 말풍선이 `재사용/지불/추천` 신호로 바뀜
- **CTA**: 칭찬보다 행동 신호를 기록해보세요.

## BS-11. 모객은 링크 뿌리기가 아니에요

- **Source**: `build-service/11-distribution.md`
- **Hook**: 잘 만들었는데 아무도 안 오면, 사람 있는 곳으로 가야 해요.
- **시청자 고통**: 홍보글만 올리고 반응이 없다고 좌절함
- **팩트체크/보강**: Distribution-first는 외부 리서치 기반 프레임. 링크 뿌리기보다 고객 채널에서 유용해지는 방향 유지.
- **Script**:

```text
이제 만드는 건 쉬워졌어요.

그래서 승부는 모객이에요.

그런데 모객을 홍보로 이해하면 바로 막혀요.

“저 이거 만들었어요. 써주세요.”

이건 상대에게 일만 요구하는 말이에요.

모객은 링크 뿌리기가 아니에요.

고객이 이미 모여 있는 곳에서 유용한 사람이 되는 일이에요.

스레드,
유튜브,
디스콰이엇,
오픈채팅,
네이버 카페.

채널은 정답이 없어요.

여러분의 고객이 이미 모여 있고,
여러분이 꾸준히 말할 수 있는 곳이면 시작할 수 있어요.
```

- **Visual**: “써주세요” 게시글 X → 커뮤니티에서 답변·사례 공유 O
- **CTA**: 여러분의 고객이 이미 모여 있는 채널 2개를 골라보세요.

## BS-12. 첫 돈은 결제 기능이 아니라 제안에서 나와요

- **Source**: `build-service/12-pg-bootpay.md`
- **Hook**: 결제 버튼 없어도 돈은 받을 수 있어요.
- **시청자 고통**: 결제 기능부터 만들다가 판매 검증을 못 함
- **팩트체크/보강**: Bootpay 연동은 프론트 결제 후 서버 검증이 핵심. 수동 결제→반복 판매→PG 자동화 순서로 보강.
- **Script**:

```text
첫 돈은 결제 기능에서 나오지 않아요.

제안에서 나와요.

초보가 자주 빠지는 함정이 있어요.

결제 페이지부터 만들고,
PG부터 붙이고,
정기결제부터 고민해요.

그런데 아직 아무도 살지 몰라요.

처음엔 수동 결제도 괜찮아요.
계좌이체,
결제 링크,
마켓플레이스 결제,
간단한 신청 폼으로 먼저 확인할 수 있어요.

반복해서 팔리기 시작하면 그때 PG를 붙이에요.

부트페이 같은 PG/커머스 도구를 붙일 때도 핵심은 같아요.
프론트에서 결제를 받고,
서버에서 금액과 상태를 다시 검증해야 해요.

순서는 이거예요.
먼저 팔고,
반복되면 자동화해요.
```

- **Visual**: 결제 기능 개발 X → 1:1 제안 → 결제 링크 → PG 연동
- **CTA**: 결제 버튼 만들기 전에, 살 사람 한 명에게 먼저 제안해보세요.
