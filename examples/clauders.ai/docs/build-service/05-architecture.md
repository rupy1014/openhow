## 핵심 요약

**이 파트는 용어 지도야. 프론트엔드, 백엔드, API, DB를 여기서 완전히 이해하려고 하면 오히려 어려워져. 처음에는 “이런 말들이 있구나” 정도만 잡고 넘어가도 돼. 실제로는 네가 만들고 싶은 걸 AI에게 말하고, AI가 추천한 방식대로 작게 만들어보고, 그 과정에서 “이게 뭐야?”라고 물어보면서 익히는 게 훨씬 자연스러워.**

초보자가 처음부터 이렇게 말하기는 어려워.

```text
API 키는 서버에서만 쓰고,
결과는 DB에 저장하고,
프론트와 백엔드를 분리해서 만들어줘.
```

이런 말을 못 하는 게 정상이지.

처음에는 이렇게 시작하면 돼.

```text
나 이런 서비스를 만들고 싶어.
사용자는 이런 걸 입력하고,
결과는 이런 식으로 보였으면 좋겠어.
나는 구조를 잘 모르니까 가장 단순한 방식으로 추천해줘.
추천하는 대로 먼저 작게 만들어줘.
그리고 네가 왜 그렇게 만들었는지 쉽게 설명해줘.
```

그러면 AI가 보통 구체적인 방식을 추천해줘.

```text
처음에는 화면만 만들어도 돼.
API 키가 필요하면 서버가 필요해.
결과를 다시 봐야 하면 DB가 필요해.
고객 5명에게 보여주려면 배포가 필요해.
```

그때 “추천하는 대로 해줘”라고 하면 돼. 그리고 만들다가 모르는 말이 나오면 바로 물어보면 돼.

```text
프론트엔드가 뭐야?
백엔드는 왜 필요해?
API 키를 숨긴다는 게 무슨 뜻이야?
DB 없이 시작해도 되는 이유가 뭐야?
이 파일은 왜 여기 들어가?
```

이게 AI 시대의 개발 공부에 더 잘 맞아. 처음부터 모든 용어를 외우는 게 아니라, **내 프로젝트에서 필요한 순간에 질문하면서 익히는 것**.

이 글에서는 딱 이 정도만 잡을 거야.

```text
화면 — 사용자가 보는 곳
서버 — 뒤에서 처리하는 곳
API — 화면과 서버가 말하는 통로
DB — 데이터를 저장하는 곳
폴더 — 코드가 정리되는 자리
```

깊게 외우려고 하지 마. 나중에 AI가 “이 기능은 서버가 필요해요”, “이건 DB에 저장해야 해요”라고 말했을 때 겁먹지 않기 위한 준비 운동이라고 보면 돼.

근데 모든 서비스가 처음부터 이 전체 구조를 가져야 하는 건 아니야.

처음 MVP는 프론트에 다 넣고 보여주는 식으로 시작해도 돼. 버튼을 누르면 미리 준비한 샘플 결과만 보여줘도 고객 반응을 볼 수 있어.

다만 서비스가 조금만 커지면 이런 질문이 나오기 시작해.

```text
이 입력은 어디서 처리하지?
결과는 어디에 저장하지?
API 키는 어디에 숨기지?
사용자가 다시 들어오면 이전 기록을 보여줘야 하나?
```

그래서 이 구조를 한 번은 봐두면 좋아. 지금 완전히 이해하라는 뜻은 아니야. “나중에 이런 질문을 하게 되는구나” 정도만 알면 돼.

## 초보자는 이렇게 일하면 더 자연스러워

처음부터 단계를 직접 설계하려고 하면 부담이 커져.

```text
화면 만들고,
샘플 결과 붙이고,
API 붙이고,
DB 붙이고,
배포하고...
```

틀린 흐름은 아니야. 그런데 이걸 초보자에게 그대로 시키면 “나는 API도 모르고 DB도 모르는데?” 하면서 포기하기 쉬워.

처음에는 개발자처럼 지시하지 말고, 만들고 싶은 장면을 말하면 돼.

예를 들면 이렇게 말하는 거야.

```text
나는 영어 문장 학습 서비스를 만들고 싶어.
사용자는 하루에 문장 하나를 보고,
뜻과 짧은 해설을 확인하고,
완료 버튼을 누를 수 있으면 좋겠어.

나는 프론트엔드, 백엔드, API, DB를 잘 몰라.
처음 고객 5명에게 보여줄 MVP로 가장 단순한 구조를 추천해줘.
추천하는 방식으로 먼저 만들어줘.

그리고 만든 뒤에는
어떤 부분이 화면이고,
어떤 부분이 서버가 필요한 부분이고,
DB가 지금 필요한지 아닌지를 쉽게 설명해줘.
```

이렇게 하면 AI가 “일단 화면만으로 시작해도 돼”, “저장은 나중에 붙여도 돼”, “API 키가 필요하면 서버가 필요해” 같은 식으로 판단해줘.

그다음에는 이렇게 이어가면 돼.

```text
추천하는 대로 해줘.

방금 만든 것에서 프론트엔드는 어디야?
백엔드는 지금 없는 상태야?
DB 없이 시작해도 되는 이유가 뭐야?
나중에 저장 기능을 붙이면 어떤 부분이 바뀌어?
초등학생도 이해하게 설명해줘.
```

이 흐름이 훨씬 현실적이야.

처음부터 정확한 개발 용어로 지시하는 게 목표가 아니야. **AI가 추천한 구조를 따라 만들고, 그 구조를 네 프로젝트 안에서 이해해가는 것**이 목표야.

## 1. 웹, 앱, 자동화 — 어디에서 돌아가게 할 건지

먼저 내가 만드는 게 어디에서 돌아가는지 알아야 해.

| 종류 | 쉽게 말하면 | 처음 만들 때 |
| --- | --- | --- |
| 웹 | 링크로 접속하는 서비스 | 제일 추천. URL 보내기 쉬워 |
| 앱 | 스마트폰에 설치하는 서비스 | 앱스토어, 심사, 기기 대응이 필요해 |
| 자동화/봇 | 화면 없이 대신 처리하는 도구 | 업무 자동화에는 좋지만 고객에게 설명이 어려울 수 있어 |

입문자라면 웹부터가 좋아.

왜냐하면 고객에게 이렇게 보낼 수 있거든.

```text
이 링크 한번 눌러보고 써봐.
어디서 막히는지 알려줘.
```

이게 정말 중요해. 서비스는 내 컴퓨터에서만 돌아가면 검증이 안 돼. 다른 사람이 링크로 열어볼 수 있어야 해.

그래서 처음에는 이렇게 말하면 돼.

```text
브라우저에서 돌아가는 웹앱으로 만들고 싶어.
URL로 5명에게 보내 피드백 받을 거야.
가장 단순한 구조를 추천해줘.
```

## 2. 프론트엔드 — 사용자가 보는 화면

프론트엔드는 사용자가 직접 보는 부분이야.

쉽게 말하면 **화면**이야.

```text
버튼
입력창
카드
이미지
결과 화면
완료 메시지
```

사용자가 “서비스를 쓴다”고 느끼는 건 대부분 프론트엔드에서 일어나.

예를 들어 영어 문장 MVP라면 프론트엔드는 이런 것들이야.

```text
오늘의 문장 제목
영어 문장
한국어 뜻
짧은 해설
오늘 완료 버튼
```

처음 MVP에서는 프론트엔드만으로도 충분한 경우가 많아.

```text
문장을 코드 안에 직접 넣고
버튼을 누르면 화면만 바뀌고
저장은 안 하고
로그인도 안 하는 방식
```

이렇게 해도 고객에게 보여주고 반응을 볼 수 있어.

그러니까 프론트엔드는 “대충 화면”이 아니야. 고객이 처음 만나는 가장 중요한 부분이야.

AI가 “일단 프론트만 만들어도 돼”라고 하면, 그 말은 “가짜로 대충 하자”가 아니야. **고객이 이해하고 눌러볼 수 있는 첫 장면부터 만들자**는 뜻에 가까워.

## 3. 백엔드 — 뒤에서 처리하는 곳

백엔드는 사용자가 직접 보지는 않지만, 뒤에서 중요한 일을 처리하는 곳이야.

쉽게 말하면 **주방**이야.

식당에서 손님은 홀에서 주문하지, 주방 안에 직접 들어가지 않잖아. 서비스도 비슷해.

프론트엔드가 손님이 보는 홀이라면, 백엔드는 주방이야.

백엔드는 이런 일을 해.

```text
AI API 호출하기
API 키 숨기기
입력값 검사하기
DB에 저장하기
결제 처리하기
관리자만 볼 정보 보호하기
```

처음 MVP에서는 백엔드가 없어도 될 수 있어. 하지만 이런 게 필요하면 백엔드가 필요해.

```text
숨겨야 하는 API 키가 있다
사용자 입력을 안전하게 처리해야 한다
결제를 붙인다
사용 기록을 저장한다
사람마다 다른 데이터를 보여준다
```

특히 API 키는 프론트에 넣으면 안 돼.

```text
OpenAI API 키
OpenRouter API 키
결제 API 키
관리자 비밀번호
```

브라우저에 들어간 코드는 사용자가 볼 수 있어. 그래서 이런 비밀 값은 백엔드에서 다뤄야 해.

처음에는 “백엔드를 직접 설계해야지”보다 이렇게 물어보면 돼.

```text
이 기능에서 백엔드가 꼭 필요해?
필요하다면 이유를 쉽게 설명해줘.
필요 없다면 프론트만으로 어디까지 가능한지 알려줘.
```

## 4. API — 화면과 서버가 말하는 통로

API는 프로그램끼리 데이터를 주고받는 통로야.

말이 어려우면 이렇게 생각하면 돼.

**API는 주문 창구야.**

```text
사용자: 버튼을 누름
프론트엔드: 서버에게 요청 보냄
API: 요청을 받는 주소
백엔드: 요청을 처리함
프론트엔드: 결과를 화면에 보여줌
```

예를 들어 사용자가 “오늘 문장 추천” 버튼을 누르면 이런 일이 일어나.

```text
1. 사용자가 버튼을 누른다
2. 프론트엔드가 /api/today 로 요청을 보낸다
3. 백엔드가 오늘 문장을 준비한다
4. 필요하면 AI API를 호출한다
5. 결과를 프론트엔드로 돌려준다
6. 화면에 오늘 문장이 보인다
```

API 주소는 보통 이런 식으로 생겨.

```text
/api/today
/api/generate
/api/save
/api/feedback
```

처음에는 이걸 외울 필요 없어. 그냥 **화면이 서버에게 부탁하는 주소**라고 생각하면 돼.

AI가 `/api/generate` 같은 파일을 만들었다면 이렇게 물어보면 좋아.

```text
이 API는 누가 호출해?
어떤 데이터를 받아서 어떤 결과를 돌려줘?
프론트에서 직접 하면 안 되는 이유가 있어?
```

## 5. DB — 데이터를 저장하는 곳

DB는 Database야.

쉽게 말하면 **서비스의 저장소**야.

```text
사용자 정보
사용 기록
생성된 결과
피드백
설정값
결제 기록
```

이런 걸 저장하고 다시 꺼내 쓰는 곳이 DB야.

그런데 모든 MVP에 DB가 필요한 건 아니야.

```text
새로고침하면 사라져도 괜찮다 → DB 없어도 됨
다시 들어왔을 때 이어서 보여줘야 한다 → DB 필요
여러 사람이 같은 데이터를 봐야 한다 → DB 필요
피드백이나 사용 기록을 분석해야 한다 → DB 필요
```

처음에는 DB 없이 시작해도 돼. 하지만 “나중에 다시 볼 데이터”가 생기면 DB가 필요해져.

이것도 직접 판단이 어려우면 AI에게 이렇게 물어보면 돼.

```text
이 MVP에서 DB가 지금 꼭 필요해?
새로고침하면 사라져도 되는 데이터와
나중에 다시 봐야 하는 데이터를 나눠줘.
처음 버전에서는 DB 없이 시작해도 되는지 추천해줘.
```

## 6. 저장 위치도 여러 가지야

“저장”이라고 다 같은 저장이 아니야.

| 저장 위치 | 쉽게 말하면 | 언제 써? |
| --- | --- | --- |
| 메모리 | 지금 화면에서만 기억 | 새로고침하면 사라져도 되는 선택값 |
| localStorage | 내 브라우저에 저장 | 내 설정, 임시 저장 |
| DB | 서버 쪽 저장소 | 여러 기기/사용자/분석에 필요한 데이터 |

예를 들어.

```text
지금 선택한 탭 → 메모리
다크모드 설정 → localStorage
사용자가 만든 결과 기록 → DB
고객 피드백 → DB 또는 설문 도구
```

이 정도만 알아도 AI에게 훨씬 정확히 말할 수 있어.

```text
오늘 선택한 문장은 새로고침하면 사라져도 돼.
하지만 고객 피드백은 나중에 볼 수 있게 저장하고 싶어.
```

처음부터 저장 방식을 맞히려고 하지 말고, 데이터의 성격을 말해줘. 그러면 AI가 저장 위치를 추천할 수 있어.

## 7. BaaS — 백엔드와 DB를 빌려 쓰는 방법

백엔드와 DB를 전부 직접 만들 필요는 없어.

이미 만들어진 서비스를 빌려 쓸 수 있어. 이런 걸 BaaS라고 해.

Backend as a Service, 즉 “백엔드 빌려쓰기”야.

대표적으로 Supabase, Firebase 같은 것들이 있어.

```text
내가 직접 만들면:
프론트엔드 + 백엔드 + DB + 로그인 모두 직접 관리

BaaS를 쓰면:
프론트엔드 + Supabase/Firebase가 제공하는 DB·로그인 기능 사용
```

입문 단계에서는 이런 도구를 쓰는 게 자연스러워.

직접 백엔드를 전부 이해하고 만들기보다, 필요한 기능을 빌려 쓰는 게 훨씬 빠르거든.

다만 BaaS도 마법은 아니야.

```text
어떤 데이터를 저장할지
누가 볼 수 있는지
로그인이 필요한지
비용이 얼마나 나올지
```

이런 건 여전히 네가 판단해야 해.

AI가 Supabase나 Firebase를 추천했다면 이렇게 물어봐.

```text
왜 이 프로젝트에 Supabase를 추천했어?
더 단순한 방법은 없어?
처음 MVP에서는 안 써도 되는지 판단해줘.
나중에 붙인다면 어떤 기능부터 붙이면 돼?
```

## 8. 폴더 — 코드가 정리되는 자리

AI가 코드를 만들어주면 파일이 여러 개 생겨.

처음엔 폴더 이름만 봐도 헷갈려.

Next.js 같은 웹 프로젝트에서는 보통 이런 느낌이야.

```text
app/          화면과 페이지
app/api/      서버 API
components/   버튼, 카드, 입력창 같은 조각
lib/          API 호출, DB 연결 같은 도구
public/       이미지, 아이콘
```

깊게 외울 필요는 없어.

다만 이런 감각은 필요해.

```text
화면을 바꾸고 싶다 → app 또는 components
버튼 모양을 바꾸고 싶다 → components
AI API 호출을 바꾸고 싶다 → app/api 또는 lib
DB 연결을 바꾸고 싶다 → lib
이미지를 넣고 싶다 → public
```

이걸 알면 AI에게 이렇게 말할 수 있어.

```text
버튼 디자인만 바꿔줘.
API 호출 로직은 건드리지 마.
어떤 파일을 수정했는지도 설명해줘.
```

처음부터 `components`니 `lib`니 정확히 몰라도 돼. AI가 파일을 만들면 그때 물어보면 돼.

```text
방금 만든 파일들을 초등학생도 이해하게 설명해줘.
각 파일이 화면, 동작, 저장 중 어디에 해당하는지 표로 정리해줘.
```

## 9. 지금은 이 정도만 기억해도 돼

비개발자가 모든 걸 깊게 알 필요는 없어.

지금은 이 정도만 기억해도 돼.

```text
프론트엔드 = 사용자가 보는 화면
백엔드 = 뒤에서 처리하는 곳
API = 화면과 서버가 말하는 통로
DB = 데이터를 저장하는 곳
BaaS = 백엔드와 DB를 빌려 쓰는 방법
폴더 = 코드가 정리되는 자리
```

그리고 더 중요한 건 이거야.

```text
처음부터 이 용어를 다 써서 지시하지 않아도 돼.
만들고 싶은 걸 말하면 AI가 구조를 추천해줘.
추천대로 만들어보고, 모르는 말을 바로 물어보면 돼.
```

몇 번 만들다 보면 “아, 이건 화면 문제구나”, “이건 API 키 때문에 서버가 필요하구나”, “이건 저장해야 하니까 DB 이야기구나” 하고 감이 와.

지금은 그 준비 운동이라고 보면 돼.

## 10. AI에게 요청할 때는 이렇게 시작해

구조를 조금 알면 좋지만, 처음부터 구조를 직접 쪼개서 지시하려고 하지 않아도 돼.

더 좋은 시작은 이거야.

```text
나는 [서비스 이름/아이디어]를 만들고 싶어.
사용자는 [누가]이고,
사용자는 [어떤 상황]에서 [무엇]을 하고 싶어 해.

첫 버전은 고객 5명에게 보여줄 MVP로 만들고 싶어.
나는 개발 구조를 잘 모르니까
가장 단순한 구조를 추천해줘.

추천한 방식대로 먼저 만들어줘.
그리고 왜 그 방식이 적절한지,
어떤 건 지금 안 해도 되는지 쉽게 설명해줘.
```

AI가 추천해주면 바로 개발자처럼 아는 척할 필요 없어.

```text
추천하는 대로 해줘.
단, 한 번에 너무 크게 만들지 말고
10분 안에 확인할 수 있는 작은 단위로 진행해줘.

각 단계가 끝날 때마다
내가 확인해야 할 화면,
눌러봐야 할 버튼,
아직 안 만든 기능을 정리해줘.
```

그리고 모르는 말이 나오면 바로 멈춰서 물어봐.

```text
방금 말한 API가 정확히 뭐야?
이 프로젝트에서 백엔드는 어떤 역할을 해?
DB는 지금 필요한 거야, 나중에 필요한 거야?
더 쉬운 방법은 없어?
지금은 안 해도 되는 건 뭐야?
```

이렇게 익혀나가는 게 좋아.

서비스 개발에서 진짜 차이는 “처음부터 완벽한 프롬프트를 쓰는 능력”이 아니야. **AI가 추천한 걸 이해하고, 필요 없는 걸 덜어내고, 다음에 무엇을 물어봐야 하는지 아는 뇌지컬**이야.

## AI에게 물어보며 공부하는 법

이런 구조 개념은 책처럼 처음부터 끝까지 외우는 것보다, 만들면서 필요한 순간에 물어보는 게 좋아.

예를 들어 API를 붙이다가 막히면 이렇게 물어봐.

```text
내가 지금 만들고 있는 서비스는 [서비스 설명]이야.
여기서 프론트엔드, 백엔드, API, DB가 각각 어떤 역할을 하는지
내 프로젝트 예시로 설명해줘.

그리고 지금 내가 막힌 부분이
프론트 문제인지, 백엔드 문제인지, DB 문제인지
확인하는 질문을 순서대로 해줘.
```

DB가 필요한지 헷갈리면 이렇게 물어봐.

```text
이 MVP에서 DB가 꼭 필요한지 판단해줘.
새로고침하면 사라져도 되는 데이터와
나중에 다시 봐야 하는 데이터를 나눠줘.
처음 버전에서 DB 없이 시작해도 되는지도 말해줘.
```

API 키가 헷갈리면 이렇게 물어봐.

```text
이 기능에서 API 키가 브라우저에 노출될 위험이 있는지 봐줘.
프론트에서 처리해도 되는 것과
서버에서 처리해야 하는 것을 나눠서 설명해줘.
```

AI가 만든 폴더가 헷갈리면 이렇게 물어봐.

```text
방금 만든 폴더와 파일을 표로 정리해줘.
각 파일이 화면, 동작, API, 저장 중 어디에 해당하는지 알려줘.
내가 수정하면 위험한 파일과 안전하게 고쳐볼 수 있는 파일도 나눠줘.
```

이게 AI 시대 공부법이야.

**필요한 개념을, 필요한 순간에, 내 프로젝트 예시로 다시 물어보는 것.**

여기서 너무 많이 설명하면 오히려 더 어려워져. 이 문서는 용어 지도를 한 번 보여주는 역할이고, 진짜 이해는 만들면서 쌓으면 돼.

## 자주 헷갈리는 포인트

### 모든 프로젝트에 백엔드가 있어야 해?

아니야. 보여주기식 MVP나 계산기, 타이머, 정적 페이지처럼 저장과 비밀 키가 필요 없는 건 프론트만으로도 충분해.

### DB가 꼭 필요해?

아니야. 새로고침하면 사라져도 괜찮은 MVP라면 DB 없이 시작해도 돼. 나중에 다시 볼 데이터가 생기면 붙이면 돼.

### localStorage에 API 키 저장하면 안 돼?

안 돼. 브라우저에 있는 건 사용자가 볼 수 있어. API 키는 서버에서 다뤄야 해.

### Supabase를 쓰면 백엔드를 몰라도 돼?

완전히 몰라도 되는 건 아니야. 많이 빌려 쓸 수는 있지만, 어떤 데이터를 저장할지, 누가 볼 수 있는지, 비용이 나올 수 있는지는 알아야 해.

### 폴더 구조를 꼭 알아야 해?

깊게 알 필요는 없어. 다만 “화면은 어디, API는 어디, 공통 조각은 어디” 정도를 조금씩 익히면 AI에게 수정 요청을 더 안전하게 할 수 있어.

### 그럼 다음 글에서는 뭘 해?

다음 글에서는 실제로 고객이 보는 화면부터 만들어. 처음부터 상태관리나 컴포넌트를 다 알 필요 없어. AI가 추천하는 방식대로 첫 화면을 만들고, 모르는 말은 그때그때 물어보면서 익히면 돼.
