## 핵심 요약

**프론트엔드는 사용자가 직접 보는 화면이야. 웹에서는 브라우저에 뜨는 화면이고, 앱에서는 휴대폰에 설치해서 보는 화면이야. 버튼, 입력창, 카드, 목록, 결과 화면처럼 “고객이 만지는 부분”을 이해하는 파트라고 보면 돼. 코드를 하나도 몰라도 괜찮아. AI가 만들어준 화면을 보면서 “이 파일은 화면을 그리는구나”, “이 값은 지금 화면이 기억하는 값이구나”, “이 버튼을 누르면 이런 일이 시작되는구나” 정도만 잡아도 충분해.**

PRD가 정해졌으면 AI에게 기능을 만들라고 하게 될 거야.

이때 먼저 물어봐야 할 게 있어.

```text
이 서비스는 웹으로 만들 거야?
앱으로 만들 거야?
```

처음 고객 5명에게 링크로 보여주는 목적이라면 보통 웹이 편해.

앱은 설치, 심사, 기기 대응이 있어서 처음엔 더 복잡할 수 있어.

하지만 개념은 비슷해.

```text
웹 프론트엔드 = 브라우저에서 보는 화면
앱 프론트엔드 = 스마트폰 앱에서 보는 화면
```

이 글에서는 웹과 앱을 구분해서 설명하되, 초보자는 먼저 **화면이 어떤 조각으로 이루어져 있는지**만 잡으면 돼.

다음 글([07 백엔드 이해](./07-build-backend))에서는 화면 뒤에서 처리되는 일을 볼 거야.

## 1. 프론트엔드는 “고객이 만지는 곳”이야

프론트엔드는 사용자가 직접 보는 부분이야.

쉽게 말하면 **화면**이야.

```text
버튼
입력창
카드
표
목록
이미지
결과 화면
에러 메시지
완료 메시지
```

웹이라면 이런 화면이야.

```text
브라우저에서 주소를 열고
입력창에 값을 넣고
버튼을 누르고
결과를 확인하는 화면
```

앱이라면 이런 화면이야.

```text
휴대폰 앱을 열고
탭을 누르고
리스트를 스크롤하고
사진을 올리고
알림을 확인하는 화면
```

고객은 서비스를 쓸 때 코드를 보지 않아.

고객은 이런 걸 봐.

```text
어디에 입력해야 하지?
어떤 버튼을 눌러야 하지?
결과가 어디에 나오지?
지금 로딩 중이야?
실패했으면 왜 실패했지?
다음에 뭘 하면 되지?
```

그래서 프론트엔드는 단순히 “예쁘게 꾸미는 영역”이 아니야.

고객이 서비스를 이해하고, 행동하고, 결과를 확인하는 곳이야.

처음에는 이 한 줄만 기억해도 돼.

```text
프론트엔드 = 사용자가 보고 누르고 입력하는 부분
```

## 2. 웹과 앱은 겉모습은 달라도 보는 기준은 비슷해

웹과 앱은 쓰는 기술이 다를 수 있어.

하지만 초보자가 처음 볼 때는 같은 질문으로 보면 돼.

| 질문 | 웹에서 | 앱에서 |
| --- | --- | --- |
| 어디에서 열어? | 브라우저 주소 | 설치한 앱 |
| 화면 단위는? | 페이지 | 화면/스크린 |
| 누르는 것은? | 클릭 | 탭 |
| 글자는 어디에 넣어? | 입력창 | 입력 필드 |
| 화면 이동은? | URL 변경, 링크 | 화면 전환, 탭 이동 |
| 확인은 어디서 해? | Chrome/Safari | iPhone/Android 시뮬레이터 또는 실제 기기 |
| 에러는 어디서 봐? | 브라우저 콘솔 | Xcode/Android Studio/IDE 로그 |

처음부터 웹 개발 지식과 앱 개발 지식을 섞어서 외울 필요 없어.

AI에게 이렇게 말하면 돼.

```text
이 프로젝트가 웹인지 앱인지 먼저 확인해줘.
웹이라면 브라우저 화면 기준으로 설명해줘.
앱이라면 모바일 앱 화면 기준으로 설명해줘.
나는 코드를 잘 모르니까 화면 단위, 버튼, 입력값, 이동 흐름을 먼저 설명해줘.
```

## 3. 화면은 보통 이런 조각으로 나뉘어

AI가 화면을 만들면 파일이 여러 개 생길 수 있어.

처음엔 복잡해 보이지만, 대부분 이런 조각이야.

| 화면 조각 | 쉽게 말하면 | 웹 예시 | 앱 예시 |
| --- | --- | --- | --- |
| 페이지/스크린 | 한 화면 전체 | 홈 페이지, 결과 페이지 | 홈 스크린, 설정 화면 |
| 컴포넌트 | 반복해서 쓰는 화면 조각 | 버튼, 카드, 입력창 | 버튼, 카드, 리스트 아이템 |
| 상태 | 화면이 기억하는 값 | 입력 중인 글자, 로딩 여부 | 선택한 탭, 입력값, 업로드 중 여부 |
| 스타일 | 모양과 배치 | CSS, Tailwind 등 | StyleSheet, SwiftUI modifier 등 |
| 이벤트 | 사용자의 행동 | 클릭, 입력, 제출 | 탭, 스와이프, 입력 |

예를 들어 문의 폼 화면이라면 이렇게 나눌 수 있어.

```text
화면 전체 → 문의하기 화면
화면 조각 → 이름 입력, 이메일 입력, 문의 내용 입력, 제출 버튼
상태 → 지금 입력한 이름/이메일/문의 내용
이벤트 → 제출 버튼 클릭 또는 탭
스타일 → 입력창 간격, 버튼 색상, 에러 메시지 위치
```

상품 설명 생성기라면 이렇게 볼 수 있어.

```text
화면 전체 → 상품 설명 생성 화면
화면 조각 → 상품명 입력, 특징 입력, 생성 버튼, 결과 카드
상태 → 입력한 상품명, 생성 중인지 여부, 생성된 결과
이벤트 → 생성 버튼 클릭 또는 탭
스타일 → 결과 카드 디자인, 로딩 표시
```

이 정도만 알아도 AI가 만든 화면을 훨씬 덜 무섭게 볼 수 있어.

## 4. 처음부터 개발자처럼 말하지 않아도 돼

웹이면 `컴포넌트`, `상태`, `props`, `CSS`, `Tailwind` 같은 말이 나올 수 있어.

앱이면 `screen`, `view`, `state`, `navigation`, `SwiftUI`, `React Native` 같은 말이 나올 수 있어.

처음 보는 사람은 당연히 모를 수 있어.

그러면 이런 프롬프트를 처음부터 못 써.

```text
ContactForm 컴포넌트를 만들고,
state로 name, email, message를 관리하고,
onSubmit에서 API 호출해줘.
```

처음엔 이런 말을 못 하는 게 정상이지.

그럼 이렇게 시작하면 돼.

```text
나는 코드를 잘 몰라.
이 PRD를 기준으로 고객이 처음 보는 화면을 만들어줘.

먼저 이 프로젝트가 웹인지 앱인지 기준을 잡아줘.
웹이면 브라우저 화면 기준으로,
앱이면 모바일 화면 기준으로 설명해줘.

화면에는 사용자가 해야 할 행동이 분명히 보였으면 좋겠어.
입력창, 버튼, 결과 영역이 필요하면 네가 추천해서 배치해줘.

만든 뒤에는
어떤 파일이 화면을 그리고,
어떤 값이 화면에서 기억되는지,
버튼을 누르면 어떤 일이 시작되는지
초등학생도 이해하게 설명해줘.
```

중요한 건 처음부터 개발자처럼 말하는 게 아니야.

AI가 만든 구조를 보고, 모르는 말을 계속 물어보는 거야.

```text
컴포넌트가 뭐야?
상태가 뭐야?
이 파일은 화면을 그리는 파일이야?
이 버튼을 누르면 어디로 연결돼?
이 값은 새로고침하거나 앱을 껐다 켜면 사라져?
```

이 질문을 하면서 감이 생겨.

## 5. 프론트엔드의 기본 흐름은 단순해

프론트엔드도 기본 흐름은 거의 비슷해.

:::canvas-flow

    { "id": "input", "label": "사용자 행동\n입력·클릭·탭", "col": 1, "row": 0, "type": "process" },
    { "id": "state", "label": "상태 변경\n입력값·로딩·결과", "col": 2, "row": 0, "type": "warning" },
    { "id": "render", "label": "다시 보여주기\n결과·에러·완료", "col": 3, "row": 0, "type": "success" }
  ],

:::

예를 들어.

```text
문의 폼
→ 이름과 문의 내용을 입력한다
→ 제출 버튼을 누른다
→ 로딩 표시가 뜬다
→ 접수 완료 메시지가 보인다
```

```text
상품 설명 생성기
→ 상품명을 입력한다
→ 생성 버튼을 누른다
→ 생성 중 표시가 뜬다
→ 결과 카드가 보인다
```

```text
예약 화면
→ 날짜를 선택한다
→ 가능한 시간이 표시된다
→ 시간을 고른다
→ 예약 버튼이 활성화된다
```

코드를 몰라도 이 흐름은 이해할 수 있어야 해.

그래야 AI가 만든 화면이 “왜 이렇게 나뉘었는지” 볼 수 있어.

## 6. 상태는 “지금 화면이 기억하는 값”이야

`상태 관리`라는 말이 나올 수 있어.

처음엔 몰라도 돼.

쉽게 말하면 **지금 화면이 기억하고 있어야 하는 값**이야.

예를 들어.

| 화면 | 상태 예시 |
| --- | --- |
| 문의 폼 | 이름, 이메일, 문의 내용, 제출 중 여부 |
| 생성 도구 | 입력한 주제, 생성 중 여부, 생성 결과 |
| 예약 화면 | 선택한 날짜, 선택한 시간, 예약 가능 여부 |
| 목록 화면 | 검색어, 선택한 필터, 현재 페이지 |
| 로그인 화면 | 이메일, 비밀번호, 에러 메시지 |

상태를 이해하면 화면이 왜 바뀌는지 감이 와.

```text
입력창에 글자를 쓴다 → 입력값 상태가 바뀐다
버튼을 누른다 → 로딩 상태가 켜진다
결과를 받는다 → 결과 상태가 채워진다
실패한다 → 에러 상태가 생긴다
```

AI가 `state`, `store`, 상태관리 도구 같은 말을 할 수 있어.

처음 듣는 말일 수 있어.

그럼 바로 물어봐.

```text
상태가 뭐야?
이 화면에서 어떤 값들이 상태야?
왜 이 값을 화면이 기억해야 해?
웹에서는 새로고침하면 사라지는 값이 뭐야?
앱에서는 앱을 껐다 켜면 사라지는 값이 뭐야?
나중에도 남아야 하는 값은 뭐야?
```

처음부터 도구 이름을 외울 필요 없어.

먼저 “화면이 기억하는 값”이라는 감각을 잡으면 돼.

## 7. 컴포넌트는 “화면 조각”이야

컴포넌트라는 말도 많이 나와.

쉽게 말하면 **화면 조각**이야.

```text
버튼
입력창
카드
리스트 한 줄
결과 박스
로딩 표시
에러 메시지
```

이런 걸 따로 떼어두면 다시 쓰기 쉬워.

웹에서도 앱에서도 비슷해.

```text
웹: Button, Card, Form, ResultBox
앱: Button, Card, Screen, ListItem
```

예를 들어 상품 설명 생성기 화면이 있다고 해보자.

```text
상품명 입력창
특징 입력창
생성 버튼
결과 카드
```

이 조각들이 컴포넌트가 될 수 있어.

왜 나누냐면 수정이 쉬워지기 때문이야.

```text
버튼 디자인만 바꾸고 싶다 → 버튼 컴포넌트 수정
결과 카드 모양만 바꾸고 싶다 → 결과 카드 컴포넌트 수정
입력창 안내 문구만 바꾸고 싶다 → 입력창 컴포넌트 수정
```

AI에게는 이렇게 물어봐.

```text
이 화면에서 어떤 부분이 컴포넌트로 나뉘었는지 알려줘.
웹/앱 기준으로 각각 어떤 역할인지 설명해줘.
각 컴포넌트가 한 줄로 무슨 역할을 하는지 알려줘.
내가 디자인만 바꾸고 싶을 때 어떤 파일을 보면 되는지도 알려줘.
```

컴포넌트를 너무 잘게 나누는 게 항상 좋은 건 아니야.

처음에는 AI가 추천한 구조를 보고, 왜 나눴는지 설명받으면 돼.

## 8. 스타일은 웹과 앱에서 부르는 말이 다를 수 있어

화면의 색, 간격, 크기, 폰트, 배치를 담당하는 게 스타일이야.

웹에서는 이런 말이 나올 수 있어.

```text
CSS
Tailwind
className
responsive
```

앱에서는 이런 말이 나올 수 있어.

```text
SwiftUI modifier
StyleSheet
theme
layout
constraint
```

처음부터 이걸 다 알 필요는 없어.

웹이면 웹 기준으로, 앱이면 앱 기준으로 설명해달라고 하면 돼.

```text
이 프로젝트는 웹이야, 앱이야?
웹이면 CSS/Tailwind가 어디에 쓰였는지 설명해줘.
앱이면 스타일이나 레이아웃이 어디에 쓰였는지 설명해줘.
나는 처음이라 색, 간격, 크기, 배치를 바꾸려면 어디를 봐야 하는지만 알려줘.
```

고칠 때는 이렇게 말하면 좋아.

```text
디자인만 고쳐줘.
기능 로직은 건드리지 마.
웹이면 브라우저 화면 기준으로 확인해줘.
앱이면 모바일 화면 기준으로 확인해줘.
```

## 9. 만들어진 화면 소스를 보는 순서

AI가 화면을 만들어줬다면 바로 다음 기능으로 넘어가지 마.

먼저 소스를 설명받아.

```text
방금 만든 화면 소스를 초보자 기준으로 설명해줘.

먼저 이게 웹 프로젝트인지 앱 프로젝트인지 말해줘.

순서는 이렇게 해줘.
1. 사용자가 처음 보는 화면 파일
2. 입력창, 버튼, 카드 같은 컴포넌트 파일
3. 화면이 기억하는 상태
4. 버튼을 눌렀을 때 실행되는 동작
5. 결과나 에러 메시지가 표시되는 부분
6. 디자인을 바꾸려면 봐야 하는 파일

각 파일마다 “이 파일은 한 줄로 뭐 하는 파일인지” 먼저 설명해줘.
```

목표는 코드를 다 외우는 게 아니야.

역할을 잡는 거야.

```text
아, 이 파일은 화면 전체구나.
아, 이 파일은 버튼 조각이구나.
아, 이 값은 입력창에 적은 글자를 기억하는구나.
아, 이 부분은 로딩 중 표시구나.
아, 이 부분은 결과를 보여주는 영역이구나.
```

이 정도면 충분해.

## 10. 화면 검증은 직접 눌러보는 거야

프론트엔드는 눈에 보이기 때문에 검증하기 좋아.

코드는 AI가 만들어줘도, 확인은 네가 해야 해.

웹이면 브라우저에서 확인해.

앱이면 시뮬레이터나 실제 기기에서 확인해.

:::steps
1. 처음 화면을 열어봐. 무엇을 해야 하는지 바로 보이나?
2. 입력창에 값을 넣어봐. 글자가 잘 들어가나?
3. 버튼을 눌러봐. 로딩, 결과, 에러 중 필요한 반응이 보이나?
4. 빈 값으로 제출해봐. 사용자에게 안내 메시지가 나오나?
5. 웹이면 모바일 크기로 줄여봐. 앱이면 작은 기기 화면에서도 봐.
6. 고객에게 보여줄 때 첫 행동이 분명한가?
:::

문제가 생기면 이렇게 말하면 돼.

```text
웹 브라우저에서 입력창에 글자를 넣고 버튼을 눌렀는데 아무 반응이 없어.
화면 문제인지, 버튼 동작 문제인지, 백엔드 연결 문제인지
초보자 기준으로 확인 순서를 알려줘.
```

앱이면 이렇게 말해.

```text
앱 화면에서 버튼을 탭했는데 아무 반응이 없어.
IDE 로그에 나온 에러는 아래와 같아.
[에러 로그 붙여넣기]
화면 문제인지, 버튼 동작 문제인지, 백엔드 연결 문제인지 확인해줘.
```

디자인 문제는 이렇게 말하면 돼.

```text
모바일 화면에서 버튼이 화면 밖으로 밀려나.
디자인만 고쳐줘.
기능 로직은 건드리지 마.
```

이렇게 증상을 구체적으로 말하는 연습이 중요해.

## 11. 한 입 끝나면 저장하고 정리해

기능 하나가 끝나면 이 리듬을 지켜.

```text
기능 끝 → 확인 → 저장 → 정리 → 다음 기능
```

- **확인**: 웹이면 브라우저에서, 앱이면 시뮬레이터나 실제 기기에서 직접 눌러봐.
- **저장**: “지금까지 만든 거 git으로 저장해줘.” 다음 기능 만들다 망가지면 이 시점으로 되돌릴 수 있어. Git은 뒤에서 따로 볼 거야.
- **정리**: “뭘 만들었고 어떤 파일이 뭘 하는지 정리해줘.” AI는 대화가 길어지면 앞에서 한 걸 잊거든. 정리해두면 다음 기능 만들 때 맥락을 다시 잡아.
- **배운 것 기록**: “예상과 달랐던 점 정리해줘.” 기능마다 적어두면 같은 실수를 안 반복하고, PRD 방향도 업데이트할 수 있어.

기능 하나 끝나면 `/compact`로 대화를 압축해. 같은 흐름을 이어가는데 길이만 줄어들어. 작업이 완전히 바뀌면 `/clear`로 새로 시작해. 이전 맥락이 다음 작업에 끼어드는 걸 막아줘.

## 자주 헷갈리는 포인트

### 프론트엔드는 디자인만 말하는 거야?

아니야. 디자인도 포함하지만, 사용자가 입력하고 클릭하거나 탭하고 결과를 확인하는 전체 경험이 프론트엔드야.

### 웹 프론트엔드와 앱 프론트엔드는 같은 거야?

개념은 비슷하지만 쓰는 도구와 확인 방법이 달라. 웹은 브라우저에서 보고, 앱은 시뮬레이터나 실제 기기에서 봐. 처음에는 “사용자가 보는 화면”이라는 공통점부터 이해하면 돼.

### 컴포넌트를 꼭 알아야 해?

처음부터 깊게 몰라도 돼. “버튼, 카드, 입력창 같은 화면 조각” 정도로 이해하면 돼. AI가 파일을 나누면 왜 나눴는지 설명해달라고 하면 돼.

### 상태관리가 뭔지 모르겠어

정상이야. 처음엔 “화면이 지금 기억하는 값”이라고 이해하면 돼. 입력창의 글자, 선택한 날짜, 로딩 여부, 결과값 같은 게 상태야.

### Tailwind나 CSS를 알아야 해?

웹 프로젝트라면 나올 수 있는 말이야. 앱 프로젝트라면 다른 스타일 도구가 나와. 처음부터 외우지 말고 “이 프로젝트가 웹인지 앱인지 먼저 말해주고, 스타일을 바꾸려면 어디를 봐야 하는지 설명해줘”라고 물어보면 돼.

### 새로고침하거나 앱을 껐다 켜면 입력한 값이 사라져

정상일 수 있어. 화면 안에서만 기억하는 값은 사라질 수 있어. 나중에 다시 봐야 하는 데이터라면 백엔드나 DB가 필요해.

### AI가 만든 화면이 너무 복잡해

“초보자 기준으로 파일을 줄이고, 지금 MVP에 필요 없는 구조는 덜어내줘”라고 말해. 처음부터 완벽한 구조보다 이해 가능한 구조가 더 중요해.
