## 핵심 요약

**에러가 나면 망한 게 아니야. “어디가 막혔는지 알려주는 신호”가 나온 거야. 내용을 그대로 복사해서 Claude에게 전달하면 대부분 고칠 수 있어. 다만 “고쳐줘”만 반복하면 시간과 토큰만 낭비할 수 있어. 지금 어디서 어떤 작업을 하다가, 어떤 현상이 생겼고, 원래는 어떻게 돼야 했는지 같이 알려줘야 해. 가능하면 왜 에러가 났는지도 이해하려고 해. 그 과정에서 개발 지식이 쌓여.**

AI로 서비스를 만들다 보면 에러는 무조건 나와.

```text
화면이 안 뜬다
버튼을 눌러도 반응이 없다
저장이 안 된다
배포 후에는 되는데 로컬에서는 안 된다
로컬에서는 되는데 배포 후 안 된다
```

이럴 때 초보자가 가장 많이 하는 말이 이거야.

```text
이거 안 돼. 고쳐줘.
```

이 말만 해도 Claude가 뭔가 고쳐주긴 해.

하지만 운이 나쁘면 이런 일이 생겨.

```text
관련 없는 파일까지 바뀐다
원래 되던 기능이 망가진다
같은 에러를 계속 다른 방식으로 고친다
에러의 진짜 원인은 그대로 남는다
시간과 토큰만 계속 쓴다
```

그래서 디버깅은 “에러를 없애는 일”만이 아니야.

**지금 어디서 끊겼는지 찾고, Claude에게 그 단서를 정확히 넘기는 일**이야.

## 1. 먼저 어디에서 문제가 보이는지 확인해

에러는 만드는 대상에 따라 보이는 위치가 달라.

웹 개발을 할 때는 보통 **브라우저 콘솔**에 에러가 떠.

앱 개발을 할 때는 Xcode, Android Studio, Cursor, VS Code 같은 **IDE 안의 로그 창**에 에러가 떠.

배포할 때는 Vercel 같은 **배포 서비스의 로그**에 에러가 뜰 수 있어.

| 만들고 있는 것 | 어디를 보면 돼? | 보통 보이는 것 |
| --- | --- | --- |
| 웹서비스 | 브라우저 콘솔 | 화면 에러, 버튼 오류, API 호출 실패 |
| 웹서비스 서버 | 터미널 / IDE 로그 | 서버 실행 에러, 환경변수 문제 |
| 앱 | Xcode / Android Studio / IDE 로그 | 빌드 에러, 실행 에러, 기기 로그 |
| 배포 | Vercel 같은 배포 로그 | 빌드 실패, 배포 실패 |

처음부터 로그 종류를 다 알 필요는 없어.

대부분 도구가 빨간 글씨나 에러 로그를 알아서 보여줘.

그걸 복사해서 Claude에게 전달하면 돼.

```text
1. 화면에서 이상한 현상을 본다
2. 웹이면 브라우저 콘솔을 본다
3. 앱이면 IDE의 에러 로그를 본다
4. 서버/배포 문제면 터미널이나 배포 로그를 본다
5. 보이는 에러를 복사한다
6. 내가 하던 작업과 기대한 동작을 같이 Claude에게 보낸다
```

## 2. 브라우저 콘솔 보는 법

화면에서는 아무 일도 안 일어나는 것처럼 보여도, 브라우저 안쪽에서는 에러가 나고 있을 수 있어.

그걸 보는 곳이 **브라우저 콘솔**이야.

여는 방법은 보통 이래.

```text
Chrome / Edge
- Windows: F12 또는 Ctrl + Shift + J
- Mac: Cmd + Option + J
```

열리면 `Console` 탭을 봐.

빨간 글씨가 있으면 그게 에러야.

예를 들어 이런 식으로 나올 수 있어.

```text
TypeError: Cannot read properties of undefined
Failed to fetch
404 Not Found
500 Internal Server Error
```

처음에는 뜻을 몰라도 돼.

그냥 빨간 에러를 통째로 복사해서 Claude에게 보내면 돼.

```text
브라우저 콘솔에 이런 에러가 나와.
[콘솔 에러 전체 붙여넣기]

내가 한 작업은 문의 폼에서 제출 버튼을 누른 거야.
원래는 “접수 완료” 메시지가 떠야 하는데 아무 반응이 없어.
원인을 초보자도 이해하게 설명하고 고쳐줘.
```

## 3. IDE나 터미널 로그도 같이 봐

웹에서는 브라우저 콘솔이 중요하지만, 모든 에러가 브라우저에만 뜨는 건 아니야.

서버 쪽 에러는 터미널에 뜰 수 있고, 앱 개발 에러는 Xcode나 Android Studio 같은 IDE 로그에 뜰 수 있어.

웹 개발에서 이런 명령을 실행해두는 경우가 많아.

```text
npm run dev
pnpm dev
yarn dev
```

이 명령이 돌아가는 창에 에러가 찍힐 수 있어.

Cursor, VS Code, Claude Code 같은 도구를 쓰면 보통 아래쪽에 `Terminal`, `Problems`, `Output` 같은 탭이 있어.

앱 개발이라면 Xcode나 Android Studio 안에 build log, run log, console 같은 영역이 있어.

정확한 이름은 도구마다 달라도 괜찮아.

빨간 글씨, Failed, Error, Warning처럼 보이는 로그가 있으면 그걸 복사하면 돼.

예를 들어 이런 에러가 나올 수 있어.

```text
Module not found
Environment variable is missing
Database connection failed
Build failed
Cannot find package
```

이것도 그대로 복사해서 Claude에게 주면 돼.

```text
IDE/터미널에는 이런 에러가 나와.
[에러 로그 전체 붙여넣기]

화면에서는 버튼을 누르면 로딩만 계속 돌아.
지금 작업은 피드백 저장 기능을 붙이는 중이었어.
프론트 문제인지, 백엔드 문제인지, 환경변수 문제인지 확인 순서를 알려줘.
```

중요한 건 에러가 보이는 곳을 찾으면, 해석하려고 오래 붙잡고 있지 말고 **그 로그를 복사해서 Claude에게 전달하는 것**이야.

```text
웹이면 브라우저 콘솔,
앱이면 IDE 로그,
서버면 터미널 로그,
배포면 배포 로그.
```

이 정도만 기억하면 돼.

## 4. 에러를 Claude에게 넘길 때 필요한 것

에러만 던지면 Claude가 추측을 많이 해야 해.

추측이 많아지면 엉뚱한 파일을 고칠 확률도 올라가.

그래서 최소한 이 5가지를 같이 보내면 좋아.

:::steps
1. **내가 하던 작업** — 지금 무엇을 만들거나 고치고 있었는지
2. **기대한 동작** — 원래는 어떻게 돼야 하는지
3. **실제 현상** — 지금은 어떻게 이상하게 동작하는지
4. **에러 로그** — 브라우저 콘솔, 터미널, 배포 로그
5. **수정 범위** — 어디까지 고쳐도 되는지, 건드리면 안 되는 곳은 어딘지
:::

템플릿으로 쓰면 이렇게야.

```text
지금 [무슨 기능]을 만들고 있었어.

기대한 동작:
- [원래 이렇게 돼야 함]

실제 현상:
- [지금 이렇게 됨]

브라우저 콘솔 에러:
[붙여넣기]

터미널/IDE 로그:
[붙여넣기]

요청:
- 원인을 먼저 설명해줘.
- 어떤 파일을 봐야 하는지 알려줘.
- 필요한 최소 범위만 수정해줘.
- 왜 이 에러가 났는지도 초보자 기준으로 설명해줘.
```

이렇게 보내면 Claude가 훨씬 정확하게 고쳐.

## 5. “고쳐줘”만 반복하면 왜 위험해?

Claude에게 “고쳐줘”만 계속 말하면 일단 뭔가를 바꿔.

하지만 문제의 원인을 못 잡은 상태라면 이런 루프가 생길 수 있어.

```text
A 파일 수정
→ 에러가 바뀜
→ B 파일 수정
→ 다른 기능이 깨짐
→ C 파일 수정
→ 처음 에러가 다시 나옴
```

이러면 시간과 토큰을 많이 쓰고도 더 꼬일 수 있어.

그래서 한 번 고친 뒤에는 꼭 물어봐.

```text
왜 이 에러가 난 거야?
방금 수정은 어떤 원리를 고친 거야?
비슷한 문제가 다시 안 나려면 내가 뭘 이해해야 해?
```

이 질문이 중요해.

그냥 고치기만 하면 다음에 같은 문제가 나와도 또 “고쳐줘” 해야 해.

왜 났는지 이해하면 개발 지식이 쌓여.

## 6. 에러는 현상일 수도 있고, 구조 문제의 힌트일 수도 있어

에러 메시지는 보통 지금 터진 현상을 보여줘.

하지만 진짜 원인은 더 앞에 있을 수 있어.

예를 들어.

```text
화면 에러: Cannot read properties of undefined
겉으로 보기엔 화면에서 값이 비어 있는 문제
근본 원인: API 응답 형식이 PRD와 다르거나, 초기 데이터 구조가 안 정해짐
```

```text
에러: 저장이 안 됨
겉으로 보기엔 DB insert 실패
근본 원인: 로그인한 사용자 id가 없거나, 저장해야 할 데이터 정의가 애매함
```

```text
에러: 버튼을 눌러도 반응 없음
겉으로 보기엔 버튼 문제
근본 원인: 클릭 이벤트가 연결되지 않았거나, 버튼이 비활성 상태거나, API 호출이 실패함
```

그래서 Claude에게 이렇게 물어보는 게 좋아.

```text
이 에러가 단순히 이 줄만의 문제인지,
아니면 데이터 흐름이나 구조가 잘못된 신호인지 봐줘.
근본 원인 후보를 3개로 나눠서 설명해줘.
```

이렇게 해야 땜질이 아니라 원인을 볼 수 있어.

## 7. 지금 어디서 무슨 작업을 하다 생겼는지가 중요해

같은 에러라도 상황에 따라 원인이 달라.

예를 들어 `Failed to fetch`라는 에러가 있다고 해보자.

이 에러만 보면 원인이 많아.

```text
API 주소가 틀림
서버가 안 켜져 있음
배포 주소가 다름
환경변수가 빠짐
CORS 문제
네트워크 문제
```

그래서 “무슨 작업 중이었는지”가 중요해.

```text
문의 폼 저장 기능을 붙이는 중이었다
로컬에서는 됐는데 배포 후 안 된다
API 주소를 바꾼 직후부터 안 된다
환경변수를 새로 추가했다
로그인 기능을 붙인 뒤부터 안 된다
```

이 정보가 있어야 Claude가 원인을 좁힐 수 있어.

좋은 질문은 이렇게 생겼어.

```text
피드백 저장 기능을 붙이는 중이었어.
로컬에서는 저장이 되는데, 배포 후에는 저장 버튼을 누르면 Failed to fetch가 떠.
방금 Vercel 환경변수를 추가했어.
브라우저 콘솔 에러는 아래와 같고,
터미널 로그는 없어.
원인을 확인하는 순서를 알려줘.
```

이 정도만 줘도 훨씬 잘 고쳐.

## 8. 에러 로그에서 볼 것 — WHAT / WHERE / WHEN

에러를 읽을 때 처음부터 영어를 다 해석하려고 하지 마.

세 가지만 보면 돼.

```text
WHAT — 무슨 에러 이름인가?
WHERE — 어떤 파일, 어떤 줄인가?
WHEN — 내가 어떤 행동을 했을 때 났나?
```

예를 들어.

```text
TypeError: Cannot read properties of undefined (reading 'map')
    at FeedbackList (FeedbackList.tsx:12:23)
```

이렇게 볼 수 있어.

```text
WHAT: TypeError
WHERE: FeedbackList.tsx 12번째 줄
WHEN: 피드백 목록 화면을 열었을 때
```

해석은 Claude에게 시키면 돼.

```text
이 에러에서 WHAT / WHERE / WHEN을 나눠서 설명해줘.
그리고 초보자 기준으로 왜 이런 에러가 나는지 알려줘.
```

## 9. 자주 만나는 에러를 너무 무서워하지 마

이름만 봐도 겁이 덜 나.

| 에러 | 쉬운 뜻 | 자주 나는 이유 |
| --- | --- | --- |
| `TypeError` | 값의 모양이 예상과 다름 | 아직 데이터가 없는데 읽으려 함 |
| `ReferenceError` | 그런 이름을 못 찾음 | 변수 이름 오타, import 누락 |
| `SyntaxError` | 코드 문법이 틀림 | 괄호, 쉼표, 따옴표 문제 |
| `404` | 주소를 못 찾음 | API 주소나 페이지 경로가 틀림 |
| `401/403` | 권한 문제 | 로그인, API 키, 접근 권한 문제 |
| `500` | 서버 안에서 터짐 | 백엔드 코드, DB, 외부 API 문제 |
| `Failed to fetch` | 요청 실패 | API 주소, 서버 실행, 배포 주소, 네트워크 문제 |

외울 필요는 없어.

“아, 이런 종류가 있구나” 정도면 돼.

에러 이름을 Claude에게 같이 주면 더 빨라.

## 10. 수정 범위를 정해줘

에러를 고칠 때 Claude가 관련 없는 곳까지 바꿔버릴 수 있어.

그래서 범위를 말해줘야 해.

```text
이 에러만 고쳐줘.
디자인은 건드리지 마.
새 라이브러리는 추가하지 마.
기존 동작은 유지해줘.
수정한 파일과 이유를 설명해줘.
```

또는.

```text
일단 원인 분석만 해줘.
아직 코드는 수정하지 마.
```

이 말도 중요해.

바로 수정하기 전에 원인을 먼저 보고 싶을 때가 있거든.

## 11. 3번 시도해도 안 되면 멈춰

같은 에러를 3번 고쳤는데 계속 나면 멈추는 게 좋아.

계속 “다시 고쳐줘”만 하면 코드가 더 꼬일 수 있어.

그럴 때는 이렇게 말해.

```text
이 에러를 3번 고쳤는데 계속 나.
지금까지 어떤 수정이 있었는지 정리해줘.
근본 원인이 뭔지 다시 가설을 세워줘.
마지막으로 잘 되던 commit과 비교해줘.
```

필요하면 되돌려.

```text
마지막으로 정상 동작하던 commit으로 돌아가는 방법을 알려줘.
되돌리면 어떤 변경사항이 사라지는지도 먼저 설명해줘.
```

그래서 기능마다 commit이 중요해.

고치다가 꼬였을 때 돌아갈 지점이 있어야 하니까.

## 12. 디버깅하면서 개발 지식이 쌓여

처음에는 에러가 그냥 무섭게 보여.

그런데 몇 번 고치다 보면 패턴이 보여.

```text
아, 이건 화면에서 값이 비어 있어서 나는 에러구나
아, 이건 API 주소가 틀린 거구나
아, 이건 환경변수를 배포에 안 넣은 거구나
아, 이건 DB 권한 문제일 수 있구나
```

이게 개발 지식이야.

책으로 먼저 외우는 것보다, 내 프로젝트에서 실제로 터진 에러를 보면서 배우는 게 훨씬 잘 남아.

그래서 Claude가 고쳐준 뒤에는 꼭 이렇게 물어봐.

```text
이번 에러에서 내가 배워야 할 개념을 3개만 정리해줘.
다음에 같은 문제가 나면 무엇을 먼저 확인하면 되는지도 알려줘.
```

이렇게 쌓이면 다음부터는 Claude에게 질문하는 수준이 달라져.

## 자주 헷갈리는 포인트

### 에러 메시지가 길어. 다 복사해야 해?

처음에는 통째로 복사해도 돼. 특히 위쪽 첫 에러와 내 파일 이름이 나온 줄은 중요해.

### 브라우저 콘솔, IDE 로그, 터미널 로그를 다 보내야 해?

가능하면 보이는 로그를 다 보내는 게 좋아. 웹이면 브라우저 콘솔, 앱이면 IDE 로그, 서버면 터미널 로그를 보내면 원인을 빨리 좁힐 수 있어.

### 영어로 떠서 읽기 싫어

읽기 싫어도 괜찮아. 그대로 Claude에게 붙여넣고 “초보자 기준으로 해석해줘”라고 하면 돼.

### 에러가 안 나는데 동작이 이상해

그때는 에러 로그보다 현상 설명이 중요해. “원래는 A가 돼야 하는데 지금은 B가 된다”라고 차이를 말해줘.

### Claude가 고쳤는데 또 다른 게 망가졌어

수정 범위가 너무 넓었을 수 있어. “이번 에러와 관련된 파일만 수정해줘”, “기존 동작은 유지해줘”라고 범위를 좁혀.

### 계속 같은 문제로 돈 것 같아

3번 정도 시도했으면 멈추고, 지금까지 수정한 내용을 정리시켜. 필요하면 마지막 정상 commit으로 돌아가.
