## 핵심 요약

**백엔드는 사용자가 보는 화면 뒤에서 일을 처리하는 부분이야. 버튼을 눌렀을 때 입력을 받고, 필요한 처리를 하고, 비밀 키를 숨기고, 결과를 저장하고, 다시 화면에 돌려주는 역할을 해. 코드를 하나도 몰라도 괜찮아. 이 글의 목표는 백엔드 코드를 외우는 게 아니라 “이 기능은 왜 화면만으로 안 되고 뒤에서 처리해야 하지?”를 이해하는 거야.**

[06 프론트엔드 이해](./06-build-frontend)에서는 사용자가 보는 화면과 상태를 봤어.

이제 다음 질문은 이거야.

```text
버튼을 누른 다음에는
뒤에서 어떤 일이 일어나야 하지?
```

예를 들어 서비스마다 이런 일이 있을 수 있어.

```text
문의 폼 → 입력 내용을 이메일이나 DB에 저장
상품 설명 생성기 → 입력값을 받아 외부 API로 결과 생성
예약 서비스 → 가능한 시간 확인 후 예약 저장
피드백 수집 서비스 → 고객 의견 저장 후 목록으로 보기
문서 요약 서비스 → 파일 내용을 읽고 요약 결과 반환
```

사용자는 화면만 보지만, 실제 서비스는 화면 뒤에서 이런 일을 해야 해.

그 부분이 백엔드야.

처음부터 백엔드를 개발자처럼 설계하려고 하지 않아도 돼.

AI에게 이렇게 시작하면 돼.

```text
이 PRD를 기준으로
백엔드에서 처리해야 하는 일을 먼저 정리해줘.
나는 코드를 잘 모르니까
화면에서 처리해도 되는 일과
서버에서 처리해야 하는 일을 나눠서 설명해줘.
```

## 1. 백엔드는 “뒤에서 처리하는 곳”이야

프론트엔드는 사용자가 보는 곳이야.

백엔드는 사용자가 직접 보지는 않지만, 뒤에서 처리하는 곳이야.

식당으로 비유하면 쉬워.

```text
프론트엔드 = 손님이 보는 홀
백엔드 = 주문을 처리하고 음식을 만드는 주방
```

손님은 메뉴판을 보고 주문해. 하지만 음식은 주방에서 만들어져.

서비스도 비슷해.

```text
사용자는 화면에서 입력한다
버튼을 누른다
결과를 본다
```

그 사이에 백엔드가 이런 일을 할 수 있어.

```text
입력값 받기
입력값이 이상하지 않은지 확인하기
외부 서비스에 요청하기
비밀 키 숨기기
DB에 저장하기
저장된 데이터 다시 불러오기
결과를 화면에 돌려주기
```

처음에는 이 한 줄만 기억해도 돼.

```text
사용자가 보는 건 프론트엔드,
사용자 몰래 뒤에서 처리하는 건 백엔드.
```

## 2. 화면만으로 되는 일과 백엔드가 필요한 일

모든 기능에 백엔드가 필요한 건 아니야.

처음 MVP에서는 화면만으로도 충분한 일이 많아.

| 기능 | 프론트엔드만으로 가능? | 백엔드가 필요한 순간 |
| --- | --- | --- |
| 소개 페이지 보여주기 | 가능 | 관리자에서 내용을 바꿔야 할 때 |
| 버튼 누르면 샘플 결과 보여주기 | 가능 | 진짜 결과를 외부 API로 만들어야 할 때 |
| 계산기 | 대부분 가능 | 계산 기록을 저장하거나 공유해야 할 때 |
| 피드백 폼 | 화면은 가능 | 제출 내용을 저장해야 할 때 |
| 로그인 | 어려움 | 사용자별 데이터가 필요할 때 |
| 결제 | 백엔드 필요 | 결제 검증과 보안 처리가 필요할 때 |

처음에는 이렇게 나눠서 생각하면 돼.

```text
보여주기만 한다 → 프론트엔드
비밀 키가 필요하다 → 백엔드
저장해야 한다 → DB
사람마다 다르게 보여줘야 한다 → 백엔드 + DB
돈이 오간다 → 백엔드 필수
```

이걸 네가 처음부터 완벽히 판단할 필요는 없어.

AI에게 물어보면 돼.

```text
이 기능은 프론트엔드만으로 가능해?
아니면 백엔드가 필요해?
필요하다면 이유를 초보자도 이해하게 설명해줘.
지금 MVP에서는 빼도 되는 백엔드 기능도 알려줘.
```

## 3. 백엔드의 기본 흐름은 단순해

백엔드라고 하면 복잡해 보이지만, 기본 흐름은 거의 비슷해.

:::canvas-flow
{
  "nodes": [
    { "id": "input", "label": "입력 받기\n사용자 요청", "col": 0, "row": 0, "type": "default" },
    { "id": "check", "label": "검사하기\n비어있나? 권한 있나?", "col": 1, "row": 0, "type": "process" },
    { "id": "work", "label": "처리하기\n계산·외부 API·업무 로직", "col": 2, "row": 0, "type": "process" },
    { "id": "save", "label": "저장/조회\n필요하면 DB", "col": 3, "row": 0, "type": "warning" },
    { "id": "result", "label": "응답하기\n화면에 결과 전달", "col": 4, "row": 0, "type": "success" }
  ],
  "edges": [
    { "from": "input", "to": "check" },
    { "from": "check", "to": "work" },
    { "from": "work", "to": "save" },
    { "from": "save", "to": "result" }
  ],
  "direction": "LR",
  "cols": 5,
  "rows": 1
}
:::

대부분의 백엔드 기능은 이 흐름 안에 있어.

```text
문의하기 버튼 클릭
→ 이름/이메일/문의 내용 받기
→ 비어 있는 값이 없는지 확인
→ DB에 저장하거나 이메일 보내기
→ “문의가 접수됐어요”라고 화면에 알려주기
```

```text
상품 설명 생성 버튼 클릭
→ 상품명과 특징 받기
→ 너무 짧거나 비어 있는지 확인
→ 외부 API로 설명 생성
→ 결과를 화면에 보여주기
→ 필요하면 생성 기록 저장
```

```text
예약 버튼 클릭
→ 날짜와 시간 받기
→ 이미 예약된 시간인지 확인
→ 예약 정보 저장
→ 예약 완료 메시지 돌려주기
```

코드를 몰라도 이 흐름은 이해할 수 있어야 해.

그래야 AI가 만든 코드가 어디쯤을 담당하는지 볼 수 있어.

## 4. 백엔드 요청은 이렇게 시작하면 돼

백엔드를 시킬 때 처음부터 개발 용어를 많이 쓰지 않아도 돼.

좋은 시작은 이거야.

```text
이 PRD를 기준으로 백엔드에서 필요한 기능을 정리해줘.

각 기능을 아래처럼 나눠줘.
- 사용자가 화면에서 하는 행동
- 백엔드가 받아야 하는 데이터
- 백엔드가 처리해야 하는 일
- 저장이 필요한지 여부
- 화면에 돌려줘야 하는 결과

나는 코드를 잘 모르니까 초보자 기준으로 설명해줘.
```

그다음 이렇게 만들면 돼.

```text
위에서 정리한 백엔드 기능 중
MVP에 꼭 필요한 것부터 하나씩 만들어줘.

한 번에 다 만들지 말고,
첫 번째 기능이 브라우저에서 확인될 때마다 멈춰서 설명해줘.
```

이게 중요해.

백엔드는 화면보다 눈에 안 보여서, 한 번에 많이 만들면 어디서 망가졌는지 알기 어려워.

그래서 **하나 만들고 확인, 하나 만들고 확인**으로 가야 해.

## 5. API는 화면과 백엔드가 말하는 창구야

API라는 말이 자주 나와.

너무 어렵게 생각하지 않아도 돼.

API는 화면이 백엔드에게 부탁하는 창구야.

```text
화면: 이 문의 내용을 저장해줘
백엔드: 알겠어. 저장하고 결과를 알려줄게
```

웹 프로젝트에서는 보통 이런 주소처럼 보일 수 있어.

```text
/api/contact
/api/generate
/api/save-feedback
/api/reservations
```

이 주소를 외울 필요는 없어.

그냥 이렇게 이해하면 돼.

```text
/api/... = 화면이 백엔드에게 부탁하는 문
```

AI가 백엔드 코드를 만들었다면 이렇게 물어봐.

```text
이번에 만든 API 목록을 정리해줘.
각 API마다
1. 화면에서 언제 호출되는지
2. 어떤 데이터를 받는지
3. 어떤 일을 하는지
4. 화면에 무엇을 돌려주는지
표로 설명해줘.
```

## 6. 비밀값은 백엔드에서 다뤄야 해

서비스를 만들다 보면 API 키라는 말이 나와.

API 키는 비밀번호 같은 거야.

```text
외부 AI 서비스 키
결제 API 키
이메일 발송 서비스 키
지도 API 키
관리자용 비밀 키
```

이런 값은 화면 코드에 넣으면 안 돼.

브라우저에서 돌아가는 코드는 사용자가 볼 수 있기 때문이야.

```text
❌ 화면 코드에 비밀 키 넣기
✅ 백엔드에서 비밀 키 사용하기
```

초보자는 이 기준만 기억하면 돼.

```text
고객에게 보여줘도 되는 것 → 프론트엔드
고객에게 보여주면 안 되는 것 → 백엔드
```

AI에게는 이렇게 검사시켜.

```text
이 프로젝트에 비밀 키가 들어가는 부분이 있는지 확인해줘.
브라우저에 노출되면 안 되는 값은 무엇인지 알려줘.
그 값들이 서버에서만 사용되는지 검사해줘.
```

`.env.local`, 환경변수 같은 말이 나올 수 있어.

처음에는 “비밀 값을 따로 숨겨두는 방법” 정도로 이해하면 돼.

## 7. 외부 API는 “다른 서비스에게 부탁하기”야

백엔드는 외부 서비스와 연결될 때도 많아.

예를 들어.

```text
LLM API → 글 생성, 요약, 대화 답변
결제 API → 결제 승인, 결제 취소
이메일 API → 가입 메일, 문의 접수 메일 발송
지도 API → 주소 검색, 거리 계산
번역 API → 문장 번역
```

이런 외부 API를 화면에서 직접 호출하면 위험하거나 불편한 경우가 많아.

그래서 보통 백엔드가 대신 호출해.

```text
화면 → 내 백엔드 → 외부 API → 내 백엔드 → 화면
```

AI에게는 이렇게 물어봐.

```text
이 기능에서 외부 API가 필요한지 판단해줘.
필요하다면 왜 프론트엔드가 아니라 백엔드에서 호출해야 하는지 설명해줘.
API 키가 필요한지도 확인해줘.
```

LLM API도 여기 안에 들어가는 한 종류일 뿐이야.

백엔드 전체를 LLM API로 이해하면 안 돼.

LLM API는 여러 외부 API 중 하나야.

## 8. DB는 “나중에 다시 볼 데이터”가 있을 때 붙여

DB는 데이터를 저장하는 곳이야.

하지만 처음부터 무조건 붙일 필요는 없어.

이 기준으로 보면 돼.

```text
새로고침하면 사라져도 괜찮다 → DB 없어도 됨
나중에 다시 봐야 한다 → DB 필요
여러 사람이 각자 자기 기록을 봐야 한다 → DB 필요
운영자가 고객 반응을 분석해야 한다 → DB 필요
```

예를 들어.

| 서비스 | 저장할 수 있는 데이터 |
| --- | --- |
| 문의 폼 | 이름, 이메일, 문의 내용, 접수 시간 |
| 피드백 수집 | 평점, 의견, 불편한 점 |
| 예약 서비스 | 예약자, 날짜, 시간, 상태 |
| 생성 도구 | 입력값, 생성 결과, 생성 시간 |
| 학습 서비스 | 완료한 콘텐츠, 점수, 진행률 |

DB가 필요해 보이면 AI에게 먼저 정리시켜.

```text
이 PRD에서 저장해야 하는 데이터를 찾아줘.
MVP에 꼭 필요한 데이터와 나중에 저장해도 되는 데이터를 나눠줘.
DB가 지금 꼭 필요한지도 판단해줘.
```

여기서 중요한 건 DB 기술 이름이 아니야.

**무엇을 저장해야 하는지**가 먼저야.

## 9. 만들어진 소스를 보는 순서

AI가 백엔드 코드를 만들었다면 바로 다음 기능을 붙이지 마.

먼저 소스를 설명받아야 해.

```text
방금 만든 백엔드 소스를 초보자 기준으로 설명해줘.

순서는 이렇게 해줘.
1. 화면에서 백엔드를 호출하는 부분
2. 백엔드가 요청을 받는 파일
3. 입력값을 확인하는 부분
4. 외부 API를 호출하는 부분이 있다면 그 부분
5. DB에 저장하거나 불러오는 부분이 있다면 그 부분
6. 화면에 결과를 돌려주는 부분

각 파일마다 “이 파일은 한 줄로 뭐 하는 파일인지” 먼저 설명해줘.
```

목표는 코드를 다 외우는 게 아니야.

역할을 잡는 거야.

```text
아, 이 파일은 화면에서 백엔드로 요청을 보내는구나.
아, 이 파일은 백엔드가 요청을 받는구나.
아, 이 부분은 비어 있는 입력을 막는구나.
아, 이 부분은 외부 API를 부르는구나.
아, 이 부분은 DB에 저장하는구나.
```

이 정도면 충분해.

## 10. CRUD는 서비스의 기본 동작이야

CRUD라는 말도 자주 나와.

처음 보면 어려워 보이지만, 그냥 서비스의 기본 행동이야.

| 용어 | 쉬운 말 | 예시 |
| --- | --- | --- |
| Create | 만들기 | 문의 등록, 예약 생성, 피드백 저장 |
| Read | 읽기 | 문의 목록 보기, 예약 확인, 피드백 목록 보기 |
| Update | 고치기 | 예약 시간 변경, 상태 수정 |
| Delete | 지우기 | 기록 삭제, 예약 취소 |

처음 MVP에서는 전부 필요하지 않을 수 있어.

```text
문의 폼 MVP → Create만 있어도 시작 가능
피드백 목록 → Create + Read 필요
예약 서비스 → Create + Read + Update 필요할 수 있음
관리자 기능 → Read + Update + Delete가 필요할 수 있음
```

AI에게는 이렇게 말하면 돼.

```text
이 MVP에서 필요한 CRUD를 최소로 나눠줘.
처음 버전에 꼭 필요한 것과 나중에 해도 되는 것을 구분해줘.
각각 사용자가 어떤 화면에서 하게 되는지도 설명해줘.
```

## 11. 검증은 화면과 데이터로 확인해

백엔드는 눈에 안 보이기 때문에 검증이 중요해.

코드는 AI가 만들어줘도 확인은 네가 해야 해.

:::steps
1. 화면에서 버튼을 눌러봐. 결과가 돌아오나?
2. 일부러 빈 값을 넣어봐. 이상한 값이 막히나?
3. 저장 기능이 있다면 새로고침 후에도 남아 있나?
4. 목록 기능이 있다면 저장된 데이터가 다시 보이나?
5. 비밀 키가 화면 코드에 노출되지 않았는지 AI에게 검사시켜봐.
:::

문제가 생기면 이렇게 말하면 돼.

```text
버튼을 눌렀는데 결과가 안 나와.
화면 문제인지, 백엔드 문제인지, 외부 API 문제인지 구분하는 순서를 알려줘.
내가 확인해야 할 파일과 로그도 알려줘.
```

또는 이렇게.

```text
저장은 되는 것 같은데 화면에 다시 안 보여.
DB 저장 문제인지, 불러오기 문제인지 구분해줘.
초보자 기준으로 확인 순서를 알려줘.
```

문제를 직접 다 고칠 필요는 없어.

중요한 건 증상을 정확히 말하고, 확인 순서를 받는 거야.

## 12. 한 입 끝나면 저장

백엔드 기능은 한 번 망가지면 어디서 깨졌는지 찾기 어려울 수 있어.

그래서 작은 기능 하나가 끝날 때마다 저장해둬야 해.

```text
문의 저장 기능이 정상 동작하는 것까지 확인했어.
문제 없으면 git commit 해줘.
메시지는 "문의 저장 백엔드 추가"로 해줘.
```

또는.

```text
외부 API 호출 결과가 화면에 나오는 것까지 확인했어.
git commit 해줘.
메시지는 "외부 API 연결 추가"로 해줘.
```

이렇게 해야 다음 기능 만들다가 망가져도 돌아갈 수 있어.

## 자주 헷갈리는 포인트

### 백엔드는 꼭 있어야 해?

아니야. 보여주기식 MVP나 계산기처럼 저장과 비밀 키가 없는 기능은 프론트엔드만으로도 시작할 수 있어.

### 백엔드랑 DB는 같은 거야?

아니야. 백엔드는 뒤에서 처리하는 코드고, DB는 데이터를 저장하는 곳이야. 백엔드가 DB에 저장하거나 DB에서 꺼내오는 일을 해.

### API랑 백엔드는 같은 거야?

완전히 같지는 않아. API는 화면이 백엔드에게 부탁하는 창구야. 백엔드는 그 요청을 받아 처리하는 곳이고.

### LLM API가 백엔드야?

아니야. LLM API는 외부 API 중 하나야. 백엔드는 LLM API, 결제 API, 이메일 API 같은 외부 서비스를 대신 호출할 수 있어.

### API 키를 localStorage에 저장하면 안 돼?

안 돼. 브라우저에 저장되는 값은 사용자가 볼 수 있어. 비밀 키는 백엔드에서만 다루는 게 안전해.

### DB는 꼭 지금 붙여야 해?

아니야. 고객에게 첫 반응만 볼 거라면 DB 없이 시작해도 돼. 나중에 다시 볼 기록이 필요해졌을 때 붙여도 돼.

### RLS 같은 보안 용어가 나오면 어떻게 해?

처음부터 외울 필요 없어. “DB에서 남의 데이터를 못 보게 막는 규칙” 정도로 이해하면 돼. AI에게 내 서비스 예시로 설명해달라고 하면 돼.

### 새 기능 만들다 망가지면?

git으로 잘 되던 시점으로 되돌리면 돼. 그래서 기능마다 commit이 중요해.
