## 핵심 요약

**서비스 만들기는 "만들어줘" 한마디로 끝나는 일이 아니야. 아이디어를 가설로 세우고, 작게 만들고, 배포하고, 고객 피드백으로 다시 다듬는 과정이야.**

자동화 입문에서는 반복 업무를 문서와 담당자 흐름으로 나누는 법을 봤지.

그런데 자동화를 제대로 굴리려면 여기서 한 단계가 더 필요해. 파일을 읽고, 데이터를 가져오고, 화면을 만들고, 버튼을 붙이고, 결과를 저장하고, 배포하는 감각이 있어야 하거든.

그래서 이제 서비스를 하나 만들어보자.

목표는 대단한 서비스를 한 번에 완성하는 게 아니야. **내 아이디어가 실제 고객에게도 의미 있는지 빠르게 확인하는 것**이야.

## 왜 서비스 만들기를 해보냐면

자동화를 하려면 결국 작은 서비스 하나가 어떻게 돌아가는지 알아야 해.

아직은 이런 게 낯설 수 있거든.

- 사용자가 뭘 입력해야 하는지
- 결과가 어디에 저장돼야 하는지
- 버튼을 누르면 어떤 일이 일어나야 하는지
- 에러가 나면 어디를 봐야 하는지
- 만든 걸 다른 사람에게 어떻게 보여줘야 하는지
- 피드백을 받으면 어디를 고쳐야 하는지

서비스를 한 번 만들어보면 이 감각이 생겨.

자동화도 사실 작은 서비스랑 비슷해. 누군가 입력을 넣고, Claude나 코드가 처리하고, 결과가 나오고, 사람이 확인하잖아.

그러니까 지금 목표는 대단한 서비스를 만드는 게 아니야. **서비스가 만들어지고, 고객 반응으로 다시 바뀌는 흐름을 한 번 몸으로 보는 것**이야.

## "만들어줘"만 치면 왜 안 될까?

Claude에게 이렇게 말할 수는 있어.

```text
블로그 자동화 웹서비스 만들어줘.
```

그러면 뭐가 나오긴 해.

근데 곧 이런 일이 생겨.

- 왜 이 기술을 골랐는지 모르겠다
- 내가 원한 글쓰기 흐름이 아니다
- 고치려고 했더니 다른 데가 망가진다
- 배포하려니까 어디서부터 해야 할지 모르겠다
- 사람에게 보여줬더니 누구를 위한 서비스인지 애매하다
- 피드백을 받았는데 무엇을 반영해야 할지 모르겠다

Claude가 못해서가 아니야.

처음에 방향을 안 잡았기 때문이야.

서비스 만들기는 Claude에게 코드를 던져놓는 시간이 아니야. 내가 가설을 세우고, Claude에게 시키고, 결과를 보고, 고객 피드백을 받아 다시 고치는 순서를 배우는 시간이야.

## 여기서 목표는 하나야

완벽한 서비스를 만드는 게 목표가 아니야.

**가설을 세우고, 만들어보고, 배포하고, 피드백받고, 다시 의견을 반영하는 흐름을 끝까지 한 번 해보는 것.**

만들고 싶은 아이디어가 있다면, 일단 **가설**로 바꿔서 시작해보면 돼.

예를 들면 이런 식이야.

```text
이런 사람이 이런 문제를 겪고 있을 것 같아.
이 기능을 만들면 그 문제가 조금은 줄어들 것 같아.
그래서 이 사람은 계속 써보거나, 주변 사람에게 추천할 수도 있을 것 같아.
```

중요한 건 이게 정답이 아니라는 점이야. 어디까지나 가설이야. 틀릴 수도 있고, 맞을 수도 있어.

그래서 서비스 만들기는 "내 생각이 맞다"를 증명하는 일이 아니야. **고객을 더 이해하고, 내 제품에 맞는 고객을 탐색하는 과정**이야.

예전에는 이 가설 하나를 확인하려면 6개월씩 걸렸어. 기획하고, 개발자 구하고, 외주 맡기고, 화면 만들고, 배포하고, 사람에게 보여주는 데 시간이 너무 많이 들었거든.

그런데 지금은 AI 덕분에 그 주기가 1주일 정도로 줄었어. 가설을 세우고, 작게 만들고, 배포하고, 피드백을 받고, 다시 의견을 반영하는 일을 훨씬 빠르게 반복할 수 있게 됐어.

그러니까 처음부터 완벽한 아이디어를 찾으려고 멈춰 있지 않아도 돼. **가설을 하나 세우고, Claude와 같이 작게 만들어서 고객 앞에 놓아보는 것.** 그게 이 파트에서 해볼 일이야.

서비스 만들기는 코드를 배우는 시간이 아니야. **내가 가진 가설로 고객을 더 이해하고, 내 제품에 맞는 고객을 찾아가는 시간**이야.
