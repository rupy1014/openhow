## 핵심 요약

**AI 시대의 서비스 만들기는 “AI에게 한 번에 만들어달라고 하기”가 아니라, 린 스타트업의 실험 주기를 빠르게 돌리는 일이야.**

이 파트의 큰 흐름은 이거야.

```text
고객 가설 → MVP 범위 → AI와 구현 → Git 저장 → 배포 → 피드백 → 다음 가설
```

예전에는 이 한 바퀴를 도는 데 몇 달이 걸렸어. 기획하고, 개발자를 구하고, 외주를 맡기고, 화면을 만들고, 배포하고, 사람에게 보여주는 시간이 길었거든.

지금은 AI 덕분에 훨씬 빨라졌어. 그래서 더 중요한 건 코드를 많이 아는 게 아니라, **무엇을 검증할지 작게 정하고, AI를 써서 빠르게 고객 앞에 놓는 감각**이야.

이 파트는 프론트엔드나 백엔드를 따로 외우는 수업이 아니야. 먼저 **AI 시대의 린 스타트업 흐름**을 잡고, 그 흐름을 실제로 돌리기 위해 필요한 도구로 [기술·구조](./04-tech), [프론트·백엔드](./05-build-frontend), [Git](./06-git), [배포](./08-deploy), [피드백](./09-feedback)을 다뤄.

## 먼저 기술보다 실험 흐름을 잡아

초보자가 가장 자주 빠지는 함정은 이거야.

```text
아이디어가 떠올랐다
→ AI에게 전체 서비스를 만들어달라고 한다
→ 뭔가 나왔다
→ 누구를 위한 건지, 어디부터 고쳐야 할지 모른다
```

AI가 못해서가 아니야. 처음에 실험을 좁히지 않았기 때문이야.

서비스 만들기는 “내 생각이 맞다”를 증명하는 일이 아니야. **고객을 더 이해하기 위해 작은 실험을 반복하는 일**이야.

그래서 순서는 이렇게 바뀌어야 해.

```text
먼저 고객과 문제를 좁힌다.
그다음 검증에 필요한 만큼만 만든다.
그리고 고객 반응으로 다음 결정을 한다.
```

AI가 강해질수록 많이 만드는 건 쉬워져. 대신 더 중요해지는 건 이 질문들이야.

- 지금 확인하려는 고객은 누구야?
- 그 고객의 어떤 문제를 줄이려는 거야?
- 첫 버전에 꼭 필요한 기능은 뭐야?
- 지금 안 만들어도 되는 건 뭐야?
- 고객 반응을 어디서, 어떻게 받을 거야?

## AI 시대의 린 스타트업 루프

이 파트에서 반복해서 보게 될 기본 루프는 이거야.

1. **고객 가설** — [아이디어 찾기](./01-idea)에서 “이런 사람이 이런 문제를 겪을 것 같다”를 좁힌다.
2. **MVP 기획** — [바이브 기획](./02-lean-plan)과 [PRD 작성법](./03-prd)으로 만들 범위와 검증 기준을 적는다.
3. **기술·구조 판단** — [기술 선택과 구조 잡기](./04-tech)에서 프론트만으로 될지, 서버·API·DB가 필요한지 판단한다.
4. **구현 이해** — [프론트엔드와 백엔드 이해](./05-build-frontend)에서 고객이 보는 화면과 뒤에서 처리되는 일을 함께 본다.
5. **저장과 복구** — [Git](./06-git)으로 “여기까지 정상” 지점을 남긴다.
6. **수정과 배포** — [고치는 법](./07-fix)으로 에러를 다루고, [배포](./08-deploy)로 URL을 만든다.
7. **고객 피드백** — [피드백과 검증](./09-feedback)으로 실제 반응을 보고, [PMF 찾기](./10-pmf)에서 다음 방향을 좁힌다.
8. **모객과 첫 결제** — [모객](./11-distribution)으로 모르는 고객을 데려오고, [첫 결제와 PG 연동](./12-pg-bootpay)으로 가격을 정해 돈을 받아본다.

여기서 핵심은 완성도가 아니야. **학습 속도**야.

첫 버전은 어설퍼도 괜찮아. 다만 무엇을 확인하려는 버전인지는 분명해야 해. 그래야 AI에게도 정확히 시킬 수 있고, 고객 반응도 제대로 해석할 수 있어.

## 기술은 목적이 아니라 실험 장비야

이 시리즈에는 PRD, 기술 선택, 프론트엔드, 백엔드, Git, 배포 같은 말이 나와.

하지만 이걸 개발자 시험 범위처럼 외우려는 게 아니야. 각각은 린 스타트업 루프를 돌리기 위한 장비야.

| 장비 | 왜 필요한가 | 바로 보기 |
| --- | --- | --- |
| 고객 가설 | 누구의 어떤 문제를 볼지 정한다 | [아이디어 찾기](./01-idea) |
| PRD | AI와 같은 목표·범위·검증 기준을 공유한다 | [PRD 작성법](./03-prd) |
| 기술·구조 | 이번 MVP에 필요한 만큼만 만든다 | [기술 선택과 구조 잡기](./04-tech) |
| 프론트·백엔드 | 화면과 화면 뒤 처리를 구분한다 | [프론트엔드와 백엔드 이해](./05-build-frontend) |
| Git | 망가져도 되돌아갈 저장 지점을 만든다 | [Git](./06-git) |
| 디버깅 | AI가 만든 결과를 고객에게 보여줄 수 있게 다듬는다 | [고치는 법](./07-fix) |
| 배포 | 내 컴퓨터 밖으로 꺼내 URL로 보여준다 | [배포](./08-deploy) |
| 피드백 | 고객 반응으로 다음 선택을 정한다 | [피드백과 검증](./09-feedback) |
| 모객 | 모르는 고객을 채널에서 데려온다 | [모객](./11-distribution) |
| 결제·PG | 가격을 정해 링크로 받다가, 팔리면 PG를 붙인다 | [첫 결제와 PG 연동](./12-pg-bootpay) |

그러니까 [기술 선택과 구조 잡기](./04-tech)를 읽을 때도 “무슨 스택이 좋은가”만 보는 게 아니야. **이번 실험에서 어디까지 만들면 충분한가**를 보는 거야.

[Git](./06-git)을 읽을 때도 명령어를 외우는 게 아니야. **AI와 빠르게 실험하다가 망가졌을 때 다시 돌아올 수 있는 안전장치**를 배우는 거야.

## 여기서 목표는 하나야

완벽한 서비스를 만드는 게 목표가 아니야.

**AI를 써서 린 스타트업의 한 바퀴를 끝까지 돌려보는 것.**

즉, 이런 문장을 실제 행동으로 바꾸는 거야.

```text
이런 사람이 이런 문제를 겪고 있을 것 같아.
이 작은 기능을 보여주면 그 문제가 조금 줄어드는지 확인할 수 있어.
그래서 이번 주에는 이 범위까지만 만들고, 5명에게 보여본 뒤 다시 판단할 거야.
```

중요한 건 처음 가설이 틀릴 수도 있다는 점이야. 오히려 틀렸다는 걸 빨리 알면 좋아. AI가 만들어주는 속도가 빠르기 때문에, 틀린 방향으로 오래 가는 것보다 작게 만들고 빨리 배우는 편이 훨씬 낫거든.

그러니까 이 파트에서 기술은 주인공이 아니야. 주인공은 **고객 가설, 작은 MVP, 실제 피드백, 그리고 다음 선택**이야.

Claude는 그 루프를 빠르게 돌리기 위한 강력한 도구고, Git·프론트엔드·백엔드·배포는 그 도구를 안전하게 쓰기 위한 최소한의 장비야.

이제 먼저 아이디어를 거창한 서비스명이 아니라 [검증 가능한 고객 가설](./01-idea)로 바꾸는 것부터 시작해보자.
