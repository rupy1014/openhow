## 핵심 요약

**코드를 몰라도 기술 선택은 해야 해. 그런데 겁먹을 필요 없어. 처음 MVP에서는 프론트에 다 넣고 보여주기식으로 검증해도 돼. 그 자체도 기술 선택이야. 중요한 건 “지금 고객 반응을 빨리 볼 건지”, “API 키를 숨겨야 하는지”, “데이터를 저장해야 하는지”, “사용자가 늘면 비용이 생기는지”를 구분하는 거야. 정답 스택은 없어. 지금 상황에 맞는 선택만 있어.**

PRD를 만들고 나면 갑자기 이런 말이 나와.

```text
HTML로 할까요?
Next.js로 할까요?
DB는 붙일까요?
API Route가 필요할까요?
Supabase를 쓸까요?
```

코드 모르는 사람 입장에서는 여기서 막혀.

“뭐가 좋은 건데?”

근데 기술 선택을 개발자처럼 깊게 할 필요는 없어. 처음에는 이렇게만 생각해도 돼.

```text
그냥 보여주기만 하면 되나?
비밀 키를 숨겨야 하나?
데이터를 저장해야 하나?
사람마다 다르게 보여줘야 하나?
사용자가 늘면 비용이 나올까?
```

이 질문에 답하면 방향이 잡혀.

## 기술 선택은 도구 이름 맞히기가 아니야

기술 선택이라고 하면 뭔가 어려워 보여.

```text
React
Next.js
Supabase
Firebase
PostgreSQL
API Route
Serverless
```

이런 말이 나오니까 겁나지.

근데 처음에는 도구 이름보다 목적이 먼저야.

예를 들어.

```text
나는 지금 화면만 보여주고 싶은가?
나는 버튼을 누르면 결과가 나오는 척만 해도 되는가?
나는 진짜 AI를 호출해야 하는가?
나는 고객이 남긴 내용을 저장해야 하는가?
나는 사용자별로 데이터를 나눠야 하는가?
```

이 목적에 따라 기술이 따라오는 거야.

그러니까 “무슨 기술이 좋아?”보다 이 질문이 먼저야.

```text
이번 MVP에서 꼭 필요한 동작이 뭐야?
```

처음부터 오른쪽 끝까지 갈 필요 없어.

처음에는 대부분 왼쪽에서 시작해.

```text

→ 저장이 필요하면 DB를 붙인다
→ 사용자별 관리가 필요하면 로그인을 붙인다
→ 사용자가 늘면 비용과 운영을 본다
```

이게 자연스러워.

## 1. 프론트에 다 넣고 시작해도 돼

프론트는 사용자가 보는 화면이야.

처음에는 화면에 필요한 내용을 그냥 다 넣고 시작해도 돼.

예를 들어 영어 문장 MVP라면.

```text
오늘의 문장 1개
한국어 뜻
짧은 해설
완료 버튼
```

이걸 전부 화면 코드 안에 넣어도 돼.

DB도 없고, 로그인도 없고, 서버도 없어.

그래도 고객에게 보여줄 수 있어.

```text
이 화면 이해돼?
출근길에 이 정도면 볼 것 같아?
완료 버튼 누르고 싶어?
내일 다시 들어올 것 같아?
```

이걸 확인하는 게 목적이면 프론트 중심으로 충분해.

이건 나쁜 구조가 아니야. **처음 가설을 빨리 확인하기 위한 선택**이야.

## 2. 보여주기식 MVP도 배울 수 있어

처음 MVP가 꼭 진짜 기능을 다 갖춰야 하는 건 아니야.

상품 설명 생성기를 만든다고 해보자.

처음부터 AI API를 붙이지 않아도 이런 식으로 검증할 수 있어.

```text
상품명을 입력한다
미리 준비한 예시 결과를 보여준다
고객이 “이 정도 결과면 써보고 싶다”고 말하는지 본다
```

이걸로도 배울 수 있어.

고객이 “별로 필요 없는데?”라고 하면 API를 붙일 필요도 없을 수 있어.

반대로 고객이 반응하면 그때 진짜 AI API를 붙이면 돼.

```text
가짜 결과로 반응 확인
→ 반응 있으면 진짜 API 연결
→ 저장이 필요하면 DB 추가
→ 반복 사용자가 생기면 로그인 검토
```

처음부터 다 만드는 게 성실한 게 아니야. **배울 수 있는 최소한만 만드는 게 더 좋은 선택일 수 있어.**

## 3. 프론트만으로 가면 안 되는 경우

프론트 중심으로 시작해도 되지만, 안 되는 경우도 있어.

특히 비밀 값이 있으면 조심해야 해.

```text
OpenAI API 키
OpenRouter API 키
결제 API 키
관리자 비밀번호
```

이런 값은 브라우저에 들어가면 노출될 수 있어.

그래서 이런 경우에는 서버가 필요해.

```text
AI API를 진짜 호출해야 한다
결제를 붙인다
관리자만 볼 수 있는 정보가 있다
외부 서비스의 비밀 키를 써야 한다
```

쉽게 말하면 이거야.

```text
보여줘도 되는 것 → 프론트
숨겨야 하는 것 → 서버
저장해야 하는 것 → DB
사람마다 나눠야 하는 것 → 로그인
```

이 기준만 알아도 충분해.

## 4. DB는 “나중에 다시 볼 데이터”가 있을 때

DB는 데이터를 저장하는 곳이야.

처음부터 무조건 붙일 필요 없어.

이런 경우에는 DB 없이 시작해도 돼.

```text
새로고침하면 사라져도 괜찮아
한 번 보여주고 반응만 보면 돼
사용자별 기록이 필요 없어
피드백은 구글폼으로 받을 거야
```

반대로 이런 경우에는 DB가 필요해.

```text
사용자가 만든 결과를 다시 보여줘야 해
사용 기록을 보고 싶어
피드백을 서비스 안에 저장하고 싶어
여러 사람이 같은 데이터를 봐야 해
```

DB를 붙이면 할 수 있는 게 많아지지만, 설정과 에러도 늘어나.

그래서 처음에는 이렇게 생각하면 돼.

```text
저장하지 않아도 배울 수 있으면 DB 없이 시작
저장해야만 배울 수 있으면 DB 붙이기
```

## 5. 상황별 선택은 이렇게 해

| 상황 | 선택 | 이유 |
| --- | --- | --- |
| 랜딩페이지, 포트폴리오 | 프론트만 | 보여주기만 하면 됨 |
| 화면 흐름 확인 | 프론트 중심 MVP | 저장 없이 반응 확인 가능 |
| 가짜 결과로 반응 보기 | 프론트 + 샘플 데이터 | API 붙이기 전 검증 가능 |
| 진짜 AI 호출 | 서버/API 필요 | API 키를 숨겨야 함 |
| 결과 저장 | DB 필요 | 나중에 다시 볼 데이터가 있음 |
| 사용자별 기록 | 로그인/인증 필요 | 사람마다 데이터를 나눠야 함 |
| 사용자가 늘어남 | 비용 검토 | API, DB, 배포 비용이 생김 |

처음에는 제일 단순한 선택부터 봐.

그리고 안 되는 이유가 생기면 하나씩 붙여.

```text
프론트로 충분해? → 프론트로 시작
API 키를 숨겨야 해? → 서버 추가
저장해야 해? → DB 추가
사람마다 달라야 해? → 로그인 추가
비용이 커져? → 사용량과 요금 확인
```

## 6. AI에게 물어볼 때도 쉽게 물어봐

AI에게 이렇게 물으면 어려운 답이 나올 수 있어.

```text
이 서비스에 가장 적합한 기술 스택 추천해줘.
```

그러면 갑자기 어려운 말이 쏟아질 수 있어.

대신 이렇게 물어봐.

```text
나는 코드를 잘 몰라.
이 PRD를 만들 때 기술 선택을 쉬운 순서로 알려줘.

1. 프론트만으로 보여주는 방법
2. 서버가 필요한 경우
3. DB가 필요한 경우
4. 로그인이 필요한 경우
5. 나중에 비용을 봐야 하는 경우

각 경우에 무엇을 할 수 있고,
무엇을 포기하는지 쉽게 설명해줘.
아직 코드는 짜지 마.
```

이렇게 물어보면 AI가 “초보자가 감당 가능한 선택지”로 설명해줄 가능성이 높아.

## 7. 비용은 언제 고민해?

처음부터 비용 최적화에 빠질 필요는 없어.

고객 5명에게 보여주는 MVP라면 비용보다 속도가 중요해.

하지만 사용자가 늘면 달라져.

```text
AI API를 많이 호출하면 비용이 나온다
이미지를 많이 생성하면 비용이 커진다
DB 저장량이 늘면 요금제가 바뀐다
트래픽이 늘면 배포 비용을 봐야 한다
로그를 많이 쌓으면 저장 비용도 생긴다
```

그래서 이렇게 보면 돼.

```text
처음 5명 검증 → 비용보다 속도
반응 있는 50명 → API 사용량 확인
반복 사용자 500명 → DB/로그인/로그 구조 확인
유료화 고민 → 단가, 결제, 운영 비용 확인
```

처음부터 이 모든 걸 설계할 필요는 없어.

다만 “나중에 비용을 보게 될 수 있다”는 감각은 가지고 있으면 좋아.

## 좋은 기술 선택의 기준

좋은 기술 선택은 화려한 스택이 아니야.

다음 질문에 답하면 돼.

```text
가장 빨리 고객에게 보여줄 수 있어?
지금은 가짜 결과로도 배울 수 있어?
비밀 키가 노출되지 않아?
지금 꼭 저장이 필요해?
로그인이 지금 꼭 필요해?
사용자가 늘면 비용을 어디서 보게 될까?
```

이 질문에 답하면 지금 단계에 맞는 선택을 할 수 있어.

## 자주 헷갈리는 포인트

### 프론트에 다 넣으면 나쁜 구조 아냐?

오래 운영할 실제 서비스라면 한계가 있어. 하지만 첫 MVP에서 고객 반응만 보는 용도라면 괜찮아. 목적이 분명하면 좋은 선택이야.

### 가짜 결과를 보여줘도 돼?

돼. 단, 고객을 속이면 안 돼. “이런 결과가 나오면 쓸 것 같은지 보고 싶다”는 식으로 확인하는 용도라면 충분히 의미 있어.

### 처음부터 DB를 붙이면 더 안전한 거 아냐?

항상 그렇진 않아. 저장할 데이터가 없는데 DB부터 붙이면 설정과 에러만 늘어. 저장이 필요해질 때 붙이면 돼.

### API 키가 있으면 무조건 서버가 필요해?

숨겨야 하는 키라면 서버가 필요해. 브라우저 코드에 넣으면 노출될 수 있어.

### 나중에 갈아엎게 되면 손해 아냐?

처음 MVP는 배우기 위한 거야. 반응 없는 아이디어를 완벽한 구조로 만드는 게 더 큰 손해야.
