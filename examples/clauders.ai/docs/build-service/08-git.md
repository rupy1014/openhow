## 핵심 요약

**Git은 “코드가 바뀐 기록”을 남기는 도구야. GitHub은 그 기록을 인터넷에 백업해두는 곳이야. 처음엔 이 정도만 알면 돼. 내 컴퓨터에만 저장해두면 망가졌을 때 돌아가기 어렵고, 컴퓨터를 바꾸거나 배포할 때도 불편해. 그래서 기능 하나가 잘 됐을 때마다 Git에 기록하고, 중요한 기록은 GitHub에 올려둔다고 생각하면 돼. 명령어를 외우는 게 아니라 “잘 됐을 때 기록해두기”만 기억하면 돼.**

AI로 개발하다 보면 이런 일이 자주 생겨.

```text
방금까진 잘 됐는데 갑자기 화면이 안 뜬다
버튼 하나 고쳤는데 다른 기능이 망가졌다
에러를 고치다가 파일이 더 꼬였다
어제 되던 상태로 돌아가고 싶다
```

이때 Git이 없으면 어디로 돌아가야 할지 막막해.

반대로 Git에 작업 기록이 있으면 이렇게 말할 수 있어.

```text
마지막으로 잘 되던 지점으로 되돌려줘.
```

그래서 Git은 개발자만 쓰는 어려운 도구라기보다, **서비스를 만들 때의 안전장치**라고 보면 돼.

## 1. Git은 변경 기록을 남기는 도구야

Git은 파일이 어떻게 바뀌었는지 기록해주는 도구야.

예를 들어 서비스를 만들면서 이런 변화가 생겨.

```text
첫 화면을 만들었다
문의 폼을 추가했다
제출 버튼을 연결했다
결과 저장 기능을 붙였다
디자인을 수정했다
에러를 고쳤다
```

Git은 이 변화들을 시점별로 남겨둘 수 있어.

```text
A 지점: 첫 화면 완성
B 지점: 문의 폼 완성
C 지점: 저장 기능 완성
D 지점: 디자인 수정
```

그러면 D에서 문제가 생겼을 때 C로 돌아갈 수 있어.

이게 Git을 쓰는 가장 큰 이유야.

```text
잘 된 시점을 기록해두고,
망가지면 그 시점으로 돌아가기.
```

## 2. commit은 “여기까지 정상”이라고 남기는 기록이야

Git에서 가장 자주 보는 말이 commit이야.

commit은 쉽게 말해 이거야.

```text
지금 상태를 기록해둬.
나중에 필요하면 여기로 돌아올 수 있게.
```

예를 들어 첫 화면이 잘 떴어.

그러면 AI에게 이렇게 말하면 돼.

```text
첫 화면이 정상적으로 뜨는 것까지 확인했어.
지금 상태를 git commit 해줘.
메시지는 "첫 화면 완성"으로 해줘.
```

문의 저장 기능이 잘 됐으면 이렇게.

```text
문의 입력 후 저장되는 것까지 확인했어.
git commit 해줘.
메시지는 "문의 저장 기능 추가"로 해줘.
```

commit 메시지는 거창할 필요 없어.

```text
첫 화면 완성
문의 폼 추가
결과 저장 추가
모바일 화면 수정
배포 에러 수정
```

이 정도면 충분해.

중요한 건 “무엇이 되는 상태였는지” 나중에 알 수 있게 쓰는 거야.

## 3. 언제 commit해야 해?

기준은 단순해.

**브라우저에서 직접 확인했고, 그 기능이 정상적으로 됐을 때.**

```text
기능 만들기
→ 브라우저에서 확인
→ 잘 되면 commit
→ 다음 기능으로 넘어가기
```

반대로 이런 상태에서는 commit하지 않는 게 좋아.

```text
에러가 아직 난다
화면이 깨져 있다
버튼이 눌리지 않는다
내가 확인하지 않았다
AI가 “아마 될 겁니다”라고만 했다
```

Git은 그냥 저장 버튼이 아니야.

**잘 되는 지점을 남기는 기록**에 가까워.

그래서 commit 전에 꼭 한 번은 직접 눌러봐야 해.

## 4. 망가지면 되돌릴 수 있어

기능을 만들다 보면 망가질 수 있어.

예를 들어.

```text
디자인만 고치려 했는데 제출 버튼이 안 눌린다
저장 기능을 붙였더니 첫 화면이 안 뜬다
에러를 고치다가 파일이 더 꼬였다
```

이럴 때 commit이 있으면 AI에게 이렇게 말할 수 있어.

```text
마지막으로 정상 동작하던 commit을 찾아줘.
지금 변경사항과 비교해서 무엇이 망가졌는지 설명해줘.
필요하면 그 commit 상태로 되돌려줘.
```

바로 되돌리기 전에 비교를 먼저 시키는 것도 좋아.

```text
되돌리기 전에 최근 commit 이후 어떤 파일이 바뀌었는지 보여줘.
어떤 변경이 문제일 가능성이 높은지 설명해줘.
```

무조건 되돌리는 게 정답은 아니야.

작게 고칠 수 있으면 고치고, 너무 꼬였으면 되돌리면 돼.

중요한 건 commit이 있어야 선택지가 생긴다는 거야.

## 5. GitHub은 온라인 백업이야

Git은 내 컴퓨터 안에 기록을 남기는 도구야.

GitHub은 그 기록을 인터넷에 올려두는 곳이야.

쉽게 나누면 이래.

| 구분 | 쉽게 말하면 | 왜 필요해? |
| --- | --- | --- |
| Git | 내 컴퓨터의 작업 기록 | 잘 되던 시점으로 돌아가기 |
| GitHub | 인터넷에 올린 작업 기록 | 백업, 협업, 배포 연결 |

내 컴퓨터에만 있으면 이런 문제가 있어.

```text
컴퓨터가 고장 난다
폴더를 실수로 지운다
다른 컴퓨터에서 이어서 작업하고 싶다
배포 서비스와 연결하고 싶다
```

GitHub에 올려두면 이런 게 가능해.

```text
코드 백업
다른 컴퓨터에서 이어서 작업
외주/팀원과 공유
Vercel 같은 배포 서비스와 연결
```

처음에는 AI에게 이렇게 말하면 돼.

```text
이 프로젝트를 GitHub에 올리는 방법을 안내해줘.
나는 GitHub가 처음이니까 단계별로 설명해줘.
```

이미 연결돼 있다면 이렇게 말하면 돼.

```text
현재 변경사항을 commit하고 GitHub에 push해줘.
```

## 6. push는 GitHub에 올리는 거야

commit은 내 컴퓨터에 작업 기록을 남기는 거야.

push는 그 기록을 GitHub에 올리는 거야.

```text
commit = 내 컴퓨터에 기록
push = GitHub에 업로드
```

그래서 기능이 끝났을 때는 보통 이렇게 해.

```text
브라우저에서 정상 동작 확인
→ git commit
→ GitHub에 push
```

AI에게는 이렇게 말하면 돼.

```text
지금 기능이 정상 동작하는 것까지 확인했어.
변경사항을 commit하고 push해줘.
commit 메시지는 "피드백 폼 저장 추가"로 해줘.
```

push까지 해두면 컴퓨터가 바뀌어도 이어서 작업하기 쉬워.

## 7. pull과 clone은 가져오는 거야

GitHub에 올린 코드는 다른 컴퓨터에서도 가져올 수 있어.

처음 통째로 가져오는 걸 clone이라고 해.

```text
GitHub에 있는 내 프로젝트를 이 컴퓨터로 가져오고 싶어.
clone 하는 방법을 알려줘.
```

이미 가져온 프로젝트에서 최신 변경사항만 받아오는 건 pull이야.

```text
GitHub에 올라간 최신 변경사항을 받아와줘.
pull 해줘.
```

흐름은 이렇게 이해하면 돼.

```text
회사 컴퓨터에서 작업 → commit → push
집 컴퓨터에서 작업 시작 → pull → 이어서 작업
```

처음부터 명령어를 외울 필요 없어.

“처음 가져오기 = clone”, “최신 내용 받기 = pull” 정도만 알면 돼.

## 8. 다른 사람과 같이 할 때도 필요해

외주 개발자, 팀원, 디자이너와 같이 작업할 때도 GitHub가 필요해질 수 있어.

GitHub에 프로젝트를 올려두면 다른 사람을 초대할 수 있어.

```text
GitHub 리포지토리에 협업자를 추가하는 방법을 알려줘.
```

다만 같이 작업하면 충돌이 날 수 있어.

충돌은 두 사람이 같은 파일의 같은 부분을 다르게 고쳤을 때 생겨.

예를 들어.

```text
나는 버튼 문구를 “제출하기”로 바꿈
다른 사람은 같은 버튼 문구를 “보내기”로 바꿈
Git은 무엇을 남겨야 할지 모름
```

이럴 때는 AI에게 이렇게 말하면 돼.

```text
git 충돌이 났어.
어떤 파일에서 충돌이 났는지 설명해줘.
내가 선택해야 할 부분을 초보자도 이해하게 보여줘.
```

충돌을 줄이려면 이렇게 하면 좋아.

```text
작업 시작 전에 pull
기능 하나 끝나면 commit + push
같은 파일을 동시에 많이 고치지 않기
누가 어떤 영역을 고치는지 미리 나누기
```

## 9. AI에게 이렇게 시키면 돼

Git 명령어를 외우는 것보다, 상황에 맞게 AI에게 요청하는 게 더 중요해.

자주 쓰는 말은 이 정도야.

```text
현재 변경사항을 확인해줘.
어떤 파일이 바뀌었는지 설명해줘.
```

```text
브라우저에서 정상 동작 확인했어.
git commit 해줘.
메시지는 "첫 화면 완성"으로 해줘.
```

```text
commit하고 GitHub에 push해줘.
```

```text
마지막으로 정상 동작하던 commit을 찾아줘.
최근 변경사항과 비교해서 문제 가능성이 큰 파일을 알려줘.
```

```text
되돌리기 전에 지금 변경사항이 사라지는지 알려줘.
안전하게 되돌리는 방법을 설명해줘.
```

특히 마지막 문장이 중요해.

되돌리기는 작업을 잃을 수 있으니까, AI에게 먼저 설명을 시키고 진행하는 게 좋아.

## 자주 헷갈리는 포인트

### git 명령어를 외워야 해?

아니야. 처음에는 “commit해줘”, “push해줘”, “변경사항 확인해줘”, “되돌릴 수 있는지 봐줘” 정도로 말하면 돼.

### commit은 얼마나 자주 해?

기능 하나가 정상 동작할 때마다 해. “화면 확인 완료”, “저장 확인 완료”, “배포 에러 수정 완료”처럼 확인된 지점마다 남기면 좋아.

### 확인 안 했는데 commit해도 돼?

가능은 하지만 추천하지 않아. 나중에 돌아갔는데 그 지점도 망가져 있으면 의미가 없거든. commit은 “여기까지 정상”일 때 남기는 게 좋아.

### push는 매번 해야 해?

중요한 기능이 끝났다면 push까지 하는 게 좋아. 그래야 GitHub에 백업되고, 배포 서비스와 연결된 경우 배포도 이어질 수 있어.

### revert, reset 같은 말이 나오면?

처음부터 외울 필요 없어. “되돌리는 방법이 여러 가지 있구나” 정도로만 알아도 돼. 실제로 되돌리기 전에는 AI에게 무엇이 사라지는지 먼저 설명시키면 돼.

### GitHub에 올리면 누구나 볼 수 있어?

공개 저장소면 볼 수 있고, 비공개 저장소면 초대한 사람만 볼 수 있어. 처음 프로젝트는 보통 비공개로 시작하는 게 편해.
