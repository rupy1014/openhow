## 핵심 요약

**기획에서 쓰이는 말들이 뭔지, 어떤 순서로 풀어볼 수 있는지, 어디까지 하면 충분한지 잡아보는 글이야. 정답 절차는 없어. 바이브 기획은 만들기 전에 의도를 여러 방식으로 표현해서 AI든 사람이든 더 정확한 의도로 일하게 만드는 과정이야.**

[아이디어 찾기](./01-idea)에서 정리한 건 이거였어.

```text
누가 쓸 건지
어떤 문제를 겪는지
무엇을 주면 어떤 행동을 할 것 같은지
첫 버전에서 누구에게 보여줄지
```

이걸 “만들 수 있는 계획”으로 바꿔야 해. 곧장 “이 아이디어로 웹서비스 만들어줘”라고 던지면 위험해. AI는 네 의도를 모르거든.

- 누구를 제일 먼저 만족시켜야 하는지
- 어떤 기능이 핵심이고 어떤 건 빼도 되는지
- 첫 화면에서 사용자가 뭘 해야 하는지
- 배포 후 어떤 행동을 보면 성공인지
- 혼자 쓸 건지, 고객에게 보여줄 건지, 팀과 같이 만들 건지

안 알려주면 AI가 알아서 채워. 그 순간부터 네 서비스가 아니라 **AI가 상상한 서비스**가 돼.

## AI 이후의 기획은 왕복이야

예전엔 이런 식이었어.

```text
아이디어 → 기획서 → 디자인 → 개발 → QA → 배포
```

각 단계가 따로 움직였고 문서가 다음 사람에게 넘어갔지. 그래서 기획은 “개발 전에 끝내는 일”처럼 보였어.

AI 이후엔 한 대화 안에서 기획·화면·구현·검증을 계속 왕복할 수 있어.

```text
아이디어 → 기획 초안 → 화면 초안 → 작은 구현 → 결과 확인 → 다시 기획 수정
```

만들고 나서야 보이는 것들이 있어.

```text
아, 첫 화면 문구가 애매하네.
아, 이 버튼은 없어도 되겠네.
아, 고객이 원하는 건 이 기능이 아니라 이 흐름이네.
```

그래서 바이브 기획은 “개발 전에 끝내는 문서”가 아니라 **만드는 과정 안에서 계속 선명해지는 의도**야. 긴 기획서를 쓰는 게 아니라 의도를 여러 방식으로 표현해보는 거고.

산출물은 이렇게 나눠 봐.

```text
글로 정리하면 PRD
순서로 정리하면 사용자 흐름
구조로 정리하면 IA
화면으로 정리하면 와이어프레임
작게 출시할 범위로 줄이면 MVP
작업으로 쪼개면 구현 계획
검증으로 정리하면 QA/피드백 기준
```

전부 다 해야 한다는 뜻은 아니야. 아이디어가 작으면 PRD 한 장과 첫 화면이면 충분하고, 복잡하면 IA·흐름·와이어프레임·구현 계획까지 필요해. 핵심은 **필요한 만큼만 선명하게**.

순서를 외우는 게 목표가 아니야. “지금 뭘 더 선명하게 해야 하지?”를 판단하는 거야.

## 1. PRD — 글로 쓰는 기획서

PRD는 Product Requirements Document, 쉽게 말하면 **무엇을 만들지 글로 정리한 문서**야. 보통 들어가는 내용.

```text
서비스 한 줄 설명
대상 고객
고객 문제
핵심 가설
만들 기능
안 만들 기능
사용자 흐름
검증 기준
```

쓰는 법은 [다음 글](./03-prd)에서 자세히 다룰 거야. 지금은 이것만.

**PRD는 AI에게 “아무거나 만들지 말고, 이 범위 안에서 만들어줘”라고 알려주는 기준선이야.**

## 2. 사용자 흐름 — 사용자가 움직이는 순서

사용자가 어떤 순서로 움직이는지 적어. 영어 문장 서비스라면.

```text
1. 사용자가 링크를 연다
2. 오늘의 영어 문장을 본다
3. 짧은 해설을 읽는다
4. 완료 버튼을 누른다
5. 내일 다시 들어온다
```

기능 목록만 쓰면 서비스가 잘 안 보여.

```text
문장 추천 기능
해설 기능
완료 기능
```

흐름으로 쓰면 첫 화면에서 뭘 보여줘야 하는지, 버튼이 어디 있어야 하는지, 뭐가 없어도 되는지 보이기 시작해.

## 3. IA — 정보구조도

IA는 Information Architecture, **페이지와 정보가 어떻게 나뉘는지 보는 지도**야. 페이지가 여러 개일 때 필요해.

```text
홈
├─ 오늘의 문장
├─ 지난 문장
├─ 내 완료 기록
└─ 설정
```

IA가 있으면 “이번 MVP에는 홈과 오늘의 문장만, 나머지는 안 만든다”처럼 경계를 그을 수 있어. AI가 페이지를 막 늘리는 것도 줄어.

## 4. 와이어프레임 — 화면 뼈대

예쁜 디자인이 아니라 **화면에 뭐가 어디 놓이는지 보는 뼈대**야. 텍스트로도 충분해.

```text
[상단] 오늘의 1문장

[중앙]
영어 문장
한국어 뜻
짧은 해설

[하단]
오늘 완료 버튼
```

조금 더 그리면.

```text
┌────────────────────┐
│ 오늘의 영어 문장    │
├────────────────────┤
│ The early bird...  │
│ 일찍 일어나는 새... │
│ 짧은 해설 2줄       │
├────────────────────┤
│ [오늘 완료]         │
└────────────────────┘
```

비개발자도 AI에게 “이런 화면으로 만들어줘”라고 말할 때 도움이 돼.

## 5. MVP 범위 — 첫 버전에 어디까지 만들지

MVP는 Minimum Viable Product, **고객에게 보여주고 반응을 볼 수 있는 가장 작은 첫 버전**이야. 작게 만든다는 건 대충 만든다는 뜻이 아니라 **가설 확인에 필요 없는 걸 빼는 것**.

영어 문장 서비스의 첫 MVP라면.

```text
오늘의 문장 1개가 보인다
짧은 해설이 보인다
완료 버튼을 누를 수 있다
내일 다시 들어오고 싶은지 확인한다
```

빼도 되는 것.

```text
로그인
레벨 시스템
커뮤니티
결제
긴 강의 콘텐츠
```

MVP의 목적은 완성도가 아니라 이걸 확인하는 거야.

```text
이 흐름이 말이 되나?
첫 화면에서 뭘 해야 하는지 보이나?
사용자가 어디서 막히나?
내 가설이 조금이라도 맞아 보이나?
```

## 6. 스토리보드 — 고객이 쓰는 장면

화면보다 **상황**을 보는 도구야. 고객이 왜 이 서비스를 쓰는지가 장면에 달린 경우 필요해.

```text
아침 8시 20분, 지하철 안.
직장인이 영어 공부 앱을 연다.
긴 강의는 볼 시간이 없다.
오늘 문장 하나만 보고 완료 버튼을 누른다.
회사 도착 전에 끝난다.
```

“긴 학습 앱이 아니라 출근길 1분 경험”이 보여. 모든 프로젝트에 필요한 건 아니지만 사용 맥락이 핵심인 서비스라면 도움이 돼.

## 7. 구현 계획 — 어떤 순서로 만들지

개발자만 보는 문서가 아니야. AI에게 한 번에 다 시키면 망가지기 쉬워서 비개발자에게도 중요해.

```text
Step 1. 첫 화면 만들기
Step 2. 오늘 문장 데이터 보여주기
Step 3. 완료 버튼 동작시키기
Step 4. 완료 기록 저장하기
Step 5. 배포하기
```

이게 있으면 “지금은 Step 1만 해줘. 다른 기능은 건드리지 마”라고 말할 수 있어. 한 번에 다 만들려고 하면 에러가 커지고 어디서 망가졌는지도 알기 어려워.

## 8. 검증 기준 — 만들고 나서 뭘 볼지

“좋은 서비스인지” 평가하는 기준만은 아니야. **이번 가설에서 뭘 배우면 되는지 정하는 기준**이야.

```text
고객 5명에게 URL을 보낸다.
3명 이상이 오늘 문장을 끝까지 본다.
2명 이상이 다음 날 다시 들어온다.
한 명이라도 “이거 매일 보내주면 좋겠다”고 말한다.
```

이게 없으면 피드백이 “좋네요 / 깔끔하네요 / 재밌네요”에서 끝나. 고맙지만 방향을 정하기엔 부족해.

## 상황별로 어떤 순서로 하면 돼?

정답은 없고 상황마다 달라. 대표적인 5가지.

### 가장 가벼운 길 — 혼자 빠르게 확인

```text
아이디어 3줄
→ PRD 한 장
→ 사용자 흐름 5단계
→ 첫 화면 와이어프레임
→ 바로 MVP 만들기
```

입문자는 대부분 여기서 시작하면 돼.

### 화면이 여러 개라면

```text
아이디어 3줄
→ PRD 한 장
→ IA
→ 사용자 흐름
→ 주요 화면 와이어프레임
→ 구현 계획
→ MVP 만들기
```

### 고객 사용 장면이 핵심이라면

```text
아이디어 3줄
→ 고객 시나리오/스토리보드
→ PRD 한 장
→ 첫 화면 문구
→ MVP 범위 정하기
→ 고객에게 보여주기
```

### 팀원·외주랑 같이 한다면

말로만 설명하면 새어나가. 두 단계로 나눠서 보여줘. 1단계는 목표·구조·화면을 같이 맞추고, 2단계는 톤·작업·역할을 맞춰서 넘기는 거야.

목적은 문서를 많이 만드는 게 아니라 **상대가 추측하지 않게 만드는 것**이야. AI랑 일할 때도 같아 — 사람이 여러 명 있는 게 아니라 네가 역할을 나눠서 시키는 거야.

```text
지금은 PRD만 정리해줘.
지금은 화면 구조만 잡아줘.
지금은 구현 순서만 나눠줘.
지금은 QA 기준만 만들어줘.
```

단계별로 나누면 AI가 덜 헤매.

### 아직 고객이 흐리다면

```text
아이디어 3줄
→ 주변 사람에게 말해보기
→ 반응 없으면 고객/문제 다시 좁히기
→ 그다음 PRD
```

기획 과정은 고정된 길이 아니야. **지금 막힌 부분을 선명하게 만드는 산출물을 골라 쓰는 것**에 가까워.

## 어느 정도까지 하면 충분해?

다 하려고 하지 마. 첫 프로젝트는 이 정도면 돼.

```text
1. PRD 한 장
2. 사용자 흐름 5단계
3. 첫 화면 와이어프레임 1개
4. 안 만들 것 목록
5. 구현 순서 3단계
6. 배포 후 확인할 검증 기준
```

“웹서비스 만들어줘”보다 훨씬 결과가 좋아져. 판단 기준은 다음 질문에 답할 수 있느냐야.

```text
누구를 위한 거야?
그 사람의 어떤 문제를 줄여?
첫 버전에서는 뭘 만들고 뭘 안 만들어?
사용자는 어떤 순서로 핵심 행동을 끝내?
첫 화면에는 뭐가 보여?
어떤 순서로 만들 거야?
배포 후 뭘 보면 배울 수 있어?
```

답할 수 있으면 시작해도 돼. 만들면서 바뀌어도 괜찮아 — 오히려 바뀌어야 해.

반대로 이런 상태라면 만들기보다 다시 좁히는 게 좋아.

```text
고객이 아직 “모든 사람”이야
문제를 한 문장으로 못 말해
기대 행동이 없어
첫 QA 대상이 없어
주변에 말했는데 아무 반응이 없어
```

이때 억지로 만들면 문서·화면은 나오는데 배포하고 나서 뭘 배워야 할지 몰라.

## 자주 헷갈리는 포인트

**IA랑 사용자 흐름은 뭐가 달라?** IA는 구조(페이지·정보가 어떻게 나뉘는가), 사용자 흐름은 순서(어디서 시작해 어떤 행동을 끝내는가).

**와이어프레임이랑 MVP는?** 와이어프레임은 화면 뼈대, MVP는 고객에게 보여주고 반응을 볼 가장 작은 버전. 와이어프레임으로 화면을 잡고 MVP로 작게 만들어.

**스토리보드는 꼭 필요해?** 출근길·회의 직후·상품 등록 중 같은 사용 장면이 핵심인 서비스만.

**기획을 많이 하면 더 좋은 거 아냐?** 아니. 길어질수록 출시가 늦어져. 목표는 완벽한 문서가 아니라 **출시 가능한 범위**.
