# Threads 자동화 특강 — 뉴스봇에서 쓰레드 발행까지

> 대상: Claude Code를 써본 클로더즈 수강생  
> 목표: `뉴스 수집 → AI 리뷰 → 채널별 다듬기 → 승인 → Threads 발행 → 매일 자동 실행` 흐름을 하나의 파이프라인으로 이해한다.  
> 핵심 메시지: 자동화는 거대한 앱을 새로 만드는 일이 아니라, 이미 반복하던 일을 **모으기 → 분류하기 → 다듬기 → 승인하기 → 내보내기 → 반복 실행**으로 쪼개는 일이다.

---

## 이 특강에서 만드는 것

매일 아침 이런 흐름이 자동으로 돈다.

```text
해외 뉴스/블로그/RSS/API
  → 새 글 수집
  → AI가 유형 분류
  → 전문 리뷰어가 한국어 리뷰 작성
  → 채널에 맞게 짧게 다듬기
  → 사람이 한 번 승인
  → Threads에 280자 단위로 이어서 발행
  → GitHub Actions가 매일 반복
```

결과물은 이런 형태다.

```text
Claude Code에 멀티에이전트가 왔다.
코드 리뷰 + 테스트 + 문서화를 AI 3명이 동시에.

바이브코딩 생산성 체감 2배 이상. 🧵 아래에 설치법 👇

#AI코딩 #ClaudeCode #바이브코딩 #멀티에이전트 #자동화
```

그리고 필요하면 같은 원본을 카카오톡, Slack, 웹사이트, 이메일용으로도 바꿀 수 있다.

## 0. 자동화는 앱 만들기와 다르다

바이브코딩에서 만든 앱은 보통 사람이 버튼을 누르면 반응한다.

```text
사람이 쓰는 앱: 버튼 클릭 → 화면 반응
자동화 파이프라인: 매일 아침 8시 → 자동 수집 → 자동 요약 → 자동 발송
```

앱의 트리거는 사용자 행동이다. 뉴스봇과 Threads 자동화의 트리거는 시간표다.

이 특강에서 다룰 자동화는 여섯 단계로 보면 된다.

```text
모으기 → 분류하기 → 다듬기 → 퇴고 → 승인 → 릴리즈
```

| 단계 | 하는 일 | 비유 |
| --- | --- | --- |
| 모으기 | 해외 뉴스 사이트에서 기사 수집 | 신문 배달 |
| 분류하기 | AI가 유형별로 분류하고 리뷰 작성 | 편집장이 기사 분배, 기자가 리뷰 |
| 다듬기 | Threads·카톡·웹·Slack에 맞게 포맷 변환 | 지면 편집 |
| 퇴고 | 번역투 제거, 톤 맞춤, 사실 확인 | 데스크 교정 |
| 승인 | 사람이 훑어보고 OK | 최종 검토 |
| 릴리즈 | Threads·카톡·웹 등에 발송 | 인쇄·배포 |

중요한 점은 각 단계가 독립적이라는 것이다. 소스를 바꾸면 경쟁사 모니터링 봇이 되고, 리뷰어를 바꾸면 채용공고 봇이 되고, 채널을 바꾸면 Threads 자동 발행 봇이 된다.

## 1. 먼저 완성된 흐름을 한 번 돌려본다

처음부터 모든 코드를 이해하려고 하지 말고, 완성된 파이프라인을 한 번 실행해본다.

### Step 1. 예제 프로젝트 받기

```bash
unzip max5-clone.zip
cd max5-clone
npm install
```

원본 자료에서는 `max5-clone.zip` 예제 프로젝트를 사용한다.

### Step 2. Claude Code에서 `/news` 실행

```bash
claude
```

Claude Code 안에서:

```text
/news
```

이 명령 하나로 수집, 분류, 리뷰 생성, 퇴고까지 돈다.

```text
📡 1단계: RSS 수집
  [hacker-news] 15개 확인 → 3개 신규
  [hackernoon] 10개 확인 → 2개 신규
  ...
✅ 수집 완료 (9개 신규)

🤖 2단계: AI 리뷰 생성
  hacker-news-agent-safehouse.md → dev_reviewer → ✅
  hackernoon-ai-startups.md → story_reviewer → ✅
  ...

✍️ 3단계: 퇴고
  번역투 제거, 톤 맞춤 ✅
```

### Step 3. 결과 확인

```bash
npm run dev
```

브라우저에서 완성된 리뷰를 확인한다. 이 화면은 단순한 웹페이지가 아니라, 여섯 단계 파이프라인이 한 번 돈 결과물이다.

## 2. 모으기 — RSS와 API로 원재료를 가져온다

자동화의 첫 단계는 좋은 원재료를 모으는 것이다.

```bash
npm run fetch
```

실행하면 여러 뉴스 소스에서 새 글을 가져온다.

```text
📡 RSS 수집 시작
  [hacker-news] 15개 확인 → 3개 신규
  [hackernoon] 10개 확인 → 2개 신규
  [marktechpost] 10개 확인 → 4개 신규
  ...
✅ 수집 완료 (9개 신규)
```

### RSS는 블로그의 택배 알림이다

블로그에 새 글이 올라오면 RSS 주소로 알림이 온다. 우리는 그 주소를 등록해두고 프로그램이 주기적으로 “새 글 있어?”라고 묻게 만든다.

```text
일반 구독: 이메일 뉴스레터 신청 → 메일함에 옴
RSS 구독: RSS URL 등록 → 프로그램이 자동으로 확인
```

RSS URL은 이런 식이다.

```text
https://hnrss.org/newest?points=100
https://hackernoon.com/feed
https://www.marktechpost.com/feed/
```

### API는 직접 물어보는 창구다

RSS는 쌓여 있는 글을 가져오는 우편함에 가깝다. API는 “오늘 인기 글 뭐야?”처럼 조건을 걸어 직접 물어보는 창구다.

```text
RSS: 수동적. 쌓여 있는 걸 가져옴
API: 능동적. 조건을 걸어서 질문함
```

예제 프로젝트에서는 RSS와 API를 함께 쓴다.

| 소스 | 방식 | 가져오는 것 |
| --- | --- | --- |
| Hacker News | API | 테크 커뮤니티 인기 글 |
| HackerNoon | RSS | AI 스타트업 트렌드 |
| MarkTechPost | RSS | AI 연구, 적용 사례 |
| The Bootstrapped Founder | RSS | 솔로프리너 운영기 |
| levels.io | RSS | 인디해커 실전기 |
| Trends.vc | RSS | AI 니치 시장 분석 |
| Product Hunt | API | 신제품 런칭 |
| Lenny's Newsletter | RSS | 프로덕트 전략 |
| SaaS Weekly | RSS | SaaS 트렌드 |
| Entrepreneurs Handbook | RSS | 창업 스토리 |

### RSS가 없는 사이트는 직접 만든다

Anthropic 블로그나 Cursor Blog처럼 RSS를 제공하지 않는 사이트도 있다. 이때는 페이지를 읽어서 RSS 파일로 바꾸는 스크래퍼를 만들 수 있다.

```text
GitHub Actions가 매시간 실행
  → 사이트 페이지를 읽어서
  → RSS 파일로 변환해서
  → GitHub에 저장
```

Claude Code에는 이렇게 시킨다.

```text
이 사이트(https://example.com/blog)의 RSS 피드를 생성하는
스크래퍼를 만들어줘. GitHub Actions로 매시간 돌게.
```

소스를 추가할 때도 같은 방식이다.

```text
RSS 소스에 GeekNews 추가해줘.
URL은 https://news.hada.io/rss
```

## 3. 분류하고 리뷰하기 — AI 편집장과 AI 기자를 둔다

수집된 기사가 들어오면 바로 발행하지 않는다. 먼저 어떤 기사인지 분류하고, 그 기사에 맞는 리뷰어가 글을 쓴다.

```text
hacker-news-agent-safehouse.md → dev_reviewer     → ✅ 리뷰 생성
hackernoon-ai-startups.md      → story_reviewer   → ✅ 리뷰 생성
producthunt-new-saas.md        → product_reviewer → ✅ 리뷰 생성
```

편집장이 기사를 읽고 담당 기자에게 넘기는 구조다. 편집장도 AI고, 기자도 AI다.

### 콘텐츠 라우터

콘텐츠 라우터는 “이 기사는 누가 리뷰할지” 결정하는 AI다.

| 이런 게 보이면 | 보낼 리뷰어 |
| --- | --- |
| GitHub URL, `npm install`, 코드 블록 | `dev_reviewer` — 개발 도구 |
| Product Hunt, 가격표, “출시” | `product_reviewer` — 서비스 리뷰 |
| MRR 숫자, “어떻게 ~했는가”, 인터뷰 | `story_reviewer` — 성공 사례 |

예를 들어 “Show HN: I built an open-source Notion alternative”라는 기사가 들어왔다고 하자. GitHub URL이 있고 설치법이 있으면 `dev_reviewer`로 보낸다.

### 리뷰어별 산출물

각 리뷰어는 전문 분야와 출력 형식이 다르다.

| 리뷰어 | 쓰는 내용 |
| --- | --- |
| `dev_reviewer` | 설치법 + Claude Code 활용 프롬프트 + 사이드 프로젝트 아이디어 |
| `product_reviewer` | 활용 팁 + 비즈니스 기회. 개발 권장은 하지 않음 |
| `story_reviewer` | 핵심 교훈 + 내 상황에 적용법 + 생존자 편향 주의 |

`product_reviewer`가 서비스 소개 글에서 “이거 Claude로 클론 코딩해봐”라고 쓰면 맥락이 안 맞다. 이런 차이를 각 리뷰어의 지침으로 나눠둔다.

### Skills는 역할별 업무 지침서다

바이브코딩에서 `CLAUDE.md`는 “이 프로젝트는 이렇게 해줘”라는 전체 지침서였다. Skills는 그 지침서를 역할별로 나눈 것이다.

```text
.agent/skills/
├── content_router/    ← 편집장. 기사 분배
├── dev_reviewer/      ← 개발 도구 담당 기자
├── product_reviewer/  ← 서비스 담당 기자
├── story_reviewer/    ← 사례 담당 기자
├── refine_content/    ← 교정 데스크
└── create_reviewer/   ← 새 기자 채용 가이드
```

각 폴더 안의 `SKILL.md`를 읽고 AI가 자기 역할을 이해한다.

```text
CLAUDE.md = 전체 프로젝트 규칙
SKILL.md = 역할별 업무 지침서
```

새 리뷰어가 필요하면 이렇게 요청한다.

```text
YouTube 영상 리뷰용 리뷰어를 새로 만들어줘.
영상 요약 + 핵심 타임스탬프 + 한줄평 형식으로.
```

Claude Code가 새 리뷰어 지침을 만들고, 콘텐츠 라우터에 YouTube URL 트리거를 추가하게 만들 수 있다.

## 4. 비용 구조 — 수집은 무료, 리뷰 생성은 유료다

중요한 구분이 있다.

```text
수집 (npm run fetch)    → 무료. RSS/API로 글 목록을 가져옴
리뷰 생성 (AI API 호출) → 유료. LLM이 글을 읽고 씀
퇴고 (AI API 호출)      → 유료. LLM이 문장을 다듬음
발송 (웹훅/API 호출)    → 대체로 무료. 채널 API 정책에 따라 다름
```

리뷰 생성 방식은 세 가지로 나눌 수 있다.

| 방법 | 동작 | 비용 | 자동화 수준 |
| --- | --- | --- | --- |
| Claude Code에서 수동 | `/news` 치면 Claude가 직접 리뷰 생성 | Claude Code 구독료에 포함 | 수동 |
| OpenRouter API | 스크립트가 자동으로 API 호출 | 토큰당 과금 | 완전 자동 가능 |
| Antigravity 워크플로우 | 수집된 기사를 워크플로우에 넣음 | 무료 플랜 있음 | 반수동 |

가장 쉬운 시작은 Claude Code에서 `/news`를 치는 것이다. 완전 자동화하려면 OpenRouter 같은 LLM API를 붙인다.

기사 하나당 리뷰를 생성하는 데 보통 2,000~5,000토큰 정도 쓴다.

| 모델 | 기사 1개당 비용 | 하루 10개 | 월 비용 |
| --- | --- | --- | --- |
| Gemini Flash | ~$0.001 | ~$0.01 | ~$0.3 |
| GPT-4o mini | ~$0.003 | ~$0.03 | ~$1 |
| Claude Haiku | ~$0.005 | ~$0.05 | ~$1.5 |
| GPT-4o | ~$0.01 | ~$0.1 | ~$3 |
| Claude Sonnet | ~$0.015 | ~$0.15 | ~$5 |

정확한 가격은 모델과 시점에 따라 바뀐다. 특강에서는 “AI가 읽고 쓰는 단계에만 비용이 든다”는 구조를 이해하는 것이 더 중요하다.

## 5. Threads용으로 다듬기 — 같은 원본도 채널마다 다르다

같은 리뷰라도 카카오톡, Threads, 웹사이트, Slack, 이메일은 문법이 다르다.

| 채널 | 포맷 | 길이 | 특이사항 |
| --- | --- | --- | --- |
| 카카오톡 | 순수 텍스트 | 약 500자 | 링크는 맨 끝에 하나만 |
| Threads | 짧은 포스트 | 약 280자 | 해시태그, 쓰레드로 이어쓰기 |
| 웹사이트 | 마크다운 | 제한 없음 | 이미지, 카테고리, 태그 필요 |
| Slack | 블록 메시지 | 약 1000자 | 구조화된 레이아웃, 버튼 가능 |
| 이메일 뉴스레터 | HTML | 약 2000자 | 제목이 핵심 |

### 카카오톡용 예시

```text
[AI 브리핑] Claude Code 멀티에이전트 지원

여러 AI 에이전트가 동시에 일하는 기능이 추가됐어.
코드 리뷰, 테스트, 문서화를 각각 다른 에이전트가 맡아.
바이브코딩할 때 /news 한 번이면 3개가 동시에 돌아가.

👉 https://example.com/article
```

### Threads용 예시

```text
Claude Code에 멀티에이전트가 왔다.
코드 리뷰 + 테스트 + 문서화를 AI 3명이 동시에.

바이브코딩 생산성 체감 2배 이상. 🧵 아래에 설치법 👇

#AI코딩 #ClaudeCode #바이브코딩 #멀티에이전트 #자동화
```

Threads용으로 바꿀 때는 다음 규칙을 둔다.

```text
- 한 포스트는 280자 안팎으로 자른다.
- 첫 포스트는 훅과 결론을 먼저 둔다.
- 이어지는 포스트는 근거, 사용법, 예시 순서로 둔다.
- 마지막 포스트에는 원문 링크나 다음 행동을 넣는다.
- 해시태그는 3~5개를 넘기지 않는다.
- 너무 광고처럼 보이는 표현은 줄인다.
```

Claude Code에는 이렇게 시킬 수 있다.

```text
content-workflow/ 리뷰들을 Threads용 포스트로 변환해줘.
각 포스트는 280자 안팎으로 나누고,
첫 포스트에는 훅을 넣고,
마지막 포스트에는 원문 링크와 해시태그를 넣어줘.
```

## 6. 퇴고 — AI 초고를 그대로 내보내지 않는다

AI가 쓴 초고에는 자주 나오는 문제가 있다.

- 번역투: “~하는 것이 중요합니다” → “~해야 해”
- 마케팅 문구: “혁신적인”, “획기적인” 같은 빈 표현
- 과장: 원문에 없는 숫자나 검증 안 된 주장
- 채널 부적합: Threads에는 너무 길고, 카카오톡에는 링크가 너무 많음

그래서 초고 작성과 퇴고를 분리한다. 기자가 글을 쓰고, 데스크가 교정하는 것과 같다.

`refine_content` 역할에는 이런 기준을 둔다.

```text
톤앤매너:
  [x] 번역투 제거
  [x] 반말체 일관성 ("~했어", "~인 거야")
  [x] 마케팅 문구 제거

사실 확인:
  [x] 검증 안 된 주장 제거
  [x] 원문에 없는 정보 추가 여부 확인
  [x] 숫자와 날짜 확인
```

퇴고만 따로 시킬 수도 있다.

```text
content-workflow/ 폴더의 리뷰들을 퇴고해줘.
번역투 제거하고, 톤을 맞춰줘.
원문에 없는 주장이나 과장된 표현은 삭제해줘.
```

톤을 바꾸고 싶으면 이렇게 요청한다.

```text
리뷰어들의 톤을 존댓말로 바꿔줘.
"~했습니다", "~인데요" 스타일로 통일해줘.
```

---

## 7. 승인 — 완전 자동 발행 전에 사람 눈을 한 번 둔다

AI가 쓴 글을 그대로 발송하면 사고가 난다.

- 원문을 잘못 해석해서 반대로 소개함
- 없는 기능을 있다고 말함
- 어제 뉴스를 오늘 뉴스처럼 씀
- Threads에서 광고처럼 보이는 문장으로 바뀜

개인 자동화라도 승인 단계를 두는 것이 좋다.

```bash
ls content-workflow/*.md
```

처음에는 리뷰 제목과 한 줄 요약만 훑어봐도 충분하다. 이상한 글이 없으면 발행한다.

팀에서 쓰는 경우에는 Slack에 미리보기를 올리고 승인 버튼을 붙일 수 있다. 하지만 특강의 기본 버전에서는 “사람이 눈으로 훑고 발행”이면 충분하다.

## 8. 릴리즈 — Threads API는 쉽지 않지만 구조는 같다

보내는 방법은 채널마다 다르다.

| 난이도 | 채널 | 필요한 것 |
| --- | --- | --- |
| 쉬움 | Slack / Discord | 웹훅 URL 하나 |
| 보통 | 카카오톡 | Kakao Developer 앱 + 토큰 |
| 보통 | 이메일 | SMTP 설정 또는 SendGrid API |
| 어려움 | Threads | Meta Developer 앱 + OAuth |
| 이미 해봤음 | 웹사이트 | Supabase + Vercel |

### Slack / Discord 웹훅

가장 쉽다. 웹훅 URL 하나면 된다.

```text
슬랙 웹훅으로 매일 뉴스레터를 보내는 기능 만들어줘.
웹훅 URL은 .env에 SLACK_WEBHOOK_URL로 넣을게.
```

### 카카오톡 나에게 보내기

Kakao Developers에서 앱을 만들고, 카카오톡 메시지 권한을 활성화하고, OAuth 토큰을 발급해 `.env`에 넣는다.

```text
카카오톡 나에게 보내기로 뉴스레터를 전송하는 기능 만들어줘.
카카오 API 설정 방법도 알려줘.
```

### Threads 발행

Threads는 Meta에서 제공하는 API를 쓴다. Instagram 계정과 Meta Developer 앱, OAuth 설정이 필요하다. Slack 웹훅보다 복잡하지만 발행 단계의 구조는 같다.

```text
Threads API로 포스팅하는 기능 만들어줘.
쓰레드 형식으로 280자씩 이어서 올리게.
```

Threads 발행 기능을 만들 때는 최소한 아래 요구사항을 명시한다.

```text
- content-workflow/threads/ 폴더의 승인된 파일만 발행한다.
- 한 파일 안의 여러 포스트는 순서대로 올린다.
- 첫 포스트 발행 후 반환된 id를 저장한다.
- 이어지는 포스트는 이전 포스트에 연결한다.
- 이미 발행한 파일은 다시 발행하지 않는다.
- 실패하면 어떤 포스트에서 실패했는지 로그로 남긴다.
```

이 요구사항을 안 적으면 “한 번 올리기는 되는데 운영이 불안한” 코드가 나오기 쉽다. 자동화는 실행보다 재실행, 실패, 중복 방지가 더 중요하다.

## 9. 매일 자동으로 돌리기 — cron과 GitHub Actions

지금까지는 사람이 `/news`를 쳤다. 이제 시간표에 맞춰 자동으로 실행하게 만든다.

```text
무료 자동화:
  → 뉴스 수집 (RSS 긁기)
  → 발송 (웹훅/API 호출)

유료 자동화:
  → AI 리뷰 생성
  → 퇴고
```

### cron은 프로그램의 알람시계다

```text
알람: 매일 아침 8시 → 나를 깨움
cron: 매일 아침 8시 → 이 스크립트를 실행함
```

cron 표현은 이렇게 생겼다.

```text
0 8 * * *
│ │ │ │ │
│ │ │ │ └── 요일
│ │ │ └──── 월
│ │ └────── 일
│ └──────── 시
└────────── 분
```

`0 8 * * *`는 매일 아침 8시 0분이라는 뜻이다. 외울 필요는 없다. Claude Code에게 “매일 아침 8시에 실행해줘”라고 하면 알아서 만든다.

### 서버 선택지

cron은 누군가가 24시간 켜져 있어야 돈다.

| 방법 | 특징 | 비용 | 추천 |
| --- | --- | --- | --- |
| 내 컴퓨터 cron | 컴퓨터가 켜져 있을 때만 동작 | 무료 | 테스트용 |
| GitHub Actions | 24시간 동작, 설정 간단 | 무료 한도 있음 | 가장 추천 |
| VPS 서버 | 자유도 높음 | 월 $5~ | 고급 |

입문자는 GitHub Actions가 제일 낫다.

### GitHub Actions 설정

`.github/workflows/` 폴더에 `.yml` 파일을 만든다.

```yaml
name: 매일 뉴스 수집
on:
  schedule:
    - cron: '0 23 * * *'  # UTC 23시 = 한국시간 8시

jobs:
  fetch-news:
    runs-on: ubuntu-latest
    env:
      OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
      SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}
    steps:
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm run fetch
      - run: npm run review
      - run: npm run send
```

특강에서는 Slack 발송을 예시로 들지만, `npm run send` 자리에 Threads 발행 스크립트를 연결하면 Threads 자동화가 된다.

```yaml
      - run: npm run format:threads
      - run: npm run publish:threads
```

Claude Code에는 이렇게 요청한다.

```text
GitHub Actions로 매일 아침 8시(한국시간)에
콘텐츠 수집 → OpenRouter API로 리뷰 생성 → Threads용 포맷 변환 → 승인된 글 발행
워크플로우를 만들어줘.
OpenRouter API 키와 Threads API 토큰은 GitHub Secrets에 넣을게.
```

환경변수는 GitHub 리포지토리의 Settings → Secrets에 넣는다.

```text
OPENROUTER_API_KEY
THREADS_ACCESS_TOKEN
THREADS_USER_ID
```

## 10. 자동화 레벨을 나눈다

처음부터 완전 자동화로 가면 설정이 많아진다. 단계별로 올리는 편이 낫다.

```text
레벨 1: 수동
  Claude Code에서 /news 치기
  추가 API 비용 없음

레벨 2: 수집만 자동
  GitHub Actions로 수집
  리뷰 생성은 내가 /news로 실행
  추가 API 비용 없음

레벨 3: 완전 자동
  GitHub Actions로 수집
  OpenRouter API로 리뷰 생성
  Threads용 포맷 변환
  승인된 글 발행
  월 몇천 원 수준의 LLM API 비용 발생
```

추천은 레벨 1부터다. `/news` 한 번 치는 게 그렇게 힘든 일은 아니다. 매일 치기 귀찮아지는 순간이 오면 레벨 3으로 올린다.

## 11. 내 것으로 바꾸기 — 소스, 리뷰어, 채널만 바꾸면 된다

이 파이프라인은 뉴스봇 하나로 끝나지 않는다.

```text
모으기 → 분류하기 → 다듬기 → 퇴고 → 승인 → 릴리즈
```

각 단계의 내용만 바꾸면 전혀 다른 봇이 된다.

| 만들고 싶은 봇 | 소스 바꾸기 | 리뷰어 바꾸기 | 채널 바꾸기 |
| --- | --- | --- | --- |
| 경쟁사 모니터링 | 경쟁사 블로그 RSS | 경쟁 분석 리뷰어 | Slack |
| 채용공고 봇 | 채용 사이트 RSS | 공고 요약 리뷰어 | 카카오톡 |
| 논문 요약 봇 | arXiv RSS | 논문 해설 리뷰어 | 이메일 |
| 트렌드 리포트 | 여러 뉴스 RSS | 트렌드 분석 리뷰어 | 웹사이트 |
| YouTube 요약 봇 | YouTube RSS | 영상 요약 리뷰어 | Threads |

경쟁사 모니터링으로 바꾸려면 이렇게 시킨다.

```text
소스를 경쟁사 블로그 3개로 바꿔줘:
https://blog.competitor1.com/feed
https://blog.competitor2.com/rss
https://competitor3.com/blog.xml
```

```text
경쟁사 분석용 리뷰어를 만들어줘.
"뭘 출시했는지", "우리한테 위협인지", "대응 방안" 형식으로.
```

```text
결과를 슬랙 #competitive-intel 채널로 보내줘.
```

YouTube 요약을 Threads로 내보내고 싶으면 이렇게 바꾼다.

```text
YouTube RSS를 소스로 쓰고,
영상 요약 리뷰어를 만든 다음,
결과를 Threads용 280자 쓰레드로 변환해줘.
```

## 12. 특강 진행안

### 1부. 결과 먼저 보여주기 — 5분

- 매일 아침 자동으로 콘텐츠가 만들어지는 화면을 보여준다.
- `뉴스봇 = 시간표가 트리거인 파이프라인`이라는 차이를 잡는다.
- 여섯 단계 지도를 먼저 보여준다.

```text
모으기 → 분류하기 → 다듬기 → 퇴고 → 승인 → 릴리즈
```

### 2부. `/news`로 한 번 돌려보기 — 10분

- 예제 프로젝트 압축 풀기
- `npm install`
- Claude Code에서 `/news`
- `npm run dev`로 결과 확인

수강생이 이해해야 할 것은 코드가 아니라 “명령 하나가 안쪽에서 여러 역할을 호출한다”는 감각이다.

### 3부. 안쪽 구조 뜯어보기 — 15분

- RSS/API로 모으기
- 콘텐츠 라우터가 분류하기
- `dev_reviewer`, `product_reviewer`, `story_reviewer`가 다르게 쓰기
- `refine_content`가 퇴고하기
- 비용은 AI가 읽고 쓰는 단계에서만 발생한다는 점

### 4부. Threads용으로 바꾸기 — 10분

- 카카오톡, Slack, 웹사이트, Threads의 포맷 차이를 비교한다.
- Threads는 280자 안팎, 훅, 이어쓰기, 해시태그가 필요하다는 점을 잡는다.
- “같은 원본을 채널별로 다르게 편집한다”는 감각을 남긴다.

### 5부. 매일 자동화하기 — 10분

- cron은 알람시계라는 비유로 설명한다.
- GitHub Actions가 24시간 대신 실행해주는 구조를 보여준다.
- 레벨 1, 2, 3으로 나눠서 처음부터 완전 자동화를 강요하지 않는다.

### 6부. 내 프로젝트로 가져가기 — 10분

- 소스, 리뷰어, 채널만 바꾸면 다른 봇이 된다는 점을 강조한다.
- 경쟁사 모니터링, 채용공고, 논문 요약, YouTube 요약 → Threads 예시를 보여준다.
- 숙제는 “내 프로젝트에 붙일 자동화 후보 1개 적기”로 끝낸다.

## 13. 수강생에게 남길 숙제

오늘 바로 구현하지 않아도 된다. 대신 자기 프로젝트에 붙일 자동화 후보를 하나 적는다.

```text
내가 반복해서 보는 소스:
- 예: 경쟁사 블로그, 유튜브 채널, 채용 사이트, 논문 RSS, 커뮤니티 글

AI가 판단해야 하는 기준:
- 예: 우리 고객에게 중요한가?
- 예: 제품 개선에 참고할 만한가?
- 예: 공유할 가치가 있는가?

최종 발행 채널:
- 예: Threads, Slack, 카카오톡, 이메일, 웹사이트

자동화 레벨:
- 레벨 1: 수동 실행
- 레벨 2: 수집만 자동
- 레벨 3: 완전 자동
```

예시:

```text
소스: Product Hunt AI 카테고리 + Hacker News Show HN
판단 기준: 비개발자도 써볼 수 있는 AI 도구인가?
리뷰어: 제품 리뷰어
채널: Threads
자동화 레벨: 처음엔 /news 수동 실행, 나중에 GitHub Actions로 완전 자동화
```

## 14. 한 장 요약

```text
1. 자동화는 앱이 아니라 파이프라인이다.
2. 뉴스봇의 기본 흐름은 모으기 → 분류하기 → 다듬기 → 퇴고 → 승인 → 릴리즈다.
3. RSS/API 수집은 대체로 무료다.
4. AI 리뷰 생성과 퇴고는 LLM API 비용이 든다.
5. Threads는 280자 안팎, 훅, 이어쓰기, 해시태그가 필요하다.
6. 발행 전 승인 단계를 두면 사고가 줄어든다.
7. GitHub Actions를 쓰면 매일 아침 자동 실행할 수 있다.
8. 소스, 리뷰어, 채널만 바꾸면 경쟁사 모니터링·채용공고·논문 요약·YouTube 요약 봇으로 바뀐다.
```

이 특강의 결론은 간단하다.

> “네 프로젝트에 자동화 1건을 붙인다면 어디에 붙일 수 있을까?”

그 질문에 답할 수 있으면, 오늘 특강은 성공이다.
