**모든 걸 코드로 강제하면 AI 가 더 멍청해져. 어디까지가 경계인지 사람이 정해야 해.**

:::success 이 페이지가 끝나면
- 어떤 규칙을 코드/스키마로 옮길지 판단할 수 있어
- 어떤 영역은 프롬프트로 둬야 하는지 알아
- "추론은 자유, 입출력만 구조화" 원칙을 이해해
:::

**사람이 하는 것**: 4가지 질문으로 각 규칙 분류
**AI 가 하는 것**: (없음 — 사람의 판단 단계)
**해결 방식**: 분류 기준
**걸리는 시간**: 20분

---

## 핵심 원칙

> 추론 과정에 JSON 스키마를 강제하면 정확도가 **떨어진다**.
> 입출력 경계에서만 스키마를 강제해야 한다. — CRANE (ICLR 2025)

즉:
- **AI 가 생각하는 단계** = 자유 텍스트 (프롬프트)
- **AI 가 답을 뱉는 단계** = 스키마 (엔지니어링)

---

## 4가지 판단 질문

내 규칙 하나씩 이 표에 던져봐.

| 질문 | Yes → | No → |
|------|-------|------|
| 한번 정하면 잘 안 바뀌나? | **엔지니어링** (스키마) | 프롬프트 |
| 위반하면 명확히 틀린가? | **엔지니어링** (검증/lint) | 프롬프트 가이드 |
| 매번 같은 결과가 나와야 하나? | **엔지니어링** (Structured Output) | 프롬프트 |
| 맥락마다 판단이 달라야 하나? | **프롬프트** (자유 추론) | 엔지니어링 |

---

## 사례 1: enum (엔지니어링)

```
"역할은 ceo, cto, cmo, cfo, engineer, designer, pm, qa, devops, researcher, general 중 하나"
```

- Q1: 잘 안 바뀜 → Yes
- Q2: ceo 대신 boss 쓰면 명확히 틀림 → Yes
- Q3: 매번 같은 결과 필요 → Yes

→ **Zod enum 으로**. 프롬프트에 박지 마.

---

## 사례 2: 톤 (프롬프트)

```
"고객한테 친근하면서 너무 캐주얼하지 않게"
```

- Q1: 잘 바뀔 수 있음 → No
- Q2: 위반 여부 애매 → No
- Q4: 맥락마다 달라야 함 → Yes

→ **프롬프트 가이드로**. 단, 가이드 자체는 정책 카탈로그(`policies/tone/*.md`) 에 분리해서 단일 출처로 관리. 호출 시점에 동적 조립.

---

## 사례 3: API 응답 형태 (엔지니어링)

```json
{ "intent_id": "abc", "status": "building", "confidence": "validated" }
```

- Q1: 한 번 정의 → Yes
- Q2: 필드 누락하면 명확히 틀림 → Yes
- Q3: 매번 동일 → Yes

→ **JSON Schema / Structured Outputs**. 프롬프트에 "이런 형태로 답해줘" 라고 쓰지 마. 엔진이 강제해.

---

## 사례 4: "이 PR 머지해도 되나?" 판단 (프롬프트)

- Q4: 맥락마다 다름 → Yes

→ **프롬프트**. AI 가 코드 읽고 자유롭게 추론. 단, 최종 답은 `{ approve: bool, reasons: string[] }` 같은 스키마로 받아.

이게 "추론은 자유, 경계만 구조화" 의 정확한 의미야.

---

## 미니 워크시트 — 내 규칙 2개 분류해보기

이론은 끝. 본인 프로젝트의 규칙 2개 골라서 직접 분류해봐.

```
[규칙 1]  ___________________________________________
  Q1 (잘 안 바뀜?):       Y / N
  Q2 (위반 명확?):         Y / N
  Q3 (매번 같은 결과?):    Y / N
  Q4 (맥락마다 다름?):     Y / N
  → 결과: 엔지니어링 / 프롬프트

[규칙 2]  ___________________________________________
  ...
```

분류 결과로 다음 페이지 결정:

| 분류 결과 | 다음에 볼 곳 |
|----------|-------------|
| 엔지니어링 | [05. 스키마로 옮기기](./05-스키마로-옮기기) |

**팁**: 둘 중 하나만 봐도 OK. 본인 프로젝트가 enum 만 있으면 05만, 톤/정책만 있으면 06만.

## 흔한 실수 3개

### 실수 A: 모든 걸 스키마로

"체인 오브 띵킹도 JSON 으로 받자!" → 정확도 하락. 추론 단계는 자유 텍스트로 두고 **마지막 답만** 스키마.

### 실수 B: 프롬프트로만 강제

"tool 과 text 섞지 마" 라고 글로 경고 → 자연어 경고만으로는 준수율 <40%. Structured Output 은 100%.

### 실수 C: enum 을 프롬프트에

"role 은 다음 중 하나: ceo, cto, ..." 를 매 프롬프트에 박음 → 매번 토큰 비용 + enum 추가 시 사람이 잊음.

→ Zod enum 한 번 정의. 프롬프트는 enum 을 import 해서 자동 조립.
