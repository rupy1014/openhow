**압축이 아니라 DRY + 조립. AI 는 여전히 풍부한 지시를 받아.**

:::success 이 페이지가 끝나면
- 같은 프롬프트 가이드가 여러 곳에 복붙된 걸 한 곳으로 합쳐
- 키 한 줄로 "톤" 같은 정책을 호출하는 구조를 만들어
- LLM 이 받는 프롬프트는 그대로 풍부한데 저장소만 깔끔해져
:::

**사람이 하는 것**: 어떤 정책을 분리할지 결정, 정책별 파일 작성
**AI 가 하는 것**: 키 → 자연어 변환 엔진, 호출 시점 조립
**해결 방식**: 엔지니어링 + 프롬프트
**걸리는 시간**: 1\~2시간

:::info 사전 지식
- YAML 또는 JSON 읽기 가능
- TypeScript 코드는 예시로만 등장 — 안 읽혀도 흐름은 잡혀
- 파일 시스템 (`mkdir`, `cat`) 정도 익숙하면 OK
:::

---

## 흔한 오해 먼저 정리

> "정책을 키로만 적으면 LLM 은 톤이 뭔지 모르잖아?"

**그렇게 작동하지 않아.** 키는 LLM 에게 안 가. 엔진이 키 → 자연어 변환을 해서 LLM 에게 풀어 보내.

```
저장소:
  policies/tone/informal_professional.md  ← 4,000 토큰 원본, 딱 1번
  policies/tone/formal.md
  policies/objection/pricing.md

런타임:
  1. workflow.json 에서 "tone: informal_professional" 읽음
  2. 엔진이 policies/tone/informal_professional.md 불러옴
  3. LLM 프롬프트에 자연어 그대로 포함
  4. LLM 은 풍부한 지시 받음 → 퀄리티 동일
```

**LLM 입장에서 본 프롬프트는 변한 게 없어.** 변한 건 저장소 모양뿐.

---

## 1. 카탈로그 구조

```
policies/
├── tone/
│   ├── informal_professional.md   ← 톤 1개당 1파일
│   └── formal.md
├── objection/
│   ├── pricing.md
│   └── timeline.md
└── guardrail/
    └── never_promise_pricing.md
```

각 파일은 **하나의 정책만** 다뤄. 1주제 1파일이 핵심.

---

## 2. 호출 인터페이스

워크플로우/에이전트 정의에는 **키만**:

```yaml
# campaigns/q2-launch.yaml
agent: marketing
tone: informal_professional
guardrails:
  - never_promise_pricing
context:
  - objection/pricing
```

→ MD 4 페이지가 아니라 4 줄.

---

## 3. 조립 엔진 (간단한 형태)

```typescript
async function assemblePrompt(spec: WorkflowSpec): Promise<string> {
  const parts: string[] = [];

  // 톤 정책 로드
  parts.push(await read(`policies/tone/${spec.tone}.md`));

  // 가드레일 로드
  for (const g of spec.guardrails) {
    parts.push(await read(`policies/guardrail/${g}.md`));
  }

  // 컨텍스트 로드
  for (const c of spec.context) {
    parts.push(await read(`policies/${c}.md`));
  }

  return parts.join("\n\n---\n\n");
}
```

**핵심**: 사용자가 가격을 묻기 전엔 `objection/pricing.md` 가 프롬프트에 안 들어가. 필요할 때만 조립 → 매번 토큰 절약.

---

## 4. 버전 관리

정책마다 버전을 둘 수 있어:

```
policies/tone/informal_professional@v1.md
policies/tone/informal_professional@v2.md  ← 새 톤 시도 중
```

A/B 테스트, 회귀 추적이 정책 단위로 가능.

---

## 5. 회귀 테스트 (Golden Eval Set)

정책마다 테스트 케이스 준비:

```
policies/tone/informal_professional.md
policies/tone/informal_professional.eval.jsonl  ← 입력/기대 출력 쌍
```

```bash
./scripts/eval-policy.sh policies/tone/informal_professional
# → 통과율 92% (이전 버전 95%) — 회귀 발생
```

정책을 수정해도 품질이 떨어지지 않는다는 걸 보장.

## 흔한 실수

### 실수 A: 1 파일 다정책

`policies/all_tones.md` 에 톤 5개를 다 적음 → 하나 호출하면 5개 다 로드. DRY 깨짐.

→ **1주제 1파일.**

### 실수 B: 정책 안에 다른 정책 참조

`policies/tone/informal.md` 안에 "pricing 정책도 같이 적용" → 의존성 그래프가 생김.

→ **정책은 평면(flat). 조합은 호출하는 쪽에서.**

### 실수 C: 조립 엔진 없이 수동 복붙

키만 적고 엔진은 안 만들면 LLM 이 키를 그대로 봄 → 톤이 뭔지 모름.

→ **조립 엔진은 필수.** 단순한 read+concat 이라도.

---

## 시작 시점 — 언제 정책 카탈로그를 만들어?

지금 정책이 1개도 없으면 분리할 게 없어. 보통 이 순서:

```
1. 마케팅/CS 같은 에이전트를 일단 만든다 (프롬프트 한 덩어리)
2. 같은 에이전트를 2\~3번 돌리다 보면 톤/규칙이 패턴으로 보임
3. 패턴이 3개 이상 잡히면 그때 카탈로그로 분리
```

**관찰값 없이 미리 분리하지 마.** 추상적인 정책 이름만 늘어나고 실제로는 안 쓰여.
