# 클로더즈 쇼츠 제작 가이드

이 폴더(`examples/clauders.ai/shorts/`)의 쇼츠 대본을 만들 때 적용하는 기준이야.
원본은 `examples/clauders.ai/docs/` 커리큘럼(시작하기 → 초보 개념잡기 → 자동화 입문 → 서비스 만들기)이고,
여기서는 그 커리큘럼의 **핵심 개념을 쇼츠 단위로 잘라낸다.**

## 0. 이 쇼츠들의 목적

검색 노출용이 아니야. **핵심 개념 한 개씩을 짧게 박아두는 용도**야.
나중에 이 쇼츠들을 묶어서 롱폼(강의 영상)을 촬영하는 게 최종 목표라서,
한 쇼츠가 곧 롱폼의 한 챕터·한 장면이 된다고 생각하고 만들어.

그래서 판단 기준은 단 하나야.

> 이 개념 하나만 60초 안에 떠먹여줄 수 있는가?

## 1. 한 쇼츠 = 한 개념

- 1개 쇼츠는 **1개 결론(판단)만** 말해. 한 편에 결론이 두 개면 나눠.
- 커리큘럼 문서 하나에서 보통 2~5개 쇼츠가 나와. 문서의 `## 1.`, `## 2.` 같은 소제목과 `자주 헷갈리는 포인트`가 쇼츠 후보의 1차 소스야.
- 좋은 쇼츠 소재는 보통 다섯 가지야. **오해 바로잡기 / 숫자 하나 / 갈림길 하나 / 사고(실수) 사례 하나 / 체크리스트 하나.**
- 문서 전체를 요약하는 "대표 쇼츠"는 섹션당 1개면 충분해. 나머지는 잘라낼 수 있는 서브 포인트로 뽑아.

## 2. 말투 — 해요체

이 쇼츠 대본은 **해요체**로 써. (원본 아티클은 반말 평어지만, 쇼츠 나레이션은 듣기 편한 해요체로 간다.)

- "~해요", "~거든요", "~더라고요", "~죠", "~할까요?"
- 친한 사람한테 말로 설명하듯. 소리 내 읽었을 때 어색하면 고쳐.
- 문장은 짧게. 한 문장에 한 가지만.
- **두괄식.** 훅에서 결론·질문부터 던지고 풀어줘.
- 어려운 말은 바로 풀어서. 전문 용어가 나오면 옆에 쉬운 말로 한 번 더.

금지:

- 번역체("~것이다", "~라고 할 수 있다"), 딱딱한 보고서 말투, 개조식 나열만 늘어놓기.
- 과장된 영업 멘트, 이모지 남발, "물론입니다!" 같은 치어풀 필러.
- **전제 없는 부정 화법.** 깔아둔 적 없는 말을 "X가 아니라 Y예요"로 부정하지 마. 그냥 Y를 말해. (단, 앞에서 깔아둔 오해를 바로잡는 대비는 OK.)

## 3. 사실은 단단하게 — 원본을 벗어나지 마

- **커리큘럼 원본에 있는 내용만** 쓴다. 없는 기능·숫자·도구를 지어내지 마.
- 커리큘럼의 핵심 메시지(예: "초보는 Opus 기본", "에러는 WHAT/WHERE/WHEN으로 본다", "3번 룰", "서버 검증 없이 결제완료 처리 금지")는 그대로 살려.
- 도구 이름·명령어(`/model`, `npm run dev`, `CLAUDE.md` 등)는 원본 표기 그대로.

## 4. 쇼츠 1편의 형식

각 쇼츠는 아래 4블록으로 써. (섹션 파일 안에서는 `## N. 제목`으로 구분)

```
## N. [구어체 질문형 제목 — 듣고 싶어지는 한 줄]

**훅:** 첫 3초에 나오는 한 문장. 결론이나 질문으로 바로 친다.

[나레이션 본문]
짧은 줄바꿈으로
호흡 단위로 끊어서.
한 줄에 한 호흡.

**한 줄 정리:** 핵심 한 문장. 요약 반복이 아니라 "이것만 기억해"로.

**화면 키워드:** 화면에 띄울 짧은 텍스트 2~4개 / 쉼표로 구분
```

- **훅**과 **한 줄 정리**, **화면 키워드**는 라벨 그대로 굵게 표기.
- 나레이션 본문은 라벨 없이 줄바꿈만. 손글씨 레퍼런스(`youtube/손글씨/shorts/01-PG연동하기-shorts.md`)의 호흡을 따라가.
- 길이 목표: 나레이션 본문 기준 **150~300자**(말로 30~60초). 넘으면 두 편으로 쪼개.

## 5. 화면 문구와 나레이션은 역할이 달라

- **화면 키워드**는 짧게(명사·숫자). **나레이션**은 친절하게 풀어서.
- 화면: `Opus / Sonnet / Haiku` → 나레이션: "같은 Claude라도 모델이 등급별로 나뉘어요."
- 화면: `WHAT / WHERE / WHEN` → 나레이션: "에러는 이 세 가지만 보면 돼요."

## 6. 영어 약어는 TTS용 발음을 따로 적어

화면 자막은 원문 표기(AI, API)를 쓰고, **나레이션은 토큰 종류에 따라 갈라서** 적어.
아래 표는 "소리 내면 이렇게 읽힌다"는 발음 참고고, 실제로 대본에 발음대로 적을지 원문으로 둘지는 §6 맨 아래 원칙을 따라.

| 화면 표기 | TTS 발음 |
| --- | --- |
| AI | 에이아이 |
| API | 에이피아이 |
| CLI | 씨엘아이 |
| SDK | 에스디케이 |
| IDE | 아이디이 |
| MCP | 엠씨피 |
| PRD | 피알디 |
| MVP | 엠브이피 |
| PMF | 피엠에프 |
| DB | 디비 |
| PG | 피지 |
| UI | 유아이 |
| LLM | 엘엘엠 |
| VS Code | 브이에스 코드 |
| Claude | 클로드 |
| Claude Code | 클로드 코드 |
| Git | 깃 |
| GitHub | 깃허브 |
| Vercel | 버셀 |
| `.env` | 닷이엔브이 / 점이엔브이 |
| `/model` | 슬래시 모델 |

원칙 (대본 나레이션 표기):

- **AI·모델 이름은 영문 원문 그대로.** AI, Claude, Claude Code, ChatGPT, GPT, Opus, Sonnet, Haiku, Gemini — 눈에 익고 깔끔해서 나레이션에서도 영문으로 둬. (골든 예시 A·B가 "AI"·"Opus/Sonnet/Haiku"를 원문으로 두는 이유가 이거야.) 그 외 영어 도구·서비스명은 한글 발음으로 적어 흐름을 매끄럽게. (Git→깃, GitHub→깃허브, Vercel→버셀, React→리액트, Next→넥스트, Supabase→슈파베이스, Notion→노션)
- **여러 글자를 하나씩 떼어 읽는 약어는 발음대로.** CLI=씨엘아이, MCP=엠씨피, API=에이피아이, PRD=피알디, MVP=엠브이피, PMF=피엠에프, DB=디비, IDE=아이디이, IA=아이에이, CTA=씨티에이, PG=피지, LLM=엘엘엠.
- **파일명·명령·확장자도 발음대로.** CLAUDE.md→클로드 점 엠디, AGENTS.md→에이전츠 점 엠디, .md→점 엠디, .env→닷이엔브이, /model→슬래시 모델. (단 부록처럼 실제 명령어를 `백틱 코드`로 보여주는 줄은 코드 표기 그대로 둬도 돼 — 한 파일 안에서만 일관되면 됨.)
- **화면 키워드는 무조건 원문 표기.**
- **화면 키워드, 그리고 약어를 '화제로 보여주는' 훅·한 줄 정리**는 원문 표기 OK. (예: 훅 "PRD, IA… 용어 어려워 보이죠?", 키워드 `WHAT / WHERE / WHEN`) 기본 패턴은 **흐르는 본문=발음(피알디), 훅·키워드=원문(PRD)**.
- **흐르는 나레이션 본문 안에서는 한 토큰의 표기를 통일.** (예: 한 편에서 `ppt`와 `피피티`를 같이 쓰지 않기.)

## 7. 골든 예시 (이대로 따라 써)

원본: `examples/clauders.ai/docs/claude-code-intro/01-model-choice.md`

### 예시 A — 오해 바로잡기형

```
## 1. AI는 똑똑한 앵무새예요

**훅:** AI가 다 이해하고 답하는 것 같죠? 그렇게 보면 위험해요.

AI는 세상을 직접 경험해서 이해하는 게 아니에요.

엄청나게 많은 글과 코드에서
패턴을 배운 도구에 가까워요.

그래서 똑똑한 앵무새라는 비유가 좋아요.

따라 한다는 뜻이 아니라,
패턴을 너무 많이 봐서
사람이 보기엔 똑똑하게 말한다는 거예요.

중요한 건 이거예요.
그럴듯하게 말한다고
항상 맞는 건 아니에요.

그래서 AI는 답을 주는 신이 아니라,
빠르게 초안을 만들고 같이 고쳐가는 파트너예요.

**한 줄 정리:** AI는 신이 아니라 초안 파트너. 맥락은 내가 주고, 확인도 내가 해요.

**화면 키워드:** 똑똑한 앵무새, 패턴 조합, 그럴듯함≠정답, 초안 파트너
```

### 예시 B — 갈림길/숫자형

```
## 4. 초보는 그냥 Opus 쓰세요

**훅:** Opus? Sonnet? Haiku? 초반부터 고르려고 하면 오히려 헤매요.

같은 Claude라도 모델이 등급별로 나뉘어요.

Opus는 박사급, Sonnet은 경력자,
Haiku는 빠른 실무자예요.

똑똑할수록 보통 느리고 비싸요.

근데 초보 때 이걸 최적화하려고 하면,
결과가 이상할 때
내 지시가 문제인지
모델이 약해서인지 구분이 안 돼요.

그래서 클로더즈는 단순하게 가요.
처음엔 제일 똑똑한 Opus로 시작해요.

변수를 하나 줄이는 거예요.
익숙해지면 그때 Sonnet, Haiku로 나누면 돼요.

**한 줄 정리:** 초보 때 모델 고민은 사치. Opus로 변수부터 줄여요.

**화면 키워드:** Opus 박사급, Sonnet 경력자, Haiku 실무자, 초보=Opus 기본
```

## 8. 파일 구조

- **섹션별 1파일.** 커리큘럼 폴더 단위로 묶어.
  - `01-getting-started-shorts.md` (시작하기)
  - `02-claude-code-intro-shorts.md` (초보 개념잡기)
  - `03-automation-shorts.md` (자동화 입문)
  - `04-build-service-shorts.md` (서비스 만들기 — 13강, 제일 두꺼움)
  - `05-appendix-shorts.md` (부록 — MCP/브라우저 자동화/멀티 도구)
- 각 파일 맨 위에 헤더 + 어떤 커리큘럼 문서에서 나왔는지 매핑.
- 각 쇼츠 제목 앞에 원본 강(lesson) 표시: `## [2강] N. 제목` 형태로 롱폼 촬영 때 추적 쉽게.

## 9. 검수 체크리스트

업로드/촬영 전 확인해:

- [ ] 한 쇼츠가 결론 하나만 말하는가? (두 개면 분리)
- [ ] 훅이 첫 문장에서 결론·질문으로 바로 치는가?
- [ ] 해요체로 일관되는가? (반말·하다체·~습니다 섞이지 않았는가)
- [ ] 커리큘럼 원본에 없는 사실·숫자·도구를 지어내지 않았는가?
- [ ] 나레이션의 영어 약어가 발음대로 읽히는가? (화면 키워드는 원문 표기)
- [ ] 한 줄 정리가 요약 반복이 아니라 "이것만 기억해"인가?
- [ ] 화면 키워드가 짧은 명사·숫자인가?
