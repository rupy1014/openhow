**좋은 팀은 많이 바꾸는 팀이 아니라, 작게 바꾸고 배운 것을 남기는 팀이다.**

---

## 먼저 이 장면부터 보자

팀노트AI 마케터가 월요일에 이런 생각을 한다.

- "랜딩 전환율이 안 오르니까 디자인 전체를 바꿔볼까?"
- "메일 오픈율도 낮으니 제목도 바꾸고 본문도 바꾸고 CTA도 바꿔야지"
- "FAQ도 순서가 별로인 것 같으니 통째로 다시 쓰자"

한꺼번에 다 바꿨다. 2주 뒤 전환율이 올랐다. 그런데 **뭘 바꿔서 올랐는지 모른다.**
다시 떨어지면 뭘 되돌려야 하는지도 모른다.

이건 실험이 아니라 도박이다.

---

## 핵심 개념: 실험은 한 번에 한 가지만 바꾼다

실험의 핵심 루프는 이렇다.

```text
가설 → 한 가지 변경 → 측정 → 한 줄 학습
```

이게 전부다. 화려한 A/B 테스트 도구가 필요한 게 아니라, **바꾼 것과 결과를 연결할 수 있으면** 실험이다.

---

## 실험할 수 있는 것

작게 바꿀 수 있는 것은 많다.

| 바꿀 것 | 예시 |
|---------|------|
| 제목(헤드라인) | "회의록 자동화" → "콜 끝나면 5분 안에 요약이 옵니다" |
| CTA 문구 | "무료 체험" → "14일 써보기" |
| FAQ 순서 | 가격 FAQ를 1번 → 3번으로 |
| 훅 문장 | "미팅 정리가 안 되시죠?" → "어제 회의 내용, 지금 말할 수 있나요?" |
| 세그먼트별 메시지 | 전체 → 5인 팀용 / 30인 팀용으로 나눔 |
| 비교표 구조 | 기능 나열 → 문제 해결 기준으로 재정리 |
| 데모 장면 | 녹화 대신 실제 사용 화면 GIF |

---

## 팀노트AI 실험 예시

**가설**: "기능 이름보다 결과를 말하면 클릭이 늘 것이다"

| 항목 | 내용 |
|------|------|
| 바꾼 것 | 랜딩 헤드라인 1개 |
| Before | "회의록 자동화 솔루션" |
| After | "콜 끝나면 5분 안에 요약이 옵니다" |
| 측정 지표 | 랜딩 CTR + 데모 신청 수 |
| 결과 | CTR 15% 상승, 데모 신청 변화 없음 |
| 한 줄 학습 | "결과형 헤드라인이 클릭을 올리지만, 전환까지 잇려면 본문도 맞춰야 한다" |

바꾼 게 하나니까, 결과가 왜 나왔는지 설명할 수 있다.

---

## 학습 로그에 남길 것

실험을 했으면 반드시 4가지를 남긴다.

1. **무엇을 바꿨는가** — 헤드라인, CTA, FAQ 순서 등
2. **왜 바꿨는가** — 어떤 가설을 검증하려고
3. **어떤 지표가 달라졌는가** — 반응/질문/신뢰 중 어디서 변화
4. **다음에 유지할 것 / 버릴 것** — 한 줄로 결론

이 4줄이 쌓이면, 3개월 뒤에 팀이 "왜 이 메시지를 쓰게 됐지?"라는 질문에 답할 수 있다.

---

## 이렇게 정리하면 된다

| 질문 | 답 |
|------|-----|
| 한 번에 몇 개를 바꾸나? | 1개 |
| 얼마나 기다리나? | 최소 1~2주 (데이터가 쌓일 만큼) |
| 어디에 기록하나? | 실험 로그 (노션, 시트, 어디든) |
| 성공/실패 기준은? | 실험 전에 정한 지표로 판단 |

---

## 막히는 지점

- **"바꿀 게 너무 많아서 하나만 고르기 어려워요."** — 가장 많은 사람이 보는 곳(헤드라인, CTA)부터 바꾼다. 트래픽이 적은 곳을 바꿔도 데이터가 안 쌓인다.
- **"실험이라고 하기엔 트래픽이 너무 적어요."** — 통계적 유의성은 나중 문제다. 지금은 "바꿨더니 느낌이 어떤가"를 기록하는 것만으로도 학습이 된다.
- **"결과가 안 나와요."** — 결과가 "변화 없음"도 학습이다. "이건 안 먹힌다"를 아는 것도 실험의 성과다.

---

## 체크 질문

- [ ] 지난 한 달 안에 한 가지만 바꿔본 적이 있는가
- [ ] 바꾼 이유와 결과를 한 줄로 말할 수 있는가
- [ ] 실험 결과를 어딘가에 기록하고 있는가
